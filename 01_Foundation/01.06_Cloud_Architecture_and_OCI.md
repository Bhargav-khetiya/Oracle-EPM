## What Is OCI?

```
OCI = Oracle Cloud Infrastructure

  Think of it as Oracle's version of AWS/Azure/GCP.

  OCI provides:
  ┌─────────────────────────────────────────────────┐
  │ COMPUTE     → Virtual Machines (run EPM servers) │
  │ STORAGE     → Disks (store Essbase data files)   │
  │ NETWORKING  → Private networks, load balancers   │
  │ IDENTITY    → User management (IDCS / IAM)       │
  │ SECURITY    → Encryption, firewalls, compliance  │
  │ DATABASE    → Oracle DB (relational data for EPM)│
  └─────────────────────────────────────────────────┘

  AS AN EPM CONSULTANT:
  You DON'T manage OCI directly (it's SaaS).
  But you MUST understand it for:
  ✅ Data residency conversations with legal teams
  ✅ Performance troubleshooting
  ✅ Network connectivity (VPN for Integration Agent)
  ✅ Maintenance window planning
  ✅ Disaster recovery planning
```

# SECTION 4: POD ARCHITECTURE

---

```
WHAT IS A POD?

  A Pod = a cluster of servers that hosts MULTIPLE tenants.

  EPM CLOUD POD LAYOUT:
  ┌───────────────────────────────────────────────────┐
  │                    POD "AMEPM-1"                   │
  │                                                    │
  │  ┌──────────────────────────────────────────────┐ │
  │  │ SHARED INFRASTRUCTURE                         │ │
  │  │ ├── OCI Load Balancer                         │ │
  │  │ ├── Network Firewall                          │ │
  │  │ └── Monitoring / Alerting                     │ │
  │  └──────────────────────────────────────────────┘ │
  │                                                    │
  │  ┌────────────┐ ┌────────────┐ ┌────────────┐    │
  │  │ TENANT A    │ │ TENANT B    │ │ TENANT C    │    │
  │  │ (Acme Corp) │ │ (Hotel Pvt) │ │ (BigBank)   │    │
  │  │             │ │             │ │             │    │
  │  │ WebLogic ─┐ │ │ WebLogic ─┐ │ │ WebLogic ─┐ │    │
  │  │ Essbase  ─┤ │ │ Essbase  ─┤ │ │ Essbase  ─┤ │    │
  │  │ Oracle DB ─┘ │ │ Oracle DB ─┘ │ │ Oracle DB ─┘ │    │
  │  │             │ │             │ │             │    │
  │  │ DATA IS     │ │ DATA IS     │ │ DATA IS     │    │
  │  │ ISOLATED    │ │ ISOLATED    │ │ ISOLATED    │    │
  │  └────────────┘ └────────────┘ └────────────┘    │
  └───────────────────────────────────────────────────┘

  KEY POINTS:
  ✅ Each tenant has SEPARATE Essbase instances (data isolation)
  ✅ Each tenant has SEPARATE Oracle DB schemas
  ❌ Tenants SHARE physical hardware (compute, storage)
  ⚠️ "Noisy Neighbor" risk: if Tenant A runs a massive calc,
     Tenant B MIGHT experience slower performance
  → Oracle mitigates this with CPU/memory quotas per tenant
```

### Multi-Tenancy Security

```
DATA ISOLATION GUARANTEE:
  ┌──────────────────────────────────────────────────┐
  │ Tenant A's data CAN NEVER be accessed by Tenant B │
  │                                                    │
  │ Mechanisms:                                        │
  │ 1. Separate Essbase processes (different JVMs)     │
  │ 2. Separate Oracle DB schemas                      │
  │ 3. Separate storage volumes (encrypted)            │
  │ 4. Network isolation (VCN segmentation)            │
  │ 5. Identity isolation (separate IDCS domains)      │
  │                                                    │
  │ Oracle SOC 2 Type II certified                     │
  │ Oracle ISO 27001 certified                         │
  │ Oracle HIPAA compliant (for healthcare tenants)    │
  └──────────────────────────────────────────────────┘
```

### Monthly Update Schedule

```
ORACLE MONTHLY UPDATE CYCLE:

  Week 1: Oracle releases update to TEST environment
  Week 2: Customer tests the update in TEST (regression testing)
  Week 3: Oracle releases SAME update to PROD environment
  Week 4: Post-update monitoring and bug reporting

  TIMELINE EXAMPLE (September 2026 Update):
  ┌────────────────────────────────────────────────┐
  │ Sep 1 (Fri)  → TEST env gets September update  │
  │ Sep 2-8      → Your team tests in TEST          │

  → This is SaaS. Oracle controls the release schedule.
  → Best practice: Always run regression tests in the 1-week window.

# SECTION 7: MAINTENANCE WINDOWS

---

```
DAILY MAINTENANCE WINDOW:

  Duration:  ~1 hour
  Timing:    Configurable (usually 2:00-3:00 AM local time)
  What happens:
    ├── Oracle MAY apply patches
    ├── System is UNAVAILABLE to users
    ├── Running jobs will be interrupted
    └── No data loss — just a brief outage

  CRITICAL RULES:
  ✅ Schedule EPM Automate batch jobs to FINISH before maintenance
  ❌ NEVER schedule data loads that span the maintenance window
  ✅ Communicate the maintenance schedule to all users
  ✅ Verify system health after each maintenance window

MONTHLY EXTENDED MAINTENANCE:

  Duration:  2-4 hours
  Timing:    Usually first weekend of the month
  What happens:
    ├── Monthly update applied (new features, bug fixes)
    ├── Essbase engine restarted
    ├── WebLogic server restarted
    └── May require testing post-update

QUARTERLY MAJOR UPDATE:

  Duration:  4-8 hours (extended window)
  Timing:    Quarterly (varies)
  What happens:
    ├── Major feature additions
    ├── UI changes
    ├── API version updates
    └── May require significant regression testing
```

# SECTION 11: BACKUP AND DISASTER RECOVERY

---

```
BACKUP STRATEGY:

  AUTOMATED BACKUPS (Oracle-managed):
  ├── Daily automated snapshots of the entire environment
  ├── Retained for 60 days
  ├── Stored in OCI Object Storage (same region)
  ├── Encrypted at rest (AES-256)
  └── Restoration: Raise Oracle SR (Service Request)

# SECTION 14: COMMON MISTAKES

---

| Mistake | Impact | Correct Approach |
|---------|--------|-----------------|
| Not testing monthly updates | New features break existing calc scripts or forms | Always regression test in Test env during the 1-week window |
| Scheduling jobs during maintenance window | Jobs fail, data loads incomplete | Schedule all jobs to complete 30 min BEFORE maintenance |
| Not whitelisting Oracle URLs on corporate proxy | Smart View can't connect, users get timeout errors | Whitelist *.oraclecloud.com and *.oracle.com |
| Choosing wrong OCI region | Data residency violation, high latency for users | Choose region based on: compliance requirements + user location |
| Giving everyone Service Administrator role | Security risk, accidental deletions | Use least-privilege: most users should be Planners |
| Not setting up SSO | Users have separate EPM passwords, help desk overloaded | Integrate IDCS with corporate AD via SAML SSO |
| No manual backups | Relying only on Oracle automated backups | Schedule nightly EPM Automate exports to a separate location |
| Ignoring resource limits | Groovy scripts crash, forms timeout | Design within limits: block size, DataGrid size, form row count |

# SECTION 15: INTERVIEW QUESTIONS

---

### Beginner

**Q1: What is OCI and why does EPM run on it?**
> OCI (Oracle Cloud Infrastructure) is Oracle's cloud computing platform — like AWS but built by Oracle. EPM Cloud runs on OCI because it provides the compute, storage, networking, and identity services needed to host Essbase and the Planning application. As a SaaS product, Oracle manages all the infrastructure; customers just log in via a browser.

**Q2: How many environments does a standard EPM Cloud subscription include?**
> Standard subscription includes 2 environments (Production + Test). Enterprise subscription includes 3 environments (Production + Test + Development). The Test environment receives monthly updates 1 week before Production, giving customers time to regression test.

### Intermediate

**Q3: A client in Germany needs to ensure their financial data stays in the EU. How do you configure this?**
> Select an EU OCI region during initial provisioning — either eu-frankfurt-1 (Frankfurt, Germany) or eu-amsterdam-1 (Amsterdam, Netherlands). Oracle guarantees that all data remains within the selected region. Document this in the project's Data Processing Agreement (DPA) and provide Oracle's GDPR compliance certifications to the client's legal team.

**Q4: How does the EPM Integration Agent connect to Oracle Cloud without opening inbound firewall ports?**
> The Integration Agent initiates an OUTBOUND HTTPS connection (port 443) to Oracle Cloud — it "phones home." This means the corporate network only needs outbound access to *.oraclecloud.com. No inbound ports need to be opened, which is critical for corporate security teams. The agent maintains a persistent tunnel through which Oracle Cloud can send data extraction requests and receive data back.

### Architect

**Q5: A client's Essbase calculations are consistently slow during US business hours but fast at night. What architectural factors could cause this?**
> Several OCI-level factors: 1) **Noisy neighbor** — another tenant on the same pod is running heavy calculations during business hours, consuming shared CPU/memory. 2) **WebLogic contention** — many concurrent users opening forms simultaneously reduces available JVM memory for Groovy and calc operations. 3) **Data cache pressure** — during the day, multiple users retrieve different Entity data, causing frequent block loads from page file to cache (thrashing). 4) **Network latency** — if users are in India accessing a US-hosted pod, daytime network congestion increases latency. Solutions: Contact Oracle Support to investigate pod resource contention, optimize calc scripts to run faster, schedule heavy calculations during off-peak hours, or request tenant relocation to a less loaded pod.
