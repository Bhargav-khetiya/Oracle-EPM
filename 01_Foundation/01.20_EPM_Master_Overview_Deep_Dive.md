# SECTION 1: WHAT IS EPM

---

## 1.1 Definition

**Enterprise Performance Management (EPM)** is the discipline of planning, budgeting, forecasting, consolidating, reporting, and analyzing an organization's financial and operational performance.

**Oracle EPM Cloud** is Oracle's SaaS platform that provides a suite of integrated applications to automate the entire EPM lifecycle.

## 1.2 Why EPM Exists — The Business Problem

### Before EPM:
```
CEO: "What's our forecast for Q3?"

→ CFO calls 12 regional VPs
→ Each VP has their own Excel model
→ Finance team spends 3 weeks collecting spreadsheets via email
→ 50+ different formats, broken formulas, version conflicts
→ Manual consolidation takes another 2 weeks
→ By the time the forecast is ready, Q3 is already halfway over
→ The forecast is already outdated
```

### After EPM:
```
CEO: "What's our forecast for Q3?"

→ CFO opens Oracle EPM Cloud
→ All 12 regions have already entered data in a centralized form
→ Data is instantly consolidated with currency translation
→ Real-time dashboards show revenue, expense, margin
→ What-if scenarios show best-case and worst-case
→ Total time: < 5 minutes
```

## 1.3 EPM vs ERP — The Critical Distinction

| Aspect | ERP (e.g., Oracle Fusion, SAP) | EPM (Oracle EPM Cloud) |
|--------|-------------------------------|------------------------|
| **Focus** | Recording transactions that already happened | Planning what WILL happen |
| **Data Direction** | Backward-looking (historical) | Forward-looking (projections) |
| **Granularity** | Individual invoices, line items | Summarized by period, account, entity |
| **Users** | Accountants, AP/AR clerks | FP&A analysts, controllers, CFO |
| **Example** | "We paid ₹5,00,000 to Vendor X on Jan 15" | "We expect to spend ₹60,00,000 on vendors in Q1" |
| **Database** | Relational (Oracle SQL) | Multidimensional (Essbase) |
| **Technology** | OLTP (Online Transaction Processing) | OLAP (Online Analytical Processing) |

**Key Insight:** ERP and EPM are complementary — ERP records Actuals, EPM plans the future. Actuals flow FROM ERP TO EPM as the baseline for planning.

```
ERP (Actuals) ──────────→ EPM (Planning)
  "What happened"           "What should happen"
  Oracle Fusion ERP          Oracle EPM Cloud
  SAP S/4HANA                
  Individual transactions    Summarized by dimensions
```

EPBCS is the **core planning engine**. It is where organizations build their budgets, forecasts, and financial models.

### Technical Architecture:

### Key Capabilities:
| Capability | Description | Example |
|-----------|-------------|---------|
| **Budgeting** | Annual budget creation and submission | FY27 Revenue Budget by entity/department |
| **Forecasting** | Rolling forecasts, re-forecasting | Q3 re-forecast with updated assumptions |
| **Scenario Modeling** | What-if analysis | "What if raw material costs increase 15%?" |
| **Driver-Based Planning** | Formula-driven models | Revenue = Rooms × Rate × Occupancy % |
| **Workforce Planning** | Headcount, compensation, benefits | 500 FTE plan with merit increases |

### Module Types within EPBCS:
| Module | Purpose | Database Type |
|--------|---------|---------------|

| **Strategic Modeling** | Long-range what-if | Separate engine (not Essbase) |

## 2.3 Pillar 2: FCCS — Financial Consolidation & Close Cloud Service

### What It Does:
FCCS automates the financial close process — consolidation of multiple legal entities, intercompany elimination, currency translation, minority interest, and journal entries.

### Why It's Separate from EPBCS:
| Concern | EPBCS | FCCS |
|---------|-------|------|
| **Purpose** | Plan the future | Close the books on the past |
| **Data** | Budgets, forecasts | Actuals (from ERP) |
| **Users** | FP&A | Corporate Controllers |
| **Regulatory** | Internal management | IFRS/GAAP compliance required |
| **Audit Trail** | Limited | Full audit trail with journals |
| **Intercompany** | Basic | Full elimination engine |
| **Ownership** | Not needed | Ownership %, minority interest |

### Key FCCS Concepts:
- **Consolidation:** Rolling up subsidiary financials to parent
- **Intercompany Elimination:** Removing transactions between entities within the same group
- **Currency Translation:** Converting subsidiary local currency to group reporting currency
- **Ownership Adjustments:** Handling 80% ownership, minority interest
- **Journals:** Adjusting entries during close
- **Close Manager:** Task list for the close process

### Example:
```
Hotel Group has 3 subsidiaries:
  → Hotel India (INR) — 100% owned
  → Hotel USA (USD) — 100% owned  
  → Hotel UK (GBP) — 80% owned (20% minority interest)

FCCS Process:
1. Load Actuals from each subsidiary's ERP
2. Translate Hotel USA from USD→INR, Hotel UK from GBP→INR
3. Eliminate intercompany: Hotel India sold services to Hotel UK for ₹5 Cr
4. Calculate minority interest: 20% of Hotel UK's net income
5. Produce consolidated group P&L, BS, CF in INR
```

## 2.4 Pillar 3: TRCS — Tax Reporting Cloud Service

### What It Does:
Automates tax provision calculations (ASC 740 / IAS 12), deferred tax computations, and tax reporting across jurisdictions.

### Key Capabilities:
- Current and deferred tax provision
- Effective tax rate calculation
- Tax rate reconciliation
- Multi-jurisdiction support
- Return-to-provision adjustments
- Tax footnote preparation

---

## 2.5 Pillar 4: ARCS — Account Reconciliation Cloud Service

### What It Does:
Manages the reconciliation of GL balances to sub-ledger or bank statements during the close process.

### Key Capabilities:
- Auto-matching of transactions
- Risk-based reconciliation profiles
- Variance thresholds and aging
- Workflow with reviewer/preparer assignment
- Integration with ERP GL balances

### Example:
```
Monthly Close Task: Reconcile Bank Account 10001
  GL Balance: ₹42,56,789
  Bank Statement Balance: ₹42,89,123
  Difference: ₹32,334
  
  Items in Transit:
    - Check #4521 (₹15,000) — issued but not yet cleared
    - Direct deposit (₹17,334) — recorded by bank, not yet in GL
  
  Reconciled: ✅ ₹42,56,789 + ₹32,334 = ₹42,89,123
```

## 2.6 Pillar 5: Narrative Reporting (NRCS)

### What It Does:
Creates board-quality reports that combine data from EPM applications with narrative text, charts, and commentary. Think of it as a "Word processor + Data connector."

### Key Features:
- DOCX-style report authoring
- Embed live data grids from EPBCS/FCCS
- Collaborative authoring with review/approval workflow
- Bursting (auto-generate entity-specific reports)
- PDF/PPTX/XLSX export

## 2.7 Pillar 6: PCMCS — Profitability & Cost Management Cloud Service

### What It Does:
Performs multi-dimensional cost allocation and profitability analysis — allocating shared costs (IT, HR, Facilities) down to products, customers, or business lines.

### Example:
```
IT Department Total Cost: ₹10,00,00,000

Allocation Basis: Headcount per Department
  Sales: 200 FTE  → Allocated: ₹4,00,00,000 (40%)
  HR: 50 FTE      → Allocated: ₹1,00,00,000 (10%)
  Ops: 150 FTE    → Allocated: ₹3,00,00,000 (30%)
  Finance: 100 FTE→ Allocated: ₹2,00,00,000 (20%)
```

---

## 2.8 Pillar 7: EDM / DM — Enterprise Data Management

### What It Does:
Manages master data (dimensions, hierarchies, mappings) across all EPM applications as a single source of truth.

### Why It Matters:
Without EDM, each pillar maintains its own dimension hierarchy → drift and inconsistency.

### Example:
```
Entity "E10001 - Hotel India" must exist identically in:
  - EPBCS (for planning)
  - FCCS (for consolidation)
  - ARCS (for reconciliation)

EDM maintains ONE master definition and pushes it to all applications.
```

## 3.1 EPBCS vs PBCS — Naming Clarification

| Term | Full Name | What It Means |
|------|-----------|---------------|
| **PBCS** | Planning and Budgeting Cloud Service | The original basic planning cloud service |
| **EPBCS** | Enterprise PBCS | The enhanced version with pre-built modules (Financials, Workforce, Capital, Projects) |
| **Planning** | Oracle Cloud Planning | The current name (Oracle merged PBCS and EPBCS branding) |

**Current Reality (2024+):** Oracle now sells "Planning" as one product. The distinction between PBCS/EPBCS is largely gone. If you buy "Enterprise" licensing, you get all modules. If you buy "Standard," you get basic planning without pre-built modules.

## 3.2 Application Types in EPBCS

### Standard Application
| Feature | Detail |
|---------|--------|
| **Dimensions** | Fixed: Account, Entity, Scenario, Version, Period, Year, Currency + up to 7 custom |
| **Plan Types** | Up to 6 BSO + 1 ASO reporting cube |
| **Forms** | Full support |
| **Business Rules** | Full Calc Manager support |
| **Best For** | Custom-built financial models from scratch |

### Enterprise Application (Modules)
| Feature | Detail |
|---------|--------|
| **Dimensions** | Pre-built + additional module-specific dimensions |
| **Plan Types** | Pre-configured cubes for each module |
| **Forms** | Pre-built forms for each module |
| **Business Rules** | Pre-built rules (can be customized) |
| **Best For** | Rapid deployment with Oracle best practices |

### Free Form Application
| Feature | Detail |
|---------|--------|
| **Dimensions** | Fully flexible — no mandatory dimensions |
| **Plan Types** | BSO only (no ASO reporting) |
| **Forms** | Full support |
| **Business Rules** | Full support |
| **Best For** | Non-financial models (headcount tracker, project scorecards) |

### Comparison:
```
Standard Application:
  → You design the Account dimension from scratch
  → You build Revenue, Expense, Net Income members manually
  → Maximum flexibility, maximum effort

Enterprise Application:
  → Oracle provides pre-built Account hierarchy for P&L, BS, CF
  → Oracle provides pre-built forms for Revenue, Expense entry
  → Pre-built rules for consolidation, currency translation
  → Faster deployment, less flexibility for customization

Free Form Application:
  → No Account, Entity, Scenario, Version dimensions required
  → You can create any dimensions you want
  → Example: A KPI tracking app with "KPI" and "Region" dimensions
```

## 3.3 Plan Types — The Cube Architecture

A Plan Type is an **Essbase cube** within the EPBCS application. Each application can have multiple plan types.

### Plan Type Limits:
| Application Type | BSO Plan Types | ASO Plan Types | Total |
|-----------------|----------------|----------------|-------|
| Standard | Up to 6 | 1 (Reporting) | 7 |
| Enterprise (Modules) | Varies per module | 1 | Module-dependent |
| Free Form | Up to 3 | 0 | 3 |

### Why Multiple Plan Types?
```
Example — Hotel Pvt Ltd Standard Application:

Plan Type 1: "Plan1" (BSO) — Revenue & Expense Budget
  Dimensions: Account, Entity, Period, Year, Scenario, Version, Currency, Department
  Dense: Account, Period
  Sparse: Entity, Year, Scenario, Version, Currency, Department

Plan Type 2: "Plan2" (BSO) — Workforce Planning
  Dimensions: Account, Entity, Period, Year, Scenario, Version, Currency, Employee
  Dense: Account, Period
  Sparse: Entity, Year, Scenario, Version, Currency, Employee

Plan Type 3: "CapPlan" (BSO) — Capital Asset Planning
  Dimensions: Account, Entity, Period, Year, Scenario, Version, Currency, Asset_Class
  Dense: Account, Period
  Sparse: Entity, Year, Scenario, Version, Currency, Asset_Class

Reporting Plan Type: "Rpt1" (ASO) — Consolidated Reporting
  → Data pushed from Plan1, Plan2, CapPlan via Smart Push
  → Used only for querying, no user input
  → ASO = fast aggregation for large datasets
```

### Key Rule: Dimension Membership Across Plan Types
- Dimensions can be **shared** across plan types or **unique** to one plan type
- Accounts can be assigned to specific plan types (via "Plan Type" membership property)
- If Account "Revenue" is in Plan1 but NOT Plan2, it exists only in Plan1's cube

```
Account: "100110 - Rooms Revenue"
  Plan Type Membership: ☑ Plan1  ☐ Plan2  ☐ CapPlan  ☑ Rpt1

Account: "300000 - Employee Salary"
  Plan Type Membership: ☐ Plan1  ☑ Plan2  ☐ CapPlan  ☑ Rpt1
```

## 4.1 Standard vs Enterprise — Detailed Decision Matrix

| Decision Factor | Choose Standard | Choose Enterprise |
|----------------|-----------------|-------------------|
| **Timeline** | 3-6 months OK | Need to go live in 4-8 weeks |
| **Existing Model** | Complex custom model from Hyperion on-prem | Greenfield implementation |
| **Finance Team** | Has EPM architects who want full control | Wants Oracle best practices |
| **P&L Structure** | Highly custom (non-standard chart of accounts) | Standard P&L / BS / CF |
| **Workforce** | Simple headcount planning | Full employee-level compensation modeling |
| **Capital** | No capital planning needed | Need asset management and depreciation |
| **Customization** | Need 100% control over dimensions and rules | Accept Oracle's pre-built structure |

## 4.2 Application Creation — What Happens Under the Hood

When you create an EPBCS application:

```
Step 1: Choose Application Type → Standard / Enterprise / Free Form
Step 2: Name the Application → "HotelBudget"
Step 3: Configure Dimensions → Account, Entity, Scenario, Version, Period, Year
Step 4: Set Currency → Multi-currency (INR, USD, GBP) or Single (INR)
Step 5: Set Fiscal Year → April start (India) vs January start (US)
Step 6: Set Plan Types → Plan1 (BSO), Plan2 (BSO), Rpt1 (ASO)

Behind the scenes, Oracle:
  → Creates Essbase BSO cubes for each Plan Type
  → Creates the ASO reporting cube
  → Sets up dimension outlines
  → Configures the Planning layer (forms, rules, workflows)
  → Deploys system member formulas
  → Initializes security framework
```

# SECTION 5: PLAN TYPES AND CUBES

---

## 5.1 Plan Type = Essbase Cube

Every Plan Type is literally an Essbase cube with its own:
- Data blocks and index
- Dense/Sparse configuration
- Stored data
- Calculation scripts
- Member formulas

## 5.2 BSO vs ASO Plan Types

| Aspect | BSO Plan Type | ASO Plan Type (Reporting) |
|--------|---------------|--------------------------|
| **User Input** | ✅ Users can enter data | ❌ Read-only (no user input) |
| **Calculations** | Full calc scripts, member formulas | Limited (MDX only, no calc scripts) |
| **Aggregation** | Explicit (run AGG / CALC DIM) | Dynamic (auto-aggregates on query) |
| **Block Storage** | Data stored in blocks | Aggregated views materialized |
| **Performance** | Excellent for write operations | Excellent for read/query operations |
| **Use Case** | Data entry, budgeting, calculations | Reporting, dashboards, large-scale queries |

## 5.3 Smart Push — Moving Data Between Plan Types

Smart Push copies data from one BSO plan type to another plan type (BSO or ASO).

```
Example:
  Plan1 (BSO) has Revenue data entered by users
  Rpt1 (ASO) is the reporting cube

  Smart Push Configuration:
    Source: Plan1
    Target: Rpt1
    Trigger: After form save (or on-demand)
    
  When user saves a form in Plan1:
    → Revenue data for that intersection is pushed to Rpt1
    → Rpt1 dashboard immediately reflects the update
```

### Smart Push Properties:
| Property | Options | Meaning |
|----------|---------|---------|
| **Trigger** | On Save, On Demand | When the push fires |
| **Scope** | Changed cells only, All cells | What data to push |
| **Data Map** | Member mappings | If dimension structures differ between cubes |

## 8.1 Scenario: Hotel Chain Annual Budgeting

```
Company: Hotel Pvt Ltd (5 hotels, 3 countries, 12 departments)
Application: EPBCS Standard
Timeline: April to March fiscal year

Implementation Steps:
1. Design dimensions (Account, Entity, Department, Scenario, etc.)
2. Build forms for Revenue entry, Expense entry, Headcount entry
3. Create business rules:
   - Revenue = Rooms_Available × Occupancy_Rate × Avg_Room_Rate
   - Total Expense = Sum of department expenses
   - Net Income = Revenue − Expense
4. Load Actuals from ERP (Oracle Fusion → EPBCS via DI)
5. Configure approval workflow (Department → Controller → CFO)
6. Build dashboards for executive reporting
7. Train 50+ users on Smart View and web forms
```

## 8.2 Scenario: Manufacturing Company Forecast

```
Company: AutoParts Ltd (25 plants, 200 product SKUs)
Application: EPBCS Enterprise (Financials module)
Challenge: Monthly rolling forecast across all plants

Solution:
1. Financials module provides pre-built P&L/BS/CF structure
2. Custom "Product" dimension (200 SKUs) added
3. Driver-based model:
   Revenue = Units_Sold × Selling_Price
   COGS = Units_Sold × Cost_Per_Unit
   Gross_Margin = Revenue − COGS
4. Rolling 12-month forecast updated monthly
5. What-if scenarios for raw material price changes
```

# SECTION 10: INTERVIEW QUESTIONS

---

## 10.1 Beginner Level

**Q1: What is Oracle EPM Cloud?**
> Oracle EPM Cloud is a SaaS platform for enterprise performance management — it provides planning, budgeting, forecasting, consolidation, close, tax reporting, and account reconciliation capabilities.

**Q2: Name the 7 pillars of Oracle EPM Cloud.**
> EPBCS (Planning), FCCS (Consolidation), TRCS (Tax), ARCS (Account Recon), Narrative Reporting, PCMCS (Profitability), EDM (Master Data).

**Q3: What is the difference between EPBCS and FCCS?**
> EPBCS is for forward-looking planning and budgeting. FCCS is for backward-looking consolidation and close. EPBCS uses Essbase cubes for user data entry. FCCS uses Essbase with pre-built consolidation rules, intercompany elimination, and currency translation.

**Q4: What is a Plan Type?**
> A Plan Type is an Essbase cube within the EPBCS application. Each application can have up to 6 BSO plan types and 1 ASO reporting plan type.

## 10.2 Intermediate Level

**Q5: When would you choose a Standard application over an Enterprise application?**
> Choose Standard when you need full control over dimension design, when migrating a complex on-prem Hyperion model, when the chart of accounts is highly customized, or when you need more than the pre-built module structure allows. Choose Enterprise when you want Oracle best practices, faster deployment, and pre-built forms/rules.

**Q6: Can an ASO plan type accept user input through forms?**
> No. ASO plan types are read-only reporting cubes. Data enters ASO only through Smart Push from a BSO plan type, or through data loads. Users cannot type into a form connected to an ASO cube.

**Q7: What is Smart Push? How does it differ from Data Maps?**
> Smart Push pushes data from one plan type to another within the SAME application (e.g., Plan1 BSO → Rpt1 ASO). Data Maps push data between DIFFERENT applications (e.g., EPBCS → FCCS). Smart Push is lighter and faster; Data Maps handle cross-application dimension mapping.

## 10.3 Advanced Level

**Q8: A client says "We don't need FCCS because we can consolidate in EPBCS." How do you respond?**
> EPBCS can do basic aggregation (sum of entities), but it lacks: (a) intercompany elimination engine, (b) ownership/minority interest calculations, (c) journal entries with audit trail, (d) IFRS/GAAP compliance features, (e) close task management. For statutory consolidation of a multi-entity group with cross-border eliminations, FCCS is necessary.

**Q9: Explain how data flows from ERP through the entire EPM suite.**
> Actuals from ERP (e.g., Oracle Fusion GL) are loaded into EPBCS via Data Integration, where they serve as the baseline for planning and variance analysis. Planned data from EPBCS can be pushed to FCCS for consolidated reporting. ARCS reconciles GL balances against sub-ledgers. TRCS computes tax provisions using the consolidated financials from FCCS. Narrative Reporting pulls from all modules to produce management and board reports. EDM ensures dimensional consistency across all applications.

**Q10: What are the implications of creating too many Plan Types?**
> Each Plan Type is a separate Essbase cube consuming memory, disk, and processing resources. More plan types mean: larger metadata, longer refreshes, more complex Smart Push configurations, more business rules to maintain, and potential confusion for users navigating between cubes. Best practice is to minimize plan types (3-4 max) and use the ASO reporting cube for consolidated queries instead of adding BSO cubes.
