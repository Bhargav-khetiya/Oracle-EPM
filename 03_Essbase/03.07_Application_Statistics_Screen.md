# 03.07 Application Statistics Screen

> **Module:** 03_Essbase  
> **Topic:** 07 - Reading the Statistics  
> **Target Audience:** Architect / Administrator  

---

## Navigation
**Navigator -> Application -> Overview -> [Select Cube] -> Statistics Tab**

## Overview
This screen is the heartbeat monitor of your Essbase engine. It tells you the exact physical geometry of the database. If your system is crashing, this is the first screen the Architect checks.

## Every Configuration Property

### 1. Dimension Statistics

#### "Number of Dimensions"
- **Architect Rule:** If a BSO cube has more than 15 dimensions, you have likely over-engineered the solution and will suffer performance degradation. ASO cubes can handle 20+.

#### "Dense Dimensions"
- **What it indicates:** Tells you which dimensions define the Block Size (usually Account and Period).

### 2. Block Storage (BSO) Statistics

#### "Block Size (Bytes)"
- **What it is:** The physical RAM required to load one single block.
- **The Red Line:** Must be between 8,000 (8KB) and 100,000 (100KB). If it says `500,000`, your system is doomed to fail during heavy aggregations.

#### "Number of Existing Blocks"
- **What it is:** The exact number of blocks currently written to the hard drive (`.pag` files).
- **Architect Note:** If this number is `10,000,000`, and your block size is `100KB`, your physical database is 1 Terabyte. EPM Cloud will likely warn you or fail.

#### "Block Density (%)"
- **What it is:** The percentage of cells *inside* the existing blocks that actually contain a number (not `#Missing`).
- **The Target:** Ideally > 10%. If it is 0.5%, your Dense dimensions are configured incorrectly, and you are wasting 99.5% of your RAM loading empty cells.

### 3. Aggregate Storage (ASO) Statistics

*(If you are viewing an `OEP_REP` cube)*

#### "Input Level Data Size"
- **What it is:** The physical size of the raw data loaded into the ASO cube.

#### "Aggregate Data Size"
- **What it is:** The physical size of the pre-calculated aggregations (Views) materialized on disk.
- **Architect Note:** If the Aggregate Data Size is 0, it means you have not run the "Execute Aggregation Process" job. The ASO cube is calculating everything on the fly dynamically. For massive ASO cubes, you MUST run the aggregation process to materialize views on disk and speed up Smart View retrievals.

## 25. Interview Questions

### Architect
**Q: You check the Statistics screen for a BSO cube. The Block Size is 50KB (Excellent). The Block Density is 40% (Excellent). The Number of Existing Blocks is 50,000. However, the rule `CALC DIM(Entity)` takes 3 hours to run. The physical geometry is perfect, so what is causing the bottleneck?**
> A: The bottleneck is likely in the Member Formulas attached to the Dense dimensions (Account), or an incredibly complex dynamic calculation. If a specific Account formula contains complex cross-dimensional logic (e.g., looking up a currency rate from a different block using `->`), the engine must perform thousands of micro-reads from the hard drive for every single block it calculates. The geometry is fine, but the *mathematical payload* is too heavy.
