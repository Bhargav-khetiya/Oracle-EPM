# 03.08 — Essbase Caches and Tuning: Complete Guide

> **Module:** 03_Essbase | **Topic:** Data Cache, Index Cache, Calculator Cache, Tuning
> **Audience:** Architect / Service Administrator

---

## 1. WHY — Why Caches Matter

**The problem:** A form query retrieves data from 500 blocks. Each block is stored on disk. Reading 500 blocks from disk takes 10 seconds. Reading 500 blocks from memory (cache) takes 0.5 seconds. Caches are the difference between a responsive application and one that drives users back to Excel.

## 2. THE 3 ESSBASE CACHES

```

│                                                                   │
│  ┌── Index Cache ──────────────────────────┐                     │
│  │ Stores: Block index (addresses)         │                     │
│  │ Purpose: Find blocks quickly            │                     │

```

## 3. INDEX CACHE — THE TABLE OF CONTENTS

### What It Does
The Index Cache stores the **block index** — a map of which blocks exist and where they are stored on disk. Without the index in memory, every query requires a disk seek to find each block.

### How It Works

```
Query: "Show me Mumbai_Hotel, Budget, Working, FY2026"

With Index in Cache:
  Index → "Block #247 is at disk position 0x4F2A0" → Read block → Done
  Time: 0.001 seconds ⚡

Without Index in Cache:
  Scan disk index file → Find block #247 → Read position → Read block
  Time: 0.05 seconds 🐌 (50× slower)
```

### Sizing

```
Index Cache Size = Number of Blocks × 128 bytes (approximate)

Hotel Pvt Ltd:
  Block count: 520 blocks
  Index size: 520 × 128 = 66,560 bytes = ~65 KB
  Recommended cache: 1 MB (generous — fits entirely in cache)

Large enterprise:
  Block count: 500,000 blocks
  Index size: 500,000 × 128 = 64 MB
  Recommended cache: 100 MB
```

## 4. DATA CACHE — THE SPEED BOOST

### What It Does
The Data Cache stores recently accessed **block data** in memory. When a form requests a block that's already in the data cache, it's served from memory instead of disk.

### Cache Hit Ratio

```
Cache Hit Ratio = (Reads from cache) / (Total reads) × 100

Healthy:     > 90% (most reads from memory)
Warning:     70-90% (some disk reads)
Critical:    < 70% (too many disk reads — cache too small)

Location: Application Statistics → Cache Hit Ratio
```

### Sizing

```
Data Cache Size = Frequently accessed blocks × Block size

Hotel Pvt Ltd:
  Active blocks: 500 (5 hotels × 3 scenarios × 3 versions × ~11)
  Block size: 200 accounts × 17 periods × 8 bytes = ~27 KB
  Working set: 500 × 27 KB = 13.5 MB
  Recommended cache: 32 MB (2× working set)
```

## 5. CALCULATOR CACHE — THE SCRATCH PAPER

### What It Does
The Calculator Cache provides working memory during business rule execution. It determines how many sparse dimension members the calculator can process in one pass (called a "task").

### Impact on Performance

```
Small Calculator Cache:
  Rule processes sparse dims in multiple passes
  Each pass = sequential scan
  Slower calculations

Large Calculator Cache:
  Rule processes all sparse dims in one pass
  Single scan of blocks
  Faster calculations

Controlled by: SET CALCTASKDIM (number of sparse dims per task)
```

## 6. CACHE TUNING IN EPBCS (CLOUD)

### What Admins CAN Control

```
In EPBCS Cloud, direct cache settings are managed by Oracle.
What admins CAN do:

1. Optimize block count (fewer blocks = less cache needed)
   → CLEARBLOCK ALL (remove empty blocks)
   → Reduce sparse cross-joins

2. Optimize block size (smaller blocks = more fit in cache)
   → Move rarely-used dense dims to sparse
   → Use Dynamic Calc instead of Store for calculated members

3. Optimize calculations
   → SET LOCKBLOCK ON (keeps blocks in cache during calc)
   → SET CALCPARALLEL 4 (parallel threads)
   → Tight FIX (process fewer blocks)

4. Monitor cache health
   → Check Application Statistics → Cache Hit Ratio
   → If < 90% → reduce block count or request Oracle to increase
```

### What Oracle Manages

```
On EPM Cloud, Oracle automatically:
  - Sets cache sizes based on cube size
  - Adjusts during maintenance window
  - Restructures database as needed
  
You cannot directly set:
  - DATACACHESZ (managed by Oracle)
  - INDEXCACHESZ (managed by Oracle)
  - But you CAN optimize what goes INTO the cache
```

## 8. COMMON MISTAKES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Ignoring cache hit ratio | Forms are slow, no obvious cause | Check Application Statistics monthly |
| Block explosion filling cache | Cache hit drops below 50% | CLEARBLOCK ALL → fix the causing rule |
| SET LOCKBLOCK OFF during calcs | Cache thrashing during rule execution | Use SET LOCKBLOCK ON |
| Not running restructure after metadata changes | Fragmentation increases | Restructure during maintenance |
| Trying to set cache params on Cloud | Settings don't apply | Focus on optimizing what's IN the cache |

## 9. INTERVIEW QUESTIONS

### Beginner
**Q: What are the 3 Essbase caches and what do they store?**
> (1) **Index Cache:** Stores the block index — a map of where each data block is located on disk. Like a table of contents. 100% hit ratio means the entire index fits in memory. (2) **Data Cache:** Stores recently accessed block data in memory. > 90% hit ratio is healthy — means most queries are served from memory, not disk. (3) **Calculator Cache:** Provides working memory during rule execution. Controls how many sparse dimensions are processed per calculation pass.

### Architect
**Q: Cache hit ratio dropped from 94% to 23% overnight. Diagnose and fix.**
> **Step 1: Check block count.** Go to Application Statistics. If block count jumped from 500 to 45,000, that's a block explosion — the cache can't hold 45K blocks. **Step 2: Find the cause.** Check Jobs Console — which rule ran overnight? Look for rules with `SET CREATEBLOCKONEQ ON` or `SET CREATENONMISSINGBLK ON` that didn't turn it off. **Step 3: Fix.** Run `CLEARBLOCK ALL` to remove empty blocks. Fix the rule to turn off block creation flags after DATACOPY. **Step 4: Verify.** Check Application Statistics — block count should return to baseline (~500). Cache hit ratio should recover to >90%. **Prevention:** Add CREATEBLOCKONEQ OFF and CREATENONMISSINGBLK OFF after every DATACOPY in all rules.
