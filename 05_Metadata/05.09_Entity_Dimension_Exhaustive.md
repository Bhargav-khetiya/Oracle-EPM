# 05.09 Entity Dimension — Exhaustive Property Reference

> **Module:** 05_Metadata

> **Target Audience:** Developer / Architect

## Introduction

The **Entity** dimension represents the organizational structure of the business — legal entities, departments, cost centers, business units, or geographic locations. It is almost always a **Sparse** dimension and is the primary driver of data block count, security assignments, and workflow (Approval) processes.

# EVERY ENTITY MEMBER PROPERTY

## 1. Member Name & Alias

| Property | Description | Best Practice |
|----------|-------------|---------------|
| **Member Name** | Unique internal identifier | Use codes: `E_1001`, `CC_FINANCE`, `BU_NORTH_AMERICA` |
| **Alias** | User-friendly display name | `North America HQ`, `Finance Department` |

---

## 2. Data Storage

| Option | When to Use |
|--------|-------------|
| **Store** | Level 0 entities (input nodes: individual departments, branches) |
| **Dynamic Calc** | Upper-level rollups in Hybrid BSO (auto-aggregated on retrieval) |
| **Shared** | Alternate hierarchies (reporting by region vs reporting by legal entity) |
| **Label Only** | Organizational headers (e.g., `--- North America Entities ---`) |
| **Never Share** | When a parent has one child and must store independently |

---

## 3. Base Currency

| Property | Description | Options | Impact |
|----------|-------------|---------|--------|
| **Base Currency** | The local currency for this entity | `USD`, `EUR`, `GBP`, `JPY`, etc. | Determines which exchange rate is applied during currency conversion |

### How Base Currency Works:
- Entity `US_HQ` has Base Currency = `USD`
- Entity `London_Office` has Base Currency = `GBP`
- When a user enters $1,000 for US_HQ, it is stored as USD
- When a user enters £800 for London_Office, it is stored as GBP
- The Currency Conversion business rule reads the Base Currency of each entity, finds the appropriate FX rate, and converts to the reporting currency

### Setting Base Currency:
```
Dimension Editor → Entity → [Select Member] → Properties → Base Currency → [Select Currency]
```

> **Architect Note:** Base Currency CANNOT be set on parent entities (they inherit from children during aggregation). Only Level 0 entities should have a Base Currency assigned.

## 4. Enable for Process Management (Approvals)

| Property | Description | Options | Impact |
|----------|-------------|---------|--------|
| **Enable for Process Management** | Whether this entity participates in the Approval workflow | ☑️ / ☐ | If enabled, users must Submit, Promote, Approve, or Reject data for this entity |

### Approval Workflow:
```
Not Started → First Pass → Under Review → Approved → Published
           ↓                    ↓
        Rejected            Signed Off
```

**Best Practice:** Only enable for Level 0 entities where actual data entry happens. Do NOT enable for rollup parents.

## 5. Consolidation Operator

| Operator | Use Case |
|----------|----------|
| `+` (Addition) | Standard entity rollup (US + UK + Germany = Total_Company) |
| `-` (Subtraction) | Intercompany elimination entities |
| `~` (Ignore) | Statistical entities that shouldn't roll up |

## 7. Security Access

| Access Level | What It Allows |
|-------------|---------------|
| **Read** | User can see data for this entity but cannot edit |
| **Write** | User can see AND edit data for this entity |
| **None** | Entity is invisible to the user |

### Security Assignment:
```
Navigator → Access Control → [Select User/Group] → Entity Dimension → [Assign Read/Write/None per member]
```

### Inheritance Rules:
- If a user has **Write** access to `North_America`, they automatically have Write access to ALL descendants (US, Canada, Mexico) unless explicitly overridden
- **Most restrictive wins:** If a user has Read on the parent but Write on a specific child, the child gets Write

## 8. UDA (User Defined Attributes)

Common Entity UDAs:

| UDA | Purpose |
|-----|---------|
| `Active` | Currently active entities (exclude inactive from calculations) |
| `Allocatable` | Entities that receive allocations |
| `Legal_Entity` | Entities that represent legal structures (for statutory reporting) |
| `Intercompany` | Entities involved in intercompany transactions |
| `Domestic` | Domestic entities (for tax calculation variations) |
| `Foreign` | Foreign entities (require currency conversion) |

## 9. Alternate Hierarchies — Legal vs Management

### The Problem:
A company has two ways to view its organizational structure:
1. **Legal Entity hierarchy:** US Holdings → US Operating → US Branch A, US Branch B
2. **Management hierarchy:** CEO → VP Sales → US Branch A, EU Branch C

These hierarchies share the same Level 0 members but have different rollup paths.

### The Solution: Shared Members
```
Entity Dimension:
├── Legal_Hierarchy (Label Only)
│   ├── US_Holdings
│   │   ├── US_Branch_A (Store)
│   │   └── US_Branch_B (Store)
│   └── EU_Holdings
│       └── EU_Branch_C (Store)
├── Management_Hierarchy (Label Only)
│   ├── VP_Sales
│   │   ├── US_Branch_A (Shared → points to Legal's US_Branch_A)
│   │   └── EU_Branch_C (Shared → points to Legal's EU_Branch_C)
│   └── VP_Operations
│       └── US_Branch_B (Shared → points to Legal's US_Branch_B)
```

**Rules for Shared Members:**
- The **first occurrence** in the outline is the "original" (Stored)
- All subsequent occurrences are **Shared** (pointers to the original)
- Data is stored ONCE, displayed in BOTH hierarchies
- When a user enters data for US_Branch_A under Legal, it automatically appears under Management

## 10. Entity Dimension Design Patterns

### Pattern 1: Simple Department Structure
```
Total_Company
├── Finance
├── HR
├── IT
├── Sales
│   ├── Sales_North
│   ├── Sales_South
│   ├── Sales_East
│   └── Sales_West
└── Operations
```

### Pattern 2: Legal Entity with Elimination
```
Total_Consolidated
├── US_Parent
│   ├── US_Operating (Store)
│   └── US_Elim (~, minus sign)
├── EU_Parent
│   ├── UK_Entity (Store)
│   ├── DE_Entity (Store)
│   └── EU_Elim (~, minus sign)
└── Corp_Elim (~, minus sign)
```

### Pattern 3: Matrix Organization (Region × Function)
```
Total_Company
├── By_Region (Label Only)
│   ├── North_America
│   │   ├── NA_Finance (Store)
│   │   ├── NA_Sales (Store)
│   │   └── NA_Ops (Store)
│   └── Europe
│       ├── EU_Finance (Store)
│       └── EU_Sales (Store)
├── By_Function (Label Only)
│   ├── Total_Finance
│   │   ├── NA_Finance (Shared)
│   │   └── EU_Finance (Shared)
│   └── Total_Sales
│       ├── NA_Sales (Shared)
│       └── EU_Sales (Shared)
```

## Interview Questions

### Intermediate
**Q: How does Base Currency work for a parent entity that has children in different currencies?**
> A: Parent entities do NOT have a Base Currency assigned. When children with different currencies (e.g., US = USD, UK = GBP) are aggregated, the system first converts each child's local currency data to a common reporting currency using the Currency Conversion business rule, then aggregates the converted values at the parent level.

### Architect
**Q: A company has 500 entities, and 200 of them are inactive (closed branches). The form takes forever to load even with Suppress Missing Blocks on. What's wrong?**
> A: Even with Suppress Missing Blocks, if 200 inactive entities have **historical data blocks** on disk, Essbase still scans the block index for all 500 entities. The fix: (1) Add a UDA `Inactive` to the 200 closed entities. (2) Modify the form's entity row selection to use `@REMOVE(@RELATIVE("Total_Entity", 0), @UDA("Entity", "Inactive"))` to exclude them. (3) Alternatively, use Valid Intersections to mark Inactive entities as invalid for the current budget year.

## Summary

| Property | Critical For |
|----------|-------------|
| **Base Currency** | Multi-currency applications — must be set on Level 0 |
| **Process Management** | Approval workflows — enable only on input entities |
| **Security (Read/Write/None)** | Data access control — most important admin function |
| **Alternate Hierarchies (Shared)** | Legal vs Management reporting — single data, dual views |
| **UDAs** | Dynamic rule scoping (`@UDA("Entity", "Active")`) |
