# 06.05 Form Formatting and Validation Rules

> **Module:** 06_Forms  
> **Topic:** 05 - Formatting and Validation  
> **Target Audience:** Functional Consultant  

---

## 1. Learning Objectives
- Use Data Validation rules to enforce business logic on the UI.
- Format cells dynamically based on thresholds (Red/Green indicators).
- Prevent Form Promotes when validations fail.

## 3. Introduction
If you tell a user "Don't increase expenses by more than 10%", 50% of the users will ignore you and do it anyway. You cannot rely on human compliance. You must enforce business limits systematically. In EPBCS, you do this directly on the Web Form using **Data Validation Rules**.

## 7. Core Concepts: The Validation Engine

Data Validation is a logic engine built into the Web Form definition. It executes in the browser when the user interacts with the form.

### Anatomy of a Rule
1. **The Condition:** `If Current Cell Value > 10,000`
2. **The Formatting (Cosmetic):** `Set Cell Background Color to RED`.
3. **The Message (Informational):** `Pop up a tooltip saying "Limit Exceeded"`.
4. **The Action (Enforcement):** `Do not allow the user to Promote this Approval Unit`.

## 13. Configuration: Building a Validation Rule

**Requirement:** Ensure no one plans a negative salary.
1. Open the Web Form in Edit mode.
2. Go to the **Data Validation** tab.
3. Create a new Rule.
4. Set Location to: `Row containing Salary`.
5. Condition: `If Value < 0`.
6. Formatting: Red background.
7. Processing: Check the box for **"Enable Approvals"** -> **Stop**. 

Now, if a user types `-500` and clicks Save, the cell turns red. If they try to click the "Promote" button to send the budget to their manager, the system physically blocks them and says "Validation Failed."

## 15. Advanced Examples: Comparing Cells
You are not limited to static numbers. You can compare cells against other cells.

**Requirement:** Next year's Travel budget cannot exceed last year's Actual Travel spend by more than 5%.
- Column A: `FY23 Actuals`
- Column B: `FY24 Budget`
- **The Rule:** Condition: `If Column B > (Column A * 1.05)` -> Flag Red.
This creates dynamic, context-aware validation.

## 18. Architect Notes: Validation vs Groovy
Data Validation rules are great for simple UI coloring and blocking approvals. 
However, **Data Validation rules do NOT stop the user from clicking Save.** The bad data still writes to the Essbase cube; it just gets flagged red and cannot be Promoted.
If you want to physically block the Save action so the bad data never reaches Essbase, you cannot use Data Validation. You MUST write a **Groovy Rule** attached to the form on "Run Before Save" and throw a `VetoException`.

## 25. Interview Questions

### Intermediate
**Q: A user types an invalid number into a form. The cell turns red, but when you check Smart View, the invalid number is saved in the database. Why did the validation rule let it save?**
> A: OOTB Data Validation rules on forms only provide visual formatting and can block the Approval/Promote workflow. They do not intercept the HTTP Save request to the database. To physically intercept a Save, you must use Groovy.

### Architect
**Q: You have a form with 100 columns and 500 rows. You put a complex Data Validation rule checking the variance of every cell against prior year. When the user opens the form, the browser freezes for 10 seconds. Why?**
> A: Data Validation rules execute client-side (in the user's web browser using JavaScript) when the form loads and when data changes. Evaluating a complex IF statement across 50,000 cells in a browser will cause massive UI lag. To fix this, simplify the rule, apply it to a smaller subset of cells, or move the validation logic to the server side via Groovy or Business Rules.

## 27. Summary
Use Data Validation for visual cues (Red/Yellow/Green) and to control the workflow. Use Groovy for absolute database protection.
