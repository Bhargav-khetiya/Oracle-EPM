# Form Precision and Validation Rules

Data validation and precision configuration at the Form layer is essential for preventing bad data from entering the database in the first place.

## 1. Grid Precision and Formatting

While the Dimension layer sets the default precision, you can override it on specific Forms.

*   **Precision Override:** In the Form layout, you can select a specific Row or Column (e.g., `Price_Per_Unit`) and force it to display 4 decimal places, overriding the Account's default 2 decimal places.
*   **Scaling:** As discussed in 05.05, scaling should be done on the Form. In the Form Options, you can set "Scale" to `Thousands`. A stored database value of `1000000` will display to the user as `1000`. When the user types `50` into the form, it will save to the database as `50000`. This is the safest way to handle scaling because the underlying math remains accurate.

## 2. Minimums and Maximums

You can configure forms to reject unreasonable inputs before they hit the database.

*   **The Problem:** A user accidentally types `10000` instead of `100` into a "Headcount" field. The calc script runs, multiplies `10000` by the average salary, and artificially inflates the company's budget by $10 million.
*   **The Solution (Validation Rules):** EPM provides Data Validation rules directly on the form.
    *   *Example:* If `Current_Cell_Value` > `500`, then set cell color to Red and throw a Validation Message: "Headcount cannot exceed 500 per department."
    *   *Enforcement:* You can check a box to **Prevent Save**. This stops the user from committing the bad data.

## 3. The "Missing" vs "Zero" Distinction

EPM treats `#MISSING` (null) and `0` very differently.

*   **#MISSING:** The cell is completely empty. Essbase does not allocate a data block for it. This is highly efficient.
*   **Zero (0):** The user explicitly typed a zero. Essbase must allocate a data block and store the 0.
*   **The Form Setting:** In Form Properties, you can choose how the system handles blanks. By default, typing a zero saves a zero. However, many architects use Groovy or Calc Scripts to explicitly clear zeros (converting them to `#MISSING`) during the overnight batch to shrink the database size, because storing millions of zeros bloats the cube and degrades performance.
