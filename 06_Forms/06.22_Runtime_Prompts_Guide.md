## 🏢 Overview
Runtime Prompts are pop-up dialogs that ask users for input before a business rule runs or a form opens. They allow dynamic behavior without hardcoding values.

### 💡 Logic & Purpose
Runtime Prompts (RTPs) bridge the gap between static code and dynamic user intent. Without RTPs, a developer would have to write 100 different business rules to calculate a 5% increase for 100 different departments. With an RTP, the developer writes *one* generic rule with a `{Department}` variable, and when the user runs it, a pop-up asks: "Which department do you want to calculate?"

### 🌀 Confusion Resolution
> **Misconception:** "I attached a business rule with a Runtime Prompt to my form to run 'On Save'. Every time a user hits Save, they complain that an annoying pop-up box interrupts them."
> **Reality:** If a business rule is attached to "Run on Save", you should check the "Hide Prompt" option in the form properties, OR configure the RTP to dynamically read the member from the form's POV/Page/Row context (e.g., using `[Current POV]`). Forcing users to manually answer prompts every time they hit save destroys the user experience.

### 😈 Twisted Interview Question
**Question:** A developer writes a Business Rule with a Runtime Prompt asking the user for a "Percentage Increase". The user types `5%` into the pop-up box, but the rule fails with a syntax error. Why?
> **Answer:** The developer likely defined the RTP variable type as a `Member` or a `String`, instead of a `Number`. Furthermore, if the user typed the literal character `%`, the calculation engine cannot process it mathematically unless the rule strips it out or the prompt type specifically validates it as a decimal (e.g., typing `0.05` instead of `5%`). Always set strict validation types for RTPs!
