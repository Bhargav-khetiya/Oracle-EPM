### 💡 Logic & Purpose
Form Best Practices exist because EPBCS is fundamentally a database viewer, not a spreadsheet. In Excel, you can have a tab with 10,000 rows and 500 columns and the user can easily scroll. If you design an EPBCS form with 10,000 rows, it will timeout and crash the server. Best practice dictates breaking large data entry tasks into smaller, focused forms connected by Navigation Flows (e.g., a "Summary" form that drills down to a "Detail" form).

### 🌀 Confusion Resolution
> **Misconception:** "Our users are used to seeing their entire P&L, across all 50 Cost Centers, for 5 years, on a single screen. We need to build a form that shows all of that."
> **Reality:** A form should be built for **Data Entry**, not for massive data dumping. If a user needs to view 50 Cost Centers and 5 Years of data simultaneously, they should be using **Smart View** or a **Financial Report**, NOT a data form. Forms should be restricted to the specific intersections the user is actively budgeting right now (e.g., 1 Cost Center, 1 Year).

### 😈 Twisted Interview Question
**Question:** An architect creates a form called "Global Expense Input". They place Account on the Rows and Period on the Columns. They place Entity, Year, and Scenario in the Page drop-downs. They leave the POV empty. Is this a good design?
> **Answer:** Absolutely terrible design! The Page drop-down loads data for the current selection, but leaving the POV empty means there are no global filters. If a user clicks the Entity Page drop-down, they will have to scroll through every single entity in the global company. Best practice: Place the user's specific region or division in the POV (using a User Variable), so the Page drop-down is restricted to only their relevant Cost Centers.
