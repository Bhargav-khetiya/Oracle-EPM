# 07.06 Cross-Dimensional Math and Block Creation

> **Module:** 07_Business_Rules  
> **Topic:** 06 - Cross-Dimensional Operators  
> **Target Audience:** Architect / Developer  

---

## 1. Learning Objectives
- Master the `->` (Cross-Dimensional) operator.
- Understand how pulling vs pushing data affects block creation.
- Avoid the "Targeting a Missing Block" disaster.

## 3. Introduction
Business Rules usually calculate data *inside* the current block (e.g., `Revenue - COGS`). But what if `New York` needs to calculate its taxes based on the `Global_Tax_Rate` stored in the `Corporate_HQ` block? You must cross the dimensional boundary using the `->` operator.

## 7. Core Concepts: The `->` Operator

The `->` operator allows you to fetch data from, or push data to, a member outside of the current `FIX` statement.

### Pulling Data (The Safe Way)
```essbase
FIX("New_York", "Working")
    "Taxes" = "Revenue" * "Global_Tax_Rate"->"Corporate_HQ";
ENDFIX
```
**The Physics:** Essbase is currently evaluating the `New_York` block. It reads the `Revenue` from New York. It sees the `->`, so it pauses, reaches over to the `Corporate_HQ` block, reads the tax rate, brings it back to `New_York`, does the math, and saves the answer in `New_York`. This is fast and safe.

### Pushing Data (The Dangerous Way)
```essbase
FIX("New_York", "Working")
    "Corporate_Overhead"->"Corporate_HQ" = "Revenue" * 0.10;
ENDFIX
```
**The Physics:** Essbase is currently evaluating the `New_York` block. It reads the `Revenue`. It calculates the 10% overhead. Then, it attempts to push the answer into the `Corporate_HQ` block. 
**The Catastrophe:** What if the `Corporate_HQ` block *does not exist yet* on the hard drive? Because the target is on the left side of the `=` sign, Essbase must physically create a brand new block for `Corporate_HQ`. If you execute this on a massive sparse scale, you will trigger a block explosion.

## 9. Internal Processing: The Left Side vs Right Side Rule

- **Right Side of the `=`: PULLING.** (Extremely fast, does not create blocks).
- **Left Side of the `=`: PUSHING.** (Dangerous, forces block creation, causes massive I/O overhead).

**Architect Rule:** Never put a Sparse cross-dimensional target (`->`) on the left side of an equation unless you are absolutely certain the target block already exists, or you explicitly wrap it in a `SET CREATENONMISSINGBLK ON;` command (and even then, restrict the FIX as tightly as possible).

## 14. Examples: The "Allocation" Rewrite
Junior developers write allocations by pushing data:
```essbase
/* DANGEROUS PUSH */
FIX("Total_Company")
    "Allocated_Expense"->"New_York" = "Overhead_Pool" * 0.20;
ENDFIX
```
Architects write allocations by pulling data:
```essbase
/* SAFE PULL */
FIX("New_York")
    "Allocated_Expense" = "Overhead_Pool"->"Total_Company" * 0.20;
ENDFIX
```
The result is mathematically identical. The second script runs 100x faster because it calculates natively within the `New_York` block without forcing the engine to jump across the database to write blocks.

## 25. Interview Questions

### Intermediate
**Q: You write a formula: `"Target_Acct"->"Next_Year" = "Source_Acct" * 1.10;`. The rule runs in 1 second, but no data appears in Next Year. You check the log, and there are no errors. Why did the formula fail?**
> A: By default, Essbase operates in **Bottom-Up** mode. It only executes formulas on blocks that currently exist. Because "Next Year" has no data yet, its physical block does not exist. Essbase saw the target block was missing and simply skipped the calculation. To force Essbase to calculate it, you must either pre-seed the Next Year block with a dummy 0, or (carefully) use `SET CREATENONMISSINGBLK ON;`.
