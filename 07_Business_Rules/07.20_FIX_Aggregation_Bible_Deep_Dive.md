# SECTION 1: FIX STATEMENT — COMPLETE MECHANICS

---

## 1.1 What is FIX?

`FIX` restricts the scope of a calculation to specific members. Without FIX, a calculation processes the ENTIRE database.

```essbase
/* Syntax */
FIX(member1, member2, @function("parent"))
    /* calculations */
ENDFIX
```

## 1.2 FIX Rules — The Complete Rulebook

### Rule 1: Members from the SAME dimension are OR'd
```essbase
FIX("Jan", "Feb", "Mar")
    /* Processes Jan OR Feb OR Mar */
    /* Same as: FIX(@CHILDREN("Q1")) */
ENDFIX
```

### Rule 2: Members from DIFFERENT dimensions are AND'd
```essbase
FIX("Jan", "Budget")
    /* Processes ONLY cells where Period=Jan AND Scenario=Budget */
    /* This is an intersection filter */
ENDFIX
```

### Rule 3: Combined — OR within dimension, AND across dimensions
```essbase
FIX("Jan", "Feb", "Mar", "Budget", "Hotel India", "Hotel USA")
    /* Period: Jan OR Feb OR Mar
       AND Scenario: Budget
       AND Entity: Hotel India OR Hotel USA
       
       Total intersections: 3 periods × 1 scenario × 2 entities = 6 */
ENDFIX
```

### Rule 4: Nested FIX further restricts scope
```essbase
FIX("Budget", @DESCENDANTS("All Entities"))
    /* Outer: All entities × Budget */
    FIX("Jan", "Feb", "Mar")
        /* Inner: further restricted to Q1 periods */
        /* Net scope: Q1 × Budget × All entities */
        "Revenue" = "Revenue" * 1.10;
    ENDFIX
    FIX("Apr", "May", "Jun")
        /* Inner: further restricted to Q2 periods */
        "Revenue" = "Revenue" * 1.05;
    ENDFIX
ENDFIX
```

### Rule 5: FIX cannot be inside IF
```essbase
/* ❌ INVALID — FIX inside IF */
IF("Revenue" > 0)
    FIX("Budget")
        "Margin" = "Revenue" - "COGS";
    ENDFIX
ENDIF

/* ✅ CORRECT — IF inside FIX */
FIX("Budget")
    IF("Revenue" > 0)
        "Margin" = "Revenue" - "COGS";
    ENDIF
ENDFIX
```

### Rule 6: FIX does NOT create blocks
```essbase
FIX("Forecast")
    "Revenue" = 100;
ENDFIX
/* If NO block exists for [Entity, Forecast, Working],
   this assignment is SILENTLY SKIPPED.
   Use SET CREATEBLOCKONEQ ON or DATACOPY to create blocks first. */
```

### Rule 7: FIX must have matching ENDFIX
```essbase
/* Every FIX MUST have ENDFIX — no exceptions */
FIX("Budget")
    "Revenue" = 100;
ENDFIX  /* ← Required */
```

### Rule 8: You can FIX on any dimension — but performance differs
```essbase
/* FIX on Sparse dimension = Block filtering = FAST */
FIX("Hotel India")  /* Only loads blocks for Hotel India */
    "Revenue" = 100;
ENDFIX

/* FIX on Dense dimension = Cell filtering only = NO I/O savings */
FIX("Revenue")  /* Loads ALL blocks, then narrows to Revenue cells */
    "Revenue" = 100;
ENDFIX
```

# SECTION 2: FIX AND BLOCKS

---

## 2.1 How FIX on Sparse Dimensions Works (Block Filtering)

```
Database has blocks:
  Block 1: [Hotel India, Budget, Working, FY26]
  Block 2: [Hotel India, Actual, Working, FY26]
  Block 3: [Hotel USA, Budget, Working, FY26]
  Block 4: [Hotel USA, Actual, Working, FY26]
  Block 5: [Hotel UK, Budget, Working, FY26]
  ...

FIX("Hotel India", "Budget")
    "Revenue" = "Revenue" * 1.10;
ENDFIX

Essbase behavior:
  1. Scan index for blocks matching: Entity=Hotel India AND Scenario=Budget
  2. Found: Block 1 only
  3. Load Block 1 into memory
  4. Within Block 1: multiply all Revenue cells by 1.10
  5. Write Block 1 back to disk
  
  Blocks 2, 3, 4, 5 are NEVER loaded → massive I/O savings
```

## 2.2 How FIX on Dense Dimensions Works (Cell Filtering)

```
FIX("Revenue")
    "Revenue" = "Revenue" * 1.10;
ENDFIX

Essbase behavior:
  1. Revenue is a DENSE dimension member
  2. Revenue exists INSIDE every block
  3. Essbase must load ALL blocks (no block filtering possible)
  4. For each block: find the Revenue cell, multiply by 1.10
  5. Write all blocks back to disk
  
  ALL blocks loaded → NO I/O savings from FIX
  The FIX only reduces COMPUTATION (fewer cells calculated per block)
```

## 2.3 Optimal FIX Strategy

```
BEST PRACTICE: FIX on Sparse first, then compute Dense within block

✅ OPTIMAL:
FIX("Hotel India", "Budget", "Working", "FY26")
    /* Only loads blocks for this specific intersection */
    "Revenue" = "Revenue" * 1.10;
    "Net_Income" = "Revenue" - "Expense";
ENDFIX

⚠️ SUBOPTIMAL:
FIX("Revenue")
    /* Loads ALL blocks just to modify Revenue cells */
    "Revenue" = "Revenue" * 1.10;
ENDFIX

❌ WORST:
/* No FIX at all */
"Revenue" = "Revenue" * 1.10;
/* Processes EVERY block, EVERY cell — entire database */
```

# SECTION 3: FIX PATTERNS AND BEST PRACTICES

---

## 3.1 Pattern: FIX with @Functions

```essbase
/* All level 0 entities (leaf entities only) */
FIX(@LEVMBRS("Entity", 0))
    "Revenue" = "Revenue" * 1.10;
ENDFIX

/* All descendants of a parent */
FIX(@DESCENDANTS("All Entities"))
    "Revenue" = "Revenue" * 1.10;
ENDFIX

/* Children only (immediate children, not grandchildren) */
FIX(@CHILDREN("Revenue"))
    /* Processes: Rooms Revenue, Banquet Revenue, F&B Revenue */
ENDFIX

/* Include parent AND children */
FIX(@ICHILDREN("Revenue"))
    /* Processes: Revenue, Rooms Revenue, Banquet Revenue, F&B Revenue */
ENDFIX

/* Using UDA */
FIX(@UDA("Account", "Revenue_Driver"))
    /* Processes all accounts tagged with "Revenue_Driver" UDA */
ENDFIX

/* Using Attribute */
FIX(@ATTRIBUTE("Region", "Asia"))
    /* Processes all entities with Region attribute = Asia */
ENDFIX
```

## 3.2 Pattern: Nested FIX for Different Logic

```essbase
/* Different growth rates for different regions */
FIX("Budget", "Working", &CurrYear)
    
    FIX("Hotel India")
        @DESCENDANTS("Revenue") = @DESCENDANTS("Revenue") * 1.15;
        /* India: 15% growth */
    ENDFIX
    
    FIX("Hotel USA")
        @DESCENDANTS("Revenue") = @DESCENDANTS("Revenue") * 1.08;
        /* USA: 8% growth */
    ENDFIX
    
    FIX("Hotel UK")
        @DESCENDANTS("Revenue") = @DESCENDANTS("Revenue") * 1.05;
        /* UK: 5% growth */
    ENDFIX
    
ENDFIX
```

## 3.3 Pattern: FIX with Substitution Variables

```essbase
/* Using admin-maintained variables */
FIX(&CurrScenario, &CurrVersion, &CurrYear)
    FIX(@RELATIVE("Entity", 0))
        "Revenue" = "Revenue" * 1.10;
    ENDFIX
ENDFIX

/* Variables:
   &CurrScenario resolves to "Budget"
   &CurrVersion resolves to "Working"
   &CurrYear resolves to "FY26"
*/
```

## 3.4 Pattern: FIX with Runtime Prompts

```essbase
/* Using Runtime Prompts from form/user */
FIX({RTP_Entity}, {RTP_Scenario}, {RTP_Year})
    "Revenue" = "Revenue" * {RTP_GrowthRate} / 100;
ENDFIX

/* {RTP_Entity} → user selects "Hotel India"
   {RTP_Scenario} → user selects "Forecast"
   {RTP_Year} → user selects "FY27"
   {RTP_GrowthRate} → user enters 12 (meaning 12%)
*/
```

# SECTION 4: AGGREGATION — AGG VS CALC DIM VS CALC ALL

---

## 4.1 CALC ALL

Calculates the **entire database** — all dimensions, all member formulas, all aggregation.

```essbase
CALC ALL;

What happens:
  Step 1: Process each dimension in outline order
  Step 2: For DENSE dimensions: execute member formulas within blocks
  Step 3: For SPARSE dimensions: aggregate (create upper-level blocks)
  
When to use:
  → After a full data load
  → When you need to recalculate everything from scratch
  → ⚠️ SLOW for large databases — avoid in production if possible
```

## 4.2 CALC DIM

Calculates a **single dimension** — member formulas AND aggregation for that dimension.

```essbase
CALC DIM("Account");
/* 
  1. For every block: execute all Account member formulas
     → Revenue = Rooms Revenue + Banquet Revenue + F&B Revenue
     → Net Income = Revenue - Expense
     → Margin % = (Revenue - Expense) / Revenue * 100
  2. No cross-block aggregation (Account is dense)
*/

CALC DIM("Entity");
/*
  1. For every block: execute Entity member formulas (if any)
  2. Aggregate across blocks: create upper-level entity blocks
     → Block[All Entities] = Block[Hotel India] + Block[Hotel USA] + Block[Hotel UK]
*/
```

## 4.3 AGG

Aggregates a specific dimension — creates parent values by summing children using consolidation operators. Does **NOT** execute member formulas.

```essbase
AGG("Entity");
/*
  1. Sum Entity children to parents using consolidation operators (+, -, ~)
  2. Create upper-level blocks: Block[All Entities] = sum of children blocks
  3. Does NOT execute any member formulas
*/

AGG("Entity", "Department");
/*
  Aggregate both Entity and Department simultaneously
  More efficient than two separate AGG commands
*/
```

## 4.4 Comparison Table

| Command | Formulas | Aggregation | Scope | Speed |
|---------|----------|-------------|-------|-------|
| `CALC ALL` | ✅ All dimensions | ✅ All dimensions | Entire DB | Slowest |
| `CALC DIM("X")` | ✅ Dim X only | ✅ Dim X only | One dimension | Medium |
| `AGG("X")` | ❌ No formulas | ✅ Dim X only | One dimension | Fastest |

## 4.5 Order of Operations — Critical Rule

```
GOLDEN RULE: Calculate DENSE dimensions before aggregating SPARSE dimensions.

CORRECT ORDER:
  CALC DIM("Account");    /* Dense — formulas within blocks */
  CALC DIM("Period");     /* Dense — time aggregation within blocks */
  AGG("Entity");          /* Sparse — aggregate across blocks */
  AGG("Department");      /* Sparse — aggregate across blocks */

WHY:
  Dense formulas (Account calculations) must run on INPUT BLOCKS first.
  Then sparse aggregation SUMS the already-calculated input blocks 
  to create parent blocks.
  
  If you AGG first → parent blocks are created with RAW input data.
  Then CALC DIM runs on parent blocks too → double-calculation or errors.

INCORRECT ORDER:
  AGG("Entity");          /* ❌ Parent blocks created with raw data */
  CALC DIM("Account");    /* ❌ Formulas run on parent blocks too — inconsistent! */
```

## 4.6 Worked Aggregation Example

```
INPUT DATA (Level 0 blocks):

Block: [Hotel India, Budget, Working, FY26, INR, Catering]
  Revenue:    Jan=18Cr  Feb=19Cr  Mar=20Cr
  Expense:    Jan=12Cr  Feb=13Cr  Mar=14Cr
  Net Income: (empty — needs calculation)
  Margin %:   (empty — needs calculation)

Block: [Hotel USA, Budget, Working, FY26, USD, Catering]
  Revenue:    Jan=30Cr  Feb=32Cr  Mar=35Cr
  Expense:    Jan=20Cr  Feb=21Cr  Mar=22Cr
  Net Income: (empty)
  Margin %:   (empty)

STEP 1: CALC DIM("Account");
  → Within each block, calculate member formulas:
  
  Block: [Hotel India...]
    Net Income = Revenue - Expense = 18-12=6, 19-13=6, 20-14=6
    Margin % = Net Income / Revenue * 100 = 6/18*100=33.3%, ...
    
  Block: [Hotel USA...]
    Net Income = 30-20=10, 32-21=11, 35-22=13
    Margin % = 10/30*100=33.3%, ...

STEP 2: CALC DIM("Period");
  → Within each block, aggregate time periods:
  
  Block: [Hotel India...]
    Q1 Revenue = Jan+Feb+Mar = 18+19+20 = 57
    Q1 Expense = 12+13+14 = 39
    Q1 Net Income = 6+6+6 = 18
    Q1 Margin % = 18/57*100 = 31.6% (NOT average of monthly!)

STEP 3: AGG("Entity");
  → Create parent blocks by summing children:
  
  NEW Block: [All Entities, Budget, Working, FY26, INR, Catering]
    Revenue Jan = Hotel India 18 + Hotel USA 30 = 48
    Revenue Feb = 19 + 32 = 51
    Revenue Mar = 20 + 35 = 55
    Expense Jan = 12 + 20 = 32
    ...
    Net Income Jan = 6 + 10 = 16 (already calculated in Step 1)
    Margin % Jan = 16/48 = 33.3%... 
    ⚠️ BUT Margin % might be wrong if it was aggregated by SUM!
    → Margin % should use ~ (ignore) operator and recalculate via formula
```

# SECTION 5: BLOCK CREATION AND DATACOPY

---

## 5.1 DATACOPY

`DATACOPY` copies entire blocks of data from one sparse member to another. It ALWAYS creates target blocks.

```essbase
/* Copy all data from Actual to Forecast */
DATACOPY "Actual" TO "Forecast";

/* What happens:
   For every block where Scenario=Actual:
     1. Create a new block with Scenario=Forecast (same other sparse members)
     2. Copy ALL dense cells from source block to target block
   
   ALL data copied — all accounts, all periods */

/* Copy within a FIX */
FIX(@LEVMBRS("Entity", 0), "Working", &CurrYear)
    DATACOPY "Actual" TO "Budget";
ENDFIX
/* Only copies for level-0 entities, Working version, current year */
```

## 5.2 DATACOPY vs Assignment

```essbase
/* DATACOPY: Copies ALL dense cells, creates blocks */
DATACOPY "Actual" TO "Forecast";
/* → Entire block contents copied
   → Target blocks created automatically
   → Fast (bulk block-level operation) */

/* Assignment: Copies ONE account at a time, may NOT create blocks */
FIX("Forecast")
    "Revenue" = "Revenue" -> "Actual";
ENDFIX
/* → Only copies Revenue (not all accounts)
   → Does NOT create blocks unless CREATEBLOCKONEQ ON
   → Slower (cell-level operation) */

/* Assignment with block creation */
SET CREATEBLOCKONEQ ON;
FIX("Forecast", @LEVMBRS("Entity", 0))
    "Revenue" = "Revenue" -> "Actual";
    "Expense" = "Expense" -> "Actual";
ENDFIX
SET CREATEBLOCKONEQ OFF;
/* → Creates target blocks as needed
   → Copies only Revenue and Expense (not all accounts)
   → Use when you need selective copy */
```

## 5.3 When to Use Which

| Need | Use |
|------|-----|
| Copy ALL data from one scenario to another | `DATACOPY` |
| Copy SPECIFIC accounts only | Assignment with `SET CREATEBLOCKONEQ ON` |
| Copy with modification (multiply by factor) | Assignment: `"Revenue" = "Revenue" -> "Actual" * 1.10;` |
| Seed a new scenario with baseline data | `DATACOPY` then modify with assignments |

# SECTION 6: SET COMMANDS — COMPLETE REFERENCE

---

## 6.1 SET AGGMISSG

```essbase
SET AGGMISSG ON;
/* During aggregation, treat #Missing as 0
   → Parent = Child1 + 0 + Child3 (if Child2 is #Missing)
   Default: ON */

SET AGGMISSG OFF;
/* During aggregation, if ANY child is #Missing, parent = #Missing
   → Parent = #Missing (even if Child1 and Child3 have values)
   Use carefully! */
```

## 6.2 SET UPDATECALC

```essbase
SET UPDATECALC ON;
/* Only recalculate blocks that have been modified since last calc
   → Skips unchanged blocks → faster
   Default: OFF */

SET UPDATECALC OFF;
/* Recalculate ALL blocks regardless of modification
   → Ensures complete accuracy but slower */
```

## 6.3 SET CREATEBLOCKONEQ

```essbase
SET CREATEBLOCKONEQ ON;
/* Create new blocks when an assignment targets a non-existent block
   → Essential for data copy operations via assignment */

SET CREATEBLOCKONEQ OFF;
/* Do NOT create blocks — silently skip assignments to non-existent blocks
   → Default behavior
   → Always turn OFF after use to prevent block explosion */
```

## 6.4 SET LOCKBLOCK

```essbase
SET LOCKBLOCK ON;
/* Keep blocks in memory during calculation instead of writing after each pass
   → Improves performance for multi-pass calculations
   → Uses more memory */

SET LOCKBLOCK OFF;
/* Write blocks to disk between calculation passes
   → Default behavior, lower memory usage */
```

## 6.5 SET CREATENONMISSINGBLK

```essbase
SET CREATENONMISSINGBLK ON;
/* During aggregation, create parent blocks ONLY if they would contain 
   non-#Missing values. Skip creating empty parent blocks. */

SET CREATENONMISSINGBLK OFF;
/* Default — create all parent blocks during aggregation */
```

## 6.6 SET MSG SUMMARY / DETAIL

```essbase
SET MSG SUMMARY;
/* Show summary calculation messages in log */

SET MSG DETAIL;
/* Show detailed cell-by-cell calculation messages (for debugging) */
```

# SECTION 7: CLEARBLOCK VS CLEARDATA

---

## 7.1 CLEARBLOCK

```essbase
CLEARBLOCK ALL;
/* Within the current FIX scope:
   Physically DELETE blocks from disk where ALL cells are #Missing
   → Recovers disk space
   → Reduces future calculation time (fewer blocks to process) */

/* Example: Clear empty blocks in Forecast */
FIX("Forecast", @LEVMBRS("Entity", 0))
    CLEARBLOCK ALL;
ENDFIX
```

### CLEARBLOCK Options:
| Option | Effect |
|--------|--------|
| `CLEARBLOCK ALL` | Delete blocks where ALL cells are #Missing |
| `CLEARBLOCK UPPER` | Delete only upper-level (aggregated) blocks |
| `CLEARBLOCK DYNAMIC` | Delete blocks with Dynamic Calc and Store values |
| `CLEARBLOCK NONINPUT` | Delete blocks created by calculations (not data loads) |

## 7.2 CLEARDATA

```essbase
CLEARDATA "Forecast";
/* Set ALL cells in "Forecast" blocks to #Missing
   → Blocks remain on disk (not deleted)
   → Cells become #Missing but block structure preserved */
```

## 7.3 Comparison

| Feature | CLEARBLOCK | CLEARDATA |
|---------|-----------|-----------|
| **What it does** | Deletes physical blocks from disk | Sets cell values to #Missing |
| **Blocks after** | Removed (gone) | Still exist (empty) |
| **Disk space** | Recovered | NOT recovered |
| **Speed** | Fast (bulk block deletion) | Slower (cell-level operation) |
| **Scope** | Sparse intersections | Can target dense members |
| **Use case** | Clean up before data load | Clear specific account data |

## 7.4 Clear and Recalculate Pattern

```essbase
/* The standard "Clear and Recalculate" pattern */

/* Step 1: Clear old calculated data */
FIX("Forecast", @LEVMBRS("Entity", 0), "Working", &CurrYear)
    CLEARDATA "Revenue";
    CLEARDATA "Expense";
    CLEARDATA "Net_Income";
ENDFIX

/* Step 2: Copy baseline from Actuals */
FIX(@LEVMBRS("Entity", 0), "Working", &CurrYear)
    DATACOPY "Actual" TO "Forecast";
ENDFIX

/* Step 3: Apply forecast adjustments */
FIX("Forecast", @LEVMBRS("Entity", 0), "Working", &CurrYear)
    "Revenue" = "Revenue" * 1.10;
ENDFIX

/* Step 4: Calculate derived values */
FIX("Forecast", @LEVMBRS("Entity", 0), "Working", &CurrYear)
    "Net_Income" = "Revenue" - "Expense";
    "Margin_Pct" = IF("Revenue" <> 0) "Net_Income" / "Revenue" * 100; ENDIF;
ENDFIX

/* Step 5: Aggregate */
FIX("Forecast", "Working", &CurrYear)
    AGG("Entity");
ENDFIX
```

# SECTION 8: CROSS-DIMENSIONAL REFERENCES

---

## 8.1 The `->` Operator

The cross-dimensional reference operator `->` lets you read or write data from a different member intersection.

```essbase
/* Syntax */
"TargetMember" -> "OtherDimensionMember"

/* Read Revenue from Actual scenario (while in Forecast context) */
"Revenue" -> "Actual"

/* Read Revenue from Hotel India (while processing a different entity) */
"Revenue" -> "Hotel India"

/* Multiple cross-dim references (chain) */
"Revenue" -> "Actual" -> "Hotel India" -> "Jan"
```

## 8.2 How Cross-Dim Works at Block Level

```essbase
FIX("Forecast", "Hotel India", "Working", "FY26")
    "Revenue" = "Revenue" -> "Actual";
ENDFIX

/* What Essbase does:
   1. Load block: [Hotel India, Forecast, Working, FY26]  (target)
   2. Load block: [Hotel India, Actual, Working, FY26]    (source)
   3. For each period (Jan-Dec):
      Copy Revenue from source block to target block
   4. Write target block back to disk
   
   Cross-dim causes Essbase to load TWO blocks simultaneously
   → More memory, more I/O
   → Performance impact for large-scale operations
*/
```

## 8.3 Cross-Dim Patterns

```essbase
/* Pattern 1: Copy between scenarios */
FIX("Forecast", @LEVMBRS("Entity", 0))
    "Revenue" = "Revenue" -> "Actual" * 1.10;
    /* Forecast Revenue = Actual Revenue × 110% */
ENDFIX

/* Pattern 2: Prior Period Reference */
FIX("Budget", @LEVMBRS("Entity", 0))
    "Revenue_Growth" = 
        IF("Revenue" -> @PRIOR("Period") <> 0)
            ("Revenue" - "Revenue" -> @PRIOR("Period")) / 
            "Revenue" -> @PRIOR("Period") * 100;
        ENDIF;
    /* Revenue Growth % = (Current - Prior) / Prior × 100 */
ENDFIX

/* Pattern 3: Cross-Entity Reference */
FIX("Budget", "Hotel USA", "Working")
    "Revenue_Target" = "Revenue" -> "Hotel India" * 1.20;
    /* USA Revenue Target = India Revenue × 120% */
ENDFIX

/* Pattern 4: Lookup from a Rate Table */
FIX(@LEVMBRS("Entity", 0), "Budget", "Working")
    "Revenue_INR" = "Revenue" -> "Local" * 
                    "Exchange_Rate" -> "HSP_Rates" -> "Average";
    /* Convert local currency revenue to INR using average exchange rate */
ENDFIX
```

# SECTION 9: @FUNCTIONS — COMPLETE REFERENCE

---

## 9.1 Member Selection Functions

| Function | Returns | Example |
|----------|---------|---------|
| `@CHILDREN("X")` | Immediate children of X | `@CHILDREN("Revenue")` → Rooms, Banquet, F&B |
| `@ICHILDREN("X")` | X + its children | `@ICHILDREN("Revenue")` → Revenue, Rooms, Banquet, F&B |
| `@DESCENDANTS("X")` | All descendants of X (recursive) | `@DESCENDANTS("All Entities")` → every entity at every level |
| `@IDESCENDANTS("X")` | X + all descendants | Includes X itself |
| `@ANCESTORS("X")` | All ancestors of X | `@ANCESTORS("100110")` → Revenue, Total P&L |
| `@IANCESTORS("X")` | X + all ancestors | Includes X itself |
| `@SIBLINGS("X")` | Same-level siblings of X | `@SIBLINGS("Jan")` → Jan, Feb, Mar (children of Q1) |
| `@ISIBLINGS("X")` | X + its siblings | Includes X itself |
| `@PARENT("X")` | Parent of X | `@PARENT("Jan")` → Q1 |
| `@LEVMBRS("Dim", n)` | All members at level n | `@LEVMBRS("Entity", 0)` → leaf entities |
| `@GENMBRS("Dim", n)` | All members at generation n | `@GENMBRS("Account", 2)` → gen 2 accounts |
| `@RELATIVE("X", n)` | Members at level n relative to X | `@RELATIVE("All Entities", 0)` → leaf entities |
| `@UDA("Dim", "tag")` | Members with UDA tag | `@UDA("Account", "Revenue_Driver")` |
| `@ATTRIBUTE("AttrDim", "val")` | Members with attribute value | `@ATTRIBUTE("Region", "Asia")` |

## 9.2 Conditional/Boolean Functions

| Function | Returns | Example |
|----------|---------|---------|
| `@ISMBR("X")` | TRUE if current member = X | `IF(@ISMBR("Jan"))` |
| `@ISANCEST("X")` | TRUE if current member is ancestor of X | `IF(@ISANCEST("Revenue"))` |
| `@ISDESC("X")` | TRUE if current member is descendant of X | `IF(@ISDESC("All Entities"))` |
| `@ISLEV("Dim", n)` | TRUE if current member is at level n | `IF(@ISLEV("Account", 0))` |
| `@ISGEN("Dim", n)` | TRUE if current member is at generation n | `IF(@ISGEN("Entity", 1))` |
| `@ISUDA("Dim", "tag")` | TRUE if current member has UDA tag | `IF(@ISUDA("Account", "Revenue_Driver"))` |

## 9.3 Navigation Functions

| Function | Returns | Example |
|----------|---------|---------|
| `@PRIOR("Dim")` | Previous sibling | `"Revenue" -> @PRIOR("Period")` → prior month |
| `@NEXT("Dim")` | Next sibling | `"Revenue" -> @NEXT("Period")` → next month |
| `@CURRMBR("Dim")` | Current member being processed | Used in loops and conditional logic |
| `@ANCESTVAL("Dim", n)` | Value from ancestor at generation n | Lookup parent-level rate |
| `@PARENTVAL("Dim")` | Value from parent member | Similar to `@ANCESTVAL` at gen+1 |

## 9.4 Mathematical/Data Functions

| Function | Purpose | Example |
|----------|---------|---------|

## 11.1 Top 10 Mistakes

| # | Mistake | Fix |
|---|---------|-----|
| 1 | No FIX statement — processes entire database | Always use FIX to restrict scope |
| 2 | FIX on dense dimension expecting I/O savings | FIX on sparse dimensions for I/O reduction |
| 3 | Missing semicolons | Every assignment must end with `;` |

| 6 | Not using CREATEBLOCKONEQ for assignments | Add SET CREATEBLOCKONEQ ON for data copy via assignment |

| 8 | Using CALC ALL in production | Use targeted CALC DIM / AGG for specific dimensions |
| 9 | Division by zero in formulas | Always check: IF("denominator" <> 0 AND "denominator" <> #Missing) |

## 12.1 Performance Rules

| Rule | Impact |
|------|--------|
| **FIX on sparse dimensions** | Reduces block I/O by 90%+ |
| **Dense calcs before sparse AGG** | Prevents inconsistent parent blocks |

# SECTION 13: INTERVIEW QUESTIONS

---

**Q1: What is the difference between FIX on a sparse vs dense dimension?**
> FIX on sparse dimensions filters at the block level — only loads blocks matching the filter, dramatically reducing I/O. FIX on dense dimensions loads ALL blocks but narrows processing to specific cells within each block — no I/O reduction.

**Q2: What is the difference between AGG and CALC DIM?**
> AGG aggregates a dimension using consolidation operators only — no member formulas. CALC DIM executes member formulas AND aggregation. Use AGG when you only need roll-up; use CALC DIM when member formulas must fire.

**Q3: Why is the order "dense calc before sparse AGG" critical?**
> Dense calculations (Account formulas, Period aggregation) must run on input blocks first. Then sparse AGG sums the already-calculated blocks to create parent blocks. If you AGG first, parent blocks have raw data; then dense calcs run on both input AND parent blocks, causing inconsistencies.

**Q4: What does SET CREATEBLOCKONEQ do?**
> It tells Essbase to create new blocks when an assignment targets a non-existent sparse intersection. Without it, assignments to non-existent blocks are silently skipped. Always use with a tight FIX and turn OFF immediately after to prevent block explosion.

**Q5: When would you use DATACOPY vs an assignment with cross-dim?**
> Use DATACOPY when copying ALL accounts for entire blocks (bulk operation, fast, always creates blocks). Use assignment with cross-dim when copying specific accounts, applying transformations, or needing conditional logic.

**Q6: Write a script that seeds Budget from prior year Actuals with 10% revenue growth.**
```essbase
SET CREATEBLOCKONEQ ON;

    DATACOPY "Actual" TO "Budget";
ENDFIX
SET CREATEBLOCKONEQ OFF;

    @DESCENDANTS("Revenue") = @DESCENDANTS("Revenue") * 1.10;
ENDFIX
```

## 📝 Summary

| Concept | Key Takeaway |
|---------|-------------|
| **FIX** | Restricts calc scope. Same-dim = OR. Cross-dim = AND. |
| **FIX on Sparse** | Block-level filtering — ⚡ major I/O reduction |
| **FIX on Dense** | Cell-level filtering — no I/O reduction |
| **CALC ALL** | Calculates entire database — avoid in production |
| **CALC DIM** | Formulas + aggregation for one dimension |
| **AGG** | Aggregation only — no formulas — fastest |
| **DATACOPY** | Bulk block copy — always creates target blocks |
| **CREATEBLOCKONEQ** | Enables block creation during assignments |
| **CLEARBLOCK** | Deletes physical blocks from disk |
| **CLEARDATA** | Sets cells to #Missing — blocks remain |
| **Cross-dim (`->`)** | Reference data from different sparse intersection |
| **Dense before Sparse** | Calculate dense dims first, then aggregate sparse |
