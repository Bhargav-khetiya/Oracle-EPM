# 08.05 System View and Object Management

> **Module:** 08_Calculation_Manager  
> **Topic:** 05 - The System View Interface  
> **Target Audience:** Consultant  

---

## 1. Learning Objectives
- Navigate the Calculation Manager System View.
- Differentiate between Rules, Formulas, Scripts, and Templates in the file structure.
- Manage object ownership and modification tracking.

## 3. Introduction
When you open Calculation Manager, you do not immediately start coding. You land on the **System View**. This is the file explorer for all backend logic in the EPM ecosystem. If you do not understand how objects are nested here, you will overwrite other developers' work or deploy rules to the wrong application.

## 7. Core Concepts: The File Hierarchy

As seen in standard Calculation Manager environments, the tree on the left pane follows a strict hierarchy:

### 1. The Server (EPM Cloud)
The root node. Expanding this shows all EPM Applications on this specific Pod.

### 2. The Application (e.g., EPBCS)
Expanding the Application reveals the **RuleSets** folder and the individual **Cubes** (e.g., `FinPlan`, `Manpower`, `Capital`).

### 3. The Cube (e.g., FinPlan)
This is where the actual logic lives. You cannot write a rule for "the whole application"; a rule must belong to a specific Essbase cube. Expanding a cube reveals four critical folders:

- **Rules:** The deployable Business Rules. These are the objects that can be attached to Forms or Action Menus.
- **Formulas:** Custom mathematical formulas that can be reused across rules.
- **Scripts:** Raw Essbase `.csc` code snippets that are not graphically designed.
- **Templates:** The reusable building blocks (flowcharts or scripts) that you drag into Business Rules. (e.g., A standardized "Clear Data" template).

## 9. Internal Processing: The Grid View Metadata
On the right side of the System View, when you click on a folder (like `Rules`), a grid appears displaying metadata about the objects. This is your primary audit trail during development.

- **Name:** The internal ID of the rule.
- **Description:** Always fill this out. A rule named `Alloc_v2` is useless to the next architect if there is no description.
- **Owner:** The user who created the object.
- **Last Modified By / Date:** The most important columns. If a rule suddenly stops working on Friday, you sort by "Last Modified Date" to find out which junior developer touched it on Thursday afternoon.

## 13. Configuration: Deployment Status
In the System View, the icons next to the rules tell a story.
- If a rule has a standard icon, it is saved in the repository.
- If it has a warning flag or red X, it has a compilation syntax error.
- **Deployment:** Right-clicking an application or cube allows you to **Deploy**. You must deploy for the Essbase engine to recognize the new logic. The System View tracks which rules are currently deployed vs which rules have un-deployed local edits.

## 25. Interview Questions

### Intermediate
**Q: You are building a new application. You create a Business Rule called `Calc_Revenue` under the `OEP_FS` (Financials) cube. Later, you realize you actually needed that rule in the `OEP_WFS` (Workforce) cube. Can you just drag and drop the rule from the FS folder to the WFS folder in System View?**
> A: No. Business Rules are rigidly bound to the dimensional outline of the cube they were created in. The `OEP_FS` rule is validating against the Financials dimensions. To move it to Workforce, you must recreate the rule (or copy/paste the script text) into a new rule under the `OEP_WFS` node, and re-validate it against the Workforce dimension outline.

### Architect
**Q: An external consultant builds 50 Business Rules and leaves the company. You log into Calculation Manager, and under the `Owner` column, all 50 rules are owned by the consultant's deactivated account. Why is this an architectural risk, and how do you fix it?**
> A: In Calculation Manager, the "Owner" has exclusive rights to certain actions, and sometimes rules can become locked if checked out by a deactivated user. The EPM Admin must log in, right-click the rules (or the application), and select **Take Ownership**. This transfers the internal lock to the active admin, preventing the rules from becoming orphaned and un-editable.

## 27. Summary
The System View is not just a file browser; it is an audit trail and a deployment manager. Keep your folders organized and always check the deployment status before testing.
