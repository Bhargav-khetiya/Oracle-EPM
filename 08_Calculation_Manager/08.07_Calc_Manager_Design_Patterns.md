# 08.07 — Calc Manager Design Patterns: Complete Guide

> **Module:** 08_Calculation_Manager | **Topic:** Reusable Patterns, Architecture, Best Practices
> **Audience:** Architect / Senior Developer

---

## 1. WHY — Why Design Patterns?

**The problem:** 50 rules, written by 3 developers over 2 years, each with a different style. No naming convention. No standard structure. When one developer leaves, the others can't maintain the rules. Month-end close breaks because rule #34 assumes rule #12 ran first, but nobody documented that dependency.

**The solution:** Standardized design patterns create consistency, maintainability, and predictability across all rules.

## 2. THE 8 PATTERNS

### Pattern 1: Initialize → Calculate → Aggregate

```
The universal structure for any calculation rule:

Rule: "Monthly_PnL"
├── Phase 1: INITIALIZE
│   ├── SET LOCKBLOCK ON
│   ├── SET CALCPARALLEL 4
│   └── @CalcMgrLogMessageTrace("START: Monthly_PnL")
│
├── Phase 2: CALCULATE (inside FIX)
│   ├── FIX(Scenario, Version, Year, Entities)
│   │   ├── Revenue calculations
│   │   ├── Expense calculations
│   │   ├── P&L calculations
│   │   └── KPI calculations
│   └── ENDFIX
│
├── Phase 3: AGGREGATE
│   ├── FIX(Scenario, Version, Year)
│   │   └── AGG("Entity")
│   └── ENDFIX
│
└── Phase 4: CLEANUP
    ├── SET LOCKBLOCK OFF
    └── @CalcMgrLogMessageTrace("END: Monthly_PnL")
```

### Pattern 2: Clear → Copy → Transform

```
The standard pattern for data seeding operations:

Rule: "Seed_Budget"
├── Phase 1: CLEAR target
│   └── FIX("Budget", "Working", &BudgetYear)
│       └── CLEARDATA "Budget"
│       └── CLEARBLOCK ALL
│
├── Phase 2: COPY source to target
│   └── FIX("Working", @RELATIVE("All_Hotels", 0))
│       └── DATACOPY "Actual" -> &PriorYear TO "Budget" -> &BudgetYear
│
└── Phase 3: TRANSFORM (apply adjustments)
    └── FIX("Budget", "Working", &BudgetYear, @RELATIVE("All_Hotels", 0))
        └── Apply growth rates, adjustments
```

### Pattern 3: Validate → Veto (Groovy)

```groovy
/* Pre-save validation that blocks the save on errors */
def errors = []

// Validation rules
operation.grid.dataCellIterator("Account#Revenue").each { cell ->
    if (cell.data < 0) errors << "Negative: ${cell.getMemberName('Entity')}"
}
operation.grid.dataCellIterator("Account#Occupancy").each { cell ->
    if (cell.data > 100) errors << "Occ>100%: ${cell.getMemberName('Entity')}"
}

// Veto if errors found
if (errors) throwVetoException("❌ Fix errors:\n${errors.join('\n')}")
```

### Pattern 4: Two-Pass (Avoid Top-Down)

```essbase
/* When you need a sparse-dimension total INSIDE a calculation */

/* ❌ BAD: Cross-dim on sparse triggers Top-Down */
FIX(@RELATIVE("All_Hotels", 0))
  "Pct_of_Total" = "Revenue" / "Revenue" -> "All_Hotels" * 100;
ENDFIX

/* ✅ GOOD: Two-pass — store total first, then calculate */
VAR v_Total;
FIX("All_Hotels", &CurrMonth)
  v_Total = "Revenue";
ENDFIX

FIX(@RELATIVE("All_Hotels", 0), &CurrMonth)
  IF(v_Total <> 0)
    "Pct_of_Total" = "Revenue" / v_Total * 100;
  ENDIF
ENDFIX
```

### Pattern 5: Dense Calc Before Sparse AGG

```essbase
/* Always calculate dense dims first, then aggregate sparse */

/* Phase 1: Dense calcs (within-block — fast) */
FIX("Budget", "Working", &CurrYear, @RELATIVE("All_Hotels", 0))
  "Total_Revenue" = "Room_Revenue" + "F&B_Revenue" + "Spa_Revenue";
  "Total_Expenses" = "Labor" + "Maintenance" + "Utilities";
  "Net_Income" = "Total_Revenue" - "Total_Expenses";
ENDFIX

/* Phase 2: Sparse AGG (cross-block — slower) */
FIX("Budget", "Working", &CurrYear)
  AGG("Entity");
ENDFIX

/* NOT the reverse — don't AGG then calc (stale totals) */
```

### Pattern 6: Hybrid Groovy + Embedded Calc

```groovy
/* Use Groovy for logic, embedded calc for math */

// Step 1: Groovy validates
def errors = []
operation.grid.dataCellIterator("Account#Revenue").each { cell ->
    if (cell.data < 0) errors << "Error: ${cell.getMemberName('Entity')}"
}
if (errors) throwVetoException(errors.join('\n'))

// Step 2: Embedded calc for heavy math
operation.application.getEssbaseServer()
    .getApplication(operation.application.getName())
    .getCube("OEP_FS")
    .executeCalcScript("""
SET LOCKBLOCK ON;
SET CALCPARALLEL 4;
FIX("Budget", "Working", "FY2026", @RELATIVE("All_Hotels", 0))
  "Net_Income" = "Total_Revenue" - "Total_Expenses";
ENDFIX
SET LOCKBLOCK OFF;
""")

// Step 3: Groovy sends notification
try {
    operation.application.getEmailService().sendMail(
        "admin@hotelpvtltd.com", "Budget Calc Done", "Complete.")
} catch (Exception e) { println "Email failed" }
```

### Pattern 7: Conditional Calc by Scenario

```essbase
/* Different logic per scenario */
FIX("Working", &CurrYear, @RELATIVE("All_Hotels", 0))

  /* Budget: Apply growth rates */
  FIX("Budget")
    "Revenue" = "Revenue" -> "Actual" -> &PriorYear * 1.05;
  ENDFIX
  
  /* Forecast: Copy actuals for closed, keep forecast for open */
  FIX("Forecast")
    FIX(@RANGE("Period", "Jan", &PriorMonth))
      DATACOPY "Actual" TO "Forecast";
    ENDFIX
  ENDFIX
  
  /* Actual: No calculation (data is loaded externally) */
  
ENDFIX
```

### Pattern 8: Idempotent Rules (Safe to Re-run)

```essbase
/* A rule should produce the same result whether run once or 10 times */

/* ❌ BAD: Not idempotent — each run adds 5% */
"Revenue" = "Revenue" * 1.05;

/* ✅ GOOD: Idempotent — always references source */
"Revenue" -> "Budget" = "Revenue" -> "Actual" -> &PriorYear * 1.05;
/* Running this 10 times gives the same result as running once */
```

## 3. NAMING CONVENTIONS

```
Rules:
  CALC_PnL_Monthly           → Calculation rule
  COPY_Actual_to_Budget       → Data movement rule
  AGG_Entity                  → Aggregation rule
  VAL_Revenue_PreSave         → Validation rule (Groovy)
  RPT_Monthly_Close_Email     → Reporting/notification rule
  SEED_Budget_FY2027          → Budget seeding rule

Rulesets:
  RS_OnSave_Revenue           → On Save ruleset
  RS_Monthly_Close            → Scheduled monthly
  RS_Annual_Budget_Seed       → Annual process

Variables (RTPs):
  RTP_Scenario                → Scenario selector
  RTP_Year                    → Year selector
  RTP_GrowthRate              → Numeric input
```

## 4. SHOW ME — Hotel Pvt Ltd Rule Architecture

```
Application: HotelApp
│
├── Calculations (CALC_*)
│   ├── CALC_Revenue_Totals     → Sum revenue sub-accounts
│   ├── CALC_Expense_Totals     → Sum expense sub-accounts
│   ├── CALC_PnL                → Net Income = Rev - Exp
│   ├── CALC_KPIs               → RevPAR, Occupancy, Margin
│   └── CALC_Currency           → INR → USD conversion
│
├── Data Movement (COPY_*)
│   ├── COPY_Actual_to_Budget   → Seed budget from actuals
│   ├── COPY_Working_to_Final   → Lock version
│   └── COPY_Rolling_Forecast   → Actuals for closed months
│
├── Aggregation (AGG_*)
│   ├── AGG_Entity              → Roll up hotels
│   └── AGG_Full                → All dimensions
│
├── Validation (VAL_*)
│   ├── VAL_Revenue_NonNegative → Groovy — check revenue ≥ 0
│   └── VAL_Budget_Complete     → Groovy — all months filled
│
├── Allocation (ALLOC_*)
│   └── ALLOC_Corporate_Cost    → Distribute HQ costs
│
├── Rulesets (RS_*)
│   ├── RS_OnSave_Revenue       → [CALC_Revenue, CALC_PnL, AGG_Entity]
│   ├── RS_OnSave_Expense       → [CALC_Expense, CALC_PnL, AGG_Entity]
│   ├── RS_Monthly_Close        → [CALC_All, CALC_Currency, ALLOC_Corp, AGG_Full]
│   └── RS_Annual_Seed          → [CLEAR, COPY_Actual_Budget, CALC_PnL, AGG_Full]

    └── RPT_Close_Email         → Groovy — send summary email
```

## 5. COMMON MISTAKES

| Mistake | Fix |
|---------|-----|
| No naming convention | Adopt CALC_/COPY_/AGG_/VAL_/RS_ prefix standard |
| Rules not idempotent | Reference source data, not target |
| No trace messages | Add @CalcMgrLogMessageTrace for debugging |
| AGG before dense calc | Dense first, then AGG |
| Cross-dim on sparse without two-pass | Store total in VAR first |
| Rules tightly coupled | Use Rulesets for sequencing |

## 6. INTERVIEW QUESTIONS

### Architect
**Q: Design the complete Calc Manager rule architecture for Hotel Pvt Ltd.**
> Organize by function: **CALC_** for calculations (Revenue, Expense, PnL, KPIs, Currency), **COPY_** for data movement (Seed Budget, Lock Version, Rolling Forecast), **AGG_** for aggregation, **VAL_** for Groovy validations, **ALLOC_** for allocations. Group into **Rulesets:** RS_OnSave_Revenue for form saves, RS_Monthly_Close for the scheduled process, RS_Annual_Seed for yearly budget cycle. Every rule follows Initialize→Calculate→Aggregate. Every Ruleset has Stop-on-Error enabled. Naming convention makes rules self-documenting. Total: ~15 rules organized in 4 Rulesets.
