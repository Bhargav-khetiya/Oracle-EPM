# Cross-Cube Allocations (@XREF and @XWRITE)

Sometimes, you need to calculate data in one cube, but use drivers that exist in a completely different cube. 

## 1. The @XREF Function (Pull)
`@XREF` pulls data *from* another cube *into* the cube currently running the calc script.

*   **Scenario:** You are calculating Revenue in the `Plan1` (BSO) cube, but you need the exact Daily Exchange Rate that is stored in the `Rates` (ASO) cube.
*   **Syntax:**
    ```essbase
    "Revenue_USD" = "Revenue_Local" * @XREF("Rates_Cube_Location_Alias", "Daily_Rate");
    ```
*   **Location Alias:** You must configure a Location Alias in EAS (or the Web UI) that securely connects `Plan1` to `Rates`.

## 2. The @XWRITE Function (Push)
`@XWRITE` pushes data *from* the current cube *to* another cube.

*   **Scenario:** You finish calculating all Allocations in `Plan1`, and you want to instantly push the final Net Income to a massive `Reporting` (ASO) cube so executives can see it.
*   **Syntax:**
    ```essbase
    @XWRITE("Net_Income", "Reporting_Cube_Location_Alias", "Net_Income");
    ```

## 3. The Performance Warning
Both `XREF` and `XWRITE` are notoriously slow if misused.
*   They establish network connections between cubes block-by-block.
*   If you use an `XWRITE` inside a massive Dense `FIX` statement that hits 100,000 blocks, Essbase will try to send 100,000 individual network pings to the other cube. It will take hours.
*   **Modern Alternative:** Use Data Maps (Smart Push) instead. It is infinitely faster to calculate everything in `Plan1`, and then trigger a bulk Data Map to push the results to `Reporting` in one shot. Use `XREF` only for pulling tiny, targeted driver values.
