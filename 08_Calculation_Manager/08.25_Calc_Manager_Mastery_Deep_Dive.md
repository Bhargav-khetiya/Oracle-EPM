# SECTION 1: CALC MANAGER ARCHITECTURE

---

## 1.1 What is Calculation Manager?

Calculation Manager is the **design environment** for creating, managing, and deploying business rules in Oracle EPM Cloud.

```
Navigation: 
  Navigator → Application → Calculation Manager
  OR
  Navigator → Rules → (view deployed rules)
```

## 1.2 Object Hierarchy

```
Calculation Manager Object Tree:

Application: HotelBudget
  └── Plan Type: Plan1 (BSO)
      ├── Rules
      │   ├── Calculate_Revenue (Script)
      │   ├── Copy_Actual_to_Budget (Graphical)
      │   ├── Allocate_Overhead (Script)
      │   └── Currency_Translation (Script)
      │
      ├── Rule Sets
      │   ├── Month_End_Calc (runs 3 rules in order)
      │   └── Budget_Preparation (runs 5 rules in order)
      │
      ├── Templates
      │   ├── Custom_Allocation_Template
      │   └── Custom_Growth_Template
      │
      ├── Components (reusable script blocks)
      │   ├── Clear_Forecast_Component
      │   └── Agg_Entity_Component
      │
      └── Variables
          ├── Substitution Variables
          ├── Runtime Prompts
          └── Global Variables
```

## 1.3 Rule Types

| Type | Language | Engine | Use Case |
|------|----------|--------|----------|
| **Calc Script** | Essbase native | Essbase calc engine | Standard calculations, aggregations, allocations |
| **Groovy** | Java-based scripting | Planning server | Complex logic, REST API, data movement, email notifications |
| **MDX Script** | MDX query language | MDX engine | ASO cube calculations, complex member sets |

## 1.4 Rule vs Template vs Component

| Object | Reusability | Deployment | Purpose |
|--------|------------|------------|---------|
| **Rule** | Standalone | Deployed to application | Complete calculation logic that can be executed |
| **Template** | Reusable | Embedded inside rules | Pre-built logic pattern (like a function) |
| **Component** | Reusable | Embedded inside rules | Reusable script block shared across rules |

```
Example:
  Template: "Growth_Calculation" (accepts parameters: Account, Growth%)
  
  Rule 1: "Calc_Revenue" 
    → Uses Growth_Calculation template with Account=Revenue, Growth=10%
  
  Rule 2: "Calc_Expense"
    → Uses Growth_Calculation template with Account=Expense, Growth=5%
  
  Both rules use the SAME template with different parameters.
  Update the template → both rules update automatically.
```

# SECTION 2: SCRIPT MODE VS GRAPHICAL DESIGNER

---

## 2.1 Script Mode

Direct Essbase Calc Script code entry:

```
┌──────────────────────────────────────────────────┐
│  Script Editor                                   │
│                                                  │
│  SET UPDATECALC OFF;                            │
│                                                  │
│  FIX("Budget", @LEVMBRS("Entity", 0))          │
│      "Revenue" = "Revenue" * 1.10;              │
│      "Net_Income" = "Revenue" - "Expense";      │
│  ENDFIX                                         │
│                                                  │
│  [Validate] [Save] [Deploy]                     │
└──────────────────────────────────────────────────┘
```

| Advantage | Disadvantage |
|-----------|-------------|
| Full control over syntax | Requires Essbase knowledge |
| Easy to copy/paste/share | Harder for visual learners |
| Best for complex logic | No visual flow diagram |
| Industry-standard scripts | Debugging requires log reading |

## 2.2 Graphical Designer

Visual flow-chart-based rule builder:

```
┌──────────────────────────────────────────────────┐
│  Graphical Designer                              │
│                                                  │
│  [Begin] → [FIX] → [Formula] → [AGG] → [End]  │
│              │                                   │
│           Entity=                                │
│           @LEVMBRS(0)                            │
│           Scenario=                              │
│           Budget                                 │
│                                                  │
│  Palette:                                        │
│  ├── System Templates                            │
│  │   ├── Condition                               │
│  │   ├── Loop                                    │
│  │   ├── Formula                                 │
│  │   ├── Member Range                            │
│  │   ├── Plan Type Map                           │
│  │   ├── Clear Data                              │
│  │   └── Copy Data                               │
│  ├── Script                                      │
│  └── Custom Templates                            │
│                                                  │
│  [Validate] [Save] [Deploy]                     │
└──────────────────────────────────────────────────┘
```

| Advantage | Disadvantage |
|-----------|-------------|
| Visual flow — easy to understand | Limited control vs raw script |
| Drag-and-drop templates | Generated code can be verbose |
| Good for simple-to-medium rules | Complex logic is harder visually |
| Wizard-driven configuration | Some advanced syntax not available |

## 2.3 When to Use Which

```
Use Script Mode when:
  → Complex calculations with nested FIX/IF
  → Performance-critical rules (manual optimization)
  → Migrating on-prem Hyperion scripts
  → Developers comfortable with Essbase syntax

Use Graphical Designer when:
  → Simple operations (clear, copy, calculate)
  → Admin-level users creating basic rules
  → Need visual documentation of rule flow
  → Using System Templates for standard operations
```

# SECTION 3: SYSTEM TEMPLATES — COMPLETE REFERENCE

---

## 3.1 Condition Template

Creates IF/ELSE logic in graphical mode.

```
Configuration:
  Condition Type: Member / Data Value / Variable
  
  Example: IF Account is "Revenue" THEN multiply by 1.10

Generated Script:
  IF(@ISMBR("Revenue"))
      "Revenue" = "Revenue" * 1.10;
  ELSEIF(@ISMBR("Expense"))
      "Expense" = "Expense" * 1.05;
  ENDIF
```

## 3.2 Loop Template

Iterates over members of a dimension.

```
Configuration:
  Dimension: Entity
  Members: @CHILDREN("All Entities")
  Variable: CurrentEntity
  
Generated Script:
  FIX(@CHILDREN("All Entities"))
      /* Loop body executes for each entity */
      "Revenue" = "Revenue" * 1.10;
  ENDFIX
```

## 3.3 Formula Template

Defines a mathematical formula.

```
Configuration:
  Target: "Net_Income"
  Formula: "Revenue" - "Expense"
  
Generated Script:
  "Net_Income" = "Revenue" - "Expense";
```

## 3.4 Member Range Template

Applies logic across a range of members.

```
Configuration:
  Dimension: Period
  Start: Jan
  End: Jun
  Operation: Copy from prior year

Generated Script:
  FIX("Jan":"Jun")
      @DESCENDANTS("Revenue") = @DESCENDANTS("Revenue") -> @PRIOR("Year");
  ENDFIX
```

## 3.5 Plan Type Map Template

Moves data between plan types (cross-cube).

```
Configuration:
  Source: Plan2 (Workforce)
  Target: Plan1 (Financials)
  Members to Map:
    Account: "Headcount" (Plan2) → "Headcount_Plan1" (Plan1)
  
  Scope:
    Entity: @LEVMBRS("Entity", 0)
    Period: @CHILDREN("YearTotal")

Generated Script:
  PLANTYPE "Plan1"
  FIX(@LEVMBRS("Entity", 0), @CHILDREN("YearTotal"))
      "Headcount_Plan1" = @XREF("Plan2", "Headcount");
  ENDFIX
```

## 3.6 Clear Data Template

Clears data for specified members.

```
Configuration:
  Dimension selections: Scenario=Forecast, Entity=@LEVMBRS(0)
  Clearblock Option: All / Upper / Dynamic / Non-Input / N/A

Generated Script (for "All"):
  FIX("Forecast", @LEVMBRS("Entity", 0))
      CLEARBLOCK ALL;
  ENDFIX

Generated Script (for "N/A"):
  FIX("Forecast", @LEVMBRS("Entity", 0))
      CLEARDATA "Account_Member";
  ENDFIX
```

## 3.7 Copy Data Template

Copies data between sparse members.

```
Configuration:
  Source: Scenario = "Actual"
  Target: Scenario = "Forecast"
  Scope: Entity = @LEVMBRS(0), Year = &CurrYear

Generated Script:
  FIX(@LEVMBRS("Entity", 0), &CurrYear)
      DATACOPY "Actual" TO "Forecast";
  ENDFIX
```

## 3.8 Global Range Template

Defines a FIX scope that wraps other templates in graphical mode.

```
Configuration:
  Scope:
    Scenario: "Budget"
    Version: "Working"
    Year: &CurrYear
    Entity: @LEVMBRS("Entity", 0)
  
  Contains: Formula templates, Condition templates, etc.

Generated Script:
  FIX("Budget", "Working", &CurrYear, @LEVMBRS("Entity", 0))
      /* All contained template scripts go here */
  ENDFIX
```

# SECTION 4: VARIABLES — COMPLETE REFERENCE

---

## 4.1 Substitution Variables

**Scope:** Application-wide. Set by admin. Available to all rules, forms, reports.

```
Definition:
  Navigator → Tools → Variables → Substitution Variables
  
  Name: CurrYear
  Value: FY26
  Plan Type: All (or specific)

Usage in Calc Scripts:
  FIX(&CurrYear)   /* Resolves to FIX("FY26") */
  
Usage in Forms:
  Member Selection: &CurrYear  /* Resolves to FY26 */

Admin Updates:
  epmautomate setsubstvars Plan1 CurrYear=FY27
  → All rules and forms automatically use FY27
```

### Common Substitution Variables:
| Variable | Example Value | Purpose |
|----------|--------------|---------|
| `&CurrYear` | FY26 | Current planning year |
| `&CurrPeriod` | Jul | Current month |
| `&PriorPeriod` | Jun | Previous month |
| `&CurrScenario` | Budget | Active scenario |
| `&BudgetYear` | FY27 | Year being budgeted |
| `&ActualMonths` | Jan:Jun | Range of months with actuals |

## 4.2 Runtime Prompts (RTP)

**Scope:** Per-rule. User provides values at execution time.

```
Definition (in Rule Properties):
  Name: RTP_Entity
  Type: Member
  Dimension: Entity
  Default: Hotel India
  Prompt: "Select Entity:"
  
  Name: RTP_GrowthRate
  Type: Numeric
  Default: 10
  Prompt: "Enter Growth Rate (%):"

Usage in Calc Script:
  FIX({RTP_Entity})
      "Revenue" = "Revenue" * (1 + {RTP_GrowthRate} / 100);
  ENDFIX

User Experience:
  When user runs rule, a dialog appears:
  ┌───────────────────────────────┐
  │  Select Entity: [Hotel India▼]│
  │  Growth Rate (%): [10      ] │
  │  [Launch]  [Cancel]          │
  └───────────────────────────────┘
```

### RTP Types:
| Type | User Input | Syntax | Example |
|------|-----------|--------|---------|
| **Member** | Select from member tree | `{RTP_Name}` | `FIX({RTP_Entity})` |
| **Numeric** | Type a number | `{RTP_Name}` | `"Rev" = "Rev" * {RTP_Rate}` |
| **String** | Type text | `"{RTP_Name}"` | Used for UDA lookup |
| **Date** | Pick date | `{RTP_Name}` | Date-driven calculations |
| **Smart List** | Select from dropdown | `{RTP_Name}` | Status-driven logic |
| **Member Range** | Select start + end | `{RTP_Start}:{RTP_End}` | `FIX({RTP_StartPd}:{RTP_EndPd})` |
| **Cross Dimension** | Select member × dim | Complex | Multi-dim member selection |

## 4.3 Design-Time Prompts (DTP)

**Scope:** Template-level. Developer provides values when embedding template into a rule.

```
Definition (in Template):
  Name: DTP_Account
  Type: Member
  Dimension: Account
  Prompt: "Select Target Account:"

Template Code:
  "{DTP_Account}" = "{DTP_Account}" * 1.10;

When embedding template into Rule:
  Developer is prompted: "Select Target Account:" → Revenue
  → Template resolves to: "Revenue" = "Revenue" * 1.10;

Different rule, same template:
  Developer selects: "Expense"
  → Template resolves to: "Expense" = "Expense" * 1.10;
```

## 4.4 Global Variables

**Scope:** Application-wide, persistent, accessible from Groovy.

```
Definition:
  Navigator → Tools → Variables → Global Variables

  Name: GV_BudgetStatus
  Type: String
  Value: "Open"

Usage in Groovy:
  String status = rtps.GV_BudgetStatus.toString()
  if (status == "Locked") {
      throwVetoException("Budget is locked. No changes allowed.")
  }
```

## 4.5 Variable Comparison

| Variable Type | Set By | When Resolved | Scope | Use Case |
|---------------|--------|---------------|-------|----------|
| **Substitution** | Admin | At rule execution | All rules/forms | CurrYear, CurrPeriod |
| **Runtime Prompt** | User | At rule launch (dialog) | Single rule execution | Entity selection, growth rate |
| **Design-Time Prompt** | Developer | At template embedding | Template → Rule | Template parameterization |
| **Global** | Admin / Groovy | Read at any time | Application | Status flags, configuration |

# SECTION 5: RULE SETS

---

## 5.1 What is a Rule Set?

A Rule Set groups multiple business rules for sequential or parallel execution.

```
Rule Set: "Month_End_Processing"
  ├── Rule 1: Clear_Forecast (sequential)
  ├── Rule 2: Copy_Actuals (sequential — depends on Rule 1)
  ├── Rule 3: Calculate_Revenue (sequential — depends on Rule 2)
  ├── Rule 4: Calculate_Expense (parallel with Rule 3 — independent)
  └── Rule 5: Aggregate_All (sequential — depends on Rules 3 & 4)

Execution Order:
  Rule 1 → Rule 2 → [Rule 3 ∥ Rule 4] → Rule 5
```

## 5.2 Rule Set Properties

| Property | Options | Description |
|----------|---------|-------------|
| **Execution Type** | Sequential / Parallel | Whether rules run one-after-another or simultaneously |
| **Stop on Error** | Yes / No | Stop rule set if any rule fails |
| **Runtime Prompts** | Shared or individual | Share RTP values across all rules or prompt per rule |
| **Plan Type** | Must match rules' plan types | All rules must be compatible |

## 5.3 Sequential vs Parallel Execution

```
Sequential:
  Rule 1 runs → completes → Rule 2 runs → completes → Rule 3 runs
  → Total time = Rule1_time + Rule2_time + Rule3_time

Parallel:
  Rule 1 and Rule 2 run simultaneously → both complete → Rule 3 runs
  → Total time = max(Rule1_time, Rule2_time) + Rule3_time
  
  ⚠️ Parallel is only safe when rules are INDEPENDENT
  (don't read data that the other rule is writing)
```

## 5.4 Example: Budget Preparation Rule Set

```
Rule Set: "Annual_Budget_Preparation"
  Step 1 (Sequential): "Clear_Budget_Data"
    → Clears all existing Budget data for &BudgetYear
  
  Step 2 (Sequential): "Seed_From_Actuals"
    → DATACOPY Actual to Budget for baseline
  
  Step 3 (Parallel):
    → "Calculate_Revenue" (10% growth on revenue)
    → "Calculate_Expense" (5% growth on expenses)
    → "Calculate_Headcount" (from Workforce plan)
    [These 3 are independent — safe to parallelize]
  
  Step 4 (Sequential): "Calculate_PnL"
    → Net Income = Revenue - Expense
    → Margin % = Net Income / Revenue
    [Depends on Step 3 completing]
  
  Step 5 (Sequential): "Aggregate_All"
    → AGG Entity, Department
    [Depends on Step 4]
```

# SECTION 6: DEPLOYMENT AND VALIDATION

---

## 6.1 Rule Lifecycle

```
1. CREATE → Design the rule in Calc Manager
2. VALIDATE → Check syntax and semantic errors
3. SAVE → Save to Calc Manager repository
4. DEPLOY → Make the rule available to users and forms
5. EXECUTE → User runs the rule (or it auto-runs from form)
```

## 6.2 Validation vs Deployment

| Action | What It Checks | Creates Executable? |
|--------|---------------|-------------------|
| **Validate** | Syntax errors, member name resolution, function validity | ❌ No — just checks |
| **Deploy** | Validates + compiles + registers in Planning | ✅ Yes — rule is now runnable |

```
Common Validation Errors:
  - "Member [Revenue] not found" → member name misspelled
  - "Syntax error near ENDFIX" → missing semicolon or bracket
  - "Unknown function @CHILDS" → wrong function name (@CHILDREN)
  - "Variable {RTP_Entity} not defined" → RTP not created
```

## 6.3 Deployment States

| State | Meaning |
|-------|---------|
| **Not Deployed** | Rule is saved but not available to users |
| **Deployed** | Rule is compiled and available |
| **Invalid** | Rule was deployed but outline changed — needs revalidation |
| **Needs Redeployment** | Rule was modified after deployment — needs redeployment |

# SECTION 7: CUSTOM TEMPLATES AND COMPONENTS

---

## 7.1 Custom Templates

You can create reusable templates with Design-Time Prompts:

```
Template: "Percentage_Growth"
  DTPs:
    DTP_Account (Member, Account dim)
    DTP_Growth (Numeric)
  
  Script:
    "{DTP_Account}" = "{DTP_Account}" * (1 + {DTP_Growth} / 100);

Usage in Rule A:
  Embed template → DTP_Account = "Revenue", DTP_Growth = 10
  → "Revenue" = "Revenue" * 1.10;

Usage in Rule B:
  Embed template → DTP_Account = "Expense", DTP_Growth = 5
  → "Expense" = "Expense" * 1.05;
```

## 7.2 Components

Components are reusable script blocks:

```
Component: "Standard_Aggregation"
  Script:
    CALC DIM("Account");
    CALC DIM("Period");
    AGG("Entity");
    AGG("Department");

Used in multiple rules:
  Rule: "Calculate_Revenue" → ends with Standard_Aggregation component
  Rule: "Calculate_Expense" → ends with Standard_Aggregation component
  Rule: "Budget_Prep" → ends with Standard_Aggregation component
  
  Update component once → all 3 rules updated automatically
```

# SECTION 8: CDF — CUSTOM DEFINED FUNCTIONS

---

## 8.1 What is a CDF?

A Custom Defined Function extends Essbase's built-in function library with Java code.

```
Example CDF: @JDE_LOOKUP(Account, Entity)
  → Calls an external Java class to look up data from JD Edwards
  → Returns a value to the Essbase calc script

Registration:
  Calc Manager → Custom Defined Functions → Register
  → Upload JAR file
  → Define function signature
  → Map parameters

Usage in Calc Script:
  "Revenue" = @JDE_LOOKUP("Revenue", "Hotel India");
```

## 8.2 Common CDF Use Cases

| Use Case | CDF | Purpose |
|----------|-----|---------|
| External data lookup | @ERP_LOOKUP | Retrieve values from ERP at calc time |
| Complex math | @COMPOUND_INTEREST | Financial functions not in Essbase |
| String manipulation | @PARSE_CODE | Parse account codes |
| Date calculations | @WORKDAYS | Count business days between dates |

# SECTION 9: CROSS-PLAN TYPE OPERATIONS

---

## 9.1 @XREF — Cross-Cube Read

```essbase
/* Read data from another plan type (cube) */
FIX("Budget", @LEVMBRS("Entity", 0), @CHILDREN("YearTotal"))
    "Headcount_Plan1" = @XREF("Plan2", "Headcount");
ENDFIX

/* @XREF Syntax:
   @XREF("TargetPlanType", "MemberInTarget")
   
   Essbase resolves matching sparse dimensions automatically:
   If current context = [Hotel India, Budget, Working, FY26, Jan]
   → @XREF reads [Hotel India, Budget, Working, FY26, Jan, Headcount] from Plan2
*/
```

## 9.2 @XWRITE — Cross-Cube Write

```essbase
/* Write data TO another plan type */
FIX("Budget", @LEVMBRS("Entity", 0), @CHILDREN("YearTotal"))
    @XWRITE("Revenue", "Rpt1");
ENDFIX

/* Pushes Revenue values FROM current plan type TO Rpt1 (ASO) */
```

## 9.3 Plan Type Map Template

The graphical way to do cross-plan-type operations:

```
Plan Type Map:
  Source Plan Type: Plan2 (Workforce)
  Target Plan Type: Plan1 (Financials)
  
  Mapping:
    Plan2."Headcount" → Plan1."HC_from_Workforce"
    Plan2."Avg_Salary" → Plan1."Salary_from_Workforce"
  
  Scope:
    Entity: @LEVMBRS(0)
    Period: @CHILDREN("YearTotal")
    Scenario: "Budget"
```

# SECTION 10: DEBUGGING AND ERROR HANDLING

---

## 10.1 Common Errors and Fixes

| Error | Cause | Fix |
|-------|-------|-----|
| "Member not found" | Misspelled member name | Check exact member name in Dimension Editor |
| "Cannot lock object" | Another user/process is running | Wait or cancel other process |
| "Insufficient access" | User lacks calc permission | Grant "Launch" permission in Security |
| "Block not found" | Assignment to non-existent block | Use SET CREATEBLOCKONEQ ON |
| "Division by zero" | Formula divides by 0 or #Missing | Add IF(denominator <> 0 AND denominator <> #Missing) |
| "Calc script time limit exceeded" | Rule takes too long | Optimize FIX scope, reduce cross-dim references |
| "Exceeded maximum number of blocks" | CREATEBLOCKONEQ created too many blocks | Tighten FIX scope |

## 10.2 Debugging Techniques

```essbase
/* 1. Use SET MSG DETAIL for verbose logging */
SET MSG DETAIL;
FIX("Hotel India", "Budget", "Jan")
    "Revenue" = "Revenue" * 1.10;
ENDFIX
SET MSG SUMMARY;

/* 2. Narrow scope to single intersection */
FIX("Hotel India", "Budget", "Working", "FY26", "Jan", "INR", "Catering")
    /* Test with ONE cell */
    "Revenue" = 1000;
ENDFIX

/* 3. Check if blocks exist */
/* If DATACOPY produces no results, source blocks might not exist */
FIX("Actual", "Hotel India", "Working", "FY26")
    DATACOPY "Actual" TO "Forecast";
ENDFIX
/* If nothing copies, check: does data exist for Actual + Hotel India? */
```

## 10.3 Job Console

```
Navigator → Tools → Jobs

Shows:
  - Rule name
  - Start/End time
  - Duration
  - Status (Completed / Failed / Running)
  - Log file (click to view detailed execution log)

Log contains:
  - Lines processed
  - Blocks read/written
  - Calculation time
  - Error messages
  - SET MSG output
```

# SECTION 11: BEST PRACTICES

---

## 11.1 Rule Design Best Practices

| Practice | Why |
|----------|-----|
| **Always use FIX** | Never let a rule process the entire database |
| **FIX on sparse dimensions first** | Block-level filtering for I/O reduction |
| **Use substitution variables for dates** | &CurrYear, &CurrPeriod — easy to maintain |
| **Use RTPs for user-selectable scope** | Entity, Scenario selection at runtime |
| **One rule per logical operation** | Calculate_Revenue, Calculate_Expense — not "Do_Everything" |
| **Combine into Rule Sets** | Sequence independent rules for organized execution |
| **Comment your scripts** | `/* Revenue calculation based on occupancy drivers */` |
| **Always check for #Missing and 0 before division** | Prevent division errors |
| **Turn CREATEBLOCKONEQ OFF after use** | Prevent uncontrolled block creation |
| **Dense calcs before sparse AGG** | Correct aggregation order |
| **Test with narrow scope first** | One entity, one period — verify logic |
| **Use Components for shared logic** | Reuse aggregation, clearing patterns |

## 11.2 Naming Convention

```
Rules:
  BR_[Module]_[Action]_[Detail]
  BR_FIN_Calc_Revenue
  BR_FIN_Copy_Actual_to_Budget
  BR_WF_Calc_Compensation
  BR_CAP_Calc_Depreciation

Rule Sets:
  RS_[Module]_[Process]
  RS_FIN_MonthEnd_Processing
  RS_FIN_Annual_Budget_Prep
  RS_WF_Headcount_Calc

Variables:
  RTP_[Type]_[Purpose]
  RTP_Entity (Member)
  RTP_GrowthRate (Numeric)
  RTP_StartPeriod (Member Range)
```

# SECTION 12: WORKED EXAMPLES — 20 COMPLETE RULES

---

## Example 1: Basic Revenue Calculation
```essbase
/* BR_FIN_Calc_Revenue */
FIX({RTP_Scenario}, "Working", &CurrYear, @LEVMBRS("Entity", 0), @CHILDREN("YearTotal"))
    "Rooms_Sold" = "Rooms_Available" * "Occupancy_Rate" / 100;
    "Rooms_Revenue" = "Rooms_Sold" * "Avg_Room_Rate";
    "Total_Revenue" = "Rooms_Revenue" + "Banquet_Revenue" + "FnB_Revenue";
ENDFIX
```

## Example 2: P&L Calculation
```essbase
/* BR_FIN_Calc_PnL */
FIX({RTP_Scenario}, "Working", &CurrYear, @LEVMBRS("Entity", 0), @CHILDREN("YearTotal"))
    "Gross_Margin" = "Revenue" - "COGS";
    "Operating_Income" = "Gross_Margin" - "Operating_Expense";
    "Net_Income" = "Operating_Income" - "Tax";
    IF("Revenue" <> 0 AND "Revenue" <> #Missing)
        "Margin_Pct" = "Net_Income" / "Revenue" * 100;
    ELSE
        "Margin_Pct" = #Missing;
    ENDIF
ENDFIX
```

## Example 3: Expense Allocation

# SECTION 13: INTERVIEW QUESTIONS

---

**Q1: What is the difference between a Rule, a Template, and a Component?**
> A Rule is a standalone executable calculation. A Template is a reusable parameterized logic pattern (using DTPs) embedded into rules. A Component is a reusable script block shared across rules. Templates accept parameters; Components don't.

**Q2: What is the difference between Substitution Variables and Runtime Prompts?**
> Substitution Variables are admin-set, application-wide, resolved at execution (&CurrYear → FY26). RTPs are user-provided at rule launch time via dialog ({RTP_Entity} → user selects Hotel India). Sub vars are the same for everyone; RTPs vary per execution.

**Q3: What is a Rule Set? When would you use parallel execution?**
> A Rule Set groups multiple rules for sequential or parallel execution. Use parallel when rules are independent (don't read each other's output). Example: Revenue calc and Expense calc can run in parallel, but Aggregation must run after both.

**Q4: Explain the validation → deployment lifecycle.**
> Validate checks syntax and member resolution without creating an executable. Deploy validates, compiles, and registers the rule as runnable. After outline changes, deployed rules may become "Invalid" and need redeployment.

**Q5: How does @XREF work for cross-plan-type calculations?**
> @XREF reads data from another plan type. Essbase uses matching sparse dimensions to locate the source cell. Example: `@XREF("Plan2", "Headcount")` reads Headcount from Plan2 using the current entity/scenario/version/year/period context.
