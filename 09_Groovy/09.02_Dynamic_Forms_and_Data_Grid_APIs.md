## 4. Business Background
Users make mistakes. A user might accidentally type `-1000` into a "Headcount" account, or type `$50,000` into a "Travel" expense when the corporate limit is $10,000. In legacy systems, you couldn't catch this until after the data was saved and a report was run. With Groovy, you can intercept the save button.

## 7. Core Concepts: The Data Grid Builder

When a Groovy rule is attached to a web form and set to "Run Before Save", the Groovy script has access to an object called the `DataGrid`. The DataGrid is a programmatic representation of the exact rows and columns on the screen.

### 1. `operation.grid`
This command grabs the specific form the user is currently looking at.

### 2. The Iterator (`dataCellIterator`)
A form might have 1,000 cells on it, but the user only changed 3 cells. 
You do not want to run complex validation logic on 997 unchanged cells. 
You use the iterator:
```groovy
operation.grid.dataCellIterator({DataCell cell -> cell.isEdited()}).each { DataCell cell ->
    // Do something only to the edited cells
}
```
This loop is the absolute foundation of high-performance Groovy scripting.

## 14. Examples: Server-Side Validation

Let's build the script that stops a user from entering a negative Headcount.

```groovy
// 1. Iterate through all cells the user just edited
operation.grid.dataCellIterator({DataCell cell -> cell.isEdited()}).each { DataCell cell ->
    
    // 2. Check if the cell belongs to the Headcount account
    if (cell.getMemberName("Account") == "Headcount") {
        
        // 3. Check if the value is negative
        if (cell.data < 0) {
            // 4. Veto the save operation and throw a custom error to the user
            throw new VetoException("Error: You cannot enter a negative headcount! Value entered: ${cell.data}")
        }
    }
}
```

## 18. Architect Notes: The Performance Trap
Never put heavy logic inside a cell iterator. 
- **The Problem:** If a user uses the "Grid Spread" feature to edit 5,000 cells at once, and your Groovy script has an API call or a complex query inside the iterator, the script will execute that API call 5,000 times in 2 seconds. The server will throttle or kill your process.
- **The Solution:** Use the iterator *only* to collect the names of the edited members into a `Set` or `List`. Then, step outside the iterator, build a single dynamic Essbase Calc Script targeting those specific members, and execute it once.

## 25. Interview Questions

### Intermediate
**Q: You want to execute a Groovy script to validate data before it saves to the database. How do you attach it to the form?**
> A: You attach the Groovy Business Rule to the form via the Business Rules tab, and critically, you set the execution trigger to **"Run Before Save"**. If you set it to "Run After Save", the invalid data has already been written to the Essbase cube.

### Architect
**Q: Explain how the `isEdited()` method on a DataCell fundamentally changes how we design calculation logic in EPBCS compared to legacy on-premise Hyperion.**
> A: In legacy Hyperion, a user would click Save on a form, and a Calc Script would run on the entire intersection defined by the POV (e.g., all 500 accounts for that Cost Center), even if the user only changed one account. This caused massive processing overhead. With Groovy and `isEdited()`, we can isolate the exact single cell the user modified in the UI, dynamically generate a Calc Script that fixes ONLY on that single account, and calculate it in milliseconds. This is called "Targeted Calculation" and it reduces server CPU load by over 90%.

## 27. Summary
Groovy allows you to build proactive, intelligent applications that guide the user and protect the database from bad data before it ever reaches the Essbase engine.
