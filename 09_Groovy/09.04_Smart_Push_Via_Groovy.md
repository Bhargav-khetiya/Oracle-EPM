# 09.04 Smart Push Via Groovy

> **Module:** 09_Groovy  
> **Topic:** 04 - Smart Push Overrides  
> **Target Audience:** Architect  

---

## 1. Learning Objectives
- Understand the limitations of standard Web Form Smart Push.
- Use Groovy to dynamically override Smart Push parameters.
- Optimize BSO to ASO synchronization.

## 3. Introduction
Standard Smart Push is configured on a Web Form (Run After Save). It pushes data based on the Form Context (the POV). 
But what if the user edits a driver on the form (e.g., `Tax Rate`) that dynamically calculates data for 50 other Cost Centers in the background? Standard Smart Push will only push the user's specific Cost Center to the ASO cube. The other 49 calculated cost centers will be stranded in BSO, out of sync. You must use Groovy to fix this.

## 7. Core Concepts: The DataMap API

Groovy provides a class called `DataMap`. This allows you to programmatically trigger a Smart Push and completely override what gets pushed.

### Standard Push vs Groovy Push

**Standard Form Push:**
1. User clicks Save on Cost Center 100.
2. Smart Push grabs `Entity: CC_100`.
3. Smart Push pushes `CC_100` to ASO.

**Groovy Push:**
1. User clicks Save on Cost Center 100.
2. The Groovy script intercepts the save.
3. The Groovy script executes the complex driver calculation (which impacts CC_101 to CC_150).
4. The Groovy script tells the Data Map: "Ignore the form. Push CC_100, CC_101, CC_102... through CC_150."
5. All calculated data is safely pushed to ASO.

## 14. Examples: The Groovy Override Script

```groovy
// 1. Identify the Data Map you want to run
def myDataMap = operation.application.getDataMap("BSO_to_ASO_Financials")

// 2. Define the exact members you want to push (overriding the form)
// In this case, we force it to push 3 specific Cost Centers, regardless of what the user is looking at.
def overrideString = "Entity:\"CC_100\",\"CC_101\",\"CC_150\""

// 3. Execute the push with the override
myDataMap.execute(overrideString, false) // false = don't wait for completion in UI (run async if possible)
```

## 18. Architect Notes: Pushing Unsaved Data
One of the most dangerous features of a Web Form Smart Push is that it pushes data directly from the browser to ASO, even if the Calc Script running on the form failed. 
By moving the Smart Push into a Groovy script, you can enforce strict sequencing:
1. Run Calc Script.
2. Check if Calc Script succeeded.
3. If Success -> Execute `DataMap.execute()`.
4. If Fail -> Throw Exception, halt the Smart Push. 
This guarantees the ASO reporting cube is never corrupted with incomplete calculations.

## 25. Interview Questions

### Architect
**Q: You have a Data Map configured to move data from EPBCS to a secondary Reporting cube. The Data Map usually takes 5 minutes to run. You want to trigger it via Groovy on a Web Form after the user clicks Save. What is the user experience problem?**
> A: If you trigger a 5-minute Data Map via Groovy synchronously on a Web Form, the user's web browser will freeze with a "Processing" spinner for 5 minutes while they wait for the push to finish. They will likely close the browser, thinking it crashed. You must either optimize the Data Map by applying strict dimensional overrides to limit the data volume to a few seconds, or run the Data Map as an asynchronous background job using REST API rather than a synchronous Groovy push.

## 27. Summary
Never rely on standard Form Smart Push for complex, multi-entity driver models. Use Groovy to intercept, calculate, and precisely push exactly what changed.
