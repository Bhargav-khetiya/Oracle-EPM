# Data Management vs. Data Integration

Oracle EPM Cloud has two distinct interfaces for moving data into the system, which often confuses new administrators. 

## 1. Data Management (The Classic Interface)

Data Management is the legacy tool, directly ported from the on-premise FDMEE (Financial Data Quality Management Enterprise Edition) software.

*   **UI/UX:** Looks older, uses a vertical menu tree.
*   **Capabilities:** Historically, it had more advanced capabilities for complex Jython scripting in mappings and event scripts (e.g., triggering an email before a load starts).
*   **Future:** Oracle is actively deprecating this interface. While it still exists in the cloud, all new features are being built in Data Integration.

## 2. Data Integration (The Modern Interface)

Data Integration is the modern, Redwood-themed interface built specifically for EPM Cloud.

*   **UI/UX:** Streamlined, wizard-driven flow (Map Dimensions -> Map Data -> Options).
*   **Capabilities:** It uses the exact same backend engine as Data Management. If you build a load rule in Data Integration, you will actually see it appear in the old Data Management interface. 
*   **New Features:** EPM Integration Agent (to connect to on-premise SQL databases without opening firewall ports), Smart Push integrations, and native connections to Oracle ERP Cloud are all managed here.

## 3. Core Concepts for Both Interfaces

Regardless of which UI you use, the architecture of loading data is the same:

1.  **Source System:** Where the data comes from (e.g., a flat file, Oracle ERP Cloud, NetSuite).
2.  **Target Application:** Where the data is going (e.g., the EPBCS Plan1 cube).
3.  **Location:** The bridge between the Source and Target. It holds the mappings. If you have 5 different sources going to the same cube, you usually create 5 Locations.
4.  **Mappings:** The translation rules. "Account 12345 in the source file equals Account 'Total_Revenue' in the target cube." (See `27.06_Data_Integration_Mapping_Screens.md` for deep dive).
5.  **Data Load Rule:** The actual job you execute. It takes the Location, asks for a specific File/Period, and runs the import and export.

## 4. The Staging Tables

When you run a load rule, the data doesn't go straight into Essbase. It hits a relational staging table first (`TDATASEG`). 
*   **Import:** Reads the flat file and puts raw data into the staging table.
*   **Validate:** Applies the mappings to the staging table. If an account isn't mapped, it fails here.
*   **Export:** Pushes the mapped staging table data into the Essbase cube. 

*Best Practice:* Always check the Workbench (Staging Table view) when a load fails to see exactly which row caused the issue.
