## 3. Introduction
If you mess up a calculation, the numbers are wrong. If you mess up Security, you violate corporate compliance laws (like SOX), and you can expose highly confidential executive compensation data to the entire company. Security is the highest-risk configuration in EPM.

## 7. Core Concepts: The Security Flow

Security in Oracle Cloud EPM is a two-step process:

### Step 1: The Identity Domain (The Bouncer)
- Managed in Oracle Cloud Infrastructure (OCI IAM) or Identity Cloud Service (IDCS).
- This creates the user's account (e.g., `JSMITH@company.com`) and assigns them a foundational Role (Service Administrator, Power User, User, Viewer).
- *This just lets them log into the website.*

### Step 2: Access Control (The Vault)
- Managed inside the EPBCS Application (Navigator -> Access Control).
- This is where you create **Groups** (e.g., `Grp_IT_Managers`).
- You add `JSMITH@company.com` to `Grp_IT_Managers`.
- You then go to the Dimension Editor, select `Entity: Cost_Center_IT`, click the key icon (Assign Access), and grant `Write` access to `Grp_IT_Managers`.
- *This lets them actually see and edit data on the forms.*

## 9. Internal Processing: Conflict Resolution
The most difficult part of EPM security is when a user exists in multiple groups with conflicting access. 

**Rule 1: Highest Level Wins (Dimensions)**
- Group A has `Read` access to `Product X`.
- Group B has `Write` access to `Product X`.
- If John is in both groups, John gets **Write** access. (Write > Read > None).

**Rule 2: Deny Overrides (The Exception)**
- Group A has `Read` access to `Product X`.
- Group B is explicitly assigned **None** (Deny) access to `Product X`.
- If John is in both groups, John gets **None**. Explicit denial overrides everything.

## 13. Configuration: Assigning Access

When you assign access to a parent member (e.g., `Total NA Geography`), you must define the scope:
1. **Member:** Access only to the parent itself (e.g., they can type data into `Total NA`, assuming it is a base-level ASO or input member).
2. **Children:** Access to the immediate kids, but NOT the parent.
3. **Descendants:** Access to every single level below the parent.
4. **Member (inclusive) and Descendants:** Access to the parent AND all levels below. (This is the most common setting).

## 16. Real Client Scenarios: The "Viewer" Trap
A client creates a user in IDCS and assigns them the **Viewer** role. 
The EPM Admin then puts that user into `Grp_Planners`. 
The Admin assigns `Grp_Planners` **Write** access to `Cost Center 100`. 
The user logs in, opens the form for Cost Center 100, and complains the form is Read-Only.

**The Architect Analysis:** 
The foundational IDCS Role is the hard ceiling. Because the user is a **Viewer** at the Identity Domain level, they can NEVER write data, regardless of how much `Write` access you give them in Access Control inside the application. You must upgrade their IDCS role to **User** before the Application-level `Write` access can take effect.

## 25. Interview Questions

### Intermediate
**Q: Why is it an architectural best practice to NEVER assign security directly to a User?**
> A: Assigning security directly to a User (e.g., granting `JSMITH` access to Cost Center 10) creates an unmaintainable system. In a company with 5,000 employees, people change jobs daily. If JSMITH transfers to HR, the admin has to hunt through the dimension tree to find and delete his specific entity assignments. If you use Groups (e.g., `Grp_Cost_Center_10`), you simply remove JSMITH from the group and add the new guy in one central Access Control screen.

### Architect
**Q: You have 3 secured dimensions: Entity, Account, and Scenario. A user has `Write` access to the Entity, `Read` access to the Account, and `Write` access to the Scenario. When they open the form to that specific intersection, can they type data into the cell?**
> A: No. The cell will be Read-Only. In EPM, security across multiple dimensions uses **Least Restrictive Intersection Logic bounded by the Most Restrictive Dimension**. Because the intersection requires the user to satisfy security on Entity AND Account AND Scenario, the `Read` access on the Account dimension acts as a bottleneck, downgrading the entire physical cell to Read-Only.

## 27. Summary
Security is a matrix. IDCS Roles provide the ceiling. Access Control Groups provide the foundation. Dimension intersections provide the exact coordinates. Master the conflict logic to keep data safe.
