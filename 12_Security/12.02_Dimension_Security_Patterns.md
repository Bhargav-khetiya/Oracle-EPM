# 12.02 — Dimension Security Patterns: Complete Guide

> **Module:** 12_Security | **Topic:** Security Inheritance, Effective Access, Design Patterns
> **Audience:** Service Administrator / Architect

---

## 1. WHY — Why Master Dimension Security Patterns?

**The problem:** You set Mumbai_Team as "Write" on All_Hotels and "None" on Delhi_Hotel. But the Mumbai team can still SEE Delhi's data! Why? Because security inheritance works top-down — "Write" on the parent cascades to ALL children. Without understanding inheritance, your security model has holes.

---

## 2. SECURITY INHERITANCE — HOW IT WORKS

```
Rule: Security cascades from PARENT to CHILDREN.
      Child inherits parent's access UNLESS explicitly overridden.

Example:
  All_Hotels → Mumbai_Team: Write

  Result (inherited):
    Mumbai_Hotel → Write (inherited from parent)
    Delhi_Hotel → Write (inherited from parent) ← PROBLEM!
    Bangalore → Write (inherited from parent)

  Fix: Set explicit None on non-Mumbai hotels
    All_Hotels → Mumbai_Team: Write
    Delhi_Hotel → Mumbai_Team: None (explicit override)
    Bangalore → Mumbai_Team: None (explicit override)
    Kolkata → Mumbai_Team: None (explicit override)
    Chennai → Mumbai_Team: None (explicit override)
    
    Now: Mumbai_Team sees ONLY Mumbai and All_Hotels total
```

### Effective Access Calculation

```
Effective access = Most specific assignment wins

Case 1: Parent=Write, Child=None
  → Child access = None (explicit override wins)

Case 2: Parent=None, Child=Write
  → Child access = Write (explicit override wins)

Case 3: Parent=Write, Child=not set
  → Child access = Write (inherited from parent)

Case 4: Parent=not set, Child=not set
  → No access (default = no assignment = no access)
```

## 3. THE 5 SECURITY DESIGN PATTERNS

### Pattern 1: Hub and Spoke (Most Common)

```
Each team gets Write on their entity, None on others, Read on total.

All_Hotels     → Everyone: Read (see consolidated total)
├── Mumbai     → Mumbai_Team: Write, Others: None
├── Delhi      → Delhi_Team: Write, Others: None
├── Bangalore  → Blr_Team: Write, Others: None
├── Kolkata    → Kol_Team: Write, Others: None
└── Chennai    → Chennai_Team: Write, Others: None

CFO            → All_Hotels: Read (sees everything, edits nothing)
Admin          → All_Hotels: Write (full access)
```

### Pattern 2: Regional Hierarchy

```
North_Region    → North_Manager: Write
├── Delhi       → Delhi_Team: Write (inherited from region)
├── Kolkata     → Kolkata_Team: Write (inherited)
└── No other teams have access

South_Region    → South_Manager: Write
├── Bangalore   → Blr_Team: Write (inherited)
├── Chennai     → Chennai_Team: Write (inherited)
└── Mumbai     → Mumbai_Team: Write (inherited? or separate region)

CFO             → All_Hotels: Read (consolidated view)
```

### Pattern 3: Scenario-Based Access

```
Scenario Dimension:
  Actual     → Planners: Read (cannot edit actuals!)
               Admin: Write (only admin loads actuals)
  
  Budget     → Planners: Write (can enter budget data)
               Viewers: Read
  
  Forecast   → Planners: Write (can enter forecasts)
               CFO: Write (CFO can adjust forecasts)
               Viewers: Read
```

### Pattern 4: Account-Based Confidentiality

```
Account Dimension:
  Revenue accounts     → All planners: Write
  Expense accounts     → All planners: Write
  Salary_Details       → HR_Team: Write, Others: None ← Confidential!
  Bonus_Pool           → CFO: Write, Others: None ← Highly confidential
  Executive_Comp       → Admin: Write, Others: None ← Top secret
```

### Pattern 5: Time-Based Access (Version Lock)

```
Version Dimension:
  Working    → Planners: Write (active editing)
  Final      → Planners: Read (locked — approved budget)
               Admin: Write (can modify if needed)
  
After approval:
  Admin changes Working → Planners: Read (lock all input)
  Admin runs Copy Working → Final
  Budget is now frozen everywhere
```

## 4. MULTI-DIMENSION SECURITY — EFFECTIVE ACCESS

When security is set on multiple dimensions, the **most restrictive** wins:

```
User: planner@hotelpvtltd.com
  Entity: Mumbai_Hotel = Write
  Scenario: Budget = Write
  Account: Salary_Details = None

Effective access at (Mumbai_Hotel, Budget, Salary_Details):
  Entity: Write ✅
  Scenario: Write ✅
  Account: None ❌
  
  Result: NO ACCESS (None on any dimension = no access)
  
The user cannot see or edit Mumbai Hotel's salary data,
even though they have Write on Mumbai and Budget.
```

## 6. SECURITY TESTING CHECKLIST

```
For each role/group:
  ☐ Can they log in? (Identity Domain)
  ☐ Do they see the correct forms? (Form Permissions)
  ☐ Do they see the correct entities? (Entity Security)
  ☐ Can they edit the right entities? (Write vs Read)
  ☐ Can they see Actual but not edit? (Scenario Security)
  ☐ Can they NOT see salary data? (Account Security)
  ☐ Can they NOT edit Final version? (Version Security)
  ☐ Can they run assigned rules? (Rule Security)
  ☐ Can they NOT access admin forms? (Form folder security)

Test matrix: 7 groups × 9 checks = 63 test cases
Run after every security change.
```

## 7. COMMON MISTAKES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Setting parent = Write without child overrides | All children get Write (too much access) | Set explicit None on non-assigned children |
| Forgetting Scenario security | Planners can edit Actuals | Set Actual = Read for planners |
| Not testing cross-dimension effective access | User sees unexpected data | Test with most restrictive dimension |
| Security on members, not groups | Maintenance nightmare | Always use groups |
| Removing user without group cleanup | Ghost permissions | Review groups quarterly |
| Not locking Final version | Users edit approved budget | Set Final = Read for non-admins |

## 8. INTERVIEW QUESTIONS

### Beginner
**Q: How does security inheritance work in EPBCS?**
> Security cascades from parent to children in the hierarchy. If you set "Write" on All_Hotels for Mumbai_Team, ALL children (Mumbai, Delhi, Bangalore, Kolkata, Chennai) inherit "Write" — giving Mumbai_Team access to everyone's data. To restrict: set explicit "None" on non-Mumbai hotels. The child's explicit assignment overrides the parent's inheritance.

### Architect
**Q: A user says they can see Delhi's salary data but they're on the Mumbai team. Diagnose and fix.**
> Check 4 things: (1) **Entity security:** Mumbai_Team should have None on Delhi_Hotel. If parent All_Hotels = Write, they inherit Write on Delhi. Fix: set explicit None on Delhi. (2) **Account security:** Salary_Details should have None for non-HR groups. Check if Mumbai_Team has any access on Salary accounts. (3) **Effective access:** Test the intersection (Delhi, Salary_Details) — both dimensions must restrict. If Entity=None AND Account=None → no access. (4) **Verify:** Log in as a test user in Mumbai_Team. Open the form. Confirm Delhi salary cells show as blank. Log the fix and set up quarterly security reviews.
