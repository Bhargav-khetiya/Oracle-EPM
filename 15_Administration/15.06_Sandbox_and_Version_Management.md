# 15.06 — Sandbox and Version Management: Complete Guide

> **Module:** 15_Administration | **Topic:** Sandboxes, Version Control, What-If Analysis
> **Audience:** Service Administrator / Planner

---

## 1. WHY — What Real-World Problem Does This Solve?

**The problem:** The CFO wants to model "What if we build a 6th hotel in Goa?" without affecting the current budget. A planner wants to try a 10% growth scenario without corrupting the 5% scenario. Without sandboxes, any what-if analysis risks contaminating production data.

**The solution:** Sandboxes are **isolated copies** of the application where users can experiment without affecting the base (production) data. Think of them as "branches" in version control.

## 2. WHAT — Sandbox Mechanics

## 3. SANDBOX LIFECYCLE

```
Step 1: CREATE SANDBOX
  Navigator → Sandboxes → Create
  Name: "Aggressive Growth"
  Description: "20% growth scenario for Board presentation"
  
Step 2: SWITCH TO SANDBOX
  User clicks sandbox dropdown → selects "Aggressive Growth"
  Now all forms show sandbox data (isolated from base)
  
Step 3: MODIFY DATA
  User enters data, runs rules — all within the sandbox
  Base data is completely unaffected
  
Step 4: COMPARE (optional)
  Open a form → toggle between Base and Sandbox
  See side-by-side comparison
  
Step 5: DECISION
  ○ PUBLISH → Merge sandbox data back to base (approved scenario)
  ○ DISCARD → Delete the sandbox (rejected scenario)
```

## 4. SANDBOX OPERATIONS

| Operation | Description | Who Can Do It |
|-----------|-------------|---------------|
| **Create** | Create a new sandbox | Service Admin, Power User |
| **Switch** | Change active context to a sandbox | Any assigned user |
| **Edit** | Modify data within the sandbox | Users with Write access |
| **Compare** | Compare sandbox vs base data | Any assigned user |
| **Publish** | Merge sandbox data back to base | Service Admin |
| **Delete** | Remove the sandbox | Creator or Admin |

### Creating a Sandbox

```
Navigator → Sandboxes → Create

Properties:
  Name: Aggressive_Growth_v1
  Description: "20% revenue growth + 6th hotel expansion"
  
  Include:
    ☑ Data (copy current base data to sandbox)
    ☑ Forms (can modify forms in sandbox)
    ☑ Business Rules (can run rules in sandbox)
    
  Assign Users:
    CFO: Read/Write
    Strategy_VP: Read/Write
    Finance_Analyst: Read Only
```

### Publishing a Sandbox

```
Navigator → Sandboxes → Select sandbox → Publish

Publish Options:
  ○ Publish all data (merge everything to base)
  ● Publish selected data (choose specific intersections)
  
  Conflict Resolution:
    If base data changed since sandbox was created:
    ○ Sandbox wins (overwrite base)
    ● Base wins (keep base, skip conflicts)
    ○ Manual resolve (show conflicts)
```

## 5. VERSION MANAGEMENT (Working vs Final)

Separate from sandboxes, the **Version dimension** provides formal version control:

```
Version Dimension:
├── Working    → Active editing version (planners modify this)
├── Final      → Locked/approved version (read-only for planners)
├── Variance   → Working - Final (calculated)
└── Custom_v1  → Additional versions as needed
```

### Version Lock Process

```
Step 1: Planners enter budget data in "Working" version
Step 2: Manager reviews Working data
Step 3: Manager approves → Admin runs "Copy Working to Final"

  DATACOPY "Working" TO "Final";
  
Step 4: Final version is locked (Read-only for planners)
Step 5: Any changes go to Working — Final stays frozen
Step 6: Next cycle → repeat
```

## 6. SANDBOX vs VERSION vs SCENARIO

| Feature | Sandbox | Version | Scenario |
|---------|---------|---------|----------|
| **Purpose** | What-if experimentation | Formal lock/approve cycle | Different planning contexts |
| **Isolation** | Full isolation from base | Same cube, different member | Same cube, different member |
| **Creation** | Admin/Power User creates | Pre-defined in outline | Pre-defined in outline |
| **Data** | Copy of base data | Independent data entry | Independent data entry |
| **Publishing** | Merge back to base | Copy command | No merge concept |
| **Users** | Specific assigned users | All users (based on security) | All users (based on security) |
| **Example** | "What if 20% growth?" | Working → Final lock | Budget vs Forecast vs Actual |

## 7. SHOW ME — Hotel Pvt Ltd

### Sandbox Use Case: Goa Expansion Analysis

```
CFO creates sandbox: "Goa_Expansion_2027"

In the sandbox:
  1. Add member "Goa_Hotel" to Entity dimension
  2. Enter projected revenue: ₹2.5 Cr (Year 1)
  3. Enter projected expenses: ₹2.0 Cr (Year 1)
  4. Run P&L calculation → Net Income = ₹50L
  5. Compare with base: Total company Net Income WITH Goa vs WITHOUT
  
  Base (5 hotels): Net Income = ₹2.35 Cr
  Sandbox (6 hotels): Net Income = ₹2.85 Cr (+₹50L)
  
Decision: Board approves → Publish sandbox → Goa_Hotel becomes permanent
Decision: Board rejects → Delete sandbox → no impact on base
```

### Version Lock Process

```
Budget Cycle Timeline:
  Sep 1:  Open Budget cycle
          → Planners work in "Working" version
          
  Oct 15: Review deadline
          → GMs review Working data on forms
          
  Oct 30: Lock Version 1
          → Admin: DATACOPY "Working" TO "Version_1_Draft"
          → "Version_1_Draft" becomes read-only
          
  Nov 15: After revisions → Lock Final
          → Admin: DATACOPY "Working" TO "Final"
          → "Final" is locked — the approved budget
          
  Dec onward: Working can still be modified for adjustments
              Final stays frozen as the approved baseline
```

## 8. COMMON MISTAKES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Too many active sandboxes | Performance degradation, storage waste | Limit to 3-5 active sandboxes |
| Publishing without review | Wrong data merged to base | Always review before publishing |
| Sandbox open for weeks | Diverges too much from base | Time-limit sandboxes (1-2 weeks) |
| Confusing sandbox with scenario | Wrong tool for the job | Sandbox = temporary experiment. Scenario = permanent planning context |
| Not deleting old sandboxes | Storage fills up | Delete sandboxes after publish/reject |

## 9. INTERVIEW QUESTIONS

### Beginner
**Q: What is a sandbox in EPBCS and when would you use one?**
> A sandbox is an isolated copy of the application where users can experiment with data without affecting the production (base) data. Use when: (1) Modeling what-if scenarios (e.g., "What if we open a new hotel?"). (2) Testing rule changes before applying to production. (3) Running sensitivity analysis (e.g., 5% vs 10% vs 15% growth). After analysis, you either **publish** (merge to base) if approved or **delete** if rejected.

### Architect
**Q: When should you use a sandbox vs a scenario vs a version for modeling?**
> **Scenario (Budget/Forecast/Actual):** For permanent, recurring planning contexts. Every company needs these. They live in the dimension outline permanently. **Version (Working/Final):** For formal lock/approve cycles within a scenario. Working = editable, Final = approved/frozen. Use DATACOPY to lock. **Sandbox:** For temporary, ad-hoc experimentation that may or may not be kept. "What if we acquire a competitor?" or "What if currency drops 20%?" — create a sandbox, experiment, then publish or discard. Rule of thumb: If you'll do it every year → Scenario. If you'll do it every month → Version. If you might do it once → Sandbox.
