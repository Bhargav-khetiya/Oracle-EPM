# 15.01 Essbase Caching and Memory Optimization

> **Module:** 15_Performance  
> **Topic:** 01 - Caching and Memory  
> **Target Audience:** Architect  

---

## 1. Learning Objectives
- Differentiate between Index Cache, Data File Cache, and Data Cache.
- Understand how memory is allocated during a calculation.
- Troubleshoot "Out of Memory" errors during data loads.

## 3. Introduction
When an Essbase calculation takes 4 hours, Junior developers blame the script. Architects blame the memory. 
Essbase is a disk-based engine (BSO). Reading and writing to a physical hard drive is the slowest operation in computing. To make Essbase fast, you must force it to hold as much data in RAM (Random Access Memory) as possible. This is called **Caching**.

## 7. Core Concepts: The Three Essbase Caches

### 1. Index Cache (`IndexCache`)
- **What it is:** The index file (`.ind`) is the map. It tells Essbase exactly where block #500 is located on the hard drive.
- **The Rule:** The Index Cache MUST be large enough to hold the *entire* physical index file in RAM. If the index file is 50MB, the Index Cache must be set to at least 50MB.
- **The Consequence:** If the index cache is too small, Essbase has to page the map from the hard drive to find the blocks. Performance will degrade by up to 80%.

### 2. Data File Cache (`DataFileCache`)
- **What it is:** A buffer for reading and writing compressed blocks to the `.pag` files on the hard drive. 
- **The Rule:** Only relevant for direct I/O operations (like massive data loads or exports). 

### 3. Data Cache (`DataCache`)
- **What it is:** The uncompressed block memory. When Essbase calculates a block, it must pull it from the hard drive, uncompress it, calculate the math, compress it, and write it back. The Data Cache is where this uncompressed math happens.
- **The Rule:** Make this as large as you can reasonably afford without starving the operating system.

## 9. Internal Processing: The Calculator Cache (`CalcCache`)
Separate from the standard Essbase caches, the **Calculator Cache** is dynamically allocated when a Business Rule runs.
- **How it works:** If you run `CALC DIM(Entity);`, Essbase will try to pre-load all the required blocks for Entity into the Calculator Cache.
- **The Limit:** By default, it is often set relatively low. If the aggregation requires more blocks than can fit in the cache, Essbase flushes the cache halfway through, writes to disk, and starts again (Thrashing). 
- **Optimization:** Use `SET CACHE HIGH;` at the top of your Business Rules to temporarily command Essbase to allocate maximum memory for that specific script.

## 18. Architect Notes: EPM Cloud Limitations
In the old Hyperion On-Premise days, the Architect manually edited the `essbase.cfg` file to set cache sizes. 
**In Oracle Cloud EPM (EPBCS):**
- You cannot edit `essbase.cfg`. Oracle manages the memory.
- If your application is poorly designed (e.g., massive block sizes, 20 dense dimensions), you will hit Oracle's hardcoded memory limits. The job will simply fail with a memory timeout.
- **Your only defense:** You must optimize the physical outline (Dense/Sparse configuration) to keep Block Sizes between 8KB and 100KB, which allows Oracle's automated caching to function efficiently.

## 25. Interview Questions

### Architect
**Q: You check the application statistics and notice the Index Size is 1 GB, but the Index Cache is only 500 MB. Users are complaining that retrieving data in Smart View is extremely slow. What is the technical mechanism causing the slowness?**
> A: The slowness is caused by **Paging**. Because the Index Cache (RAM) is smaller than the physical Index File, Essbase cannot hold the entire map in memory. When a user requests data, Essbase looks in the RAM cache. If the block address isn't there (a Cache Miss), Essbase must physically read the hard drive to find the address in the index file, then read the hard drive again to get the data block. This double-disk read causes severe latency. In an on-premise environment, you would increase the Index Cache to >1GB. In Cloud EPM, you must restructure the outline to reduce the index size.

## 27. Summary
Memory is speed. The more blocks you can calculate in RAM before writing back to the hard drive, the faster your rules will execute. Protect your block size to protect your memory.
