# Performance Optimization Guide

Optimizing Oracle EPM, specifically the Essbase engine (BSO), is a highly technical architectural skill.

## 1. Block Size and Fragmentation

The foundation of BSO performance is the Data Block.
*   **Ideal Block Size:** Typically between 8 KB and 100 KB. 
    *   If blocks are too small (e.g., < 1 KB), the index becomes massive, and the system wastes time reading millions of tiny blocks. Solution: Make a sparse dimension dense.
    *   If blocks are too massive (e.g., > 1 MB), calculating them requires too much RAM, causing paging and slowdowns. Solution: Make a dense dimension sparse.
*   **Fragmentation:** As data is loaded, cleared, and calculated, Essbase blocks get scattered on the disk, creating empty "holes". This slows down I/O reads.
    *   **Measurement:** Check the "Average Fragmentation Quotient" in the application properties. 
    *   **Solution:** A database restructure (or full export/import) defragments the blocks.

## 2. Restructure Types

Any change to the Dense/Sparse configuration or the Outline triggers a restructure when you refresh the database.

*   **Index Restructure:** Occurs when you add or delete a Sparse member. Essbase only has to rewrite the index (the pointers to the blocks). This is usually very fast.
*   **Dense Restructure:** Occurs when you add, move, or delete a Dense member. Essbase must rewrite *every single data block in the entire database* to accommodate the new shape. This can take hours on massive databases.
    *   *Best Practice:* Try to batch Dense outline changes together and do them during a weekend maintenance window.

## 3. Calculation Tuning (SET Commands)

In Calculation Manager scripts, you can alter the engine's behavior using `SET` commands.

*   `SET CALCPARALLEL n;`: Tells Essbase to use `n` processor threads. Extremely useful for massive aggregations. *Trap: Do not set this higher than the physical cores on the server minus 2.*
*   `SET CACHE HIGH;`: Increases the calculator cache memory, reducing disk I/O.
*   `SET MSG SUMMARY;` vs `SET MSG DETAIL;`: Controls the amount of logging output. Detail provides block-by-block timing, which is great for debugging but terrible for performance if left on in production.
*   `SET UPDATECALC OFF;`: Forces Essbase to calculate every block in the `FIX`, ignoring the "clean/dirty" status. Useful when you *know* you need a full recalculation.
