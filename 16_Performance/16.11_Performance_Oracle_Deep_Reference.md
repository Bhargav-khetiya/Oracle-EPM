## 📌 Pillar 1: Database Design — Complete Tuning Guide

### Block Size Calculator

```
Block Size = (Dense_Dim1_L0) × (Dense_Dim2_L0) × ... × 8 bytes

Optimal Range: 10 KB – 100 KB

< 10 KB  → Too many tiny blocks → index overhead → SLOW retrieval
> 100 KB → Too few huge blocks → wasted space → SLOW calculations
> 1 MB   → CRITICAL → blocks too large → application may hang
```

### Real-World Block Size Examples

| Application | Account(L0) | Period(L0) | Custom(Dense, L0) | Block Size | Status |
|-------------|------------|-----------|-------------------|------------|--------|
| Small Hotel | 100 | 12 | — | 9.4 KB | ⚠️ Slightly small |
| Medium Retail | 300 | 12 | — | 28 KB | ✅ Optimal |
| Large Mfg | 500 | 12 | — | 47 KB | ✅ Optimal |
| Bad Design | 500 | 12 | 50 (Dense) | 2.3 MB | ❌ WAY too large |
| Fixed Design | 500 | 12 | 50 (Sparse) | 47 KB | ✅ Moved to Sparse |

### Block Count Calculator

```
Max Blocks = Sparse_Dim1(L0) × Sparse_Dim2(L0) × ... 

Too Many Blocks (>500,000):
→ Index file becomes huge
→ Retrieval slows down
→ Consider making a Sparse dim Dense

Too Few Blocks (<100):
→ Blocks might be too large
→ Consider making a Dense dim Sparse
```

### Data Density Analysis

```
Density = (Cells with data) / (Total possible cells) × 100

Dense dimension → should have >30% density
Sparse dimension → typically <10% density

If a "Sparse" dimension has >50% density → consider making it Dense
If a "Dense" dimension has <10% density → consider making it Sparse
```

### 💡 Logic & Purpose
Density is the ratio of populated cells to empty cells inside a physical block. Because Dense dimensions define the shape of the block, every Dense combination exists physically on the hard drive whether it has data or not (`#MISSING`). The architect's goal is to ensure that a block on the hard drive is actually full of data (High Density), rather than being 95% empty space.

### 🌀 Confusion Resolution
> **Misconception:** "I created a 'Projects' dimension. Since a single Entity might work on 5 different projects out of our 100 available projects, the density is 5%. Therefore, Projects should be Dense to keep the block count low."
> **Reality:** A 5% density is extremely sparse! If you make Projects Dense, Essbase will allocate physical hard drive space for all 100 projects inside *every single block*, meaning 95% of your database memory footprint will be empty `#MISSING` data. The 'Projects' dimension MUST be Sparse so that Essbase only creates blocks for the 5 projects that actually have data.

### 😈 Twisted Interview Question
**Question:** An application has the `Entity` dimension set as Sparse. An admin notices that for the 'Sales' department, data exists for all 500 accounts and all 12 months. Since the data is very dense for the 'Sales' department, the admin changes `Entity` to Dense. Performance immediately tanks application-wide. Why?
> **Answer:** You cannot assign Dense/Sparse based on a *single* member's data pattern! While 'Sales' might have data for every account, the 'IT' department likely has zero revenue accounts, and 'HR' has zero manufacturing accounts. By making `Entity` Dense, the admin forced Essbase to build a massive, multi-megabyte block matrix for every single entity. `Entity` is structurally a Sparse dimension in 99% of applications because no single entity utilizes every account.

### 🎯 Hands-On: Database Performance Audit

```
Exercise 1: Block Size Calculation
1. List all Dense dimensions with Level 0 member counts
2. Calculate: Product of all L0 counts × 8 bytes
3. Is result between 10-100 KB?
4. If too large: which dimension should move to Sparse?
5. If too small: which Sparse dimension could move to Dense?
6. Document: "Current block size: __ KB. Recommendation: ___"

Exercise 2: Block Count Analysis
1. List all Sparse dimensions with Level 0 member counts
2. Calculate: Product of all L0 counts = Maximum possible blocks
3. Navigate to Application → Database Statistics → note actual blocks
4. Block density = Actual / Maximum × 100
5. If density < 1%: data is very sparse → design is correct
6. If density > 50%: consider reducing Sparse dimensions
7. Document findings

Exercise 3: Memory Impact Analysis
1. Calculate: Block Size × Actual Block Count = Total Data Volume
2. Is total < 1 GB? (Good for EPBCS)
3. Is total < 4 GB? (Acceptable for EPBCS)
4. Is total > 4 GB? (Consider redesign)
5. Plan: "If we add 200 entities next year, volume becomes __ GB"
```

## 📌 Pillar 2: Calculation Optimization — Complete Guide

### SET Commands — Performance Impact

| Command | Good For | Bad For | Default |
|---------|----------|---------|---------|
| `SET UPDATECALC ON` | Skip clean blocks | First-time full calc | OFF |
| `SET CREATEBLOCKONEQ ON` | Data copy to new intersections | Accidental block creation | OFF |
| `SET AGGMISSG OFF` | Skip missing during aggregation | Correct only if missing = 0 | ON |
| `SET CACHE HIGH` | Complex calculations | Memory-constrained | Default |
| `SET MSG SUMMARY` | Production (less logging) | Debugging | DETAIL |
| `SET MSG DETAIL` | Debugging (full logging) | Production (slow) | DETAIL |
| `SET CALCPARALLEL 4` | Multi-threaded calculation | Single-threaded apps | OFF |
| `SET FRMLBOTTOMUP ON` | Bottom-up formula evaluation | Top-down formulas | OFF |

### Calculation Anti-Patterns (What NOT to Do)

| Anti-Pattern | Problem | Fix |
|-------------|---------|-----|
| `CALC ALL;` | Calculates EVERYTHING | Use targeted FIX + AGG |
| No FIX statement | Processes all sparse combinations | Always FIX on sparse dims |
| FIX on parent members | Processes parents unnecessarily | FIX on @RELATIVE(dim, 0) |
| Cross-dim in inner loop | Each reference = separate block read | Pre-calculate, assign to temp member |
| `SET MSG DETAIL` in prod | Verbose logging = slow | Use SUMMARY in production |
| Multiple small AGG calls | Each AGG scans all blocks | One AGG per dimension |

### Optimization Techniques — Ranked by Impact

| # | Technique | Impact | Effort |
|---|-----------|--------|--------|
| 1 | Narrow FIX scope | 🔴 Very High | Low |
| 2 | SET UPDATECALC ON | 🔴 Very High | Low |
| 3 | Replace CALC ALL with targeted AGG | 🔴 Very High | Medium |
| 4 | SET AGGMISSG OFF | 🟡 High | Low |
| 5 | Minimize cross-dim references | 🟡 High | Medium |
| 6 | Use Dynamic Calc for parents | 🟡 High | Medium |
| 7 | SET CALCPARALLEL | 🟢 Medium | Low |
| 8 | Pre-aggregate in source before load | 🟢 Medium | High |

### 🎯 Hands-On: Calculation Performance Lab

```
Exercise 4: FIX Scope Impact Test
Write a simple rule: "Revenue" = "Units" * "Price"
Test 4 versions (time each in Job Console):

Version 1 (Worst): No FIX
   "Revenue" = "Units" * "Price";

Version 2 (Bad): FIX on Scenario only
   FIX("Budget")
       "Revenue" = "Units" * "Price";
   ENDFIX

Version 3 (Good): FIX on Scenario + Version + Year
   FIX("Budget", "Working", &BudgetYear)
       "Revenue" = "Units" * "Price";
   ENDFIX

Version 4 (Best): Full FIX
   FIX("Budget", "Working", &BudgetYear, @RELATIVE("Entity", 0))
       "Revenue" = "Units" * "Price";
   ENDFIX

Document: "V1: __s, V2: __s, V3: __s, V4: __s"
Expected: V4 is 10-100x faster than V1

Exercise 5: SET Command Impact
Write the same rule with different SET combinations:

Test A: No SET commands → time it
Test B: Add SET UPDATECALC ON → time it
Test C: Add SET AGGMISSG OFF → time it
Test D: Add SET MSG SUMMARY → time it
Test E: All 3 SET commands → time it

Document: Impact of each SET command

Exercise 6: AGG vs CALC DIM
Test 1: AGG("Entity") → time it
Test 2: CALC DIM("Entity") → time it (includes formulas)
Document: When to use AGG (no formulas) vs CALC DIM (with formulas)
```

## 🎓 Interview Questions

**Q: A business rule takes 45 minutes. How do you get it under 5?**
> (1) Check FIX — narrow to L0 entities, specific scenario/version/year. (2) Add SET UPDATECALC ON. (3) Replace CALC ALL with targeted AGG. (4) Check for cross-dim references in loops — pre-calculate. (5) Add SET AGGMISSG OFF. (6) Split into parallel rules if independent. (7) Check block size — too large means slow block I/O.

**Q: What is the optimal block size and why?**
> 10-100 KB. Below 10 KB: too many tiny blocks → index file grows → retrieval slows. Above 100 KB: blocks contain too much data → calculations process unnecessary cells → slow. Above 1 MB: blocks may not fit in cache → severe performance degradation.

**Q: How would you approach a performance audit of an existing EPM application?**
> 3 pillars: (1) Database: Check block size, Dense/Sparse assignment, member counts. (2) Calculations: Check FIX scope, SET commands, rule duration in Job Console. (3) Forms: Check cell count, suppression settings, rules on load. Use Activity Reports for trends. Create a baseline document and compare monthly.
