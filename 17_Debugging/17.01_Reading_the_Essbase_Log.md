# 17.01 Reading the Essbase Log

## 1. Learning Objectives
- Locate the raw Essbase Application log in Oracle Cloud.
- Decipher the cryptic error codes.
- Identify the root cause of failed jobs.

## 3. Introduction
When a Business Rule fails, the user sees a generic pop-up: "The rule failed to execute." This is useless. The user will call you and say, "The system is broken." To find out exactly what broke, you must read the raw Essbase log file.

## 7. Core Concepts: The Log Structure

In Oracle Cloud EPM, the Essbase Application log is accessed via the **Jobs Console**. When a job fails, a hyperlink to a `.txt` log file is generated.

### Anatomy of a Log Entry
A standard log entry looks like this:
`[Tue Oct 24 14:32:10 2024] [FinPlan] [ERROR:1200315] [admin@company.com] [Rule: Calc_Deprec] Error executing formula for [Depreciation] (line 12): division by zero`

**Breaking it down:**
1. **Timestamp:** Exactly when the engine crashed.
2. **Cube:** `[FinPlan]` - The physical database where the rule was running.
3. **Error Code:** `[ERROR:1200315]` - Oracle's internal error dictionary code.
4. **User:** `[admin@company.com]` - Who ran the rule.
5. **The Payload:** `Error executing formula... division by zero`.

## 9. Internal Processing: Common Errors and What They Mean

### 1. The Syntax Error (1200315)
`Error: member [Revnue] not found in database`
- **Cause:** Typo in the script. The developer spelled Revenue wrong. (This should be caught in Calc Manager validation, but sometimes dynamic variables bypass validation).

### 2. The Data Error (1200324)
`Error: division by zero at block [Cost Center 100]`
- **Cause:** The script tried to divide by a `#Missing` or `0` data point.
- **The Fix:** Find Cost Center 100, check the data, and update the script to wrap the division in an `IF("Denominator" <> 0)` statement.

### 3. The Block Explosion Timeout
`Error: Max execution time exceeded` OR `Memory allocation failure`
- **Cause:** The script forced Essbase to calculate millions of empty blocks (Top-Down calculation on Sparse dimensions), running out of RAM or hitting the Cloud 2-hour timeout limit.
- **The Fix:** The script is fundamentally broken. Rewrite the `FIX` statements to be tighter, or remove `SET CREATENONMISSINGBLK ON`.

### 4. The Lock Error (1042017)
`Error: Cannot calculate. Database is locked by another user or process.`
- **Cause:** User A ran a massive script that locked the Entity dimension. While it was running, User B tried to run a different script on the same Entity. Essbase protects the data by locking it during write operations.
- **The Fix:** Wait for User A's job to finish, or kill the blocking job in the Jobs console.

## 18. Architect Notes: The `SET MSG` Command
If a script runs successfully but produces the wrong numbers, there is no error in the log. How do you fix it?
You insert `SET MSG DETAIL;` at the top of the Business Rule.
This commands Essbase to print *everything* it is doing into the log file.
- It will print: `Calculating Block [New York]... 0.05 seconds.`
- It will print: `Calculating Block [Boston]... 0.04 seconds.`
You read the log to see if it actually calculated the blocks you expected it to calculate. If it didn't print `Boston`, then your `FIX` statement is wrong.

## 25. Interview Questions

### Intermediate
**Q: A user complains a rule takes 10 minutes. You check the log and see thousands of lines saying "Warning: Missing block for Member X created." What is happening?**
> A: The script contains a command (likely `SET CREATENONMISSINGBLK ON` or a sparse cross-dimensional target) that is physically forcing Essbase to generate empty data blocks on the hard drive. Block creation is the slowest I/O operation in Essbase. The script must be optimized to only create blocks where data actually exists.

## 27. Summary
The log never lies. Do not guess why a rule failed; open the log file immediately. It will tell you the exact line number and block where the engine crashed.
