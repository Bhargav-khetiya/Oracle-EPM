# Resolving Network Timeouts

A "Timeout" is the most frustrating error for users and administrators. It means the system gave up waiting for a response. Understanding *which* layer timed out is critical.

## 1. The Smart View Timeout (Client-Side)

**Symptom:** A user clicks "Refresh" in Excel. After 3 minutes, Excel throws a pop-up saying "The request timed out." However, when the admin checks the Job Console, the calculation or retrieval is still running successfully on the server.

**The Cause:** Excel/Windows has a built-in HTTP limit (usually 3-5 minutes). Excel gave up waiting, but the Essbase server is still crunching the numbers.

**The Fix (Registry Keys):**
Administrators must push registry key updates to the users' laptops.
*   `ReceiveTimeout`: Increases the time Windows will wait for an HTTP response from the cloud server (e.g., set to 15 minutes).
*   `ServerInfoTimeout`: Increases the ping timeout.
*   *Note:* While you can fix this technically, the *architectural* fix is to optimize the Essbase query or calc script so it doesn't take 15 minutes.

## 2. The Gateway Timeout (504 Error - Server-Side)

**Symptom:** You launch a Business Rule from a Web Form. The form spins for exactly 3 minutes, then throws a Red Error Bar saying "504 Gateway Timeout". 

**The Cause:** The Oracle Cloud load balancers (OHS) have a hardcoded 3-minute limit on synchronous HTTP requests to prevent runaway processes from hanging the web server.

**The Fix:**
*   **Run in Background:** On the Web Form properties, edit the attached Business Rule and check the box **"Run in Background"**. 
*   **Result:** When the user clicks Save, the form immediately returns control to the user. A job is submitted to the Job Console. The user does not stare at a spinning wheel, and the load balancer limit is bypassed because the job is running asynchronously on the Essbase server directly.

## 3. EPM Automate Timeout (Connection Reset)

**Symptom:** An EPM Automate batch script fails with `Connection Reset by Peer` after a 4-hour database refresh.

**The Cause:** EPM Automate holds an HTTP connection open while waiting for the job to finish. If a firewall, proxy server, or ISP blips for even a millisecond during those 4 hours, the connection is severed.

**The Fix:**
*   Move away from synchronous EPM Automate commands for massive jobs.
*   Use the REST API polling method instead. You send the job, get the JobID, disconnect, and then send a tiny `GET` request every 5 minutes to check if it's done. This is immune to 4-hour network drops.
