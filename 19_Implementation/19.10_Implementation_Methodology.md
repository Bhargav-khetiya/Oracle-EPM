## 🏢 Overview

Oracle EPM implementation follows a structured methodology — from requirement gathering through go-live and hypercare. Understanding this lifecycle is critical for consultants, as it defines your daily activities on a project.

---

## 📌 Implementation Lifecycle

```
Phase 1: DISCOVER (2-4 weeks)
├── Requirement gathering
├── Current state assessment
├── Stakeholder interviews
└── Business process documentation

Phase 2: DESIGN (3-6 weeks)
├── Solution architecture
├── Dimension design
├── Form/report design
├── Integration design
└── Security model

Phase 3: BUILD (6-12 weeks)
├── Application creation
├── Metadata loading
├── Form development
├── Business rule development
├── Integration setup
└── Security configuration

Phase 4: TEST (3-6 weeks)
├── Unit testing
├── Integration testing
├── User acceptance testing (UAT)
├── Performance testing
└── Security testing

Phase 5: DEPLOY (1-2 weeks)
├── Production setup
├── Data migration
├── User training
├── Go-live cutover
└── Change management

Phase 6: HYPERCARE (4-8 weeks)
├── Post-go-live support
├── Issue resolution
├── Performance tuning
├── Knowledge transfer
└── Transition to BAU
```

## 📌 Phase 1: Discover

### Requirement Gathering

| Technique | What You Get |
|-----------|-------------|
| **Stakeholder interviews** | Business requirements, pain points |
| **Workshop sessions** | Collaborative requirement refinement |
| **Current state analysis** | Existing reports, spreadsheets, processes |
| **Data analysis** | Source systems, data volumes, quality |

### Key Questions to Ask

| Area | Questions |
|------|-----------|
| **Business Process** | What is your current budgeting process? How long does it take? |
| **Users** | How many users? Roles? Geographies? |
| **Data** | Source systems? Data volume? Frequency of loads? |
| **Dimensions** | Chart of accounts structure? Entity hierarchy? |
| **Reports** | What reports do you need? Board-level? Operational? |
| **Timeline** | When is the next budget cycle? Go-live deadline? |
| **Integration** | ERP system? Data format? API availability? |

### 💡 Logic & Purpose
The Implementation Methodology exists to protect the project from scope creep and structural failure. The **Discover** phase is not just about writing down what the client wants; it's about challenging *why* they do things a certain way. Consultants must translate flawed human processes into optimized system architecture, rather than just paving over the cow paths.

### 🌀 Confusion Resolution
> **Misconception:** "The client gave me a massive Excel workbook with 50 tabs that they currently use for budgeting. My job in the Design phase is to replicate this Excel workbook exactly as EPM web forms so the users don't have to learn a new layout."
> **Reality:** EPM is a multi-dimensional database, NOT a spreadsheet! Replicating an Excel workbook 1-to-1 into EPM forms is the #1 cause of project failure. Excel allows unstructured data entry (typing text next to numbers, custom formulas per cell). EPM requires rigid dimensionality. You must extract the *business logic* from the spreadsheet and redesign it into a centralized, dimensional model, which often means the forms will look entirely different than the legacy Excel file.

### 😈 Twisted Interview Question
**Question:** During the Discover phase, the client insists they need a custom dimension called "Reporting". When you ask what goes in it, they say: "Oh, it holds things like 'Quarter 1', 'Variance to Budget', 'Local Currency', and 'Total Company'." Why must you immediately reject this design, and where do those items actually belong?
> **Answer:** The client is trying to shove multiple different dimensional concepts into a single "junk dimension", treating it like an Excel column. You must reject this because it destroys multi-dimensional calculation logic. 
> - 'Quarter 1' belongs in the **Period** dimension.
> - 'Variance to Budget' belongs in the **Scenario** (or Version) dimension.
> - 'Local Currency' belongs in the **Currency** dimension.
> - 'Total Company' belongs in the **Entity** dimension.

## 📌 Phase 3: Build

### Build Order (Dependencies)

```
1. Application & Cubes → Must exist first
2. Dimensions & Members → Foundation for everything
3. Substitution Variables → Used by forms and rules
4. Smart Lists → Referenced by forms
5. Forms → User interface
6. Business Rules → Calculations
7. Task Lists → User workflows
8. Data Integration → Data flow
9. Security → Access control (last — after testing)
```

### Naming Conventions

| Object | Convention | Example |
|--------|-----------|---------|
| Dimension members | Code + Alias | `100110` / `Rooms Revenue` |
| Forms | `FR_Category_Name` | `FR_Revenue_Input` |
| Business Rules | `BR_Action_Target` | `BR_Calculate_Revenue` |
| Rule Sets | `RS_Process_Name` | `RS_Monthly_Close` |
| Task Lists | `TL_Process_Name` | `TL_Budget_Submission` |
| Data Load Rules | `DL_Source_Target` | `DL_ERP_Actuals` |

## 📌 Phase 4: Test

### Testing Types

| Type | What | Who | When |
|------|------|-----|------|
| **Unit Test** | Individual forms, rules | Developer | During build |
| **Integration Test** | End-to-end data flow | Developer + Analyst | After build |
| **UAT** | Business scenarios | Business users | After integration test |
| **Performance Test** | Load times, calc times | Performance team | Before go-live |
| **Security Test** | Access verification | Security team | Before go-live |

## 🎓 Interview Questions

**Q: Describe the typical EPM implementation lifecycle.**
> A: Discover (requirements) → Design (solution architecture) → Build (development) → Test (UAT) → Deploy (go-live) → Hypercare (post-launch support). Each phase has specific deliverables and sign-offs.

**Q: What is the first thing you do on a new EPM project?**
> A: Requirement gathering — understand the business process, pain points, data sources, reporting needs, user base, and timeline. This feeds into the Business Requirements Document (BRD).

**Q: In what order should you build an EPM application?**
> A: Application → Dimensions → Variables → Smart Lists → Forms → Business Rules → Task Lists → Data Integration → Security. This follows the dependency chain.

**Q: What is hypercare and why is it important?**
> A: Hypercare is the 4-8 week period immediately after go-live where the implementation team provides intensive support. It's critical because this is when real users encounter real issues with real data. Quick resolution builds confidence and adoption.
