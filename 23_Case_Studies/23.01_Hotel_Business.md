You are implementing Oracle EPBCS for a hospitality group.

**Departments:**

**Revenue Streams:**
- Room bookings

## 🏗️ 2. The Application Architecture

To support this business, you built an application with multiple cubes.

### The Financial Planning Cube (FinPlan)
This cube handles the Profit & Loss (P&L) statement.

**Key Dimensions Used:**
- **Entity:** To separate Hotel vs Manufacturing
- **Department:** To track expenses by HR, IT, etc.
- **Account:** To store Revenue and Expense line items.

### The Account Structure (The Chart of Accounts)

The core of the FinPlan cube is the **Account Dimension**. Let's look at how the Hotel Revenue is structured:

```
Net Profit (Dynamic Calc)
├── Income (Dynamic Calc)
│   ├── Hotel Revenue (Dynamic Calc)
│   │   ├── Rooms Revenue (Store)        ← Data Entry: ₹18 Cr
│   │   └── Banquet Revenue (Store)      ← Data Entry: ₹10 Cr
│   │
│   ├── Catering Revenue (Dynamic Calc)
│   │   ├── InFlight Catering (Store)    ← Data Entry: ₹5 Cr
│   │   └── Railway Catering (Store)     ← Data Entry: ₹2 Cr
│   │
│   └── Food Sales Revenue (Dynamic Calc)
│       ├── Online Food Sales (Dynamic Calc)
│       │   ├── Zomato Revenue (Store)   ← Data Entry: ₹1 Cr
│       │   └── Swiggy Revenue (Store)   ← Data Entry: ₹1.5 Cr
│       │
│       └── Offline Food Sales (Dynamic Calc)
│           └── Restaurant DineIn (Store)← Data Entry: ₹3 Cr
│
└── Expense (Dynamic Calc)
    ├── HouseKeeping Expense (Dynamic Calc)
    │   ├── Rooms Housekeeping (Store)   ← Data Entry: ₹2 Cr
    │   └── Banquet Housekeeping (Store) ← Data Entry: ₹1 Cr
    │
    └── Manpower Expenses (Dynamic Calc)
        ├── Salary Expense (Store)       ← Data Entry: ₹8 Cr
        └── Employee Bonus (Store)       ← Data Entry: ₹1 Cr
```

**How the math works automatically:**
1. Someone enters ₹1 Cr for Zomato and ₹1.5 Cr for Swiggy.
2. EPM automatically calculates **Online Food Sales** = ₹2.5 Cr.
3. This rolls up into **Food Sales Revenue**, which rolls into **Income**, which ultimately calculates the **Net Profit**.

## 🛠 3. Driver-Based Planning in Action (Catering)

Instead of manually guessing Catering Revenue, the business uses drivers.

In the **Custom1** dimension, we set up the drivers:
- `Number_of_Meals` (Aggregation: Addition)
- `Selling_Price_Per_Meal` (Aggregation: Never Share)

### The Business Rule (Calculation):
The Technical Consultant writes a Groovy script or Business Rule that says:

```
"Railway Catering Revenue" = "Number_of_Meals" * "Selling_Price_Per_Meal"
```

### The Form View:
A user opens a Planning Form for the Railway Catering department.

| Driver | Jan | Feb | Mar |
|--------|-----|-----|-----|
| Number of Meals | 10,000 | 12,000 | 15,000 |
| Price Per Meal | ₹150 | ₹150 | ₹150 |
| **Railway Catering Rev** | **₹15,00,000** | **₹18,00,000** | **₹22,50,000** |

*The Revenue row is calculated automatically and is read-only.*

### 💡 Logic & Purpose
Driver-based planning eliminates the "black box" budget. If a department head just types in ₹22,50,000 for March, management cannot argue with it. But if they type 15,000 meals at ₹150, management can challenge the volume metric (Why do you expect 15,000 meals when last March we only did 10,000?). 

### 🌀 Confusion Resolution
> **Misconception:** "We should make EVERY revenue and expense line item driver-based to be as accurate as possible."
> **Reality:** Over-engineering driver models is the leading cause of EPM implementation failure. If you try to calculate 'Office Supplies Expense' by driving it off 'Number of Pencils per Employee * Price per Pencil', you will create massive administrative overhead for a $500 variance. Apply drivers ONLY to material items (Revenue, COGS, Salary). Leave minor expenses as direct input.

### 😈 Twisted Interview Question
**Question:** In the table above, the user entered `Price Per Meal` = ₹150 for Jan, Feb, and Mar. What should the Time Balance property on the `Price Per Meal` account be set to, and what happens if the admin accidentally leaves it as the default `Flow`?
> **Answer:** It must be set to `Average` (or `Balance` depending on design), and Data Storage must be `Never Share`. If left as `Flow`, Essbase will sum the price across the months, meaning the Q1 `Price Per Meal` will display as ₹150 + ₹150 + ₹150 = **₹450**! The subsequent Q1 calculation would result in massively inflated revenue because the rate aggregated incorrectly.

## ️ 4. Multi-Currency Example

The Hotel Pvt Ltd also has a branch in New York. 
- India uses **INR**
- NY uses **USD**

### How EPM handles it:
1. The Entity `E10001_NY` is assigned a base currency of `USD`.
2. The Entity `E10001_India` is assigned a base currency of `INR`.
3. In the Account dimension, **Revenue** is set to use the **Average** exchange rate.
4. The admin inputs the exchange rate: `1 USD = ₹83 INR`.

When the CFO runs the global consolidated report in `INR_Reporting` (Reporting Currency):
- India Revenue (₹100 Cr) remains ₹100 Cr.
- NY Revenue ($2 Million) is automatically multiplied by 83 = ₹16.6 Cr.
- Total Group Revenue = **₹116.6 Cr**.

## 🔒 5. Security & Access Control

Different people need different access to the forms and data.

| User | Role | What They See / Do |
|------|------|--------------------|
| **Catering Manager** | Data Entry | Can only see forms for the "Catering" department. Enters meal counts. |
| **HR Manager** | Data Entry | Can only see "Manpower Expenses". Enters salary and bonus data. |
| **Hotel GM** | Reviewer | Can see ALL departments for E10001 (Hotel). Cannot edit, only reviews. |
| **Group CFO** | Viewer | Can see Total Entity (Consolidated). Uses ASO reporting cube for fast dashboards. |
