# ⚡ Cheat Sheet: Essbase Database

> **Quick revision for Essbase concepts**

---

| Concept | Definition |
|---|---|
| **Essbase** | Extended Spreadsheet Database |
| **Cube** | Multi-dimensional data structure |
| **Dimension** | Business category (Account, Entity, Period) |
| **Member** | Item within a dimension (Jan, Revenue) |
| **Dense** | Most combos have data → block interior |
| **Sparse** | Patchy data → determines block count |
| **Block** | Data container = Dense dims crossed |
| **Index** | Lookup table: Sparse combo → block location |

**Storage Options:**

| Type | Write? | Best For |
|---|---|---|
| **BSO** | ✅ Yes | Planning & Budgeting |
| **ASO** | ❌ No | Reporting (read-only) |
| **Hybrid BSO** | ✅ Yes | Modern default (best of both) |

**Block Formulas:**
```
Block Size = Dense1_members × Dense2_members × 8 bytes
Block Count = Only sparse combos WITH data
```

**Hierarchy Terms:**
- Generation = top-down (Root = Gen 1)
- Level = bottom-up (Leaf = Level 0)

---

### 💡 Pro Tip: The Block Size Trap
> **Misconception:** "Our cube is slow, so we should make Period sparse to reduce block size."
> **Reality:** Making Period sparse is the deadliest mistake in Essbase design. Yes, blocks get smaller, but the index balloons exponentially because every month now creates a new block pointer. Essbase has to jump around the disk 12x more to calculate a full year. Account and Period should almost *always* remain Dense.
