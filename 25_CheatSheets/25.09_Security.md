## 🔒 3 Security Layers
1. **Identity Domain** — Who can log in (SSO/IDCS)
2. **Application Roles** — What features they access
3. **Data Access** — What data they see

## 📌 Roles (Highest → Lowest)
| Role | Can Do |
|------|--------|
| Service Administrator | Everything |
| Power User | Create forms, rules, metadata |
| User | Enter data, run assigned rules |
| Viewer | View only |

## 📌 Data Access Permissions
| Permission | Effect |
|-----------|--------|
| **Write** | See + Edit |
| **Read** | See only |
| **None** | Hidden completely |

## ⭐ Best Practices
- ✅ Assign security to GROUPS, not individuals
- ✅ Actual scenario → Read only (never Write)
- ✅ Use None for sensitive entities
- ✅ Test with a test user account
- ❌ Never give everyone Service Admin
- ❌ Never assign security individually

## 📌 Approval Workflow
```
Preparer → Submit → Reviewer → Approve/Reject → Approver → Final
```

## 📌 Quick Commands
```bash

```

### 💡 Pro Tip: Cell-Level Security Overrides
> **Misconception:** A user with Service Admin access can always see all data, no matter what.
> **Reality:** Even a Service Admin can be blocked by **Cell-Level Security**. While dimension-level access control applies to regular users and power users, a Cell-Level Security rule defined in the web interface specifically overrides *everything*, including Admin rights. If you ever wonder why an Admin can't see a specific cell, check Cell-Level Security rules.
