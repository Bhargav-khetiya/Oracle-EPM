## Navigation

## Overview
By default, Essbase allows data entry at *any* level-0 combination. If you have `Hardware` (Product) and `HR` (Cost Center), Essbase will happily let a user budget $10,000 of Hardware revenue to the HR department. 
This destroys accounting accuracy. **Valid Intersections** act as a physical firewall, blocking data entry at nonsensical combinations before it ever reaches the database.

## The Configuration Screen

### 1. Anchor Dimension
This is the "Driver" of the rule.
- **Example:** `Entity` (Cost Center). 
- If you select `HR Department`, the rule will pivot off this selection.

### 2. Valid Intersections (Target Dimensions)
This is what is allowed/denied based on the Anchor.
- **Example:** `Account`.
- You define that if `Entity` = `HR Department`, then `Account` is ONLY allowed to be `Salaries` and `Benefits`.

### 3. "Unselected Members are Valid" (The Danger Checkbox)
This is the most critical checkbox on the screen.
- **If Checked (Default):** If you build a rule for the `HR Department`, but you do NOT build a rule for the `IT Department`, the system assumes `IT Department` is allowed to use ALL accounts. This is a "Whitelist" approach.
- **If Unchecked:** The system flips to a "Blacklist" (Strict) approach. If you don't explicitly define a rule for the `IT Department`, the IT Department is completely blocked from all accounts.
- **Architect Note:** Always leave this **Checked** unless you want to spend the next 6 months writing thousands of rules for every single intersection in the company.

## How it Reflects in the UI (Forms and Smart View)

1. **Web Forms:** If a user opens a Web Form that has `HR` in the POV, the rows for `Revenue` accounts will physically disappear, or turn gray and read-only. The system protects the user from making a mistake.
2. **Smart View:** If a user uses a Flex Form and types `$500` into `HR -> Revenue` and clicks Submit, Smart View will reject the submission and highlight the cell in red, throwing a Valid Intersection violation error.

## Advanced Architecture: Security Overlaps

**The Scenario:** 
- User A is in Group "Sales Managers". They have WRITE access to the `Sales Department` in the Security Access Control screen.
- The Architect builds a Valid Intersection saying `Sales Department` CANNOT use the `Depreciation` account.

**The Result:** Valid Intersections **OVERRIDE** Security. Even though the user has global write access to the Sales Department, the Valid Intersection firewall will block them from touching Depreciation. Valid Intersections are evaluated *after* security grants.

## 25. Interview Questions

### Architect
**Q: You build a Valid Intersection rule stating that `Entity: Europe` can only use `Currency: EUR`. You open a Web Form, but `Europe -> USD` is still white and allowing data entry. Why?**
> A: Valid Intersections only evaluate Base (Level-0) members unless specifically configured otherwise. If `Europe` is a Parent member, the rule will not cascade down to `France` and `Germany` automatically unless you selected `ILvl0Descendants(Europe)` in the Anchor definition. Furthermore, Valid Intersections must be explicitly enabled on the specific Web Form's properties screen ("Suppress Invalid Data" checkbox). If that checkbox is off, the form ignores the firewall.
