# Jobs and Scheduling Deep Dive (Job Types)

While we covered the Job Console screens previously, understanding the specific *types* of jobs you can run and schedule is critical for administration.

## 1. Job Types Available

In EPM Cloud, a "Job" is a distinct process type. The most critical job types are:

*   **Rules:** Executes a Calculation Manager business rule.
*   **Rulesets:** Executes a sequential or parallel chain of business rules.
*   **Data Maps / Smart Push:** Pushes data from one cube to another (e.g., from an input BSO cube to a reporting ASO cube) while executing necessary mapping translations.
*   **Import Data / Export Data:** Moves data in and out of the application via flat files. 
    *   *Note:* This is the native Planning import, not Data Management/Data Integration. It is faster but has zero transformation capabilities.
*   **Import Metadata / Export Metadata:** Updates the dimension outlines (e.g., adding new Cost Centers).
*   **Refresh Database:** A required job after any Metadata import. It restructures the Essbase cube to reflect the new dimensions.
*   **Clear Cube:** Wipes specific data regions based on an MDX or calculation script definition. Highly useful before a massive data load to ensure no orphaned data remains.

## 2. Scheduling Constraints

When using the native EPM Cloud scheduler, there are limits compared to enterprise orchestration tools:

*   **Sequential Chains:** If you schedule a Metadata Import, a Database Refresh, a Data Load, and a Ruleset to run nightly, the native scheduler cannot link them together dynamically based on success/failure codes. If the Metadata Import fails, the Database Refresh will still try to run on its scheduled time.
*   **EPM Automate Solution:** To solve this, architects wrap these job types in an `EPM Automate` batch script. EPM Automate can check the return code of the metadata import and abort the entire script if it fails, preventing corruption.

## 3. The "Invalid Data" Trap during Jobs

A common issue when scheduling Rules or Data Maps is job failure due to invalid data (e.g., a rule dividing by zero or encountering a locked block). 
*   **Job Console Check:** If a Ruleset job says "Completed with Errors", you must open the job details. Often, 99% of the rule executed perfectly, but one specific entity failed.
*   **Groovy Vetoes:** If a scheduled job triggers a Groovy rule that contains a `veto()` validation, the entire job will halt and log the veto message in the console.
