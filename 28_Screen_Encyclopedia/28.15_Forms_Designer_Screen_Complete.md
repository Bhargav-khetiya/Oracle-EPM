# 📝 28.15 — Forms Designer Screen: Complete Encyclopedia

> **Source:** Oracle® Fusion Cloud EPM Administering Planning (Aug 2026), Chapter 25 — Administering Forms
> **Navigation:** Home → Navigator (≡) → Create and Manage → Forms → Click (Create) or click existing form
> **Audience:** Service Administrator / Power User

---

## 1. WHY — What Problem Do Forms Solve?

**The problem:** EPBCS stores data in a multidimensional Essbase cube. Users can't directly interact with a raw cube — they need structured input screens that show exactly the right rows, columns, and context for data entry.

**The solution:** Forms are **customized data entry grids** that present specific intersections of the multidimensional cube. Each form controls which dimensions are on rows, columns, page axis, and POV — creating a tailored input experience for each business process.

**Consultant importance:** Form design is THE most critical EPBCS skill. 80% of an implementation's user experience depends on how well forms are designed. This is the screen you'll spend the most time on.

---

## 2. WHAT — Plain English Definition

A Form is a **tabular grid interface** that:
- Shows specific **dimension members** as rows and columns
- Lets users **enter data** into the cells at dimension intersections
- Can run **business rules** on save (Calculate Form, allocation rules)
- Can be configured as **read-only** (for reporting)
- Can embed **Smart Lists** (dropdowns), **action menus** (right-click), and **validation rules**
- Supports **ad hoc analysis** in Smart View

**Two Types of Forms:**
| Type | Available Since | Key Difference |
|------|----------------|----------------|
| **Forms 1.0** | Original | Legacy — de-supported from Oct 2025 for NEW forms |
| **Forms 2.0** | Recent | Current standard — better performance, new features |

### 5.2 Axis Rules (What Goes Where)

| Axis | Purpose | Dimension Restrictions |
|------|---------|----------------------|
| **Rows** | Data rows (account lines, products, etc.) | Must have at least 1 dimension |
| **Columns** | Typically time periods | Cannot assign: Account, Scenario, Version |
| **Page** | User selection dropdown (changes visible data) | Typically: Entity, Scenario |
| **POV** | Fixed context (user sets once, stays constant) | Any dimension |

> ⚠️ **Critical Rule:** A dimension can appear on ONLY ONE axis. Cannot put the same dimension on both rows and columns.

### 5.3 Member Selection (for each dimension on an axis)

When you click the edit icon next to a dimension on an axis, the **Member Selector** opens:

| Selection Method | Description |
|-----------------|-------------|
| **Members** | Pick individual members from the hierarchy tree |
| **User Variables** | Use a user variable — each user sees their own value |
| **Substitution Variables** | Use a system-wide variable (e.g., &CurrMonth) |
| **Attributes** | Filter by attribute values (e.g., Hotel_Type = "5-Star") |
| **UDAs** | Filter by User Defined Attributes |

**Member Functions (Function Selector):**

| Function | Example | Result |
|----------|---------|--------|
| **Children of** | Children(Total Revenue) | All direct children of Total Revenue |
| **IChildren of** | IChildren(Total Revenue) | Total Revenue + its direct children |
| **Descendants of** | Descendants(Total Revenue) | All descendants at all levels |
| **IDescendants of** | IDescendants(Total Revenue) | Total Revenue + all descendants |
| **DescendantsPF** | DescendantsPF(Total Revenue) | Descendants with Parent First ordering |
| **Siblings of** | Siblings(Room Revenue) | All siblings of Room Revenue |
| **Level 0 of** | Level0(Total Revenue) | Only leaf-level descendants |
| **Ancestors of** | Ancestors(Room Revenue) | All ancestors up to root |
| **Parent of** | Parent(Room Revenue) | The parent of Room Revenue |

**Exclude Members:**
| Mode | Behavior |
|------|----------|
| **Exclude** | Excludes by member ID — only that specific base/shared member |
| **Exclude All** | Excludes by name — excludes base + all shared instances |

## 6. SEGMENT PROPERTIES — EVERY OPTION

Click a row number (1, 2) or column letter (A, B) to access segment properties:

| Property | Options | Description |
|----------|---------|-------------|
| **Apply to all rows/columns** | ☑/☐ | If checked, same properties apply to all row/column segments |
| **Hide** | ☑/☐ | Conceals the segment (used for calculation-only rows/columns) |
| **Read-only** | ☑/☐ | Makes the segment non-editable (for comparison data) |
| **Show separator** | ☑/☐ | Bold border before the segment for visual distinction |
| **Suppress hierarchy** | ☑/☐ | Removes hierarchical indentation |
| **Suppress missing data** | ☑/☐ | Hides rows/columns with all #MISSING values |
| **Suppress invalid Scenario/Time Periods** | ☑/☐ | Hides periods outside the scenario's date range |
| **Column width** | Default/Small(50px)/Medium(100px)/Large(300px)/Size-to-Fit/Custom | Width of data columns |
| **Row height** | Default/Medium/Size-to-Fit/Custom | Height of data rows |
| **Enable drop-down for dimensions** | ☑/☐ | Allows runtime member selection dropdown on row dimensions |

## 7. GRID PROPERTIES — EVERY OPTION

| Property | Options | Description |
|----------|---------|-------------|
| **Suppress missing blocks** | ☑/☐ | Essbase-level suppression of empty blocks (may skip Dynamic Calc members) |
| **Suppress missing data** | ☑/☐ | Hide rows/columns with all #MISSING |
| **Suppress invalid data** | ☑/☐ | Hide read-only cells with invalid data |
| **Use Database Suppression** | ☑/☐ | Essbase-level row suppression — reduces data returned, improves performance but suppresses formula-calculated-to-zero rows |
| **Default row height** | Medium/Size-to-Fit/Custom(px) | Height for all rows unless overridden |
| **Default column width** | Small/Medium/Large/Size-to-Fit/Custom(px) | Width for all columns unless overridden |
| **Suppress invalid Scenario/Time Periods** | ☑/☐ | Grid-level: hides periods outside scenario range |
| **Global Assumptions Form** | ☑/☐ | Marks form for global assumptions transfer (test→prod migration) |
| **Enable Autosave** | ☑/☐ | Auto-saves changes when navigating between cells, enables Ctrl+Z undo |
| **Run Form Calc on Autosave** | ☑/☐ | If Autosave is on, recalculates dynamic members and shows green background |
| **Suppress Missing also Suppresses Zero** | ☑/☐ | Treats zeros same as #MISSING for suppression |
| **Remove Form Suppressions in Ad Hoc** | ☑/☐ | Allows Smart View ad hoc analysis despite suppression settings |
| **Enable Calc On the Fly** | ☑/☐ | In Forms 2.0: hover shows member formula; calculates without submitting |
| **Pivot Rows and Columns after load** | ☑/☐ | Transposes grid on load (also available at runtime via Actions menu) |

## 13. FORMULA ROWS AND COLUMNS

You can add calculated rows and columns to forms that compute values at the form level (NOT stored in Essbase):

```
Formula Row Example:
Row "Variance" = Row "Budget" - Row "Actual"
Row "Variance %" = (Row "Budget" - Row "Actual") / Row "Budget" * 100
```

**Operators Available:**
| Operator | Symbol | Example |
|----------|--------|---------|
| Addition | + | Row1 + Row2 |
| Subtraction | - | Row1 - Row2 |
| Multiplication | * | Row1 * Row2 |
| Division | / | Row1 / Row2 |
| Percentage | % | Row1 / Row2 * 100 |

**Key Facts about Formula Rows/Columns:**
- NOT stored in Essbase — calculated at display time only
- Cannot be referenced by business rules
- Can reference other formula rows/columns
- Appear with a calculation icon in the form

## 15. DO's AND DON'Ts

### ✅ DO
- **DO** always test forms after creation by opening them as a test user
- **DO** use Suppress Missing Data to keep forms clean
- **DO** attach Calculate Form rule to "Run on Save" for proper aggregation
- **DO** use User Variables on the Page axis so each user sees their own entity
- **DO** use "Suppress invalid Scenario/Time Periods" to auto-hide out-of-range periods
- **DO** set meaningful form descriptions/instructions for business users
- **DO** use formula rows for variance calculations (avoids storing computed data in Essbase)

### ❌ DON'T
- **DON'T** create new Forms 1.0 — they are de-supported since Oct 2025
- **DON'T** put more than ~20 columns on a form (performance degrades)
- **DON'T** use "Suppress missing blocks" without testing — it can suppress valid Dynamic Calc members
- **DON'T** use "Use Database Suppression" if you have formula columns that might result in #MISSING
- **DON'T** put Label Only parents before their first child — prevents saving data in the first child
- **DON'T** use attributes on axes (row/column) — creates cross-dimensional references that degrade performance. Use attribute filters instead.
- **DON'T** forget to assign access permissions — without them, no users can see the form

## 16. INTERVIEW QUESTIONS

### Beginner
**Q: You created a new form but users say they can't see it in the Data card listing. What are two possible causes?**
> **A:** (1) No access permissions have been assigned — go to the form's Access Permissions tab and grant Read or Write access to the appropriate users/groups. (2) The form's Display Property "Hide form" is checked — this hides the form from the Data listing (it's only accessible via dashboards, action menus, or navigation flows). Uncheck "Hide form" to make it visible.

### Intermediate
**Q: A user enters 100 in a parent member cell (Total Revenue) but after saving, the children (Room Revenue, F&B Revenue) don't show the spread values. Why?**
> **A:** The form's Display Properties does not have "Enable Grid Spread" checked. Without this, parent cell entry is blocked or doesn't spread. Enable Grid Spread allows users to enter at parent level and have the value distributed to children based on the spreading pattern (even/proportional). Also check: (1) The parent member's Data Storage — if it's Dynamic Calc, it's read-only and won't accept input. (2) The Version type — if it's "Bottom Up", data can only be entered at level 0 (leaf members), not at parent levels.

### Architect
**Q: A Hotel Pvt Ltd client has 5 hotel entities, 250 accounts, 12 months + quarters + year total. The form takes 45 seconds to load. What are 5 things you would check to improve performance?**
> **A:** 
> (1) **Enable "Suppress missing data" and "Suppress missing blocks"** — reduces data volume by not fetching empty intersections. Test with both to ensure Dynamic Calc members still appear.
> (2) **Enable "Use Database Suppression"** — pushes suppression to Essbase level, reducing data transferred. But verify formula columns don't get suppressed.
> (3) **Reduce the number of members** — if 250 accounts are on rows but only 50 have data for the selected entity, consider using Level0(account_parent) instead of Descendants to eliminate unnecessary hierarchy display.
> (4) **Check dimension order and block size** — if Account and Period are dense with too many stored upper-level members, block size is too large. Set upper-level members to Dynamic Calc in the dimension editor.
> (5) **Remove attribute dimensions from axes** — if attributes are on rows/columns, they create cross-dimensional references. Use attribute filtering (form option) instead.
> Bonus: (6) Check if "Enable Enhanced Calc in Forms" is on at the application level — this evaluates formulas during data entry and can slow rendering. (7) Consider splitting the form into entity-specific forms with fewer rows.
