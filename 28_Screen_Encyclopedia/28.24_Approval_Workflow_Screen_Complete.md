## 1. WHY — What Problem Does the Approval Workflow Solve?

**The problem:** In a budgeting process, multiple people enter data at different organizational levels. The GM enters hotel data, the Regional Director reviews, the CFO approves. Without a formal workflow, data gets changed after review, there's no audit trail of approvals, and the process is chaotic.

**The solution:** The Approval Workflow creates a **formal promote-review-approve chain** tied to the Entity dimension hierarchy. Data flows up the hierarchy — each level must be approved before rolling up.

---

## 2. WHAT — Plain English Definition

The Approval Workflow (also called Planning Unit / Approvals) is a **bottom-up or top-down data promotion system** that:
- Uses the **Entity dimension** as the primary approval dimension
- Assigns **owners** and **reviewers** to each entity level
- Controls data **locking** — once approved, data can't be changed
- Provides **status tracking** at every level
- Supports **three budget templates**: Bottom-Up, Distribute, Free-Form

```
Approval Flow: Bottom-Up (Most Common)

  Data Entry at level 0 (leaf entities)
     ↓
  Mumbai_Hotel GM enters data → Promotes → 
     ↓
  Western_Region Director reviews → Approves/Promotes →
     ↓
  National_Controller reviews → Approves/Signs Off →
     ↓
  CFO reviews → Signs Off (LOCKED — no more changes)
```

## 5. THREE APPROVAL TEMPLATES

| Template | Description | Data Flow | Ownership Flow |
|----------|-------------|-----------|---------------|
| **Bottom Up** | Data entered at leaf level, rolled up | Level 0 → Parent → Top | Level 0 owners → Parent reviewers → Top approver |
| **Distribute** | Targets set at top, distributed down | Top → Children → Level 0 | Top owner distributes → Level 0 enters actuals → Roll back up |
| **Free Form** | Flexible — users select next owner | Any direction | Users pick the next owner from dropdown |

## 6. APPROVAL STATUS LIFECYCLE

```
┌─────────────┐    ┌─────────────┐    ┌──────────────┐    ┌──────────┐
│  Not Started │ →  │  1st Pass    │ →  │  Under Review│ →  │ Approved │
│  (Not begun) │    │  (Data entry)│    │  (Reviewing) │    │ (Signed) │
└─────────────┘    └─────────────┘    └──────────────┘    └──────────┘
                         ↓                    ↓
                    ┌──────────┐        ┌──────────────┐
                    │ Promoted │ →      │   Rejected   │
                    │ (Sent up)│        │ (Sent back)  │
                    └──────────┘        └──────────────┘
```

| Status | Meaning |
|--------|---------|
| **Not Started** | Budget cycle hasn't begun for this entity |
| **1st Pass** | Owner is entering/editing data (first round) |
| **Under Review** | Reviewer is checking the data |
| **Approved** | All reviewers approved; data is locked |
| **Signed Off** | Final sign-off — completely locked |
| **Promoted** | Owner promoted data to the next reviewer |
| **Rejected** | Reviewer sent data back to owner for corrections |

### Actions Available

| Action | Who Can Do It | What It Does |
|--------|--------------|--------------|
| **Start** | Admin | Initiates the budget cycle |
| **Promote** | Owner | Sends data up to the next reviewer |
| **Reject** | Reviewer | Sends data back to the owner |
| **Approve** | Reviewer | Approves data and sends to next level |
| **Sign Off** | Top-level approver | Final lock — no more changes |
| **Force Promote** | Admin | Overrides and pushes forward |
| **Freeze** | Admin | Prevents changes without promoting |
| **Exclude** | Admin | Removes entity from the approval process |

## 8. HOTEL PVT LTD EXAMPLE

### Budget Approval Flow for FY2027

```
Timeline: October 2026

Step 1: Admin starts budget cycle
  → Navigator → Workflow → Manage Approvals
  → Scenario: Budget, Version: Working → Go
  → Click "Start" → All entities move to "1st Pass"

Step 2: Hotel GMs enter budget data (weeks 1-2)
  → Mumbai GM logs in → Opens Revenue Entry form → Enters data
  → Runs Calculate P&L rule → Reviews P&L dashboard
  → Goes to Approvals → Clicks "Promote" for Mumbai_Hotel
  → Mumbai status changes to "Under Review"
  → Ownership passes to Western Region Director

Step 3: Regional Directors review (week 3)
  → Western Dir logs in → Reviews Mumbai P&L form
  → If OK → Clicks "Approve" → Mumbai moves to "Approved"
  → If issues → Clicks "Reject" → Mumbai goes back to "1st Pass"
    → Mumbai GM gets notification → Makes corrections → Re-promotes

Step 4: CFO final review (week 4)
  → CFO reviews All Hotels consolidated P&L
  → All entities must be "Approved" before CFO can Sign Off
  → CFO clicks "Sign Off" → All data is LOCKED
  → Budget is final for FY2027
```

## 9. INTERVIEW QUESTIONS

### Beginner
**Q: What happens to data when an approval unit is "Signed Off"?**
> **A:** The data becomes completely LOCKED. No user — including the Service Administrator — can modify data at that intersection (Scenario/Version/Entity combination) unless the admin explicitly reopens the approval unit. This ensures budget integrity after final approval. To make changes after sign-off, the admin must go to Manage Approvals → select the entity → Change Status back to a lower level.

### Intermediate
**Q: A Regional Director rejected Mumbai_Hotel's budget with the comment "Revenue targets too low." What happens next?**
> **A:** (1) Mumbai_Hotel's status changes from "Under Review" back to "1st Pass." (2) Ownership returns to the Mumbai GM. (3) The Mumbai GM receives an email notification (if notifications are enabled). (4) The rejection comment is stored in the approval unit's annotations/details. (5) The Mumbai GM opens the revenue form, makes corrections, and clicks "Promote" again. (6) Mumbai_Hotel moves back to "Under Review" with the Regional Director as owner. (7) This cycle repeats until the Director approves.

### Architect
**Q: Hotel Pvt Ltd has 5 hotels in 3 regions (West: Mumbai+Bangalore, North: Delhi, East: Kolkata+Chennai). Design the approval hierarchy.**
> **A:**
> ```
> All Hotels (Owner: CFO, Reviewer: VP Finance)
> ├── Western Region (Owner: West Director)
> │   ├── Mumbai_Hotel (Owner: Mumbai GM)
> │   └── Bangalore_Hotel (Owner: Bangalore GM)
> ├── Northern Region (Owner: North Director)
> │   └── Delhi_Hotel (Owner: Delhi GM)
> └── Eastern Region (Owner: East Director)
>     ├── Kolkata_Hotel (Owner: Kolkata GM)
>     └── Chennai_Hotel (Owner: Chennai GM)
> ```
> Template: Bottom Up. GMs enter data → promote to Regional Directors → Directors review and approve → CFO does final sign-off. The key design decision: whether to use a "Secondary dimension" (e.g., Department) for finer granularity. If F&B and Rooms have separate budget owners within each hotel, add Department as the secondary dimension in the Extended Approval Flow. This allows department heads to submit individually before the hotel GM consolidates.
