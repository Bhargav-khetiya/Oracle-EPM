# Account Dimension Properties Exhaustive Guide

The Account dimension is typically the most complex dimension in any Oracle EPM application. It governs how data behaves over time, how it aggregates, and how it is formatted.

## 1. Time Balance Properties

Time Balance dictates how a parent time period (e.g., Q1) aggregates the data of its children (Jan, Feb, Mar) for a specific account.

| Property | Behavior | Use Case |
| :--- | :--- | :--- |
| **Flow (Addition)** | Adds the children (Jan + Feb + Mar = Q1). | Revenue, Expenses, Units Sold. |
| **First** | Takes the value of the first child (Jan = Q1). | Opening Headcount, Beginning Inventory. |
| **Last** | Takes the value of the last child (Mar = Q1). | Ending Balance, Closing Headcount. |
| **Average** | Averages the children ((Jan+Feb+Mar)/3). | Average Price, Average Exchange Rate. |
| **Fill** | Fills empty parent periods with child data (rarely used outside specific reporting apps). | Legacy reporting requirements. |

### Deep Dive: Time Balance Skip Properties
When using First, Last, or Average, you must define how to handle `#MISSING` (null) or zero data.
*   **None:** Does not skip missing or zero values. If Mar is `#MISSING`, a `Last` Time Balance will return `#MISSING` for Q1.
*   **Missing:** Skips null values. If Mar is missing, a `Last` Time Balance looks at Feb.
*   **Zero:** Skips zeros.
*   **Missing and Zero:** Skips both.

> [!WARNING] 
> **The Two-Pass Trap with Time Balance:** If an account has a Time Balance of `Average` and is also marked as `Two-Pass`, Essbase will calculate the average *first* based on the children, and then the Two-Pass formula will overwrite that average at the parent level. Always ensure Time Balance and Member Formulas don't conflict.

## 2. Data Storage Properties (ASO vs BSO)

Data storage properties dictate how Essbase handles the member's data in memory. The behavior changes significantly between Block Storage (BSO) and Aggregate Storage (ASO) cubes.

### Block Storage (BSO)
*   **Store:** Data is saved to the disk. Used for base-level input accounts.
*   **Dynamic Calc:** Data is calculated on the fly when a user queries it. It is never saved to disk. Used for ratios, variances, and upper-level summations to save space.
*   **Dynamic Calc and Store:** Calculated on the fly the *first* time it's queried, then saved to disk for faster subsequent retrievals. Rarely recommended due to unpredictable lock states.
*   **Shared:** A pointer to another member in an alternate hierarchy. It does not store data itself but displays the data of the base member.

### Aggregate Storage (ASO)
*   **Addition (+), Subtraction (-):** In ASO, storage is primarily defined by the consolidation operator. ASO does not use "Dynamic Calc" for standard rollups; the engine aggregates everything dynamically by design.
*   **Formula (MDX):** If an ASO member has a custom calculation (e.g., a ratio), you must use an MDX formula, not Essbase calc script syntax.

## 3. Exchange Rate Types

For multi-currency applications, the Account dimension dictates which exchange rate to use during the currency translation process.

*   **Average:** Multiplies the local data by the Average Rate for the period (e.g., P&L accounts like Revenue).
*   **Ending:** Multiplies by the Ending Rate for the period (e.g., Balance Sheet accounts like Cash or Assets).
*   **Historical:** Multiplies by a specific historical rate tied to a transaction date (e.g., Equity).

## 4. Profitability and Cost Management (PCMCS) Specifics
As referenced in the HPCM Administration guide, some properties are specific to profitability models:
*   **Driver Basis:** Defines if an account is used as a driver for allocations.
*   **Allocation Type:** Can dictate if the account behaves as an Expense (source) or a Revenue (target) in the model.
