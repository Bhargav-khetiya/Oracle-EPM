# Essbase Calculation Commands Deep Dive

This document provides an exhaustive reference of core Essbase calculation commands used within Calculation Manager and Essbase scripts. 

## 1. Block Context and Scope: `FIX` ... `ENDFIX`

The `FIX` statement is the most critical command in Essbase. It defines the scope (the slice of the database) on which the calculation operates. 

### Deep Dive: Syntax & Behavior
```essbase
FIX (Member_List)
   /* Calculation Logic */
ENDFIX
```

*   **Member List Rules:** You can include specific member names, member set functions (e.g., `@DESCENDANTS("Market")`), or UDA/Attribute functions.
*   **Intersection Logic:** Essbase evaluates the cross-dimensional intersection of all members in the `FIX`. If you `FIX` on "Actual" and "FY23", the script only calculates data blocks where Scenario = Actual AND Year = FY23.
*   **Empty FIX:** What happens if the `FIX` evaluates to zero members? The script compiles, but during execution, Essbase bypasses the entire `FIX` block. This is a common silent failure.

### Notable Behaviors & Performance Traps
*   **Nested FIXes:** You can nest `FIX` statements. The inner `FIX` inherits the outer `FIX`. However, you *cannot* redefine a dimension in an inner `FIX` that was already fixed in the outer `FIX`. This will cause a syntax error (Error: Dimension [X] is already fixed).
*   **Dense vs. Sparse FIX:** Fixing on Dense dimensions behaves differently than fixing on Sparse dimensions. 
    *   **Sparse FIX:** Limits the number of blocks brought into memory. This is highly efficient. Always try to `FIX` on Sparse dimensions as much as possible.
    *   **Dense FIX:** Brings the *entire block* into memory, but only updates the specific Dense cells. It does not reduce the number of blocks processed.

### Example: Dynamic FIX with User Variables
```essbase
/* Using a Calculation Manager runtime prompt in a FIX */
FIX ( {rtp_Scenario}, {rtp_Version}, {rtp_Year}, "Working", @RELATIVE("Entity", 0) )
    "Local_Currency" = "USD_Input" * "FX_Rate";
ENDFIX
```

## 2. Conditional Logic: `IF` ... `ENDIF`

The `IF` command allows block-level conditional logic.

### Deep Dive: Syntax & Behavior
```essbase
"Target_Member" (
    IF (Condition)
        /* Logic */
    ELSEIF (Condition)
        /* Logic */
    ELSE
        /* Logic */
    ENDIF;
)
```

*   **Member Block Requirement:** An `IF` statement *must* be enclosed within a member formula block (associated with a specific member, usually Dense). You cannot have a standalone `IF` statement floating in the script.
*   **Condition Operators:** Standard operators apply: `==`, `!=`, `>`, `<`, `>=`, `<=`, `AND`, `OR`, `NOT`.
*   **Cross-Dimensional Operators (`->`):** Very common in `IF` statements to check a condition in a different slice. 
    *   Example: `IF ("Sales" -> "Jan" > 100)`

### Notable Behaviors & Performance Traps
*   **IF on Sparse:** Using `IF` on Sparse dimensions forces Essbase to evaluate the condition block by block. If the condition is rarely met, Essbase still brings the block into memory to check.
*   **Top-Down vs. Bottom-Up:** By default, Essbase calculates bottom-up (only calculating blocks that exist). If you use complex cross-dimensional `IF` statements, it may force top-down calculation, which is drastically slower because Essbase has to check every potential block combination.
*   **@ISMBR vs ==:** Use `@ISMBR("MemberName")` to check the current context in a dimension, rather than trying to evaluate a string.

### Example: Allocation with IF
```essbase
"Admin_Alloc" (
    IF (@ISMBR("Headquarters") AND "Total_Revenue" > 0)
        "Admin_Alloc" = "Corporate_Expenses" * ("Total_Revenue" / "Total_Revenue"->"Total_Geography");
    ENDIF;
)
```

## 3. Calculation and Aggregation: `CALC DIM` and `AGG`

These commands roll up data along the hierarchies.

### `CALC DIM` vs `AGG`

| Feature | `CALC DIM` | `AGG` |
| :--- | :--- | :--- |
| **Supported Dimensions** | Sparse and Dense | **Sparse ONLY** |
| **Formulas** | Executes all member formulas in the hierarchy during rollup | Ignores member formulas; only performs addition (+) based on consolidation operators |
| **Speed** | Slower (evaluates formulas) | Much faster (straight math) |

### Deep Dive: Syntax
```essbase
CALC DIM ("Product", "Market");
AGG ("Entity", "Project");
```

### Notable Behaviors & Performance Traps
*   **Two-Pass Calculation:** If you have dynamic calc or two-pass members, `CALC DIM` will evaluate them during the batch process, whereas `AGG` will bypass them (which is usually desired for dynamic members anyway, as they calculate on retrieval).
*   **Order of Operations:** The order in which you list dimensions in `CALC DIM` or `AGG` matters significantly for performance. 
    *   **Best Practice:** Always aggregate dimensions in order from the *smallest* (fewest members) to the *largest* (most members), or based on the hourglass shape of your outline.
*   **Fixing around AGG:** You should always `FIX` on the specific scenario/version/year you are aggregating to avoid recalculating the entire database.

### Example: Standard Rollup Script
```essbase
/* Clear existing upper-level data before aggregation to prevent doubling */
FIX ("Actual", "FY23", "Final")
    CLEARBLOCK UPPER;
    
    /* Aggregate specific sparse dimensions */
    AGG ("Entity", "Product", "Market");
ENDFIX
```

## 4. Cross-Dimensional Operator (`->`)

While not a command per se, the cross-dim operator is foundational.

### Deep Dive: Behavior
The `->` operator points to a specific data intersection, overriding the current `FIX` context for that specific operand.

```essbase
"Current_Month_Sales" = "Sales" -> "Jan";
```

### Notable Behaviors
*   **Missing Intersections:** If the right side of a cross-dim expression is `#MISSING` (null), the result is `#MISSING`.
*   **Performance:** Extensive use of cross-dims on the *left side* of an equation (assigning data to a cross-dim) is known as "cross-dimming to a target." This is notoriously slow because Essbase has to create blocks dynamically (block creation).
    *   *Avoid:* `"Sales" -> "Actual" = 100;` 
    *   *Prefer:* `FIX("Actual") "Sales" = 100; ENDFIX`
