# SECTION 1: MEMBER FORMULA FUNDAMENTALS

---

## 1.1 What is a Member Formula?

A Member Formula is an Essbase calculation expression **attached directly to a member in the dimension outline**. It defines how that member's value is calculated.

```
Member: "Gross_Margin_Pct" (Account Dimension)
  Data Storage: Dynamic Calc
  Formula:
    IF("Revenue" <> 0 AND "Revenue" <> #Missing)
        "Gross_Margin" / "Revenue" * 100;
    ELSE
        #Missing;
    ENDIF;
```

## 1.2 When Member Formulas Execute

| Data Storage | When Formula Executes | Result |
|-------------|----------------------|--------|
| **Dynamic Calc** | Every time the member is queried (form open, report) | Calculated on-the-fly, NOT stored |
| **Dynamic Calc and Store** | On first query, then stored for future reads | Calculated once, stored until cleared |
| **Store** | During CALC DIM or CALC ALL | Pre-calculated and stored in block |

```
Dynamic Calc (most common for member formulas):
  User opens form → Essbase evaluates formula → returns result → discards
  User opens form again → Essbase evaluates formula again → returns result
  → ALWAYS fresh, NEVER stale
  → But: computational overhead on EVERY retrieval

Store (less common):
  Admin runs CALC DIM("Account") → formula evaluates → result stored in block
  User opens form → reads stored value → instant
  → Can be STALE if underlying data changed since last CALC DIM
```

## 1.3 Where to Define Member Formulas

```
Path: Navigator → Dimensions → [Select Dimension] → 
      [Select Member] → Properties → Formula field

Steps:
  1. Open Dimension Editor
  2. Navigate to the member (e.g., "Gross_Margin_Pct")
  3. Click the member to open properties
  4. Find the "Formula" field
  5. Type the formula
  6. Click "Validate" (checks syntax)
  7. Click "Save"
  8. Run "Refresh Database" (applies formula to Essbase outline)
```

## 1.4 Key Differences from Business Rules

| Feature | Member Formula | Business Rule (Calc Script) |
|---------|---------------|---------------------------|
| **Location** | Embedded in member metadata | Separate object in Calc Manager |
| **Trigger** | Auto (Dynamic Calc) or CALC DIM (Store) | Manual or form-triggered |
| **FIX Statement** | ❌ NOT allowed | ✅ Full support |
| **DATACOPY** | ❌ NOT allowed | ✅ Full support |
| **Runtime Prompts** | ❌ NOT available | ✅ Full support |
| **SET Commands** | ❌ NOT allowed | ✅ Full support |
| **Scope** | Applies to ONE member across ALL intersections | Can target any intersection |
| **IF/ELSE** | ✅ Supported | ✅ Supported |
| **Cross-Dim (`->`)** | ✅ Supported (but performance-critical) | ✅ Supported |
| **@Functions** | ✅ Most supported | ✅ All supported |
| **Maintenance** | Part of metadata — requires Refresh DB | Independent — deploy from Calc Manager |

# SECTION 2: SYNTAX RULES

---

## 2.1 Basic Syntax

```essbase
/* Every formula must end with semicolons */
"Revenue" - "Expense";

/* IF/ELSE must use ENDIF with semicolon */
IF(condition)
    expression;
ELSE
    expression;
ENDIF;

/* Member names MUST be quoted if they contain special characters or spaces */
"100110"       /* ✅ Quoted — numeric name */
"Net Income"   /* ✅ Quoted — contains space */
Revenue        /* ⚠️ Works but risky — always quote */
"Revenue"      /* ✅ Best practice — always quote */
```

## 2.2 Operators

| Operator | Meaning | Example |
|----------|---------|---------|
| `+` | Addition | `"Revenue" + "Other_Income"` |
| `-` | Subtraction | `"Revenue" - "COGS"` |
| `*` | Multiplication | `"Units" * "Price"` |
| `/` | Division | `"Net_Income" / "Revenue"` |
| `%` | Percentage | Less common in formulas |
| `==` | Equal to | `IF("Status" == 1)` |
| `<>` or `!=` | Not equal | `IF("Revenue" <> 0)` |
| `>` | Greater than | `IF("Revenue" > 100000)` |
| `<` | Less than | `IF("Margin" < 0)` |
| `>=` | Greater or equal | `IF("Revenue" >= 50000)` |
| `<=` | Less or equal | `IF("Expense" <= "Budget")` |
| `AND` | Logical AND | `IF("Rev" > 0 AND "Rev" <> #Missing)` |
| `OR` | Logical OR | `IF("Status" == 1 OR "Status" == 2)` |
| `NOT` | Logical NOT | `IF(NOT @ISMBR("Q1"))` |

## 2.3 Special Values

| Value | Meaning | Usage |
|-------|---------|-------|
| `#Missing` | No data (null) | `IF("Revenue" <> #Missing)` |
| `#MISSING` | Same as above (case insensitive) | Same |
| `0` | Zero value | `IF("Revenue" == 0)` |

## 2.4 Critical Syntax Pitfalls

```essbase
/* ❌ WRONG: Missing semicolon */
"Revenue" - "Expense"

/* ✅ CORRECT: Semicolons required */
"Revenue" - "Expense";

/* ❌ WRONG: Assignment with = in member formula (different from calc scripts) */
"Net_Income" = "Revenue" - "Expense";

/* ✅ CORRECT: Member formula IS the expression — no assignment needed */
"Revenue" - "Expense";
/* The formula DEFINES the member's value — no "member = " prefix */

/* ❌ WRONG: FIX inside member formula */
FIX("Budget")
    "Revenue" - "Expense";
ENDFIX

/* ✅ CORRECT: No FIX allowed — formula applies to ALL intersections */
"Revenue" - "Expense";
/* This runs for EVERY intersection the member exists in */

/* ❌ WRONG: Using DATACOPY */
DATACOPY "Actual" TO "Budget";
/* DATACOPY is a calc script command — not available in member formulas */
```

# SECTION 3: DATA STORAGE AND MEMBER FORMULAS

---

## 3.1 Dynamic Calc Members with Formulas

```
Most common combination: Dynamic Calc + Member Formula

Member: Gross_Margin
  Data Storage: Dynamic Calc
  Formula: "Revenue" - "COGS";

Behavior:
  → Gross_Margin cell does NOT exist in the data block
  → When queried: formula fires, reads Revenue and COGS from block, computes result
  → Result returned to user but NOT stored
  → Block size is SMALLER because Gross_Margin doesn't occupy space
```

## 3.2 Store Members with Formulas

```
Less common: Store + Member Formula

Member: Allocated_Overhead
  Data Storage: Store
  Formula: "Total_Overhead" * "Allocation_Pct" / 100;

Behavior:
  → Allocated_Overhead cell EXISTS in the data block
  → Formula does NOT auto-execute on query
  → Formula executes ONLY when admin runs CALC DIM("Account")
  → After CALC DIM: result is stored in the block
  → Subsequent queries read the stored value (fast)
  → Value becomes STALE if Total_Overhead or Allocation_Pct change
```

## 3.3 Choosing Dynamic Calc vs Store for Formula Members

```
Use DYNAMIC CALC when:
  → Formula is simple (A - B, A / B * 100)
  → Users need ALWAYS-FRESH values
  → You want to reduce block size
  → The formula doesn't use expensive cross-dim references

Use STORE when:
  → Formula is extremely complex or slow
  → Cross-dimensional references are needed
  → Values are queried very frequently
  → You can schedule regular CALC DIM to keep values fresh
  → The formula result is used by other members' formulas
```

---

## 4.1 Mathematical Functions in Member Formulas

| Function | Purpose | Example |
|----------|---------|---------|
| `@ABS(x)` | Absolute value | `@ABS("Variance")` |
| `@ROUND(x, n)` | Round to n decimals | `@ROUND("Margin_Pct", 2)` |
| `@TRUNCATE(x, n)` | Truncate to n decimals | `@TRUNCATE("Rate", 4)` |
| `@POWER(x, n)` | Exponentiation | `@POWER(1.05, "Years")` |
| `@MOD(x, y)` | Modulus | `@MOD("Month_Number", 3)` |
| `@INT(x)` | Integer part | `@INT("FTE")` |
| `@REMAINDER(x, y)` | Remainder | Same as @MOD |
| `@LOG(x)` | Natural log | `@LOG("Growth_Factor")` |
| `@EXP(x)` | e^x | `@EXP("Rate")` |
| `@MIN(a, b)` | Minimum of two values | `@MIN("Revenue", "Budget_Rev")` |
| `@MAX(a, b)` | Maximum of two values | `@MAX("Expense", 0)` |

## 4.2 Member Navigation Functions

| Function | Purpose | Example |
|----------|---------|---------|
| `@PRIOR("Dim")` | Previous sibling | `"Revenue" -> @PRIOR("Period")` |
| `@NEXT("Dim")` | Next sibling | `"Revenue" -> @NEXT("Period")` |
| `@CURRMBR("Dim")` | Current member being processed | Used in conditional logic |
| `@PARENTVAL("Dim")` | Value from parent | `@PARENTVAL("Entity")` |
| `@ANCESTVAL("Dim", n)` | Value from ancestor at gen n | `@ANCESTVAL("Account", 1)` |
| `@SUM(range)` | Sum across a range | `@SUM("Jan":"Jun")` |
| `@AVG(range)` | Average across a range | `@AVG(@CHILDREN("Revenue"))` |
| `@COUNT(range)` | Count non-missing | `@COUNT(@CHILDREN("Q1"))` |

## 4.3 Boolean/Conditional Functions

| Function | Purpose | Example |
|----------|---------|---------|
| `@ISMBR("X")` | TRUE if current member = X | `IF(@ISMBR("Jan"))` |
| `@ISANCEST("X")` | TRUE if ancestor of X | `IF(@ISANCEST("Revenue"))` |
| `@ISDESC("X")` | TRUE if descendant of X | `IF(@ISDESC("All Entities"))` |
| `@ISLEV("Dim", n)` | TRUE if at level n | `IF(@ISLEV("Account", 0))` |
| `@ISUDA("Dim", "tag")` | TRUE if has UDA | `IF(@ISUDA("Account", "Taxable"))` |

# SECTION 5: PATTERN — MARGIN AND RATIO CALCULATIONS

---

## 5.1 Gross Margin Percentage

```essbase
/* Member: Gross_Margin_Pct (Dynamic Calc) */
IF("Revenue" <> 0 AND "Revenue" <> #Missing)
    ("Revenue" - "COGS") / "Revenue" * 100;
ELSE
    #Missing;
ENDIF;

/* Line-by-line explanation:
   Line 1: Guard against division by zero — check Revenue is non-zero and not empty
   Line 2: (Revenue - COGS) = Gross Margin, divided by Revenue, times 100 = percentage
   Line 3-4: If Revenue is 0 or missing, show #Missing instead of error
*/
```

## 5.2 Net Margin Percentage

```essbase
/* Member: Net_Margin_Pct (Dynamic Calc) */

ELSE
    #Missing;
ENDIF;
```

## 5.3 Operating Expense Ratio

```essbase
/* Member: OpEx_Ratio (Dynamic Calc) */

    #Missing;

```

## 5.4 Revenue Per Available Room (RevPAR)

# SECTION 6: PATTERN — VARIANCE CALCULATIONS

---

## 6.1 Budget Variance Amount

```essbase
/* Member: Revenue_Var_Amt (Dynamic Calc) */
"Revenue" -> "Actual" - "Revenue" -> "Budget";

/* Cross-dim reference: reads Revenue from both Actual and Budget scenarios
   Result: Positive = actual exceeded budget (favorable for revenue)
   Result: Negative = actual fell short of budget (unfavorable) */
```

## 6.2 Budget Variance Percentage

```essbase
/* Member: Revenue_Var_Pct (Dynamic Calc, Two-Pass) */
IF("Revenue" -> "Budget" <> 0 AND "Revenue" -> "Budget" <> #Missing)
    ("Revenue" -> "Actual" - "Revenue" -> "Budget") / 
    @ABS("Revenue" -> "Budget") * 100;
ELSE
    #Missing;
ENDIF;

/* Uses @ABS to ensure correct sign regardless of negative budget values */
```

## 6.3 Full Variance Formula (Expense-Aware)

```essbase
/* Member: Variance_Pct (Dynamic Calc, Two-Pass) */
/* Handles both Revenue (non-expense) and Expense members correctly */
IF("Revenue" -> "Budget" <> 0 AND "Revenue" -> "Budget" <> #Missing)
    IF(@ISUDA("Account", "Expense_Type"))
        /* For expenses: negative variance = favorable (spent less than budget) */
        ("Revenue" -> "Budget" - "Revenue" -> "Actual") / 
        @ABS("Revenue" -> "Budget") * 100;
    ELSE
        /* For revenue: positive variance = favorable (earned more than budget) */
        ("Revenue" -> "Actual" - "Revenue" -> "Budget") / 
        @ABS("Revenue" -> "Budget") * 100;
    ENDIF
ELSE
    #Missing;
ENDIF;
```

## 8.3 Month-over-Month Growth Percentage

```essbase
/* Member: Revenue_MoM_Pct (Dynamic Calc) */
IF("Revenue" -> @PRIOR("Period") <> 0 AND "Revenue" -> @PRIOR("Period") <> #Missing)
    ("Revenue" - "Revenue" -> @PRIOR("Period")) / 
    @ABS("Revenue" -> @PRIOR("Period")) * 100;
```

## 8.4 Year-over-Year Growth


## 8.5 CAGR (Compound Annual Growth Rate)

```essbase
/* Member: Revenue_CAGR (Dynamic Calc, Two-Pass) */
/* CAGR over the period range defined by Year members */
IF("Revenue" -> "FY23" <> 0 AND "Revenue" -> "FY23" <> #Missing 
   AND "Revenue" > 0)
    (@POWER("Revenue" / "Revenue" -> "FY23", 1 / 3) - 1) * 100;
    /* 3-year CAGR from FY23 to FY26 */
ELSE
    #Missing;
ENDIF;
```

# SECTION 9: PATTERN — CUMULATIVE AND YTD

---

## 9.1 YTD Revenue (Cumulative Sum)

```essbase
/* Member: Revenue_YTD (Dynamic Calc) */
IF(@ISMBR("Jan"))
    "Revenue";
ELSEIF(@ISMBR("Feb"))
    "Revenue" -> "Jan" + "Revenue";
ELSEIF(@ISMBR("Mar"))
    "Revenue" -> "Jan" + "Revenue" -> "Feb" + "Revenue";
ELSE
    /* For other months, use @SUM for efficiency */
    @SUMRANGE("Revenue", @MEMBERAT("Period", 1), @CURRMBR("Period"));
ENDIF;

/* Alternative using @SUM with explicit range */
/* Note: @SUMRANGE is more elegant but syntax varies */
```

## 9.2 Running Average

```essbase
/* Member: Revenue_Running_Avg (Dynamic Calc) */
IF(@ISMBR("Jan"))
    "Revenue";
ELSEIF(@ISMBR("Feb"))
    ("Revenue" -> "Jan" + "Revenue") / 2;
ELSEIF(@ISMBR("Mar"))
    ("Revenue" -> "Jan" + "Revenue" -> "Feb" + "Revenue") / 3;
ENDIF;
/* Continue for each month... or use @AVG with range */
```

```essbase

    1;  /* Smart List: 1 = "On Target" */
```


```essbase

    1.10;  /* Q2: High season (110%) */
ELSEIF(@ISMBR("Jul") OR @ISMBR("Aug") OR @ISMBR("Sep"))
    1.20;  /* Q3: Peak season (120%) */
ELSE
    0.95;  /* Q4: Moderate (95%) */
ENDIF;
```

## 10.4 IF with UDA

```essbase

IF(@ISUDA("Account", "Taxable"))
    "Revenue" * "Tax_Rate" / 100;
ELSEIF(@ISUDA("Account", "Tax_Exempt"))

ELSE
    #Missing;
ENDIF;
```

# SECTION 14: TWO-PASS CALCULATIONS

---

## 14.1 What is Two-Pass?

Two-Pass is a member property that forces Essbase to calculate the member in a **second pass** after all other Dynamic Calc members have been evaluated.

## 14.2 When You Need Two-Pass

```
Problem:
  Revenue % of Total = Revenue / Total Revenue * 100
  
  Both "Revenue" and "Total Revenue" are Dynamic Calc.
  If Essbase calculates "Revenue % of Total" BEFORE "Total Revenue" is ready:
    → Total Revenue = #Missing (not yet calculated)
    → Revenue % of Total = Revenue / #Missing = #Missing ← WRONG!

Solution:
  Tag "Revenue % of Total" as TWO-PASS:
  
  First Pass: Calculate Revenue, Total Revenue (and all other Dynamic Calcs)
  Second Pass: Calculate Revenue % of Total (now Total Revenue is available)
```

## 14.3 Examples Requiring Two-Pass

```essbase
/* Member: Revenue_Pct_of_Total (Dynamic Calc, TWO-PASS) */
IF("Revenue" -> "All Entities" <> 0 AND "Revenue" -> "All Entities" <> #Missing)
    "Revenue" / "Revenue" -> "All Entities" * 100;
ELSE
    #Missing;
ENDIF;

/* This formula references "Revenue" at the "All Entities" parent level.
   "All Entities" Revenue is itself a Dynamic Calc (sum of children).
   Two-Pass ensures All Entities is calculated BEFORE this % formula runs. */
```

```essbase
/* Member: Entity_Revenue_Share (Dynamic Calc, TWO-PASS) */
/* Percentage of entity's revenue compared to group total */
IF("Revenue" -> "Hotel Group" <> 0)
    "Revenue" / "Revenue" -> "Hotel Group" * 100;
ELSE
    #Missing;
ENDIF;

/* "Hotel Group" revenue is Dynamic Calc (sum of all hotels).
   TWO-PASS needed so Hotel Group is calculated first. */
```

## 14.4 Two-Pass Rules

| Rule | Detail |
|------|--------|
| Only on Dense dimension members | Two-Pass works on Account members (typical Dense dim) |
| Only on Dynamic Calc members | Store members don't need Two-Pass |
| Adds calculation overhead | Second pass = extra processing time |
| Use sparingly | Only when formula depends on other Dynamic Calc results |

# SECTION 15: PERFORMANCE IMPLICATIONS

---

## 15.1 Performance Impact of Member Formulas

| Formula Type | Performance Impact | Why |
|-------------|-------------------|-----|
| Simple arithmetic (A + B) | ✅ Minimal | In-block calculation, no extra I/O |
| Cross-dim within same block | ⚠️ Moderate | Requires lookup within block |
| Cross-dim to different block | ❌ Heavy | Must load another block from disk |
| @PRIOR / @NEXT | ⚠️ Moderate | Must navigate to sibling cell |
| Complex nested IF/ELSE | ⚠️ Moderate | Conditional evaluation overhead |
| @SUM with wide range | ❌ Heavy | Must scan many cells |

## 15.2 Performance Best Practices

```
✅ DO:
  - Use Dynamic Calc for simple formulas (reduces block size)
  - Always check for #Missing and zero before division
  - Keep formulas short and direct
  - Use consolidation operators (+, -) instead of formulas for simple sums

❌ DON'T:
  - Use cross-dim (`->`) to different sparse intersections in Dynamic Calc formulas
    → Each query causes additional block loads
  - Chain multiple cross-dim references:
    "Revenue" -> "Actual" -> "Hotel India" -> "Jan" → loads 3+ blocks!
  - Put complex formulas on members displayed on frequently-opened forms
  - Use Dynamic Calc for members that are targets of business rule assignments
    (Dynamic Calc members cannot receive data — they compute it)
```

## 15.3 When to Convert Dynamic Calc to Stored + Business Rule

```
CONVERT when:
  → Formula uses 3+ cross-dim references (too many block loads per query)
  → Formula is on a member visible on a high-traffic form (100+ users)
  → Form retrieval time exceeds 5 seconds due to Dynamic Calc overhead
  → The source data rarely changes (schedule CALC DIM daily)

KEEP as Dynamic Calc when:
  → Formula is simple (A - B, A / B * 100)
  → No cross-dim references
  → Freshness is critical (values must always be current)
  → Block size reduction is important
```

# SECTION 16: DEBUGGING MEMBER FORMULAS

---

## 16.1 Common Errors

| Error | Cause | Fix |
|-------|-------|-----|
| "Syntax error" | Missing semicolon, unmatched quotes | Add `;` at end, check all `"` pairs |
| "#Missing everywhere" | IF condition always fails | Check condition logic; add ELSE clause |
| "Division by zero" | Denominator is 0 or #Missing | Add IF guard: `IF(denom <> 0 AND denom <> #Missing)` |
| "Wrong result" | Operator precedence | Use parentheses: `(A - B) / C * 100` not `A - B / C * 100` |
| "No data after Refresh DB" | Formula on Store member, CALC DIM not run | Run CALC DIM("Account") after Refresh DB |
| "#Missing in parent period" | Formula doesn't account for time aggregation | Dynamic Calc parents aggregate formula results automatically |

## 16.2 Testing a Member Formula

```
Step 1: Set formula on the member
Step 2: Refresh Database
Step 3: Open a form showing the member
Step 4: Check one specific intersection manually:
  
  Expected: Revenue = ₹18Cr, COGS = ₹10Cr
  Formula: Gross Margin = Revenue - COGS = ₹8Cr
  
  If form shows #Missing:
    → Is Revenue or COGS #Missing? (check)
    → Is the formula validated? (check Dimension Editor)
    → Was Refresh DB run? (check)

Step 5: Check a parent period (Q1):
  Jan GM = ₹8Cr, Feb GM = ₹9Cr, Mar GM = ₹7Cr
  Q1 GM should = ₹24Cr (if Time Balance = Flow)
  
  If Q1 shows wrong value:
    → Check Time Balance property on the Account
    → Check if formula handles parent periods correctly
```

# SECTION 17: MEMBER FORMULA VS BUSINESS RULE — DECISION MATRIX

---

## 17.1 Use Member Formula When

| Criterion | Example |
|-----------|---------|
| **Inherent mathematical relationship** | Margin % = Margin / Revenue |
| **Should ALWAYS calculate the same way** | Net Income = Revenue - Expense |
| **Applies to ALL intersections equally** | Occupancy Rate = Sold / Available |
| **Simple formula (no FIX needed)** | RevPAR = Revenue / Rooms Available |
| **Real-time accuracy needed** | Dynamic Calc for always-fresh values |
| **KPI or ratio** | ROI, Current Ratio, Debt/Equity |

## 17.2 Use Business Rule When

| Criterion | Example |
|-----------|---------|
| **Different logic for different intersections** | India: 15% growth, USA: 8% growth |
| **Needs FIX statement** | Only calculate for Budget, Working, FY26 |
| **Batch operation** | Copy Actuals to Budget for all entities |
| **Runtime Prompts needed** | User selects entity and growth rate |
| **Data movement** | DATACOPY from one scenario to another |
| **Aggregation** | AGG("Entity") to create parent blocks |
| **Complex multi-step logic** | Clear → Copy → Calculate → Aggregate |
| **SET commands needed** | SET CREATEBLOCKONEQ, SET LOCKBLOCK |

# SECTION 19: INTERVIEW QUESTIONS

---

**Q1: What is the difference between a Member Formula and a Business Rule?**
> Member formula is embedded in the dimension outline, executes automatically (Dynamic Calc) or during CALC DIM (Store), applies to one member across all intersections, and cannot use FIX/DATACOPY/RTPs. Business rule is a separate Calc Manager object, runs on-demand or on form save, can target specific intersections with FIX, and supports all Essbase commands.

**Q2: Can a member formula contain a FIX statement?**
> No. FIX is not allowed in member formulas. The formula applies to ALL intersections the member exists in. Use IF/ELSE with @ISMBR or @ISUDA for conditional logic instead.

**Q3: What is Two-Pass and when is it needed?**
> Two-Pass forces a Dynamic Calc member to calculate in a second pass after all other Dynamic Calcs complete. It's needed when a formula references another Dynamic Calc member (e.g., Revenue % of Total needs Total Revenue calculated first).

**Q4: How does Dynamic Calc affect block size?**
> Dynamic Calc members do NOT occupy cells in the data block. This reduces block size, saving memory and disk. A block only contains cells for Stored members. Dynamic Calc is ideal for parent members and KPIs.

**Q5: Why should you always check for #Missing and 0 before division?**
> Division by #Missing or 0 causes errors or #Missing results. The standard guard is: `IF("denominator" <> 0 AND "denominator" <> #Missing)`. Without this, forms will show #Missing for calculated ratios whenever the denominator lacks data.

**Q6: Write a member formula for Gross Margin % that handles edge cases.**
```essbase
IF("Revenue" <> 0 AND "Revenue" <> #Missing AND "COGS" <> #Missing)
    @ROUND(("Revenue" - "COGS") / "Revenue" * 100, 2);
ELSE
    #Missing;
ENDIF;
```

## 📝 Summary

| Concept | Key Takeaway |
|---------|-------------|
| **Member Formula** | Calculation attached to a member in the outline |
| **Dynamic Calc** | Formula fires on every query — always fresh, not stored |
| **Store** | Formula fires during CALC DIM — pre-computed, stored |
| **No FIX** | FIX, DATACOPY, RTPs, SET commands NOT allowed |
| **Cross-Dim** | Supported but expensive — each `->` loads a block |
| **Two-Pass** | Second calculation pass for formulas depending on other Dynamic Calcs |
| **Always Guard Division** | `IF(denom <> 0 AND denom <> #Missing)` |
| **Consolidation Operators** | Use `+` `-` `~` for simple rollups instead of formulas |
| **Performance** | Simple formulas = fine. Cross-dim in Dynamic Calc = expensive |
| **Use For** | Inherent math relationships, KPIs, ratios |
| **Don't Use For** | Batch operations, data movement, conditional by intersection |
