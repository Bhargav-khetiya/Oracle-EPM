### Q1: The Dynamic Calc and Store Trap
**Question:**
"A junior consultant sets several upper-level expense summary members to `Dynamic Calc and Store` in a Hybrid BSO Planning application, believing it gives the benefit of dynamic calculation while speeding up repeat queries. What actually happens in Modern Cloud EPM, and why is this property considered an anti-pattern or prohibited?"

**Consultant Model Answer:**
> "`Dynamic Calc and Store` is an obsolete property from early on-premises Essbase that is strictly an **anti-pattern** and largely deprecated in modern Oracle Cloud EPM:
>
> 1. **Underlying Behavior:** When a cell marked `Dynamic Calc and Store` is first retrieved, Essbase calculates it dynamically and writes the calculated result into the physical data block on disk.
> 2. **The Invalidation Disaster:** The moment any child or driver cell is modified, the stored parent cell becomes **dirty (stale)**. However, Essbase does not automatically clear the stored cell. If a subsequent retrieval occurs before a full recalculation, Essbase may return the stale stored number instead of recalculating, leading to data inaccuracy.
> 3. **Hybrid BSO Incompatibility:** In Modern Hybrid BSO, sparse aggregations are computed in sub-milliseconds in memory using the ASO dynamic vector engine. Setting `Dynamic Calc and Store` forces Essbase to write blocks to disk, defeating the entire zero-block footprint of Hybrid BSO and triggering unnecessary disk I/O and block locking.
>
> **Best Practice:** In Modern Hybrid BSO, use **`Dynamic Calc (~)`**. Never use `Dynamic Calc and Store`."

### Q2: Time Balance Property with Skip Options
**Question:**
"An Account member `Headcount_Ending` has Time Balance set to `LAST`, and Skip set to `SKIP MISSING`. In a quarterly report, the values are: Jan = 100, Feb = 120, Mar = `#Missing`. What does Q1 display? What if Skip was set to `NONE`?"

**Consultant Model Answer:**
> "The Time Balance property controls how balance-sheet and flow metrics aggregate across the Time dimension:
>
> 1. **With `SKIP MISSING`:**
>    - When evaluating the end of Q1, Essbase inspects March. Seeing March is `#Missing`, it steps backward in time to the most recent non-missing period in the quarter, which is February.
>    - **Result:** Q1 displays **`120`**.
>
> 2. **With `NONE` (Do Not Skip):**
>    - Essbase strictly inspects the final period of the quarter (March). Because March is `#Missing`, Essbase does not step back.
>    - **Result:** Q1 displays **`#Missing`**.
>
> **Production Insight:** For inventory and headcount ending balances, `SKIP MISSING` is mandatory to prevent quarterly and annual totals from wiping out if the current month's closing data load is delayed."

### Q3: Time Balance: Flow vs Balance and Expense Reporting
**Question:**
"How does the `Variance Reporting` property (`Expense` vs `Non-Expense`) interact with calculation formulas and variance reporting in Planning?"

**Consultant Model Answer:**
> "`Variance Reporting` dictates how Essbase evaluates differences between Actual and Budget:
> 
> - **Non-Expense (Revenue, Assets):** Favorable variance is when Actual > Budget.
>   $$\text{Variance} = \text{Actual} - \text{Budget}$$
> - **Expense (Cost of Goods Sold, Operating Expenses):** Favorable variance is when Actual < Budget (spending less is good).
>   $$\text{Variance} = \text{Budget} - \text{Actual}$$
>
> **The Production Impact:**
> In Planning web forms and Financial Reporting (FR / Management Reporting), variance columns respect this property automatically when using built-in variance calculations. If an expense account is misconfigured as `Non-Expense`, positive budget variances (overspending) display in green/positive instead of red/negative, misleading executive leadership."

### Q4: The Single-Child Implied Share Security Leak
**Question:**
"A user has `WRITE` access to `Entity_Total` and `READ-ONLY` access to `Entity_US`. `Entity_US` is the only child under `Entity_Total`. Can the user submit data to `Entity_Total` and change the data in `Entity_US`? How does Essbase handle this?"

**Consultant Model Answer:**
> "In a Classic BSO cube where `Entity_Total` is stored, Essbase automatically converts `Entity_Total` into an **Implied Share** pointer to `Entity_US`.
>
> When the user opens an input form at `Entity_Total`:
> 1. In standard Planning forms without cell-level security enforcement, the cell renders as editable because the user has `WRITE` access to `Entity_Total`.
> 2. When the user clicks **Save**, Essbase attempts to commit the data. Because `Entity_Total` has no physical block cell of its own, the write request resolves to the memory address of `Entity_US`.
> 3. If cell-level security is evaluated strictly on write-back, the commit fails with a security access violation. However, in ad-hoc Smart View submissions, this can cause a **security bypass** where the read-only child is updated by submitting through the parent!
>
> **The Remediation:**
> Change `Entity_Total` to **`Dynamic Calc (~)`** (in Hybrid BSO) or set its property to **`Never Share`** (in Classic BSO). This forces distinct security boundaries."

### Q5: Attribute Dimensions vs Standard Dimensions
**Question:**
"What is the difference between an **Attribute Dimension** and a **Standard Dimension** in terms of block size, index structure, and data loading?"

**Consultant Model Answer:**
> | Feature | Standard Dimension | Attribute Dimension |
> | :--- | :--- | :--- |
> | **Block Size Impact** | Defines block size if DENSE (8 bytes per member). | **Zero impact** on block size. |
> | **Index Size Impact** | Defines block count and index entries if SPARSE. | Does **not** create index entries in `.IND`. Stored in separate attribute pointers. |
> | **Storage Association** | Members define coordinates in the data matrix. | Associated only with **Level 0 members** of a base sparse dimension. |
> | **Data Loading** | Data can be loaded directly to intersections. | **Cannot load data directly** to an attribute intersection; data is derived dynamically from base members. |
> | **Query Performance** | Fast physical retrieval. | Slower than standard sparse queries because Essbase must dynamically filter base members using attribute tables. |

### Q6: UDA (User Defined Attribute) vs Attribute Dimension vs Smart List
**Question:**
"When would you use a UDA versus an Attribute Dimension versus a Smart List in an enterprise Planning application?"

**Consultant Model Answer:**
> - **Use a UDA (User Defined Attribute):**
>   - When you need a lightweight text tag on outline members purely to drive **calculation scripts** (e.g., `@UDA("Entity", "Major_Market")` in a `FIX` statement).
>   - UDAs do not create dimensions and cannot be placed on form axes or sliced in Smart View.
> - **Use an Attribute Dimension:**
>   - When users need to **slice, dice, and filter** financial data by characteristics (e.g., Color, Size, Entity Region) in Smart View and reports, but you do not want to explode the cube's block footprint by adding a standard dimension.
> - **Use a Smart List:**
>   - When users must enter or select categorical/qualitative data **at a specific cell intersection** on a form (e.g., selecting `Capitalization_Type` or `Approval_Status` for a specific project). Smart Lists are cell data, not outline metadata.

### Q7: Consolidation Operator: `~` (Ignore) vs `^` (Never Consolidate)
**Question:**
"What is the precise difference between the consolidation operator `~` (Ignore) and `^` (Never Consolidate)?"

**Consultant Model Answer:**
> - **`~` (Ignore):**
>   - The member's value is **ignored during normal hierarchical aggregation** (`AGG` or `CALC ALL`) into its immediate parent.
>   - However, its value **can still be referenced** in calculation scripts, member formulas, or cross-dimensional formulas.
>   - Commonly used on Dynamic Calc parents, statistical drivers, and alternate hierarchy roots.
> - **`^` (Never Consolidate):**
>   - An extreme restriction: Essbase prevents the member from being consolidated in **any** dimension aggregation pass under any circumstances.
>   - Rarely used in modern EPM; `~` (Ignore) is the industry standard for non-consolidating members."

### Q8: The Dense Dimension Addition Block Explosion
**Question:**
"A Classic BSO cube has 3 Dense dimensions (`Accounts`: 500 members, `Period`: 20 members, `View`: 3 members). The current block size is $500 \times 20 \times 3 \times 8 \text{ bytes} = 240 \text{ KB}$. A developer changes `Entity` (1,000 members) from Sparse to Dense. What happens to the block size, and what catastrophic error occurs?"

**Consultant Model Answer:**
> "The block size explodes exponentially:
> $$\text{New Block Size} = 500 \times 20 \times 3 \times 1,000 \times 8 \text{ bytes} = 240,000,000 \text{ bytes} \approx \mathbf{240 \text{ MB per block!}}$$
>
> **The Catastrophic Consequences:**
> 1. Essbase will fail during Database Refresh with an error: `Block size exceeds maximum limit (maximum allowable block size is 100 MB in Essbase)`.
> 2. Even if it were below 100 MB (e.g., 50 MB), every single data read or write would require transferring 50 MB between disk and memory cache.
> 3. The `Data Cache` would hold only a handful of blocks, causing severe cache thrashing, system freezing, and application crashes.
> 
> **Rule:** `Entity` must always remain **SPARSE**."

### Q9: Shared Member Precedence Collision
**Question:**
"During a metadata load via Data Management, 50 new shared cost centers fail with the error: `Member [CC_999] already exists in dimension`. What caused this?"

**Consultant Model Answer:**
> "In Oracle Cloud EPM Planning:
> 1. A member name must be **unique** across the entire application unless **Duplicate Member Names** are explicitly enabled.
> 2. When creating a shared member, the metadata record must explicitly flag the property **`Data Storage = Shared`**.
> 3. If Data Management loads a record with an existing member name (`CC_999`) but leaves `Data Storage` as `Store` or blank, Planning treats it as an attempt to create a duplicate base member rather than a shared pointer, resulting in the collision error.
> 4. Additionally, if the record attempts to load the shared member before the base member in the load file sequence, the refresh engine rejects it due to the Outline Precedence Rule."

### Q10: Solve Order Collision on 3 Dimensions
**Question:**
"At the intersection of `Gross_Margin_%` (Account, Solve Order 10), `Variance_%` (Scenario, Solve Order 20), and `YearTotal` (Period, Solve Order 0), what is the exact sequence of calculations executed by Essbase?"

**Consultant Model Answer:**
> "Essbase calculates the intersection in ascending order of Solve Order, with the **highest Solve Order executing LAST**:
>
> 1. **Step 1 (Solve Order 0 - `YearTotal`):**
>    Essbase sums the base monthly numbers (`Jan + Feb + ... + Dec`) for all stored accounts and scenarios.
> 2. **Step 2 (Solve Order 10 - `Gross_Margin_%`):**
>    Essbase evaluates the gross margin formula:
>    $$\text{Gross Margin } \% = \frac{\text{Gross Profit}}{\text{Total Revenue}}$$
>    This computes margin percentages across all periods, including `YearTotal`.
> 3. **Step 3 (Solve Order 20 - `Variance_%` - EXECUTED LAST AND WINS):**
>    Essbase evaluates the variance percentage formula:
>    $$\text{Variance } \% = \frac{\text{Actual} - \text{Budget}}{\text{Budget}}$$
>    This evaluates using the gross margin percentages calculated in Step 2.
>
> The result at `(Gross_Margin_%, Variance_%, YearTotal)` accurately reflects the variance between the full-year Actual margin % and Budget margin %."

### Q11: Two-Pass Calculation on Accounts
**Question:**
"What is the `Two-Pass` property in BSO, on which dimensions is it valid, and why is it not used in Modern Hybrid BSO?"

**Consultant Model Answer:**
> - **What It Is:** In Classic BSO, the `Two-Pass Calculation` property forces Essbase to recalculate dynamic formulas on a second pass after the outline consolidation completes.
> - **Valid Dimensions:** Valid **only** on the **Accounts** dimension and **Time** dimension.
> - **Classic Use Case:** Ratios like `Margin %` that need to evaluate on consolidated parent totals rather than summing child ratios.
> - **Why Deprecated in Hybrid BSO:**
>   Hybrid BSO utilizes the ASO dynamic calculation engine, which supports **generalized Solve Order (0 to 127)** across **all dimensions**. Solve Order provides deterministic, multi-dimensional precedence, rendering the rigid Two-Pass flag obsolete."

### Q12: Dynamic Calc Parent with Children having Different Consolidation Operators
**Question:**
"In a Hybrid BSO cube, a Dynamic Calc parent `Total_Adjustments` has three children:
- `Adj_Add` (Operator `+`)
- `Adj_Subtract` (Operator `-`)
- `Adj_Stat` (Operator `~`)
How does the dynamic vector engine compute `Total_Adjustments`?"

**Consultant Model Answer:**
> "The dynamic vector engine evaluates the children sequentially according to their outline operators:
> $$\text{Total\_Adjustments} = \text{Adj\_Add} - \text{Adj\_Subtract}$$
> `Adj_Stat` is completely ignored from the sum because its consolidation operator is set to `~` (Ignore). 
> 
> However, `Adj_Stat`'s data remains fully queryable at its own Level 0 coordinate and can be utilized in member formulas or driver allocations."

### Q13: Smart List Storage Internals
**Question:**
"When a user selects the string `'Approved'` from a Smart List in a Planning form, what is physically stored in the Essbase data block cell?"

**Consultant Model Answer:**
> "Essbase **does not store strings or text** in data blocks. Essbase is a pure 64-bit IEEE floating-point numeric calculation engine.
>
> 1. In Planning, every Smart List entry is mapped to an internal integer ID (e.g., `'Pending' = 1`, `'Approved' = 2`, `'Rejected' = 3`).
> 2. When the user selects `'Approved'`, Planning submits the numeric value **`2.0`** to Essbase.
> 3. Essbase stores the 8-byte double-precision float `2.0` in the physical block cell.
> 4. When queries are retrieved, Planning matches the numeric float `2.0` against the Smart List dictionary and renders the text string `'Approved'` in the user interface."

### Q14: Outline Restructure Types
**Question:**
"What is the difference between an **Index-Only Restructure**, a **Sparse Restructure**, and a **Dense Restructure** during a Database Refresh?"

**Consultant Model Answer:**
> 1. **Index-Only Restructure (Fastest):**
>    - Occurs when changes are made to member aliases, UDAs, or formulas that do not change block structure or indexing.
>    - Only the outline file (`.otl`) is rewritten. Takes seconds.
> 2. **Sparse Restructure:**
>    - Occurs when members are added, deleted, or moved in **Sparse** dimensions.
>    - Data blocks (`.pag`) are not rewritten! Only the index file (`.ind`) is restructured to add or reorder block pointers.
> 3. **Dense Restructure (Slowest & Most Dangerous):**
>    - Occurs when members are added, deleted, or moved in **Dense** dimensions, or when a dimension changes between Dense and Sparse.
>    - **Every single data block (`.pag`) in the entire database must be unpacked, resized, and rewritten to disk cell-by-cell!**
>    - Requires 2x available disk space; can take hours on multi-gigabyte cubes."

### Q15: The "Formula on Stored Member" Trap
**Question:**
"What happens if you assign a member formula to a member whose Data Storage property is set to `Store` in a BSO cube?"

**Consultant Model Answer:**
> "In BSO, assigning a formula to a `Store` member creates a **batch-calculated stored cell**:
> 1. The formula does **not** evaluate dynamically upon user retrieval.
> 2. Queries to that member return `#Missing` or stale data until a calculation script (`CALC ALL;` or targeted business rule) is executed to evaluate the formula and write the result into the stored block.
> 3. If a user manually submits data to this cell, the submitted data will persist until the next business rule execution overwrites it with the formula result.
>
> **Best Practice:** If a formula must calculate dynamically upon every retrieval without running a batch script, set Data Storage to **`Dynamic Calc (~)`**."
