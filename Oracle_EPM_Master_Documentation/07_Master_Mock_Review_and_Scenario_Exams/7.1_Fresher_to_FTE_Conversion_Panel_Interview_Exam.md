## Section 1: Storage Architecture & Cube Sizing Edge Cases (Q1–Q10)

### Q1: The Oversized Dense Block Pathology
**Scenario:** A client has a Classic BSO cube where three dimensions are Dense: `Accounts` (600 members), `Period` (20 members), and `Entity` (2,000 members). The current block size is $600 \times 20 \times 2,000 \times 8 \text{ bytes} \approx 192 \text{ MB}$. The nightly batch calculation takes 7 hours, and Smart View retrieves frequently time out.
**Question:** Explain the exact physical engine bottleneck causing this latency, and detail the architectural steps to resize the block to optimal performance.
**Consultant Model Answer:**
> "The engine bottleneck is severe **Write Amplification and Cache Starvation** caused by an oversized data block that exceeds Essbase's recommended range (8 KB to 100 KB):
> 1. In Essbase, the fundamental unit of disk I/O is the entire block. To update or read an 8-byte cell, Essbase must transfer the entire 192 MB block into RAM. A 1 GB Data Cache can only hold 5 blocks at a time, resulting in continuous cache thrashing and disk I/O saturation.
> 2. **The Remediation:**
>    - Change the `Entity` dimension from **DENSE** to **SPARSE**.
>    - The new block size will be: $600 \times 20 \times 8 \text{ bytes} = 96 \text{ KB}$, which falls squarely within the optimal 50 KB–100 KB target range.
>    - The 1 GB Data Cache will now hold over 10,000 blocks simultaneously in RAM.
>    - Perform a Database Refresh (Dense Restructure) to rewrite the `.pag` files. Nightly calculations and query retrievals will accelerate by 10x to 30x."

### Q2: Why ASO Query Speeds Collapse Over Time
**Scenario:** An ASO reporting cube was deployed with sub-second query performance. After 6 months of automated hourly data loads from Oracle Fusion ERP, user ad-hoc queries in Smart View now take 40 seconds, even though total data volume only grew by 10%.
**Question:** What internal physical storage degradation occurred in ASO, and what automated maintenance script must be implemented?
**Consultant Model Answer:**
> "The degradation is caused by **severe ASO Slice Fragmentation**:
> 1. ASO is an append-only architecture. Every hourly ERP data load generated a new physical data slice (`.dat` file). Over 6 months, the cube accumulated thousands of fragmented incremental slices.
> 2. For every ad-hoc query, the ASO engine must scan every single slice, decompress multiple bitmap indexes, and reconcile duplicate coordinates in RAM.
> 3. **The Remediation:**
>    - Execute an immediate **Merge All Slices** with the **'Drop Zero Cells'** flag enabled to consolidate all slices into the Main Base Slice and permanently purge zero/deleted rows:
>      `epmautomate mergeDataSlices <CubeName> all dropZeroCells`
>    - Rebuild the materialized aggregate views (`epmautomate executeAggregateStorageOutlineOptimization`).
>    - **Automation:** Schedule an automated job to merge incremental slices intraday (every 2–4 hours) and run a full Merge All Slices nightly."

### Q3: Hybrid BSO Dual-Kernel Execution Trap
**Scenario:** A Hybrid BSO cube has a Dynamic Calc sparse parent member `Total_Marketing` with formula:
```essbase
@SUMRANGE("Expense", @CHILDREN("Total_Marketing")) + "Direct_Driver"->"Corp";
```
When queried in Smart View, the retrieval takes 25 seconds instead of 0.2 seconds.
**Question:** Why did the Hybrid engine fail to calculate this in memory, and how do you fix it?
**Consultant Model Answer:**
> "The calculation experienced a **Dual-Kernel Fallback from Vector Mode to Procedural BSO Mode**:
> 1. In Modern Hybrid BSO, sparse aggregations are computed at hardware bus speeds by the integrated ASO dynamic vector engine.
> 2. However, when a member formula contains complex cross-dimensional operators (`->`) referencing other sparse dimensions combined with range functions (`@SUMRANGE`) that cannot be resolved by the vector engine, Hybrid BSO aborts vector processing and drops down to the legacy single-threaded procedural BSO calculation engine.
> 3. **The Fix:**
>    - Remove the procedural formula from the sparse parent `Total_Marketing`.
>    - Make `Total_Marketing` a standard dynamic rollup parent (`+` operator).
>    - Move the driver calculation to a dedicated Level 0 Account member, allowing the Hybrid vector engine to aggregate the hierarchy in sub-milliseconds."

### Q4: The Undersized Block Trap
**Scenario:** A developer designs a BSO cube where only the `Period` dimension (12 stored months) is Dense. Block size is $12 \times 8 = 96 \text{ bytes}$. The cube contains 8,000,000 blocks.
**Question:** Why is a 96-byte block size disastrous for Essbase performance?
**Consultant Model Answer:**
> "An undersized block creates **Index Table Bloat and Pointer Overhead**:
> 1. For every 96-byte data block, Essbase must maintain an entry in the sparse index file (`.ind`). The index pointer and header overhead can exceed the size of the data block itself!
> 2. Traversing 8,000,000 index entries to retrieve a small financial statement requires massive memory bus traversal and index cache thrashing.
> 3. **The Fix:** Add the `Accounts` dimension to the Dense configuration. If `Accounts` has 200 stored members, the new block size becomes $200 \times 12 \times 8 = 19.2 \text{ KB}$, and the total block count collapses from 8,000,000 to 40,000 blocks, drastically reducing index traversal overhead."

### Q5: Dynamic Calc Parents in Hybrid BSO vs Classic BSO
**Scenario:** An architect migrating a Classic BSO application to Modern Hybrid BSO changes all upper-level sparse parents from `Stored (+)` to `Dynamic Calc (~)`. The project manager fears data loss.
**Question:** Explain why no data is lost and why storing upper-level parents in Hybrid BSO is an anti-pattern.
**Consultant Model Answer:**
> "No data is lost because upper-level parents represent **mathematical consolidations of Level 0 stored data**:
> 1. In Classic BSO, parents were stored on disk to avoid slow query-time calculations.
> 2. In Modern Hybrid BSO, the ASO dynamic vector engine calculates sparse rollups dynamically upon query execution in sub-milliseconds directly from Level 0 blocks.
> 3. Setting upper-level parents as `Stored` in Hybrid BSO is an anti-pattern because it forces batch scripts to calculate and write physical blocks to disk, causing unnecessary disk I/O, inflating database backup size, and extending batch calc windows for zero query speed benefit."

### Q6: Transparent Partition Sizing
**Scenario:** A company links a BSO planning cube to an ASO reporting cube via a Transparent Partition. Users querying ASO report severe query latency.
**Question:** What architectural flaw causes transparent partition queries to stall?
**Consultant Model Answer:**
> "In a Transparent Partition, the target ASO cube does not store data; it forwards the query in real-time to the source BSO cube. If the source BSO cube has unaggregated data or complex dynamic formulas at the requested intersection, the source BSO engine must calculate the data on-the-fly before returning it across the network to ASO. 
> 
> **The Modern Architecture Fix:** Replace the Transparent Partition with **Smart Push / Data Maps** scheduled via Groovy or REST API. Pushing pre-calculated Level 0 slices into ASO allows ASO to store the data physically and serve queries from memory in sub-seconds."

### Q7: Evaluating Block Density Percentage
**Scenario:** A cube shows: Potential Blocks = 10,000,000; Existing Blocks = 50,000; Block Density = 15%.
**Question:** How do you interpret these metrics, and is this cube healthy?
**Consultant Model Answer:**
> "Yes, this represents a very healthy cube:
> - **Existing vs Potential:** The cube is sparse ($50,000 / 10,000,000 = 0.5\%$ block sparsity), which is normal for multidimensional business models where not every entity sells every product.
> - **Block Density (15%):** Means that within each existing 80 KB block, an average of 15% of the dense cells contain valid non-missing data. This is an efficient density ratio that avoids block bloat while preventing index explosion."

### Q8: Materialized Views vs Aggregate Storage Slices
**Scenario:** After running 'Merge All Slices', an admin notices that Smart View queries became 5x slower.
**Question:** What happened to the aggregate views, and what step was skipped?
**Consultant Model Answer:**
> "Executing 'Merge All Slices' rewrites the entire Main Base Slice, which **automatically drops and invalidates all existing materialized aggregate views**. 
> 
> The admin skipped the mandatory second step: **Rebuilding Aggregate Views**. Without aggregate views, ASO must aggregate every query dynamically from raw Level 0 tuples. Running `Execute Aggregate Storage Outline Optimization` immediately restores sub-second query performance."

### Q10: BSO Page File Splitting (.PAG)
**Scenario:** An Essbase database directory contains `ess00001.pag`, `ess00002.pag`, and `ess00003.pag`.
**Question:** Why does Essbase split page files, and what controls this behavior?

## Section 2: Outline Properties, Implied Sharing & Security Traps (Q11–Q20)

### Q11: The Single-Child Implied Share Historical Corruption
**Scenario:** In Q1, `Parent_A` had only one child `Child_1` (Stored `+`). In Q2, `Child_2` was added under `Parent_A`. Q1 reports now show `Parent_A` as `#Missing`.
**Question:** Explain the exact physical pointer change that corrupted Q1 reports, and how to fix it without re-aggregating history.
**Consultant Model Answer:**
> "In Q1, Essbase treated `Parent_A` as an **Implied Share** (a memory alias to `Child_1`), storing zero physical data for the parent. When `Child_2` was added, implied sharing broke, instantiating `Parent_A` as an independent physical stored block cell. Because historical months were not re-calculated, the stored cells for Jan–Mar remained empty (`#Missing`).
> 
> **The Fix:** In Modern Hybrid BSO, change `Parent_A` from `Stored (+)` to **`Dynamic Calc (~)`**. It will immediately compute the sum of its children dynamically on-the-fly for all historical and future periods with zero batch calculation required."

### Q12: Cell-Level Security Bypass via Implied Sharing
**Scenario:** A user has `WRITE` access to `Parent_X` and `READ` access to `Child_X`. `Child_X` is the sole child of `Parent_X`. The user submits data to `Parent_X`.
**Question:** What happens to `Child_X`, and why is this a critical audit vulnerability?
**Consultant Model Answer:**
> "Because `Parent_X` is an implied share, it has no physical storage of its own; it points directly to `Child_X`'s physical cell. Submitting data to `Parent_X` writes directly into the physical storage of `Child_X`, **bypassing the Read-Only security restriction on the child**!
> 
> **The Remediation:** Assign the property **`Never Share`** to `Parent_X` (in Classic BSO) or make it **`Dynamic Calc (~)`** (in Hybrid BSO) to decouple physical storage."

### Q13: Shared Member Precedence Rule
**Scenario:** A metadata load fails during Database Refresh with: `Shared member [CC_100_Shared] appears before base member in outline`.
**Question:** Why does the Essbase compiler enforce this ordering rule?
**Consultant Model Answer:**
> "Essbase compiles outlines in a single top-down serialization pass. When the compiler encounters a shared member, it must resolve an internal pointer to the base member's symbol table address. If the base member has not yet been processed, that address does not exist. Essbase refuses forward-referencing to prevent memory corruption and circular pointer dependencies."

### Q14: Does Adding 1,000 Shared Dense Members Double Block Size?
**Scenario:** An interviewer asks: 'If I add 1,000 shared members to the Accounts dimension (which is Dense), does the block size double?'
**Question:** How do you answer?
**Consultant Model Answer:**
> "No, the block size will **not increase by even a single byte**.
> 
> Block size is strictly determined by multiplying the count of **Stored Base Members** in Dense dimensions by 8 bytes. Dense shared members do not occupy an 8-byte cell slot inside the block array; they point to the memory offset of the primary base member. Only the outline symbol table (`.otl`) expands slightly in RAM."

### Q15: Dynamic Calc and Store Deprecation
**Scenario:** A client wants to use `Dynamic Calc and Store` on summary accounts in Hybrid BSO to speed up reports.
**Question:** Why is this an anti-pattern in Modern Cloud EPM?
**Consultant Model Answer:**
> "`Dynamic Calc and Store` writes calculated results into physical disk blocks upon first retrieval. If underlying child cells change, the stored parent block becomes dirty but is not automatically invalidated, leading to stale/corrupted reporting. Furthermore, in Hybrid BSO, the dynamic vector engine computes parents in RAM in sub-milliseconds; writing blocks to disk defeats the zero-block architecture."

### Q19: The Consolidation Operator `~` (Ignore)
**Scenario:** A parent has three children with consolidation operators `+`, `-`, and `~`.

**Consultant Model Answer:**
> "Essbase evaluates: $\text{Parent} = \text{Child}_1 - \text{Child}_2$. The third child (`~`) is completely ignored from the parent sum, but its value remains fully queryable at its own coordinate."

## Section 3: Calculation Scripts, Execution Order & Groovy Guardrails (Q21–Q30)

### Q21: Forcing Bottom-Up Mode on Top-Down Formulas
**Scenario:** A calc script log displays: `Formula on [Net_Sales] will be executed in Top-Down mode`.
**Question:** What causes Essbase to select Top-Down mode, and how do you force Bottom-Up?
**Consultant Model Answer:**
> "Essbase chooses Top-Down mode when a formula contains cross-dimensional operators (`->`) or complex `IF` logic evaluating sparse members, forcing the engine to scan the entire potential Cartesian grid. 
> 
> You force Bottom-Up mode using the compiler directive:
> ```essbase
> "Net_Sales"(
>     @CALCMODE(BOTTOMUP);
>     "Net_Sales" = "Units" * "Price";
> )
> ```
> This restricts execution strictly to existing data blocks."

---

### Q22: The `SET EMPTYMEMBERSETS ON;` Disaster
**Scenario:** A business rule has `FIX(&RTP_Department)` without `SET EMPTYMEMBERSETS ON;`. A user launches the rule without selecting a department.
**Question:** What catastrophic event occurs in Essbase?
**Consultant Model Answer:**
> "With `EMPTYMEMBERSETS OFF` (the default), Essbase treats the empty prompt set as an invalid restriction, **wipes out the FIX boundary, and calculates the entire database across all departments, all years, and all scenarios**! This overwrites closed historical actuals and freezes the server for hours. `SET EMPTYMEMBERSETS ON;` stops the script safely if an empty member set is detected."

---

### Q23: Why `FIXPARALLEL` Fails on Cross-Slice Allocations
**Scenario:** A developer parallelizes an allocation rule using `FIXPARALLEL (8, @RELATIVE("Total_Entity", 0))`. Corporate overhead is allocated to entities based on total revenue. The resulting numbers are zero or scrambled.
**Question:** Why did `FIXPARALLEL` produce invalid numbers?
**Consultant Model Answer:**
> "`FIXPARALLEL` partitions the specified dimension (`Entity`) into 8 independent worker threads. Thread 1 calculating `Entity_A` cannot access or synchronize with `Total_Entity` or corporate offset blocks being calculated by Thread 2. Parallel threads cannot read uncommitted cross-slice data. 
> 
> **The Fix:** Pre-calculate the scalar driver (Total Revenue) in a serial pre-calc step, then run `FIXPARALLEL` strictly to multiply the pre-calculated scalar driver against local entities."

### Q24: Groovy `DataCellIterator` Performance Optimization
**Scenario:** A user edits 2 cells on a 15,000-cell web form. A traditional calc script takes 45 seconds to calculate on save.
**Question:** How does a Groovy business rule achieve a sub-second runtime on form save?
**Consultant Model Answer:**
> "Groovy inspects the HTTP payload in memory *before* calling Essbase:
> ```groovy
> operation.grid.dataCellIterator({DataCell cell -> cell.edited}).each { cell -> ... }
> ```
> It identifies the exact 2 modified cells, extracts their dimensional coordinates, and dynamically generates a surgical calc script targeting strictly those 2 blocks:
> ```essbase
> FIX("E101", "Acct_500", "FY25", "Working") ... ENDFIX
> ```
> Essbase modifies only 2 blocks in memory cache, executing in 0.15 seconds."

### Q25: Pre-Save Validation via `throwVetoException`
**Scenario:** A business policy mandates that no planner can enter an operational expense increase exceeding 20%.
**Question:** How do you enforce this using Groovy without touching Essbase?
**Consultant Model Answer:**
> "Use Groovy's `throwVetoException()` during the pre-save phase:
> ```groovy
> operation.grid.dataCellIterator("Opex_Increase_%").each { cell ->
>     if (cell.edited && cell.data > 0.20) {
>         throwVetoException("Validation Error: Proposed increase of ${cell.data*100}% exceeds 20% limit.")
>     }
> }
> ```
> The form save is aborted in the application tier. Essbase is never touched, zero blocks are dirtied, and an explicit red error message is displayed to the user."

### Q26: Intelligent Calculation (`SET UPDATECALC ON;`) Stale Rollups
**Scenario:** A nightly calculation script has `SET UPDATECALC ON;`. Planners load new data, but parent reports still display yesterday's numbers.
**Question:** What failed in Intelligent Calculation?
**Consultant Model Answer:**
> "Intelligent Calculation calculates only blocks with their **Dirty Bit = 1**. If upper-level parent blocks were previously marked clean (dirty bit = 0) and the child updates failed to flip the parent's dirty flag, Essbase skips the parent calculation. In production batch calculations, always set **`SET UPDATECALC OFF;`** to guarantee 100% calculation integrity."

### Q27: `@PRIOR` Boundary Failure Across Years
**Scenario:** `"Opening_Cash" = @PRIOR("Closing_Cash", 1, @RELATIVE("Period", 0));` returns `#Missing` in January `FY25`.
**Question:** Why did `@PRIOR` fail, and what is the fix?
**Consultant Model Answer:**
> "`@PRIOR` cannot automatically jump across the `Years` dimension; January is the first member in the period range, so seeking 1 period prior falls off the array. 
> 
> **The Fix:** Use `@MDSHIFT`:
> ```essbase
> "Opening_Cash" = @MDSHIFT("Closing_Cash", -1, "Period", , -1, "Years", );
> ```"

### Q28: `CALC AGG` vs `CALC DIM`
**Scenario:** An interviewer asks: 'When should you use `CALC AGG` instead of `CALC DIM` in a calculation script?'
**Question:** How do you answer?
**Consultant Model Answer:**
> "`CALC AGG` executes a pure hierarchical rollup (`+`, `-`, `~`) and **completely ignores member formulas**. It is blazing fast. `CALC DIM` evaluates both hierarchical consolidations AND member formulas. If sparse dimensions have no member formulas, always use `CALC AGG`."

## Section 4: Solve Order, Evaluation Order & Multi-Cube Integrity (Q31–Q40)

### Q31: The Classic Trap: Evaluation Order vs Solve Order
**Scenario:** A cell displays `$1.00` instead of a Smart List drop-down menu.
**Question:** Which setting is misconfigured: Evaluation Order or Solve Order?
**Consultant Model Answer:**
> "**Evaluation Order** is misconfigured in Planning Dimension Settings. A currency dimension (e.g., `Scenario`) has higher evaluation priority than `Account`. Internal integer ID `1` is rendered as `$1.00`. Move `Account` to Priority 1 in Evaluation Order to restore the Smart List dropdown. Solve Order has zero impact on UI data types."

---

### Q32: Solve Order Collision on Ratios and Quarters
**Scenario:** At `(Gross_Margin_%, Q1)`, `Q1` displays `120%` (the sum of monthly margins: $40\% + 40\% + 40\%$).
**Question:** What Solve Order configuration fixes this?
**Consultant Model Answer:**
> "Set `Q1` (Time) to **Solve Order `0`** and `Gross_Margin_%` (Account) to **Solve Order `10`**. In Essbase, **the higher Solve Order calculates LAST and wins**. Essbase will sum base dollars to Q1 first, and then evaluate the margin formula on quarterly totals."

---

### Q33: The Dangerous Anti-Pattern: Solve Order on Sparse Rollups
**Scenario:** A consultant assigns `Solve Order = 50` to `Total_Entity` (a sparse parent). Smart View retrievals jump from 0.5 seconds to 4 minutes.
**Question:** What caused this performance collapse?
**Consultant Model Answer:**
> "Assigning a high solve order to a structural sparse parent forces Essbase to disable the high-speed ASO dynamic vector engine and fall back to slow, cell-by-cell procedural calculations across the entire entity hierarchy. Structural sparse rollup parents must **always remain at Solve Order `0`**. Solve orders $> 0$ should only be assigned to calculated member formulas (ratios, variances)."

---

### Q34: Multi-Cube Formula Refresh Crash
**Scenario:** An Account formula `Salary * 0.15` compiles fine in `Workforce`, but Database Refresh aborts on `FinPlan` with: `Unknown member [Salary]`.
**Question:** How do you resolve this without removing the account from `FinPlan`?
**Consultant Model Answer:**
> "Wrap the formula in a plan-type isolation tag:
> ```essbase
> <PlanType: Workforce>
> "Salary" * 0.15;
> </PlanType: Workforce>
> ```
> This instructs the compiler to deploy the formula strictly to the `Workforce` cube while leaving `FinPlan` unencumbered."

---

### Q35: Procedural Calc Syntax in ASO Reporting Cubes
**Scenario:** A member formula containing `@VARPER("Actual", "Budget")` causes the ASO cube refresh to fail with: `Syntax error: Invalid MDX expression`.
**Question:** Why did this fail, and how do you write the ASO equivalent?
**Consultant Model Answer:**
> "ASO does not support procedural Essbase calculation functions (`@`). ASO formulas must be written in **MDX (Multi-Dimensional Expressions)**:
> ```mdx
> IIF([Budget] == 0, MISSING, ([Actual] - [Budget]) / [Budget] * 100)
> ```"

---

### Q36: 3-Way Collision Hierarchy
**Scenario:** An intersection collides on `Gross_Margin_%` (Account), `Variance_%` (Scenario), and `YearTotal` (Period).
**Question:** Define the required Solve Order hierarchy.
**Consultant Model Answer:**
> "- **Solve Order 0:** `YearTotal` (Time sums base dollars first).
> - **Solve Order 10:** `Gross_Margin_%` (Calculates margin on full-year consolidated dollars).
> - **Solve Order 20 (Highest Wins):** `Variance_%` (Calculates variance percentage between the resulting full-year margin ratios)."

---

### Q37: Division by Zero in ASO MDX Formulas
**Scenario:** An ASO query returns `#NumericOverflow` across several forecast periods.
**Question:** What caused this, and how do you fix it?
**Consultant Model Answer:**
> "In ASO, dividing by zero or `#Missing` raises an arithmetic overflow exception. The MDX formula must be protected using `IIF`:
> ```mdx
> IIF([Denominator] == 0 OR [Denominator] == MISSING, MISSING, [Numerator] / [Denominator])
> ```"

### Q40: Two-Pass Calculation Restriction
**Scenario:** Can you set the `Two-Pass` property on the `Scenario` dimension?
**Consultant Model Answer:**
> "No. In Essbase, `Two-Pass` is syntactically restricted strictly to the **Accounts** and **Time** dimensions. In modern EPM, use **Solve Order** on Scenario instead."

## Section 5: Production Crises, Locking, Restructure & Crash Recovery (Q41–Q50)

### Q41: The Block Explosion Recovery Workflow
**Scenario:** A bad calculation rule creates 12,000,000 empty blocks, expanding the cube from 400 MB to 45 GB.
**Question:** Detail the exact 3-step recovery workflow.
**Consultant Model Answer:**
> "1. **Purge Empty Blocks:** Execute a targeted script with `CLEARBLOCK EMPTY;` scoped to the affected scenario/year to physically remove all-missing blocks from the index.
> 2. **Wipe Corrupted Slices:** If blocks contain invalid numbers, run `CLEARBLOCK ALL;` on the affected scenario.
> 3. **Compact Database:** Run a Database Refresh (Cube Restructure) to compact the `.pag` and `.ind` files on disk."

### Q42: Multi-User Lock Contention on Shared Sparse Blocks
**Scenario:** User A edits `Salaries` in `E101`. User B edits `Travel` in `E101`. User B receives `Lock Timeout`.
**Question:** Why did User B fail when editing a completely different account?
**Consultant Model Answer:**
> "Essbase concurrency operates at the **physical block level, not the cell level**. Because `E101` is sparse and accounts are dense, both accounts reside inside the **same physical data block**. User A's transaction acquired an exclusive lock on the entire block, forcing User B to stall until the timeout expired."

### Q43: The `.TCT` File & Crash Recovery
**Scenario:** The server loses power during a large data load.
**Question:** What is the `.tct` file, and how does Essbase recover upon restart?
**Consultant Model Answer:**
> "The `.tct` (Transaction Control Table) is Essbase's **Write-Ahead Log (WAL)**. Upon restart, the recovery manager scans the `.tct`: committed transactions are **rolled forward** to `.pag`, while uncommitted in-flight transactions are **rolled back** using pre-image logs, guaranteeing database consistency."

### Q44: Read-Only Child in Grid Spread
**Scenario:** A planner inputs \$500,000 at `Total_Department` using Proportional Spread. Closed months Jan–Mar hold \$200,000 and are Read-Only.
**Question:** What happens to Apr–Dec, and what does `Total_Department` display upon save?
**Consultant Model Answer:**
> "Planning locks Jan–Mar at \$200,000, deducts it from the target ($\$500K - \$200K = \$300K$), and distributes the remaining \$300,000 proportionally across the writable months (Apr–Dec). `Total_Department` displays exactly **`$500,000`**."

### Q45: Residual Penny Rounding Algorithm
**Scenario:** An uneven amount (\$100.00) is spread evenly across 3 children.
**Question:** How does Planning prevent a 1-cent rounding variance?
**Consultant Model Answer:**
> "Planning allocates $\$33.33$ to each child, detects a residual of $+\$0.01$ ($\$100.00 - \$99.99$), and assigns the residual penny to the **first writable child cell** (January = $\$33.34$), guaranteeing mathematical tie-back."
