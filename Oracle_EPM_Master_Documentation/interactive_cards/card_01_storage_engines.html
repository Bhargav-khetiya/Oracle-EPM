Interactive Architecture Card 01

Essbase Storage Engines: BSO vs. ASO vs. Hybrid BSO

OCI Cloud EPM Ready FTE Review Core

Classic BSO

Procedural

Block Storage Option (Physical Arrays)

📦 Storage Atom

Multidimensional data block (Dense × Sparse array). All dense cells pre-allocated (8 bytes/cell).

✓ Core Strengths

Complex procedural calc scripts, `@LOOP`, cross-dimensional driver allocations, in-place write-back.

✕ Bottlenecks

Block explosion beyond 10–12 dimensions; long batch CALC ALL windows; oversized blocks saturate I/O.

Target Size: 50 KB – 100 KB / block

ASO

Declarative

Aggregate Storage Option (Bitmap)

📦 Storage Atom

Compressed coordinate tuples + bitmap index tables. Zero pre-allocation for missing cells.

✓ Core Strengths

Scales to 25+ dimensions and millions of members; sub-second dynamic aggregations; lightning fast data loads.

✕ Bottlenecks

No procedural calc scripts; MDX formulas only; write-back accumulates slices requiring merges.

Sparsity Handling: Extreme (99.99%+)

Hybrid BSO

STANDARD

Dual-Kernel Engine (Modern Cloud EPM)

⚙️ Dual-Kernel Engine

BSO Block Engine at Level 0 (input storage) + ASO Dynamic Vector Engine at upper rollup levels.

✓ Core Strengths

Full business rules at Level 0 + instant sub-second sparse rollups with zero stored upper blocks.

⚠️ Watch Out

Unsupported procedural functions (`@SUMRANGE`) force fallback to slow BSO mode. Keep parents Dynamic Calc.

Upper Parents: Dynamic Calc (~)
