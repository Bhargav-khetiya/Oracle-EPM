Scenario 1: Oversized 192 MB Dense Block Collapse Storage

A BSO cube has Accounts (600), Period (20), and Entity (2,000) set to Dense. Block size is 192 MB. Nightly calc takes 7 hours. Explain the engine bottleneck and exact fix.

Consultant Answer: The bottleneck is Severe Write Amplification & Cache Starvation. A 1 GB data cache holds only 5 blocks. Changing Entity to SPARSE collapses block size to 96 KB (optimal range). Data cache now holds 10,000+ blocks in RAM; calcs accelerate by 20x.
Scenario 11: Single-Child Implied Share Historical Corruption Outline

In Q1, Parent_A had 1 child. In Q2, Child_2 was added. Q1 reports now show Parent_A as #Missing. Why did this happen without any calculation run?

Consultant Answer: Implied sharing automatically broke! Parent converted from an in-memory alias pointer into a physical stored cell. Because historical months were not re-calculated, parent cells remain empty (#Missing). Fix: Change Parent to Modern Hybrid Dynamic Calc (~).
Scenario 24: Groovy Surgical Form Save vs Calc Script Groovy

A planner edits 2 cells on a 15,000-cell web form. Traditional calc script takes 45s on save. How does Groovy achieve 0.15s execution?

Consultant Answer: Groovy uses operation.grid.dataCellIterator({DataCell cell -> cell.edited}) to inspect in-flight HTTP payloads, extracting coordinates for strictly the 2 modified blocks and generating a surgical dynamic FIX script. Essbase touches only 2 blocks in RAM.
Scenario 41: Block Explosion Overnight Crisis (500 MB → 48 GB) Crises

A bad allocation script creates 12M empty blocks overnight. Smart View hangs. Detail your immediate 3-step surgical recovery plan.

Consultant Answer: 1) Put app in maintenance mode. 2) Execute targeted CLEARBLOCK EMPTY; scoped to affected slice to physically remove empty blocks from .IND index. 3) Execute Database Refresh to compact .PAG files. Remove SET CREATENONMISSINGBLK ON; from the rule.
