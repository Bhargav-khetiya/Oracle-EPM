# SECTION 1: WHY HISTORY MATTERS

---

```
WHY should an EPM consultant care about history?

  REASON 1: INTERVIEWS
    "What is Hyperion?" is asked in 80% of interviews.
    If you say "I don't know Hyperion," the interviewer thinks
    you're too junior.

  REASON 2: CLIENT CONTEXT
    90% of current EPBCS clients migrated FROM Hyperion.
    When they say "We used to do this in HFP..." you need to
    understand what they're comparing against.

  REASON 3: PRODUCT NAMES
    Clients call the same product 5 different names:
    "Hyperion Planning" = "HFP" = "Planning" = "PBCS" = "EPBCS"
    You must know the lineage to understand what they mean.

  REASON 4: TECHNICAL DECISIONS
    Many EPBCS design patterns (Dense/Sparse, BSO, calc scripts)
    were invented in the 1990s. Understanding WHY they were designed
    that way helps you use them correctly today.
```

# SECTION 2: THE COMPLETE TIMELINE

---

```
THE ORACLE EPM TIMELINE — 35 YEARS OF EVOLUTION

  1991 ─── ARBOR SOFTWARE FOUNDED
  │        Robert Bloom and Jim Dorrian create Essbase
  │        in Sunnyvale, California.
  │        "Extended Spread Sheet Database" — a multidimensional
  │        database for financial analysis.
  │        → This is when Block Storage (BSO) was invented.
  │
  1992 ─── ESSBASE 1.0 RELEASED
  │        First commercial OLAP database.
  │        Runs on OS/2, Windows NT.
  │        Competing with: Cognos TM1, SAP BPC (later).
  │
  1995 ─── HYPERION SOLUTIONS CORPORATION FORMED
  │        Merger of IMRS (a reporting company) + Arbor Software.
  │        New company name: Hyperion Solutions.
  │        Products: Essbase + Hyperion Reporting.
  │
  1998 ─── HYPERION PLANNING 1.0
  │        First dedicated PLANNING application built on Essbase.
  │        Web-based interface for budget data entry.
  │        → This is the ancestor of today's EPBCS.
  │
  2000 ─── HYPERION FINANCIAL MANAGEMENT (HFM)
  │        Financial consolidation module.
  │        Handles multi-currency, intercompany eliminations.
  │        → This is the ancestor of today's FCCS.
  │
  2002 ─── AGGREGATE STORAGE OPTION (ASO) INTRODUCED
  │        Essbase gets a second storage engine for reporting.
  │        ASO = optimized for read-heavy, aggregate-heavy queries.
  │        → BSO for input, ASO for reporting — pattern still used today.
  │
  2003 ─── HYPERION FINANCIAL REPORTING (HFR)
  │        Pixel-perfect financial report designer.
  │        → Still exists as "Financial Reporting" in EPM Cloud.
  │
  2004 ─── SMART VIEW FOR EXCEL
  │        Hyperion releases the Excel add-in.
  │        Finance users can access Essbase from Excel.
  │        → Smart View is still the #1 user access method today.
  │
  2005 ─── HYPERION SYSTEM 9 (UNIFIED PLATFORM)
  │        All Hyperion products unified under one platform.
  │        Single login, shared services, common workspace.
  │        → Concept of "Shared Services" still exists in EPM Cloud.
  │
  2007 ─── ★ ORACLE ACQUIRES HYPERION — $3.3 BILLION ★
  │        March 1, 2007 — Oracle completes the acquisition.
  │        All Hyperion products become "Oracle Hyperion" products.
  │        Oracle Hyperion Planning, Oracle Hyperion HFM, etc.
  │        → This is the most important date in EPM history.
  │
  2008 ─── ORACLE HYPERION EPM SYSTEM 11
  │        Major release unifying all products.
  │        Calc Manager introduced (replacing Business Rules editor).
  │        → Calc Manager is still the UI used in EPBCS today.
  │
  2010 ─── ORACLE HYPERION 11.1.2.x
  │        Long-running on-premise release series.
  │        11.1.2.1, 11.1.2.2, 11.1.2.3, 11.1.2.4
  │        Stable, widely deployed across Fortune 500.
  │        → Many companies are STILL running 11.1.2.4 in 2024.
  │
  2014 ─── ★ PBCS LAUNCHED (CLOUD ERA BEGINS) ★
  │        Oracle launches Planning and Budgeting Cloud Service.
  │        First cloud-native EPM product.
  │        Single-app architecture (Standard app only).
  │        → The beginning of the end for on-premise.
  │
  2016 ─── EPBCS LAUNCHED (ENTERPRISE CLOUD)
  │        Enhanced PBCS with pre-built modules:
  │        Financials, Workforce, Capital, Projects.
  │        Enterprise app type introduced (multiple cubes).
  │        → This is the product most consultants work with today.
  │
  2017 ─── GROOVY SUPPORT ADDED TO EPBCS
  │        Java-based scripting added to Business Rules.
  │        EPM consultants can now write object-oriented code.
  │        → Game-changer for advanced logic and integrations.
  │
  2018 ─── FCCS LAUNCHED (CLOUD CONSOLIDATION)
  │        Cloud replacement for HFM.
  │        Financial Consolidation and Close Cloud Service.
  │        → Many HFM customers still migrating to FCCS.
  │
  2019 ─── EDMCS LAUNCHED (METADATA GOVERNANCE)
  │        Enterprise Data Management Cloud Service.
  │        Centralized metadata management across EPM apps.
  │        → Important for large enterprises with 5+ EPM applications.
  │
  2020 ─── NARRATIVE REPORTING + FREE FORM APPS
  │        Narrative Reporting replaces Hyperion Financial Reporting.
  │        Free Form applications introduced (no pre-built modules).
  │        → Free Form = pure Essbase cube with Planning UI on top.
  │
  2021 ─── ORACLE ANNOUNCES HYPERION ON-PREMISE EOL ROADMAP
  │        Oracle signals that Hyperion on-premise will eventually
  │        reach end-of-life. Cloud is the future.
  │        → Massive migration wave begins.
  │
  2022 ─── STRATEGIC MODELING ADDED TO EPBCS
  │        Long-range planning (5-10 year models) added.
  │        Replaces Hyperion Strategic Finance (HSF).
  │        → Complete suite now available in cloud.
  │
  2023 ─── AI/ML FEATURES (IPM INSIGHTS)
  │        Intelligent Performance Management.
  │        Predictive planning, auto-forecasting using ML.
  │        → Oracle starts integrating AI into EPM Cloud.
  │
  2024 ─── HYBRID BSO BECOMES DEFAULT
  │        Hybrid mode (Dynamic Calc parents) is now the default
  │        for all new BSO cubes.
  │        → Reduced storage, better performance out-of-the-box.
  │
  2025 ─── GEN AI INTEGRATION
  │        Oracle announces GenAI features for EPM:
  │        Natural language queries, automated commentary.
  │        → "Ask the AI: Why is Revenue down 5% in Q3?"
  │
  2026 ─── CURRENT STATE
           EPBCS is Oracle's flagship EPM product.
           Monthly cloud updates (mandatory).
           Hyperion on-premise support continues but with
           reduced investment. Migration incentives offered.
```

# SECTION 5: THE CLOUD MIGRATION

---

## On-Premise to Cloud — What Changed and What Didn't

```
WHAT STAYED THE SAME:
  ✅ Essbase engine (same database, same calc scripts)
  ✅ Smart View (same Excel add-in)
  ✅ Calc Manager (same rule designer)
  ✅ Dense/Sparse concept (unchanged since 1992)
  ✅ FIX, AGG, CALC DIM, @functions (same syntax)
  ✅ BSO, ASO architecture (same principles)
  ✅ Dimension design best practices (same)

WHAT CHANGED:
  🆕 SaaS delivery (no servers to manage)
  🆕 Monthly mandatory updates (can't stay on old version)
  🆕 Groovy scripting (didn't exist on-prem)
  🆕 Pre-built OOTB modules (Financials, Workforce, etc.)
  🆕 Hybrid BSO (new storage mode)
  🆕 REST API (full programmatic access)
  🆕 Data Integration (replaced FDMEE)
  🆕 IDCS/OCI IAM (replaced Shared Services)
  🆕 EPM Automate (replaced manual batch scripts)
  🆕 Navigation Flows (custom UI — didn't exist before)
  🆕 IPM Insights (AI/ML features)

WHAT WAS REMOVED:
  ❌ MaxL (Essbase admin scripting — replaced by REST API)
  ❌ EAS (Essbase Administration Services — no direct Essbase access)
  ❌ Essbase Studio (data integration for Essbase — replaced by DI)
  ❌ Custom Java plugins (replaced by Groovy Sandbox)
  ❌ Direct server access (SSH/RDP — it's SaaS now)
  ❌ Custom Essbase configurations (cache settings, etc.)
```

## Migration Patterns

```
MIGRATION APPROACHES:

  APPROACH 1: LIFT AND SHIFT
    Take the existing Hyperion application and replicate it
    exactly in EPBCS Cloud.
    ✅ Fastest, least risk
    ❌ Doesn't take advantage of cloud features
    Timeline: 2-4 months

  APPROACH 2: MIGRATE AND MODERNIZE
    Migrate core functionality, add cloud-native features
    (Groovy, Navigation Flows, OOTB modules).
    ✅ Best balance of speed and improvement
    ✅ Users get a better experience
    Timeline: 4-8 months

  APPROACH 3: RE-IMPLEMENT
    Design from scratch using OOTB EPBCS modules.
    Treat it as a new implementation, not a migration.
    ✅ Best long-term architecture
    ❌ Most expensive, highest risk
    Timeline: 6-12 months

  MOST COMMON: Approach 2 (Migrate and Modernize)
```

# SECTION 8: COMMON MISTAKES

---

| Mistake | Impact | Correct Approach |
|---------|--------|-----------------|
| Saying "Hyperion" when you mean "EPM Cloud" | Shows you're behind the times | Use "Oracle EPM Cloud" or "EPBCS" for cloud |
| Not knowing that Essbase predates Oracle | Shows lack of historical knowledge | Essbase = Arbor Software (1991) → Hyperion (1995) → Oracle (2007) |
| Thinking PBCS and EPBCS are the same | They have different feature sets | EPBCS = Enterprise (OOTB modules). PBCS = Standard only |
| Ignoring monthly updates | New features break existing customizations | Test every monthly update in Test env BEFORE Prod |
| Treating cloud like on-prem | Trying to SSH into servers, use MaxL | Embrace SaaS: use REST API, EPM Automate, Groovy |
| Not understanding the migration timeline | Getting caught off-guard by EOL announcements | Track Oracle's support lifecycle for Hyperion |

# SECTION 9: INTERVIEW QUESTIONS

---

### Beginner

**Q1: What is Hyperion?**
> Hyperion was a software company (originally Arbor Software, founded in 1991) that created Essbase, the multidimensional OLAP database. Hyperion was acquired by Oracle in 2007 for $3.3 billion. "Hyperion Planning" was the on-premise predecessor to today's Oracle EPM Cloud (EPBCS).

**Q2: What is the difference between Hyperion Planning and EPBCS?**
> Hyperion Planning was the on-premise product installed on company servers. EPBCS is the cloud successor — SaaS, hosted on Oracle Cloud Infrastructure. EPBCS adds: Groovy scripting, OOTB modules (Financials, Workforce), REST API, Navigation Flows, Hybrid BSO, and mandatory monthly updates.

### Intermediate

**Q3: A client is migrating from Hyperion Planning 11.1.2.4 to EPBCS. What are the key things that will change for them?**
> 1) No more MaxL or EAS — use EPM Automate and REST API instead. 2) Monthly mandatory updates — they must test every month. 3) Groovy is available — they can replace complex calc scripts with Groovy logic. 4) Hybrid BSO is the default — parents are Dynamic Calc. 5) FDMEE is replaced by Data Integration. 6) Shared Services is replaced by IDCS. 7) No direct server access — everything is through the web UI or API.

### Architect

**Q4: When would you recommend a "re-implement" vs. a "lift-and-shift" migration to cloud?**
> Re-implement when: 1) The current Hyperion app has fundamental design flaws (wrong Dense/Sparse, too many dimensions), 2) The client wants to adopt OOTB modules (Financials, Workforce), 3) The business requirements have significantly changed since the original implementation, or 4) The current app is more than 8 years old with heavy technical debt. Lift-and-shift when: 1) The current design is sound, 2) Time is critical (e.g., Hyperion support ending), 3) Budget is limited, or 4) User training disruption must be minimized.

**Q5: What happened to MaxL in EPBCS? How do you perform the equivalent tasks?**
> MaxL was the Essbase administration scripting language for on-premise (export data, clear data, refresh outline, manage users). In EPBCS, MaxL does not exist. The equivalents are: 1) EPM Automate (command-line: `exportData`, `importData`, `recreate`), 2) REST API (programmatic: POST/GET to Essbase endpoints), 3) Groovy (`cube.clearData()`, `cube.calculate()`), 4) The Planning web UI (manual administration). Most MaxL scripts can be converted to EPM Automate batch scripts or REST API calls.
