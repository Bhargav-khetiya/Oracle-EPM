# SECTION 3: PHASE 1 — DISCOVER AND ASSESS

---

## What Happens

```
PHASE 1: DISCOVER AND ASSESS
Duration: 2-3 weeks
Team: Architect + Project Manager + 1-2 Business Analysts

GOAL: Understand the client's current state, pain points,
      and high-level requirements.

ACTIVITIES:
  Week 1:
  ├── Kickoff meeting with executive sponsor
  ├── Stakeholder interviews (CFO, FP&A head, controllers)
  ├── Document current budget process (as-is)
  ├── Inventory existing tools (Excel, Hyperion, SAP BPC?)
  └── Identify pain points and wish list

  Week 2:
  ├── Review current financial reports and KPIs
  ├── Assess data sources (ERP, HR system, flat files)
  ├── Evaluate IT infrastructure (network, SSO, firewall)
  ├── Identify integration requirements
  └── Assess change management needs

  Week 3:
  ├── Draft high-level scope document
  ├── Create preliminary project plan
  ├── Estimate budget and resource needs
  └── Present findings to executive sponsor

KEY QUESTIONS TO ASK:
  □ "How do you create your budget today?" (Process)
  □ "How many people are involved?" (Scale)
  □ "How long does the budget cycle take?" (Timeline)
  □ "What are your biggest frustrations?" (Pain points)
  □ "What reports does the CFO need?" (Outputs)
  □ "What ERP system do you use?" (Data source)
  □ "Do you need multi-currency?" (Complexity)
  □ "How many legal entities/cost centers?" (Dimensions)
```

### Phase 1 Deliverables

| Deliverable | What It Contains | Who Approves |
|------------|-----------------|-------------|
| **Discovery Report** | Current state, pain points, opportunities | Executive Sponsor |
| **Preliminary Scope** | In-scope/out-of-scope modules and features | Project Steering Committee |
| **High-Level Project Plan** | Timeline, milestones, resource estimates | PM + Sponsor |
| **Risk Register** | Identified risks and mitigation plans | PM |

# SECTION 4: PHASE 2 — REQUIREMENTS GATHERING

---

```
PHASE 2: REQUIREMENTS GATHERING
Duration: 3-4 weeks
Team: Full team (Architect + Developers + Business Analysts)

GOAL: Document EXACTLY what the client needs — every form,
      every report, every calculation, every data source.

ACTIVITIES:

  WORKSHOP 1: FINANCIAL PROCESSES (Week 1)
  ├── Map the budget cycle (month-by-month workflow)
  ├── Identify all Scenarios (Budget, Forecast, Actual)
  ├── Define Version strategy (Working, Final, Board)
  ├── Define approval workflow requirements
  └── Deliverable: Process Flow Document

  WORKSHOP 2: DIMENSIONS AND METADATA (Week 2)
  ├── List all Account hierarchies (P&L, BS, CF)
  ├── List all Entity hierarchies (legal entities, cost centers)
  ├── Identify Custom dimensions (Product, Channel, Project)
  ├── Define member naming conventions
  ├── Identify Substitution Variables
  └── Deliverable: Dimension Requirements Document

  WORKSHOP 3: FORMS AND REPORTS (Week 3)
  ├── Walk through every form the users need
  ├── Mock up form layouts in Excel
  ├── Define which dimensions go on Rows, Columns, POV
  ├── Identify Runtime Prompts needed
  ├── List all dashboard and report requirements
  └── Deliverable: Form & Report Catalog

  WORKSHOP 4: CALCULATIONS AND INTEGRATION (Week 4)
  ├── Document every calculation needed
  │   (Revenue = Rooms × Occupancy × Rate)
  ├── Identify allocation rules
  ├── Map data sources to EPM dimensions
  ├── Define data load frequency (daily, weekly, monthly)
  ├── Define security requirements (who sees what)
  └── Deliverable: Calculation Spec + Integration Spec

REQUIREMENTS DOCUMENT TEMPLATE:
  ┌──────────────────────────────────────────────────┐
  │ REQ ID: REQ-FRM-001                               │
  │ Category: Forms                                    │
  │ Title: Revenue Driver Input Form                   │
  │ Description: Users enter Rooms Available,          │
  │   Occupancy %, and ADR by month. System            │
  │   calculates Room Revenue = Rooms × Occ × ADR.    │
  │ Priority: P1 (Must Have)                           │
  │ Requested By: FP&A Manager                        │
  │ Source Workshop: Workshop 3, Day 2                 │
  │ Dependencies: Account dim (REQ-DIM-001)           │
  │ Acceptance Criteria: User enters 3 drivers,       │
  │   Revenue auto-calculates on form save.            │
  └──────────────────────────────────────────────────┘
```

# SECTION 5: PHASE 3 — DESIGN

---

```
PHASE 3: DESIGN
Duration: 3-4 weeks
Team: Architect (lead) + Senior Developers + Business Analysts

GOAL: Translate requirements into a technical blueprint that
      developers can build from.

THE TECHNICAL DESIGN DOCUMENT (TDD):

  Chapter 1: APPLICATION ARCHITECTURE
  ├── Application type (Standard vs Enterprise)
  ├── Plan Types (cubes) and their purposes
  ├── Dense/Sparse assignment
  ├── Block size calculations
  └── Environment strategy (Dev/Test/Prod)

  Chapter 2: DIMENSION DESIGN
  ├── Complete hierarchy for EVERY dimension
  ├── Member properties (Store, Dynamic Calc, etc.)
  ├── Consolidation operators
  ├── Account types and Time Balance settings
  ├── Shared Members and alternate hierarchies
  └── Custom dimensions and their purpose

  Chapter 3: FORM DESIGN
  ├── Form layout specifications (rows, columns, POV)
  ├── Form properties (precision, grid options)
  ├── Business rules (Run on Load, Run on Save)
  ├── Runtime Prompts
  ├── Smart Push configuration
  └── Validation rules

  Chapter 4: CALCULATION DESIGN
  ├── Calc script pseudo-code for every business rule
  ├── FIX scope analysis
  ├── Cross-cube references (@XREF, Smart Push)
  ├── Groovy script specifications
  └── Execution order and dependencies

  Chapter 5: INTEGRATION DESIGN
  ├── Data source mapping (ERP fields → EPM members)
  ├── Load frequency and schedule
  ├── Integration Agent setup (if on-premise sources)
  ├── Error handling and retry logic
  └── Validation checks

  Chapter 6: SECURITY DESIGN
  ├── Role assignments
  ├── Entity-level access control
  ├── Form/folder permissions
  ├── Valid Intersections
  └── SSO/IDCS configuration
```

### Design Review — The Critical Gate

```
DESIGN REVIEW MEETING:

  WHO ATTENDS:
  ├── Client: CFO/VP Finance, FP&A Managers, IT Lead
  ├── SI: Architect, Project Manager, Lead Developer
  └── Duration: 2-4 hours

  WHAT IS REVIEWED:
  ├── Dimension hierarchies (walk through every tree)
  ├── Form mockups (client validates layout)
  ├── Calculation logic (client confirms formulas)
  ├── Data integration flow (client confirms sources)
  └── Timeline and milestones

  APPROVAL:
  Client MUST sign off on the TDD before Phase 4 (Build).
  
  WHY? Because changing dimensions AFTER build = rework.
  Rework = cost overruns + delayed go-live + unhappy client.

  RULE: "Change is free in Design, expensive in Build,
         and catastrophic in Production."
```

# SECTION 6: PHASE 4 — BUILD

---

```
PHASE 4: BUILD
Duration: 6-8 weeks
Team: All developers + Architect (review) + BA (testing)

GOAL: Build the application in the DEV environment.

BUILD ORDER (Dependencies drive the sequence):

  WEEK 1-2: FOUNDATION
  ├── Create application in EPBCS (app type, calendar)
  ├── Build ALL dimensions (Account, Entity, Period, etc.)
  ├── Set Dense/Sparse assignments
  ├── Configure Substitution Variables
  ├── Set up dimension properties (Store, Dynamic Calc)
  └── Verify block size (restructure and check)

  WEEK 3-4: FORMS AND UI
  ├── Create all data input forms
  ├── Configure form properties (precision, grid settings)
  ├── Set up Runtime Prompts
  ├── Create Composite Forms and Dashboards
  ├── Configure Navigation Flows
  ├── Set up Task Lists
  └── Configure Smart Push rules

  WEEK 5-6: CALCULATIONS
  ├── Write all calc scripts (FIX, AGG, CALC DIM)
  ├── Write member formulas (Dynamic Calc members)
  ├── Write Groovy scripts (validation, dynamic logic)
  ├── Create Business Rules in Calc Manager
  ├── Create Rule Sets (execution sequences)
  ├── Link rules to forms (Run on Load, Run on Save)
  └── Test all calculations with sample data

  WEEK 7-8: INTEGRATION AND SECURITY
  ├── Set up Data Integration pipelines
  ├── Configure Integration Agent (if needed)
  ├── Create data mapping tables
  ├── Set up security (roles, access control)
  ├── Configure Valid Intersections
  ├── Configure Approval Flows
  ├── Set up EPM Automate scripts (daily jobs)
  └── Internal developer testing (unit tests)

CODE REVIEW PROCESS:
  Every calc script and Groovy script MUST be reviewed by
  the Architect before deployment.
  
  CHECKLIST:
  □ FIX statement narrows scope appropriately
  □ No CALC ALL on large databases
  □ Comments explain business logic, not code syntax
  □ Groovy has error handling (try/catch)
  □ No hardcoded member names (use variables)
  □ Performance tested with realistic data volume
```

# SECTION 7: PHASE 5 — DATA MIGRATION

---

```
PHASE 5: DATA MIGRATION
Duration: 3-4 weeks (overlaps with later Build weeks)
Team: DI Developer + Business Analyst + Client IT

GOAL: Get data from source systems into EPBCS.

DATA MIGRATION TYPES:

  TYPE 1: HISTORICAL ACTUALS
  ├── Source: ERP (Oracle ERP, SAP, Tally)
  ├── Volume: 2-5 years of monthly data
  ├── Frequency: One-time bulk load
  └── Challenge: Account/Entity mapping from ERP to EPM

  TYPE 2: METADATA (DIMENSIONS)
  ├── Source: ERP master data + Excel files
  ├── Content: Account hierarchy, Entity list, Employee list
  ├── Frequency: Monthly refresh (after initial load)
  └── Challenge: Naming convention alignment

  TYPE 3: ONGOING ACTUALS
  ├── Source: ERP (monthly close data)
  ├── Frequency: Monthly (automated via DI pipeline)
  ├── Challenge: Timing — data must be available after ERP close
  └── Solution: EPM Automate batch script scheduled nightly

  TYPE 4: BUDGET/FORECAST DATA
  ├── Source: Existing Excel budgets (if migrating)
  ├── Volume: Current year + next year
  ├── Frequency: One-time (for migration)
  └── Challenge: Excel format varies by department

DATA MIGRATION STEPS:
  1. EXTRACT    → Pull data from source system
  2. TRANSFORM  → Map source fields to EPM dimensions
  3. VALIDATE   → Check for errors (unmapped members, #Missing)
  4. LOAD       → Push into Essbase cube
  5. VERIFY     → Compare source totals to EPM totals
  6. RECONCILE  → Fix any discrepancies

  GOLDEN RULE: 
  "The data in EPM must EXACTLY match the source system.
   If Revenue in ERP = ₹1,20,00,000, then Revenue in EPM
   MUST also = ₹1,20,00,000. Not ₹1,19,99,999."
```

# SECTION 8: PHASE 6 — TESTING

---

```
PHASE 6: TESTING
Duration: 4-6 weeks
Team: Business Analysts + Client Super Users + Developers (fixes)

TESTING STAGES:

  STAGE 1: SYSTEM INTEGRATION TEST (SIT) — 2 weeks
  ├── WHO: EPM development team
  ├── WHAT: Verify all components work together
  │   ├── Forms open correctly
  │   ├── Calc scripts produce correct results
  │   ├── Data loads complete without errors
  │   ├── Smart View connects and retrieves data
  │   ├── Security filters work as designed
  │   └── Smart Push moves data between cubes
  ├── ENVIRONMENT: Test (migrated from Dev via LCM)
  └── EXIT CRITERIA: All SIT test cases pass

  STAGE 2: USER ACCEPTANCE TEST (UAT) — 3-4 weeks
  ├── WHO: Client business users (NOT the EPM team)
  ├── WHAT: Client validates against their requirements
  │   ├── "Does this form match our budget template?"
  │   ├── "Is this calculation correct for our business?"
  │   ├── "Can I see only my department's data?"
  │   ├── "Does the approval flow work correctly?"
  │   └── "Does the dashboard show the right KPIs?"
  ├── ENVIRONMENT: Test (with realistic data)
  ├── DEFECT MANAGEMENT: Log in Jira/ServiceNow
  │   ├── P1 (Critical): Blocks go-live → fix immediately
  │   ├── P2 (High): Major issue → fix before go-live
  │   ├── P3 (Medium): Important → fix in Phase 8
  │   └── P4 (Low): Nice-to-have → backlog
  └── EXIT CRITERIA: Zero P1/P2 defects, client sign-off

  STAGE 3: PERFORMANCE TEST — 1 week
  ├── WHO: Architect + Developers
  ├── WHAT: Test with production-scale data
  │   ├── Load realistic data volume (100% of entities)
  │   ├── Run calc scripts and measure time
  │   ├── Open forms with 50+ concurrent users
  │   └── Run Smart View retrieval with large POV
  ├── BENCHMARKS:
  │   ├── Form open: < 5 seconds
  │   ├── Data save: < 3 seconds
  │   ├── Calc script: < 5 minutes
  │   └── Data load: < 30 minutes
  └── EXIT CRITERIA: All benchmarks met
```

### The UAT Sign-Off Document

```
UAT SIGN-OFF TEMPLATE:

  "We, the undersigned, confirm that the Oracle EPBCS
   application has been tested against the approved
   requirements and is ready for production deployment.

   □ All P1 and P2 defects have been resolved
   □ Form layouts match approved designs
   □ Calculations produce correct results
   □ Security filters restrict access appropriately
   □ Data integration pipelines load data correctly
   □ Performance meets agreed benchmarks

   Signed: _____________  Date: ___________
   Name: CFO / VP Finance
   
   Signed: _____________  Date: ___________
   Name: FP&A Manager"

  → Without this sign-off, DO NOT go-live.
  → This protects both the client and the consultant.
```

# SECTION 9: PHASE 7 — GO-LIVE AND CUTOVER

---

```
PHASE 7: GO-LIVE AND CUTOVER
Duration: 1-2 weeks
Team: EVERYONE (all hands on deck)

THE CUTOVER PLAN (Step-by-Step):

  DAY -7: PRE-CUTOVER
  ├── Freeze all changes in Dev/Test
  ├── Final LCM migration: Test → Prod
  ├── Verify Prod environment setup
  ├── Run full data load in Prod
  ├── Run all calc scripts in Prod
  └── Final reconciliation (Prod vs source)

  DAY -3: READINESS CHECK
  ├── Verify all user accounts provisioned
  ├── Verify SSO works for all users
  ├── Verify Smart View connections
  ├── Verify EPM Automate scripts in Prod
  ├── Verify backup schedule configured
  └── Go/No-Go decision meeting

  DAY 0: GO-LIVE DAY ★
  ├── Send "Welcome to EPM Cloud" email to all users
  ├── Disable old system (Excel/Hyperion) access
  ├── Monitor user logins and form access
  ├── War room: All consultants available for support
  ├── Track issues in real-time (Jira/Teams channel)
  └── End-of-day status report to executive sponsor

  DAY +1 to +7: STABILIZATION
  ├── Monitor system performance daily
  ├── Fix any critical issues immediately
  ├── Provide hands-on support to struggling users
  ├── Collect user feedback
  └── Daily status calls with client

GO/NO-GO DECISION CRITERIA:
  GO if:
    ✅ UAT sign-off obtained
    ✅ All P1/P2 defects resolved
    ✅ Data reconciliation complete
    ✅ User training completed
    ✅ Backup and DR verified
    ✅ Executive sponsor approved

  NO-GO if:
    ❌ Any P1 defect remains open
    ❌ Data reconciliation fails
    ❌ Users not trained
    ❌ Executive sponsor not confident
```

# SECTION 10: PHASE 8 — HYPERCARE AND STABILIZATION

---

```
PHASE 8: HYPERCARE
Duration: 4-8 weeks (sometimes 3 months)
Team: Reduced team (1-2 consultants + client super users)

GOAL: Ensure the system is stable and users are self-sufficient.

HYPERCARE ACTIVITIES:

  WEEK 1-2: INTENSIVE SUPPORT
  ├── On-site or dedicated remote support (8 hours/day)
  ├── Fix P3/P4 defects from UAT backlog
  ├── Address user feedback and minor enhancements
  ├── Monitor first data load cycle (Actuals → EPM)
  ├── Monitor first budget submission cycle
  └── Daily status calls

  WEEK 3-4: REDUCED SUPPORT
  ├── Support reduced to 4 hours/day
  ├── Knowledge transfer to client super users
  ├── Create operations runbook
  ├── Document all known issues and workarounds
  └── Weekly status calls

  WEEK 5-8: TRANSITION TO BAU
  ├── Support reduced to as-needed (2-3 hours/week)
  ├── Hand over EPM Automate scripts to client ops
  ├── Complete admin training for client team
  ├── Final documentation package delivered
  ├── Lessons learned session
  └── Project closure and sign-off

EXIT CRITERIA:
  ✅ Client team can handle day-to-day operations
  ✅ All P3 defects resolved or accepted
  ✅ Documentation package complete
  ✅ Admin training completed
  ✅ Knowledge transfer sign-off
  ✅ First full budget cycle completed successfully
```

# SECTION 14: HOTEL PVT LTD — IMPLEMENTATION STORY

```
HOTEL PVT LTD — EPBCS IMPLEMENTATION TIMELINE

  PROJECT: "HotelPlan" — Revenue + Expense Planning
  Duration: 7 months (March 2026 → September 2026)
  Team: 6 people (3 consultants + 3 client)
  Budget: ₹1.2Cr (consulting) + ₹45L (Oracle license/year)

  MARCH (Phase 1: Discover)
  ├── Consultant team visits Hotel Mumbai HQ
  ├── Interviews CFO, 5 Hotel GMs, Finance Controller
  ├── Current state: Excel-based budgeting (12-week cycle)
  ├── Pain: Version chaos, late submissions, no variance reports
  └── Scope: Revenue Planning + Expense Budget + KPI Dashboard

  APRIL (Phase 2: Requirements + Phase 3: Design)
```

# SECTION 15: COMMON MISTAKES

---

| Mistake | Impact | Correct Approach |
|---------|--------|-----------------|
| Skipping Phase 1 (Discover) | Building the wrong thing | Always assess current state before designing |
| Weak requirements (vague) | Scope creep, rework | Every requirement must have acceptance criteria |
| No TDD sign-off | Client changes requirements after build | Get written sign-off before Phase 4 |
| Building in Prod directly | No rollback if something breaks | ALWAYS build in Dev, test in Test, deploy to Prod |
| Skipping performance testing | System crashes on Day 1 with 100 users | Test with production-scale data before go-live |
| No data reconciliation | CFO doesn't trust the numbers | Reconcile EVERY data load to 3+ decimal places |
| No user training | Users call help desk 50 times on Day 1 | Train super users first, then they train end users |
| No hypercare plan | Consultant leaves, client is stranded | Plan 4-8 weeks of post-go-live support |
| No change management | Users resist the new system | Communicate early, involve users in design |

# SECTION 16: INTERVIEW QUESTIONS

---

### Beginner

**Q1: What are the main phases of an EPM implementation?**
> The 8 phases are: 1) Discover/Assess, 2) Requirements Gathering, 3) Design, 4) Build, 5) Data Migration, 6) Testing (SIT + UAT), 7) Go-Live/Cutover, 8) Hypercare/Stabilization. A typical implementation takes 4-12 months depending on complexity.

**Q2: What is the difference between SIT and UAT?**
> SIT (System Integration Testing) is done by the EPM development team to verify all technical components work together. UAT (User Acceptance Testing) is done by the CLIENT's business users to verify the system meets their requirements. UAT is the gate — the client must sign off before go-live.

### Intermediate

**Q3: What is a Technical Design Document (TDD)?**
> The TDD is the blueprint of the EPM application. It contains: application architecture (app type, plan types), dimension hierarchies with all member properties, form specifications (layout, properties, business rules), calculation logic (pseudo-code for every calc script), integration design (data sources, mappings), and security design (roles, access control). The TDD must be signed off by the client before the Build phase begins.

**Q4: How do you handle scope creep during an EPM implementation?**
> 1) Establish a formal Change Request (CR) process in Phase 1. 2) Any new requirement must be submitted as a CR with: description, priority, impact on timeline, and impact on budget. 3) The project steering committee reviews and approves/rejects CRs. 4) Approved CRs are documented and the project plan is updated. 5) Never agree to scope changes verbally — always get written approval.

### Architect

**Q5: A client's go-live is in 2 weeks. UAT found 3 P2 defects and 15 P3 defects. What do you recommend?**
> For the 3 P2 defects: Fix immediately — these are critical. Extend the UAT window by 1 week if needed to retest the fixes. No go-live until P2s are resolved. For the 15 P3 defects: Log them in the Hypercare backlog. They should NOT delay go-live. Fix them during Phase 8 (Hypercare) over the first 4 weeks. Communicate this plan to the executive sponsor: "We go live on schedule with zero P1/P2 defects. The 15 P3s (cosmetic/minor) will be fixed during Hypercare." This is the standard approach — waiting for perfection means never going live.
