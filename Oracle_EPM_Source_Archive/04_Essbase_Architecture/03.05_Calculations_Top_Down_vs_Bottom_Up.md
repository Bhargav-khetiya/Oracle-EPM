# 03.05 — Calculations: Top-Down vs Bottom-Up: Complete Guide

> **Module:** 03_Essbase | **Topic:** Calculation Engine Mechanics
> **Audience:** Architect / Senior Consultant

---

## 1. WHY — What Real-World Problem Does This Solve—

**The problem:** You write a business rule that should take 2 seconds. Instead, it takes 2 hours. There's no syntax error — the formula is mathematically correct. But Essbase chose a different **algorithm** to execute it, and that algorithm is exponentially slower. Understanding WHY Essbase chose the slow path is the most important performance skill in EPM.

---

## 2. WHAT — The Two Calculation Algorithms

Essbase has exactly two algorithms for traversing the database during calculation. The formula you write determines which algorithm Essbase uses.

```
BOTTOM-UP (The Fast Way):
┌───────────────────────────────────────────────────┐
│ Essbase scans the HARD DRIVE for existing blocks  │
│ Opens each block that has data                    │
│ Applies the formula to cells INSIDE the block     │
│ Closes the block and moves to the next one         │
│                                                    │
│ ⚡ Speed: Processes only existing data             │
│ 📊 If 200 blocks exist → 200 calculations         │
└───────────────────────────────────────────────────┘

TOP-DOWN (The Slow Way):
┌───────────────────────────────────────────────────┐
│ Essbase reads the OUTLINE (dimension hierarchy)   │
│ Starts from the top-most parent                   │
│ Works down through EVERY possible member combo    │
│ Checks: "Do I need to calculate here—            │
│                                                    │
│ 🐌 Speed: Evaluates ALL possible intersections    │
│ 📊 If 36,000 possible combos → 36,000 evaluations│
│    Even if only 200 have data!                    │
└───────────────────────────────────────────────────┘
```

### Visual Comparison

```
Database: 5 hotels × 3 scenarios × 3 versions × 3 years
Possible blocks: 5 × 3 × 3 × 3 = 135
Blocks with data: 20 (only Budget/Working/FY2026 for each hotel)

BOTTOM-UP:                    TOP-DOWN:
  Processes: 20 blocks          Evaluates: 135 combinations
  Time: 2 seconds               Time: 15 seconds
  
  Scale up to 100 entities:
  BOTTOM-UP: 400 blocks         TOP-DOWN: 2,700 combos
  Time: 8 seconds               Time: 5 minutes

  Scale up to 1,000 entities:
  BOTTOM-UP: 4,000 blocks       TOP-DOWN: 27,000 combos
  Time: 40 seconds              Time: 2 hours
```

## 3. WHAT TRIGGERS EACH ALGORITHM—

### Bottom-Up Triggers (FAST — What You Want)

```essbase
/* 1. Simple within-block formulas */
"Total_Revenue" = "Room_Rev" + "F&B_Rev" + "Spa_Rev";
/* All Account members (Dense) → same block → Bottom-Up */

/* 2. FIX on sparse dimensions */
FIX(@RELATIVE("All_Hotels", 0))
  "Net_Income" = "Total_Revenue" - "Total_Expenses";
ENDFIX
/* FIX limits scope → processes only matching blocks */

/* 3. Aggregation of sparse dimensions */
AGG("Entity");
/* Bottom-Up: reads existing blocks, sums to parents */
```

### Top-Down Triggers (SLOW — What You Avoid)

```essbase
/* 1. Cross-dimensional reference on SPARSE dimension */
"Bonus" = "Salary" -> "Corporate_HQ";
/* Entity is Sparse → Essbase must look across blocks */
/* Forces outline-driven traversal */

/* 2. @ANCESTVAL, @PARENTVAL on sparse dimensions */
"Allocation" = "Total_Cost" * ("Revenue" / @ANCESTVAL("Entity", "Revenue"));
/* Looks up the ancestor's value → forces Top-Down */

/* 3. SET CREATENONMISSINGBLK ON + broad formula */
SET CREATENONMISSINGBLK ON;
"NewAccount" = "ExistingAccount" * 1.10;
/* Creates blocks for EVERY possible intersection → explosion */

/* 4. No FIX statement at all */
"X" = "Y" + "Z";
/* No FIX = process entire cube = Top-Down behavior */
```

## 4. HOW TO DETECT WHICH ALGORITHM IS RUNNING

### Method 1: Check the Calc Log

```
Enable calc logging:
  Essbase → Database Properties → Calc → SET MSG DETAIL

Log output for Bottom-Up:
  "Calc: Using bottom-up calculation method"
  "Processing block [Mumbai_Hotel, Budget, Working, FY2026]"
  "Blocks processed: 20"

Log output for Top-Down:
  "Calc: Using top-down calculation method"
  "Outline pass..."
  "Blocks evaluated: 27,000"
  "Blocks created: 5,400"  ← BLOCK EXPLOSION!
```

### Method 2: Timing

```
If a simple formula takes disproportionately long:
  5 hotels: 2 seconds → 10 hotels: 4 seconds → Linear = Bottom-Up ✅
  5 hotels: 2 seconds → 10 hotels: 30 seconds → Exponential = Top-Down ❌
```

## 5. THE DECISION TREE

```
Is the formula a simple within-block operation—
├── YES (all members in same Dense dimension)
│   → BOTTOM-UP ✅
│
└── NO (references members in different Sparse blocks)
    │
    ├── Is there a cross-dim (->) on a Sparse dimension—
    │   → TOP-DOWN ❌ (use two-pass pattern to avoid)
    │
    ├── Is CREATENONMISSINGBLK or CREATEBLOCKONEQ ON—
    │   → May create excessive blocks (turn OFF after use)
    │
    ├── Is @ANCESTVAL or @PARENTVAL used on Sparse dim—
    │   → TOP-DOWN ❌ (store ancestor value in variable first)
    │
    └── Is there a FIX statement limiting scope—
        ├── YES → Likely BOTTOM-UP within the FIX scope ✅
        └── NO → Processes entire cube → effectively Top-Down ❌
```

## 6. SHOW ME — Hotel Pvt Ltd: Same Calculation, Two Ways

### The Business Requirement

"Each hotel's Corporate Allocation = Corporate Overhead × (Hotel Revenue / Total Revenue)"

### The Slow Way (Top-Down)

```essbase
/* ❌ Forces Top-Down — cross-dim on sparse Entity */
FIX("Budget", "Working", &CurrYear)
  FIX(@RELATIVE("All_Hotels", 0))
    IF("Total_Revenue" -> "All_Hotels" <> 0)
      "Corp_Allocation" = "Total_Corp_Overhead" -> "Corporate_HQ" *
        ("Total_Revenue" / "Total_Revenue" -> "All_Hotels");
    ENDIF
  ENDFIX
ENDFIX

/* Two cross-dim references on Entity (Sparse):
   -> "Corporate_HQ" and -> "All_Hotels"
   Forces Top-Down. With 5 hotels: 15 seconds.
   With 500 entities: 4 hours. */
```

### The Fast Way (Bottom-Up)

```essbase
/* ✅ Two-pass pattern — eliminates cross-dim on sparse */
SET LOCKBLOCK ON;

/* Pass 1: Store corporate overhead in a variable */
VAR v_CorpOverhead;
VAR v_TotalRevenue;

FIX("Corporate_HQ", "Budget", "Working", &CurrYear, "YearTotal")
  v_CorpOverhead = "Total_Corp_Overhead";
ENDFIX

FIX("All_Hotels", "Budget", "Working", &CurrYear, "YearTotal")
  v_TotalRevenue = "Total_Revenue";
ENDFIX

/* Pass 2: Allocate to each hotel — no cross-dim! */
FIX("Budget", "Working", &CurrYear)
  FIX(@RELATIVE("All_Hotels", 0))
    IF(v_TotalRevenue <> 0)
      "Corp_Allocation" = v_CorpOverhead * ("Total_Revenue" / v_TotalRevenue);
    ENDIF
  ENDFIX
ENDFIX

SET LOCKBLOCK OFF;

/* All sparse references replaced with variables.
   Bottom-Up only. With 5 hotels: 2 seconds.
   With 500 entities: 10 seconds. LINEAR scaling! */
```

## 7. COMMON MISTAKES

| Mistake | Algorithm | Fix |
|---------|-----------|-----|
| Cross-dim on sparse dimension | Top-Down | Two-pass pattern with variables |
| No FIX statement | Top-Down behavior | Always wrap formulas in FIX |
| @PARENTVAL on sparse dim | Top-Down | Store parent value in variable first |
| CREATEBLOCKONEQ left ON | Block explosion | Turn OFF immediately after use |
| Assuming AGG is always fast | Bottom-Up but slow if many dims | AGG only sparse dims that changed |

## 8. INTERVIEW QUESTIONS

### Beginner
**Q: What is the difference between Bottom-Up and Top-Down calculation in Essbase—**
> **Bottom-Up:** Essbase scans existing data blocks on disk and applies formulas only to blocks that have data. Fast because it skips empty intersections. **Top-Down:** Essbase reads the dimension outline from the top and evaluates every possible member combination, even empty ones. Slow because it processes millions of potential intersections. A cross-dimensional reference on a sparse dimension (`-> "OtherEntity"`) is the #1 trigger for Top-Down.

### Architect
**Q: A corporate allocation rule works fine with 5 entities (2 seconds) but takes 4 hours with 500 entities. Diagnose and fix.**
> The rule likely contains a cross-dimensional reference on the Entity dimension (sparse), such as `-> "Corporate_HQ"` or `-> "All_Hotels"`. This forces Top-Down calculation. With 5 entities, Top-Down evaluates 5 × (other sparse combos) = manageable. With 500 entities, it evaluates 500 × (combos) = explosion. **Fix:** Use the two-pass pattern: (1) Store the Corporate/All_Hotels values in calc script variables. (2) Use those variables in the allocation formula — no cross-dim needed. Result: Bottom-Up calculation that scales linearly (500 entities = 10 seconds instead of 4 hours).
