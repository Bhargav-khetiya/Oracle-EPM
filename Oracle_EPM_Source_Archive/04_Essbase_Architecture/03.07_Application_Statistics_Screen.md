# 03.07 — Application Statistics Screen: Complete Guide

> **Module:** 03_Essbase | **Topic:** Application Statistics, Database Properties, Monitoring
> **Audience:** Service Administrator / Architect

---

## 1. WHY — What Real-World Problem Does This Solve—

**The problem:** How big is the cube— How many blocks exist— Is the database fragmented— Is the cache optimally sized— Without statistics, you're tuning performance blindly. A 5GB cube with 80% fragmentation needs restructuring, but you'd never know without checking.

**The solution:** Application Statistics shows real-time metrics about the Essbase database — block count, database size, fragmentation, cache utilization, and dimension density. It's the **health dashboard** for your cube.

---

## 2. HOW TO ACCESS

```
Method 1 (Web): Calculation Manager → Essbase → Database Properties → Statistics
Method 2 (EPM Automate): epmautomate getAppStatistics
Method 3 (REST API): GET /HyperionPlanning/rest/v3/applications/{app}/statistics
```

## 3. ALL STATISTICS — COMPLETE REFERENCE

### Block Storage (BSO) Statistics

| Metric | Description | Healthy Range | Action If Bad |
|--------|-------------|---------------|---------------|
| **Number of Existing Blocks** | Physical data blocks on disk | Depends on app | If much higher than expected → block explosion |
| **Potential Number of Blocks** | Max possible blocks (all sparse combos) | N/A (theoretical max) | If existing/potential ratio > 50% → over-dense |
| **Block Size (bytes)** | Size of one data block | 8KB - 100KB optimal | > 200KB → too many dense members |
| **Block Density (%)** | % of cells in a block with data | > 20% ideal | < 5% → too many dense dims → redesign |
| **Database Size (disk)** | Total size on disk | Varies | Track growth monthly |
| **Average Clustering Ratio** | Data locality on disk | > 0.8 optimal | < 0.5 → restructure needed |
| **Fragmentation (%)** | Wasted space from deletes/updates | < 20% optimal | > 30% → restructure |

### Dimension Statistics

| Metric | Description |
|--------|-------------|
| **Dimension Name** | Each dimension in the cube |
| **Members** | Total member count |
| **Stored Members** | Members that store data (non-Dynamic Calc) |
| **Dense/Sparse** | Storage classification |
| **Compression** | Compression dimension (the first Dense dim) |

### Cache Statistics

| Metric | Description | Healthy Range |
|--------|-------------|---------------|
| **Data Cache Size** | Memory allocated for data blocks | Enough to hold frequently used blocks |
| **Index Cache Size** | Memory for block index | > total index size |
| **Data Cache Hit Ratio** | % of reads served from cache | > 90% |
| **Index Cache Hit Ratio** | % of index lookups from cache | > 95% |

## 4. READING THE STATISTICS — DIAGNOSTIC GUIDE

### Scenario 1: Block Explosion Detection

```
Check: Existing Blocks = 500,000 (Expected: 5,000)
Diagnosis: Block explosion — 100× more blocks than expected
Cause: A rule with CREATEBLOCKONEQ ON created blocks everywhere
Fix: 
  1. Identify when block count jumped (check Jobs Console)
  2. CLEARBLOCK ALL (removes empty blocks)
  3. Fix the rule that caused the explosion
  4. Re-run CLEARBLOCK ALL
  5. Restructure database
```

### Scenario 2: Poor Block Density

```
Check: Block Density = 2%
Diagnosis: 98% of cells in each block are empty
Cause: Too many members in Dense dimensions
       Example: 500 accounts × 12 months × 2 currencies = 12,000 cells/block
       But only 240 cells have data = 2% density
Fix:
  1. Move low-cardinality sparse dims from Dense to Sparse
  2. Or move high-cardinality dims from Dense to Sparse
  3. Target: 20-50% block density
```

### Scenario 3: High Fragmentation

```
Check: Fragmentation = 45%
Diagnosis: Nearly half the database file is wasted space
Cause: Many data clears, imports, and overwrites without restructuring
Fix:
  1. Export data
  2. Clear all data
  3. Restructure database
  4. Reimport data
  OR: Simply run "Compact Outline" in Calc Manager
```

## 6. COMMON MISTAKES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Never checking statistics | Performance degrades silently | Check monthly |
| Ignoring fragmentation > 30% | Slow queries, disk waste | Restructure database |
| Not monitoring block count | Block explosion goes undetected | Set baseline, alert on 2× increase |
| Cache too small | Hit ratio < 80% | Increase cache allocation |
| Block size > 200KB | Slow I/O, memory issues | Move dense dims to sparse |

## 7. INTERVIEW QUESTIONS

### Beginner
**Q: What is Block Density and why does it matter—**
> Block Density is the percentage of cells within a block that actually contain data (not #MISSING). If density is 2%, that means 98% of each block is empty space — extremely wasteful. This happens when too many members are Dense, creating oversized blocks. Ideal density is 20-50%. Fix: Move low-density dimensions from Dense to Sparse.

### Architect
**Q: After a data load, block count jumped from 5,000 to 500,000. What happened and how do you fix it—**
> **Block explosion.** The data load (or a rule running after the load) had SET CREATEBLOCKONEQ ON or SET CREATENONMISSINGBLK ON, which created blocks for every possible sparse combination — even ones without data. **Fix:** (1) Run CLEARBLOCK ALL to remove empty blocks. (2) Check the data load mapping — are values being loaded to non-existent sparse intersections— (3) Check if a rule with CREATEBLOCKONEQ ON ran after the load. (4) After cleanup, verify block count returns to ~5,000. (5) Set up monitoring to alert when block count exceeds 2× baseline.
