## 🏗️ Essbase Internal Architecture — Complete

### How Essbase Stores Data

```
Essbase Database
├── essn.pag files (Page files — actual data)
│   └── Contains DATA BLOCKS (one per unique sparse combination)
├── essn.ind files (Index files — block pointers)
│   └── Maps sparse combinations → block locations
├── essn.otl file (Outline — dimension metadata)
│   └── All dimensions, members, properties, formulas
└── essn.log file (Transaction log)
    └── Change tracking for recovery
```

### Data Block Internals

```
One Block = One unique intersection of ALL Sparse dimension members

Example Sparse dimensions: Entity(100) × Scenario(3) × Version(2) × Year(5)
Maximum possible blocks = 100 × 3 × 2 × 5 = 3,000 blocks

Each block contains:
┌─────────────────────────────────────────────────┐
│  All Dense dimension L0 intersections           │
│  Account(200 L0) × Period(12 L0) = 2,400 cells  │
│  Size = 2,400 × 8 bytes = 19,200 bytes = ~19 KB │
└─────────────────────────────────────────────────┘

Block Header (metadata):
- Block address (sparse dimension combination)
- Dirty flag (modified since last calc?)
- Lock status (being written to?)
- Compression info
```

### Block Creation & Lifecycle

```
1. Block does NOT exist by default
2. Block is CREATED when:
   - Data is loaded to that intersection
   - User enters data in a form
   - A calc script writes data (with SET CREATEBLOCKONEQ ON)
3. Block is DESTROYED when:
   - All cells in the block become #Missing
   - Admin runs CLEARBLOCK
4. Empty blocks waste space → periodically clean with CLEARBLOCK
```

### 🎯 Hands-On: Understanding Blocks

```
Exercise 1: Block Existence Test
1. Open a form → enter data for Entity=E10001, Scenario=Budget, Year=FY27
2. Save → a block is now created for (E10001, Budget, Working, FY27)
3. Open Smart View ad-hoc → check: can you see data? YES
4. Clear all data for that intersection → block still exists (with #Missing)
5. Run: CLEARBLOCK in a calc script → block is destroyed
6. Ad-hoc → data no longer retrievable (block gone)

Exercise 2: Block Count Impact
1. Calculate maximum possible blocks for your application:
   Entities(L0) × Scenarios × Versions × Years × Custom_Sparse_Dims
2. Calculate actual blocks: Application → Overview → Database Statistics
3. Block density = Actual / Maximum × 100
4. If density < 5% → Sparse assignment is correct
5. If density > 50% → consider making a Sparse dim Dense
```

## 📌 BSO vs ASO — Complete Technical Comparison

| Feature | BSO (Block Storage) | ASO (Aggregate Storage) |
|---------|--------------------|-----------------------|
| **Write-back** | ✅ Yes — users enter data | ❌ No — read-only |
| **Calc Scripts** | ✅ Full calc script support | ❌ No calc scripts |
| **Formulas** | ✅ Member formulas | ✅ MDX formulas only |
| **Data Load** | ✅ Load to any intersection | ✅ Load to L0 only |
| **Aggregation** | Manual (AGG/CALC DIM) or on-the-fly (Dynamic Calc) | ✅ Automatic |
| **Block Storage** | ✅ Physical blocks | ❌ No blocks — cell-based |
| **Performance: Retrieval** | Good | ✅ Excellent (built for it) |
| **Performance: Calc** | ✅ Excellent | Limited |
| **Max Dimensions** | 32 | 32 (but more efficient with many) |
| **Use Case** | Planning, budgeting, forecasting | Reporting, consolidation, analysis |
| **EPBCS Cubes** | FinPlan, Workforce, Capital | Reporting (OEP_REP) |

### When to Use Each in EPBCS

```
BSO Cubes (write-back, calculations):
├── FinPlan → Revenue planning, expense budgeting, P&L
├── OEP_WFP (Workforce) → Headcount, salaries, benefits
└── OEP_CAP (Capital) → Asset purchases, depreciation

ASO Cubes (fast reporting):
└── OEP_REP (Reporting) → Consolidated views, dashboards
    ↑ Data pushed from BSO cubes via Smart Push / Data Maps
```

### 🎯 Hands-On: BSO vs ASO Comparison


## 🎓 Essbase Calculation Order — Critical for Interview

### Evaluation Order

```
Step 1: Member Formulas are evaluated FIRST
Step 2: Consolidation operators (+, -, ~) are evaluated SECOND
Step 3: Two-Pass members are recalculated LAST

Example:
Account hierarchy:
├── Revenue (+) [no formula → uses consolidation]
│   ├── Product A (+)
│   └── Product B (+)
├── Expenses (+) [no formula → uses consolidation]
│   ├── Salary (+)
│   └── Rent (+)
├── Profit [formula: Revenue - Expenses] ← Step 1: formula overrides (+)
└── Margin % [formula: Profit / Revenue * 100, Two-Pass] ← Step 3: recalculated

Execution flow:
1. Product A, Product B → sum into Revenue (consolidation)
2. Salary, Rent → sum into Expenses (consolidation)
3. Profit = Revenue - Expenses (formula, overrides consolidation)
4. Margin % = Profit / Revenue * 100 (Two-Pass, runs AFTER all aggregation)
```

### Why Two-Pass is Critical

```
WITHOUT Two-Pass (Margin % as regular Dynamic Calc):
Entity: Mumbai → Revenue=1000, Profit=300 → Margin=30%
Entity: Delhi → Revenue=500, Profit=100 → Margin=20%
Total Company → Revenue=1500, Profit=400, Margin=30%+20%=50% ← WRONG!

WITH Two-Pass:
Entity: Mumbai → Revenue=1000, Profit=300 → Margin=30%
Entity: Delhi → Revenue=500, Profit=100 → Margin=20%
Total Company → Revenue=1500, Profit=400 → recalculated: Margin=400/1500=26.7% ✅
```

### 💡 Logic & Purpose
The "Two-Pass" setting exists to fix the mathematical impossibility of summing percentages or ratios across a hierarchy. During Pass 1, Essbase aggregates all standard members up the hierarchy (Sum, subtract, etc.). During Pass 2, Essbase goes back through and recalculates any member tagged as "Two-Pass" at the parent level, ensuring the parent ratio uses the newly aggregated total numbers, rather than adding up the children's ratios.

### 🌀 Confusion Resolution
> **Misconception:** "I tagged my Account as Two-Pass, but it still isn't calculating correctly at the top level."
> **Reality:** A Two-Pass tag ONLY works if the member is *also* tagged as `Dynamic Calc`. If the member is tagged as `Store`, Essbase completely ignores the Two-Pass flag. Furthermore, if you are doing a complex cross-dimensional ratio calculation, both the numerator and denominator accounts must exist in the same dimension (usually Account) for Two-Pass to fire reliably.

### 😈 Twisted Interview Question
**Question:** An architect creates an Account called "Gross Margin %". They set it to `Dynamic Calc` and check the `Two-Pass` box. The formula is `"Gross Profit" / "Total Revenue"`. However, when users look at Q1, the margin percentage is wildly incorrect, but January is correct. What happened?
> **Answer:** The architect forgot to set the `Time Balance` property to `Never Share` (or `None`). Because the Time Balance defaulted to `Flow` (Addition), the Period dimension simply added January Margin (30%) + February Margin (30%) + March Margin (30%) = Q1 Margin (90%), ignoring the Two-Pass calculation at the time level. Two-Pass must be paired with `Time Balance = None / Never Share` to calculate correctly across Periods!

## 📌 Essbase Addressing Modes

### Cell Addressing

```
Simple Address: "Revenue"
→ Uses current POV for all other dimensions

Cross-Dimensional Address: "Revenue" -> "Actual" -> "FY26"
→ Explicit reference to specific members
→ Uses -> operator to specify dimensions

Example in calc script:
FIX("Budget", "Working", "FY27")
    "Revenue" = "Revenue" -> "Actual" -> "Final" -> "FY26" * 1.10;
    /* Left side: uses FIX context (Budget, Working, FY27) */
    /* Right side: explicitly references Actual, Final, FY26 */
ENDFIX
```

### @Functions for Addressing

```
@PRIOR("Revenue")          → Previous period's Revenue (Jan → reads Dec prior year)
@NEXT("Revenue")           → Next period's Revenue
@SHIFT("Revenue", -3)      → 3 periods ago
@PARENTVAL("Entity", "Revenue") → Revenue at parent entity level
@CURRMBRRANGE("Period", "Jan", "Jun") → Loop through Jan-Jun
```

### 🎯 Hands-On: Addressing Practice

```
Exercise 8: Cross-Dimensional References
1. Write a rule that copies Actual FY26 to Budget FY27:
   FIX("Budget", "Working", "FY27", @RELATIVE("Entity", 0))
       "Revenue" = "Revenue" -> "Actual" -> "Final" -> "FY26";
   ENDFIX
2. Write a rule that calculates Year-over-Year growth:
   "YoY_Growth" = ("Revenue" - "Revenue" -> &PriorYear) / "Revenue" -> &PriorYear * 100;
3. Write a rule using @PRIOR for Month-over-Month:
   "MoM_Change" = "Revenue" - @PRIOR("Revenue");
4. Test all 3 rules → verify results in a form
```

## 🎓 Interview Questions (Oracle Official Level)

**Q: Explain what happens internally when a user opens a form.**
> (1) EPM sends a retrieval request to Essbase. (2) Essbase identifies which blocks are needed (based on Sparse member POV). (3) For each block, it reads the Index file to find the block location. (4) It reads the Page file to get the block data. (5) For Dynamic Calc members, it calculates on-the-fly. (6) Results are sent back to the EPM layer, which formats them into the form layout.

**Q: What determines how many blocks exist in a database?**
> Number of blocks = Product of Level 0 member counts of all SPARSE dimensions that have data. Example: Entity(50) × Scenario(3) × Version(2) × Year(5) = 1,500 maximum blocks. Actual blocks will be fewer — only intersections WITH data create blocks.

**Q: Why do we make parents Dynamic Calc instead of Store?**
> Store parents physically save the aggregated value, consuming disk space and requiring explicit aggregation (AGG/CALC DIM). Dynamic Calc parents aggregate on-the-fly during retrieval — no storage, always current. Trade-off: slightly slower retrieval but always accurate and less disk usage.

**Q: Explain the difference between SET UPDATECALC ON and SET CREATEBLOCKONEQ ON.**
> SET UPDATECALC ON tells Essbase to only recalculate "dirty" blocks (blocks with changed data since last calc) — performance optimization. SET CREATEBLOCKONEQ ON tells Essbase to create new blocks when assigning data to sparse intersections that don't yet have blocks — without it, data assignments to new intersections are silently lost.

## 📝 Summary

| Key Point | Detail |
|-----------|--------|
| **Block** | One per unique Sparse member combination. Size = Dense L0 × 8 bytes |
| **Index** | Maps Sparse combos to block locations in Page file |
| **BSO** | Write-back, calc scripts, blocks — for planning |
| **ASO** | Read-only, auto-aggregate, cell-based — for reporting |
| **Calc Order** | Formulas first → Consolidation → Two-Pass last |
| **Two-Pass** | Recalculates AFTER aggregation — essential for ratios |
| **Addressing** | `->` for cross-dim, @PRIOR/@NEXT for temporal |
