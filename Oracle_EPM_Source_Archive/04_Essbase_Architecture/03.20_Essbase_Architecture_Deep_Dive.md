# SECTION 1: OLAP FUNDAMENTALS

---

## 1.1 OLTP vs OLAP

| Aspect | OLTP (SQL Databases) | OLAP (Essbase) |
|--------|---------------------|----------------|
| **Full Form** | Online Transaction Processing | Online Analytical Processing |
| **Purpose** | Record individual transactions | Analyze aggregated data |
| **Data Model** | Relational (tables, rows, columns) | Multidimensional (cubes, dimensions, members) |
| **Query Type** | "Show me invoice #47823" | "Show me total Q3 revenue for all hotels" |
| **Optimization** | Write-heavy (INSERT, UPDATE) | Read-heavy (SELECT with aggregation) |
| **Aggregation** | Must use GROUP BY, SUM() queries | Pre-calculated or dynamic aggregation |
| **Example Product** | Oracle Database, MySQL, PostgreSQL | Oracle Essbase, SAP BW, IBM TM1 |

## 1.2 What Makes Essbase Special

Essbase stores data at the **intersection** of multiple dimensions. Instead of scanning millions of rows with GROUP BY, Essbase directly addresses the cell.

```
SQL approach to find January Budget Revenue for Hotel India:
  SELECT SUM(amount) 
  FROM transactions 
  WHERE account = 'Revenue' 
    AND period = 'Jan' 
    AND scenario = 'Budget' 
    AND entity = 'Hotel India'
    AND year = 'FY26';
  → Scans potentially millions of rows
  → Requires indexes, joins, optimization

Essbase approach:
  Direct address: [Revenue, Jan, Budget, Hotel India, FY26]
  → Immediate lookup — no scanning
  → The data is PRE-POSITIONED at this intersection
```

## 1.3 The Cube Mental Model

Think of a 3D Rubik's Cube:
```
                    Entity
                   ↗
            ┌──────────────┐
           /│             /│
          / │            / │
         /  │           /  │
        ┌───┼──────────┐   │
        │   │          │   │
Period→ │   │   DATA   │   │ ← Each cell at the intersection
        │   │          │   │    contains a number
        │   └──────────┼───┘
        │  /           │  /
        │ /            │ /
        │/             │/
        └──────────────┘
              ↑
           Account
```

But Essbase is not limited to 3 dimensions. A typical EPBCS application has 8-15 dimensions, creating a **hypercube**.

```
Hotel Pvt Ltd Hypercube (10 dimensions):
  Account × Entity × Period × Year × Scenario × Version × 
  Currency × Department × PlanElement × Custom1

One cell = one number at ONE specific intersection:
  [Revenue, Hotel India, Jan, FY26, Budget, Working, INR, Catering, No PlanElement, No Custom1]
  = ₹18,00,000
```

## 2.1 Dimensions

A **Dimension** is a category of analysis. Each dimension contains **members** organized in a **hierarchy**.

```
Example Dimensions and their Members:

Account Dimension:
  Total P&L
    ├── Revenue
    │   ├── 100110: Rooms Revenue
    │   ├── 100120: Banquet Revenue
    │   └── 100130: F&B Revenue
    └── Expense
        ├── 200000: Salaries
        ├── 200010: Benefits
        └── 200020: Utilities

Entity Dimension:
  All Entities
    ├── E10001: Hotel India
    ├── E10002: Hotel USA
    └── E10003: Hotel UK

Period Dimension:
  YearTotal
    ├── Q1
    │   ├── Jan
    │   ├── Feb
    │   └── Mar
    ├── Q2
    │   ├── Apr
    │   ├── May
    │   └── Jun
    ├── Q3 ...
    └── Q4 ...

Scenario Dimension:
  All Scenarios
    ├── Actual
    ├── Budget
    └── Forecast
```

## 2.2 Members

**Members** are the individual items within a dimension.

### Member Types:
| Member Type | Description | Can Accept Data Input— | Example |
|-------------|-------------|----------------------|---------|
| **Level 0 (Leaf)** | Bottom of the hierarchy, no children | ✅ Yes | "Jan", "100110: Rooms Revenue" |
| **Parent** | Has children, typically aggregates | ❌ (usually Dynamic Calc) | "Q1", "Revenue" |
| **Shared** | An alias pointer to an existing member | Depends on base member | "Rooms Revenue" in alternate hierarchy |
| **Label Only** | No data storage — organizational only | ❌ No | "Operating Accounts" (a grouping label) |

## 2.3 Hierarchies

Members are organized in parent-child relationships:

```
Revenue (Parent — Level 2, Generation 1)
  ├── Rooms Revenue (Child — Level 1, Generation 2)
  │     ├── Room Revenue Rack (Leaf — Level 0, Generation 3)
  │     └── Room Revenue Discounted (Leaf — Level 0, Generation 3)
  ├── Banquet Revenue (Leaf — Level 0, Generation 2)
  └── F&B Revenue (Leaf — Level 0, Generation 2)

Consolidation:
  Revenue = Rooms Revenue + Banquet Revenue + F&B Revenue
  Rooms Revenue = Room Revenue Rack + Room Revenue Discounted
```

# SECTION 3: DENSE VS SPARSE — THE COMPLETE MENTAL MODEL

---

## 3.1 The Core Concept

Every dimension in Essbase is classified as either **Dense** or **Sparse**. This classification fundamentally determines how data is physically stored.

### Dense Dimension
> A dimension where **most** intersections will have data values.

### Sparse Dimension
> A dimension where **most** intersections will be empty (#Missing).

## 3.2 Why This Matters — The Storage Problem

```
Consider a simple application with 5 dimensions:
  Account: 500 members
  Period: 12 members
  Entity: 100 members
  Scenario: 3 members
  Version: 2 members

Total possible intersections = 500 × 12 × 100 × 3 × 2 = 3,600,000 cells

But in reality:
  - Not every entity has data for every account (e.g., "Hotel India" has no "US Tax Expense")
  - Not every scenario has data for every version (e.g., "Actual" has no "Working" version)
  - Maybe only 10% of intersections actually have data = 360,000 cells

Storing all 3,600,000 cells wastes 90% of storage.
Essbase's dense/sparse system avoids this waste.
```

## 3.3 How Dense/Sparse Creates Blocks

Essbase uses the Dense/Sparse classification to create **data blocks**:

```
BLOCK = All Dense Dimension Members × One Specific Sparse Intersection

If Dense = Account (500) × Period (12)
   Sparse = Entity (100) × Scenario (3) × Version (2)

Each block:
  → Contains 500 × 12 = 6,000 cells (all dense member combinations)
  → Is identified by ONE sparse member combination

Block identifiers (sparse intersections):
  Block #1: [Hotel India, Budget, Working]    → 6,000 cells
  Block #2: [Hotel India, Budget, Final]      → 6,000 cells
  Block #3: [Hotel India, Actual, Working]    → 6,000 cells
  Block #4: [Hotel USA, Budget, Working]      → 6,000 cells
  ... and so on

Maximum possible blocks = 100 × 3 × 2 = 600 blocks
But only blocks WITH data are actually created!

If only 150 sparse intersections have data:
  → 150 blocks × 6,000 cells = 900,000 cells stored
  → Compared to 3,600,000 cells without Dense/Sparse optimization
  → 75% storage savings!
```

## 3.4 The Block Diagram

```
            SPARSE DIMENSIONS (identify which blocks exist)
            ──────────────────────────────────────────────
            Entity: Hotel India    Scenario: Budget    Version: Working
                        │                │                │
                        └────────────────┼────────────────┘
                                         │
                                    BLOCK #1
                    ┌────────────────────────────────────┐
                    │     Jan    Feb    Mar   ...  Dec   │
                    │ Rev  18Cr  19Cr   20Cr  ...  25Cr │ ← Dense: Account
                    │ Exp  12Cr  13Cr   14Cr  ...  16Cr │    × Period
                    │ NI    6Cr   6Cr    6Cr  ...   9Cr │    = Block cells
                    │ Sal   5Cr   5Cr    5Cr  ...   7Cr │
                    │ Ben   2Cr   2Cr    2Cr  ...   3Cr │
                    │ Util  1Cr   1Cr    1Cr  ...   1Cr │
                    │ ...                               │
                    └────────────────────────────────────┘
                    (500 Account rows × 12 Period columns 
                     = 6,000 cells per block)
```

## 3.5 Dense/Sparse Assignment Rules

| Rule | Explanation | Example |
|------|-------------|---------|
| **Dimensions with high population density → Dense** | If most cells will have data | Account (every entity has most accounts), Period (every account has data for most months) |
| **Dimensions with low population density → Sparse** | If most combinations are empty | Entity × Scenario × Version (many combinations won't exist) |
| **Account and Period are almost always Dense** | Oracle best practice | Dense: Account, Period |
| **Entity, Scenario, Version, Year are almost always Sparse** | Oracle best practice | Sparse: Entity, Scenario, Version, Year |
| **Custom dimensions → Usually Sparse** | Unless very small and always populated | Department (Sparse unless < 5 members) |
| **Performance: Fewer Dense dimensions = Smaller blocks** | Fewer dense dims = less memory per block | 2 dense dims is common; 3+ dense dims creates large blocks |

## 3.6 Worked Example: Block Size Calculation

```
Application: Hotel Pvt Ltd

Dense Dimensions:
  Account: 500 members (level 0 only, excluding Dynamic Calc)
  Period: 16 members (Jan-Dec + Q1-Q4... but only stored members count)
    → Stored Level 0: 12 (Jan through Dec)
    → Dynamic Calc parents: Q1, Q2, Q3, Q4, YearTotal (5, not stored)
    → Stored level 0 = 12

Block Size = 500 × 12 = 6,000 cells
Each cell = 8 bytes (double-precision float)
Block Size in bytes = 6,000 × 8 = 48,000 bytes ≈ 47 KB

Sparse Dimensions:
  Entity: 50 level 0 members
  Scenario: 3 members
  Version: 2 members
  Year: 5 members
  Department: 12 members
  Currency: 3 members

Maximum possible blocks = 50 × 3 × 2 × 5 × 12 × 3 = 54,000 blocks
Actual blocks (with data) ≈ 5,000 blocks (dense population ~9%)

Total database size ≈ 5,000 × 47 KB ≈ 235 MB

IMPORTANT: Only STORED members count toward block size.
Dynamic Calc members do NOT create cells in the block.
```

## 3.7 The "FIX on Sparse vs Dense" Performance Difference

```
FIX on SPARSE dimension (e.g., FIX("Hotel India")):
  → Essbase checks the index: "Which blocks have Hotel India—
  → Loads ONLY those blocks from disk
  → Skips all blocks for Hotel USA, Hotel UK, etc.
  → ⚡ MAJOR I/O reduction

FIX on DENSE dimension (e.g., FIX("Revenue")):
  → Essbase must load ALL blocks (because Revenue is inside every block)
  → Then within each block, it narrows to just the Revenue cells
  → ❌ NO I/O reduction — same number of blocks loaded
  → Only reduces calculation scope within each block

PERFORMANCE IMPLICATION:
  Always FIX on SPARSE dimensions first, then narrow within blocks.
  
  ❌ Bad:  FIX("Revenue")  → loads all blocks
  ✅ Good: FIX("Hotel India", "Budget", "Working") → loads only relevant blocks
```

# SECTION 4: BLOCKS — THE HEART OF ESSBASE

---

## 4.1 What is a Block—

A **Block** is the fundamental unit of data storage in BSO Essbase.

| Property | Description |
|----------|-------------|
| **Identity** | Defined by one member from each sparse dimension |
| **Contents** | All cells from the dense dimension cross-product |
| **Size** | Fixed within an outline (changes require restructure) |
| **Empty Block** | A block where ALL cells are #Missing |
| **Input Block** | Contains at least one user-entered value |
| **Upper-Level Block** | Identified by a parent sparse member (created by aggregation) |

## 4.2 Block Existence

A block **exists** (is physically on disk) only if:
1. Data has been loaded/entered into that sparse intersection, OR
2. A calculation created data at that intersection, OR
3. A DATACOPY operation created it

A block does **NOT exist** if no data has ever been written to that sparse intersection.

```
Example:
  Hotel India + Budget + Working + FY26 + INR + Catering → Block EXISTS (has data)
  Hotel India + Forecast + Final + FY30 + GBP + Legal     → Block DOES NOT EXIST (no data ever entered)
```

## 4.3 Empty Blocks vs Non-Existent Blocks

| Concept | Description | Disk Space |
|---------|-------------|------------|
| **Non-Existent Block** | Block was never created. No sparse combination has been touched. | Zero |
| **Empty Block** | Block was created (data was entered once), then all data was cleared to #Missing. Block still exists on disk with all cells = #Missing. | Wastes space |

**Problem:** Over time, data clearing operations can create thousands of empty blocks. This wastes disk, memory, and calculation time.

**Solution:** `CLEARBLOCK ALL` removes empty blocks from disk. Regular "Restructure Database" also removes them.

## 4.4 Upper-Level Blocks

When you aggregate data, Essbase creates blocks at **parent levels** of sparse dimensions.

```
Before aggregation:
  Block: [Hotel India, Budget, Working]  → EXISTS (input data)
  Block: [Hotel USA, Budget, Working]    → EXISTS (input data)
  Block: [All Entities, Budget, Working] → DOES NOT EXIST

After AGG on Entity dimension:
  Block: [Hotel India, Budget, Working]  → EXISTS (unchanged)
  Block: [Hotel USA, Budget, Working]    → EXISTS (unchanged)
  Block: [All Entities, Budget, Working] → NOW EXISTS (sum of India + USA)
```

# SECTION 5: INDEX AND DATA FILE ARCHITECTURE

---

## 5.1 File Structure (BSO)

```
Essbase Database Files:
┌──────────────────────────────────────────┐
│                                          │
│  essn.ind  ← INDEX FILES                 │
│    Contains: Block headers               │
│    Maps: sparse intersection → data file │
│    position (block location pointer)     │
│                                          │
│  essn.pag  ← DATA (PAGE) FILES          │
│    Contains: Actual cell values          │
│    Each block's dense data stored here   │
│                                          │
│  essn.otl  ← OUTLINE FILE               │
│    Contains: Dimension structure,        │
│    member names, properties, formulas    │
│                                          │
└──────────────────────────────────────────┘
```

## 5.2 How a Data Retrieval Works

```
User query: "Show me Revenue for Hotel India, Jan, Budget, Working"

Step 1: Essbase identifies the BLOCK by sparse members:
         Entity=Hotel India, Scenario=Budget, Version=Working
         → Look up in INDEX (essn.ind)

Step 2: Index returns: "Block found at position 45,280 in essn.pag"

Step 3: Essbase reads the block from DATA FILE (essn.pag) at position 45,280
         → Loads all 6,000 cells of that block into memory

Step 4: Within the loaded block, Essbase locates the DENSE intersection:
         Account=Revenue, Period=Jan
         → Cell offset within block = (Revenue_position × 12) + Jan_position

Step 5: Returns the value: ₹18,00,000
```

# SECTION 6: BSO VS ASO VS HYBRID

---

## 6.1 BSO — Block Storage Option

| Feature | BSO |
|---------|-----|
| **Storage Model** | Data stored in blocks (dense × sparse) |
| **User Input** | ✅ Supports direct data entry |
| **Calculations** | ✅ Full Essbase Calc Script support |
| **Member Formulas** | ✅ Full support |
| **Aggregation** | Explicit — must run AGG or CALC DIM |
| **Data Loading** | Via Data Integration, flat files |
| **Typical Use** | Data entry, budgeting, calculations |
| **Block Compression** | RLE (Run-Length Encoding) by default |
| **Maximum Dimensions** | ~25 (practical limit) |

## 6.2 ASO — Aggregate Storage Option

| Feature | ASO |
|---------|-----|
| **Storage Model** | Materialized views + dynamic aggregation |
| **User Input** | ❌ No direct data entry |
| **Calculations** | ❌ No Calc Scripts (MDX only, limited) |
| **Member Formulas** | Limited — MDX-based only |
| **Aggregation** | Dynamic — aggregates on-the-fly during query |
| **Data Loading** | Via Data Integration, flat files, Smart Push |
| **Typical Use** | Reporting, dashboards, large datasets |
| **Aggregation Views** | Can pre-build selected aggregation levels |
| **Maximum Dimensions** | ~100+ (handles more dimensions) |

## 6.3 Hybrid BSO

Hybrid BSO is a **BSO mode** where specific members are calculated using **ASO-style dynamic aggregation** within a BSO cube.

```
How Hybrid Works:

Standard BSO:
  Parent member "Total Revenue" has consolidation operator " / 
  → Must run AGG or CALC DIM to calculate
  → Result is STORED in the block
  → Users see stale data until aggregation runs

Hybrid BSO:
  Parent member "Total Revenue" is tagged as "Dynamic Calc" 
  → Calculated on-the-fly when queried (like ASO)
  → NOT stored in the block
  → Users ALWAYS see fresh aggregated values
  → No need to run AGG for this member
```

### When to Use Hybrid Members:
| Use Hybrid (Dynamic Calc) | Use Stored |
|---------------------------|-----------|
| Parent members that just SUM children | Input members where users enter data |
| Calculated ratios (Margin %) | Members that are targets of DATACOPY |
| Members queried infrequently | Members queried very frequently with complex formulas |
| When you want real-time aggregation | When calculation is expensive and should be pre-computed |

## 6.4 Comparison Table

| Feature | BSO (Standard) | BSO (Hybrid) | ASO |
|---------|----------------|--------------|-----|
| Data Entry | ✅ | ✅ | ❌ |
| Calc Scripts | ✅ | ✅ | ❌ |
| Real-time Aggregation | ❌ (must run AGG) | ✅ (for Dynamic Calc members) | ✅ |
| Block-based Storage | ✅ | ✅ | ❌ |
| Performance for Write | ⚡ Excellent | ⚡ Excellent | ❌ N/A |
| Performance for Read | ⚠️ Must pre-aggregate | ⚡ Good (dynamic parents) | ⚡ Excellent |
| Typical EPBCS Use | Input plan types | Most EPBCS plan types (default) | Reporting plan type |

# SECTION 7: CELL ADDRESSING

---

## 7.1 How Essbase Finds Any Cell

Every cell in Essbase is uniquely identified by specifying one member from each dimension.

```
Cell Address:
  [Account: Revenue, Entity: Hotel India, Period: Jan, Year: FY26, 
   Scenario: Budget, Version: Working, Currency: INR, 
   Department: Catering, PlanElement: No PlanElement, Custom1: No Custom1]

This address resolves to:
  1. Sparse intersection → Identifies the BLOCK
     Entity=Hotel India, Scenario=Budget, Version=Working, Year=FY26, 
     Currency=INR, Department=Catering, PlanElement=No PlanElement, Custom1=No Custom1
  
  2. Dense intersection → Identifies the CELL within the block
     Account=Revenue, Period=Jan
```

## 7.2 Cross-Dimensional References

In calc scripts and member formulas, you reference cells using the `->` operator:

```essbase
/* Cross-dimensional reference syntax */
"Target_Account" -> "Entity_Member" -> "Period_Member"

/* Example: Get Revenue from Hotel India for Jan */
"Revenue" -> "Hotel India" -> "Jan"

/* Example: Get Budget Revenue (from current entity, period) */
"Revenue" -> "Budget"

/* Example: Copy data from one scenario to another */
FIX("Forecast", @DESCENDANTS("All Entities"))
    "Revenue" = "Revenue" -> "Actual";
ENDFIX

/* This means: For each entity under All Entities, 
   set Forecast Revenue = Actual Revenue */
```

# SECTION 8: LEVELS VS GENERATIONS

---

## 8.1 Levels (Bottom-Up Counting)

Levels count from the **bottom** of the hierarchy, starting at 0.

```
Revenue               ← Level 2
  ├── Rooms Revenue   ← Level 1
  │   ├── Rack Rate   ← Level 0 (leaf)
  │   └── Discount    ← Level 0 (leaf)
  ├── Banquet Revenue ← Level 0 (leaf)
  └── F&B Revenue     ← Level 0 (leaf)
```

## 8.2 Generations (Top-Down Counting)

Generations count from the **top** of the hierarchy, starting at 0 (or 1 depending on context — Oracle typically starts at Generation 0 for the dimension root, Generation 1 for first children).

```
Account (dim root)    ← Generation 0
  Revenue             ← Generation 1
    ├── Rooms Revenue ← Generation 2
    │   ├── Rack Rate ← Generation 3
    │   └── Discount  ← Generation 3
    ├── Banquet Rev.  ← Generation 2
    └── F&B Revenue   ← Generation 2
```

## 8.3 Why This Matters

Functions like `@LEVMBRS` and `@GENMBRS` use these concepts:

```essbase
/* Select all Level 0 members of Entity dimension */
@LEVMBRS("Entity", 0)
/* Returns: Hotel India, Hotel USA, Hotel UK (all leaves) */

/* Select all Generation 2 members of Account dimension */
@GENMBRS("Account", 2)
/* Returns: Rooms Revenue, Banquet Revenue, F&B Revenue */

/* In a FIX statement: */
FIX(@LEVMBRS("Entity", 0))
    /* This processes only leaf entities — skips parent entities */
ENDFIX
```

## 8.4 Ragged Hierarchies and Level Inconsistency

```
Problem with unbalanced hierarchies:

All Entities          ← Level 2
  ├── Hotel India     ← Level 1
  │   ├── Mumbai      ← Level 0
  │   └── Delhi       ← Level 0
  ├── Hotel USA       ← Level 0 ← ⚠️ This is Level 0 but at Generation 1!
  └── Hotel UK        ← Level 0

Hotel USA has no children — it is Level 0 but Generation 1.
Hotel India is Level 1, Generation 1 — same generation, different level!

@LEVMBRS("Entity", 0) returns: Mumbai, Delhi, Hotel USA, Hotel UK
@GENMBRS("Entity", 1) returns: Hotel India, Hotel USA, Hotel UK

This difference is critical when writing FIX statements for aggregation.
```

# SECTION 9: DYNAMIC CALC VS STORE

---

## 9.1 Overview

| Property | Store (Data Storage = "Store") | Dynamic Calc |
|----------|-------------------------------|--------------|
| **Data Physical Storage** | ✅ Written to disk in the block | ❌ NOT stored on disk |
| **Calculation Timing** | During CALC DIM / AGG / business rule | On-the-fly when queried |
| **Memory** | Occupies space in block | Does NOT occupy space in block |
| **User Input** | ✅ User can enter data | ❌ User CANNOT enter data |
| **Block Size Impact** | Adds cells to block | Does NOT add cells to block |
| **Performance** | Fast retrieval (pre-computed) | Slightly slower retrieval (computed each time) |
| **Freshness** | Stale until recalculated | Always current |

## 9.2 Dynamic Calc — How It Works

```
Member: "Gross Margin %" (Dynamic Calc)
Formula: IF("Revenue" <> 0) "Gross Margin" / "Revenue" * 100; ENDIF;

When user opens a form showing Gross Margin %:
  1. Essbase receives the query
  2. Essbase checks: is Gross Margin % Dynamic Calc— → Yes
  3. Essbase executes the member formula in real-time
  4. Essbase reads Revenue and Gross Margin from the block
  5. Calculates: (Revenue - COGS) / Revenue * 100
  6. Returns the result to the user
  7. Does NOT store the result in the block
  8. Next query → repeats the calculation

Benefit: Always accurate, no need to run a business rule
Cost: Slightly slower for complex formulas
```

## 9.3 Dynamic Calc and Store

A third option: calculated on first query, then stored for subsequent queries.

```
First query:  Calculate → Return → Store result in block
Second query: Read stored result → Return (fast, no calculation)
...until underlying data changes → must clear stored values → recalculates
```

**Use Case:** Expensive calculations that don't change frequently.

## 9.4 Two-Pass Calculation

**Problem:** Some calculations depend on values that are themselves Dynamic Calc.

```
Revenue (Dynamic Calc) = Rooms Revenue + Banquet Revenue + F&B Revenue
Revenue % of Total (Dynamic Calc, Two-Pass) = Revenue / Total Revenue * 100

Normal calculation order:
  1. Calculate Revenue (needs children first)
  2. Calculate Total Revenue (needs Revenue first)
  3. Calculate Revenue % of Total (needs both Revenue AND Total Revenue)

If Revenue % of Total runs BEFORE Total Revenue is calculated → wrong answer.

Solution: Tag "Revenue % of Total" as TWO-PASS.
  → Essbase calculates it in a SECOND pass after all other Dynamic Calcs complete.
```

## 9.5 Member Storage Decision Matrix

```
┌─────────────────────────────────────────────────────┐
│           IS THE MEMBER A LEAF (LEVEL 0)—           │
│                                                     │
│    YES ──────────────────────┐                      │
│     │                        │                      │
│  Does user enter data—    Is it a calc'd KPI—       │
│     │                        │                      │
│   YES → STORE              YES → DYNAMIC CALC       │
│                              + Member Formula        │
│                                                     │
│    NO (PARENT) ────────────────────────────────┐    │
│     │                                          │    │
│  Simple SUM of children—   Complex formula—    │    │
│     │                          │               │    │
│   YES → DYNAMIC CALC         YES → DYNAMIC CALC│    │
│   (no formula needed,        + Member Formula  │    │
│    uses consolidation                          │    │
│    operator " / )                               │    │
│                                                │    │
│  Needs Two-Pass—                               │    │
│     │                                          │    │
│   YES → DYNAMIC CALC + TWO-PASS               │    │
└─────────────────────────────────────────────────────┘
```

# SECTION 10: THE CALCULATION PASS

---

## 10.1 What Happens During CALC ALL

`CALC ALL` is the "calculate everything" command. It processes the ENTIRE database.

```
CALC ALL execution order:

Step 1: Process each dimension in outline order
Step 2: For each dimension:
  a. Calculate DENSE dimensions first (member formulas within blocks)
  b. Then aggregate SPARSE dimensions (create/update upper-level blocks)

Detailed:
  Dimension 1: Account (DENSE)
    → Within each block: execute member formulas top-down
    → Revenue = Rooms Revenue + Banquet Revenue + F&B Revenue
    → Net Income = Revenue - Expense
    → Gross Margin % = Gross Margin / Revenue * 100

  Dimension 2: Period (DENSE)
    → Within each block: aggregate periods
    → Q1 = Jan + Feb + Mar
    → YearTotal = Q1 + Q2 + Q3 + Q4

  Dimension 3: Entity (SPARSE)
    → Across blocks: create parent blocks
    → Block [All Entities, Budget, Working] = Block [Hotel India,...] + Block [Hotel USA,...]

  Dimension 4: Scenario (SPARSE) — skip (usually no aggregation)
  Dimension 5: Version (SPARSE) — skip (usually no aggregation)
```

## 10.2 CALC DIM

`CALC DIM` calculates a **single dimension** — all member formulas and aggregation for that dimension.

```essbase
CALC DIM("Account");
/* Executes all Account member formulas within every block
   and aggregates Account hierarchy */

CALC DIM("Entity");
/* Aggregates Entity dimension — creates parent-level blocks */
```

## 10.3 AGG

`AGG` aggregates a specific dimension — creates parent-level values by summing children according to consolidation operators. **Does NOT execute member formulas.**

```essbase
AGG("Entity");
/* Creates upper-level blocks:
   All Entities = Hotel India + Hotel USA + Hotel UK
   But does NOT execute any member formulas on Entity members */

/* Key Difference: 
   AGG = only consolidation (sum by operators)
   CALC DIM = consolidation + member formulas */
```

## 10.4 Order of Operations Rule

```
CRITICAL RULE: Always calculate DENSE dimensions before aggregating SPARSE dimensions.

WHY:
  Dense calculations happen WITHIN blocks.
  Sparse aggregation happens ACROSS blocks (creates new upper-level blocks).
  
  If you aggregate Entity first (creating parent blocks),
  then calculate Account formulas...
  → The Account formulas run on the ALREADY-AGGREGATED parent blocks
  → But the input blocks also get Account formulas
  → This can cause DOUBLE-COUNTING or incorrect values
  
CORRECT ORDER:
  1. CALC DIM("Account");    ← Dense first
  2. CALC DIM("Period");     ← Dense second  
  3. AGG("Entity");          ← Sparse last
  4. AGG("Department");      ← Sparse last
  
INCORRECT ORDER:
  1. AGG("Entity");          ← ❌ Sparse first — parent blocks created
  2. CALC DIM("Account");   ← ❌ Now Account formulas run on parent blocks 
                                  AND input blocks — inconsistent results
```

# SECTION 11: AGGREGATION MECHANICS

---

## 11.1 Consolidation Operators

Each member has a consolidation operator that determines how it rolls up to its parent.

| Operator | Meaning | Example |
|----------|---------|---------|
| `+` (Plus) | Add to parent | Revenue children: Rooms + Banquet + F&B |
| `-` (Minus) | Subtract from parent | Expense is subtracted: Net Income = Revenue + (-Expense) |
| `*` (Multiply) | Multiply into parent | Rarely used |
| `/` (Divide) | Divide into parent | Rarely used |
| `%` (Percent) | Calculate percentage into parent | Rarely used |
| `~` (Tilde / Ignore) | Do NOT aggregate to parent | "Rooms Available" should not sum into Revenue |
| `^` (Caret / Never) | Never consolidate | Member with formula — formula calculates the value |

```
Account Hierarchy with Operators:

Net Income                    ← Calculated by formula (^)
  ├── (+) Revenue             ← Sum of children
  │   ├── (+) Rooms Revenue   ← Input member
  │   ├── (+) Banquet Revenue ← Input member
  │   └── (+) F&B Revenue     ← Input member
  ├── (-) Expense             ← Subtracted from Revenue
  │   ├── (+) Salaries        ← Input member  
  │   ├── (+) Benefits        ← Input member
  │   └── (+) Utilities       ← Input member
  └── (~) Gross Margin %      ← Ignored — has its own formula
```

## 11.2 Worked Aggregation Example

```
Input Data (Level 0):
  Rooms Revenue  [Hotel India, Jan, Budget] = 18,00,000
  Banquet Revenue [Hotel India, Jan, Budget] = 5,00,000
  F&B Revenue    [Hotel India, Jan, Budget] = 3,00,000
  Salaries       [Hotel India, Jan, Budget] = 8,00,000
  Benefits       [Hotel India, Jan, Budget] = 2,00,000
  Utilities      [Hotel India, Jan, Budget] = 1,00,000

After CALC DIM("Account"):
  Revenue = Rooms Revenue (+) + Banquet Revenue (+) + F&B Revenue (+)
          = 18,00,000 + 5,00,000 + 3,00,000 = 26,00,000
  
  Expense = Salaries (+) + Benefits (+) + Utilities (+)
          = 8,00,000 + 2,00,000 + 1,00,000 = 11,00,000
  
  Net Income = Revenue (+) + Expense (-) 
             = 26,00,000 + (-11,00,000) = 15,00,000
             (OR: Net Income = Revenue - Expense because Expense operator is -)
  
  Gross Margin % = (Revenue - Expense) / Revenue * 100 (member formula, ~ ignored in consolidation)
                 = (26,00,000 - 11,00,000) / 26,00,000 * 100
                 = 57.69%
```

## 11.3 AGG vs CALC DIM vs CALC ALL

| Command | What It Does | When to Use |
|---------|-------------|-------------|
| `CALC ALL` | Calculates entire database — all dims, all formulas | Full recalculation after major data load |
| `CALC DIM("DimName")` | Calculates one dimension — formulas + aggregation | After data entry in specific dimension |
| `AGG("DimName")` | Aggregates one dimension — NO formulas | When you only need roll-up, not formula execution |
| `AGG("DimName", "DimName2")` | Aggregates multiple dimensions | Consolidate Entity + Department together |

# SECTION 12: BLOCK CREATION RULES

---

## 12.1 What Creates Blocks—

| Action | Creates Blocks— | Details |
|--------|----------------|---------|
| **Data Load** | ✅ Yes | Loading data to a new sparse intersection creates a block |
| **User Input (Form Save)** | ✅ Yes | Entering data creates a block if it doesn't exist |
| **DATACOPY** | ✅ Yes | Copies data and creates target blocks |
| **Calc Script Assignment** | ⚠️ Depends | Only if `SET CREATEBLOCKONEQ ON` is set |
| **Cross-Dim Reference** | ⚠️ Depends | Writing via `->` may or may not create blocks |
| **AGG** | ✅ Yes | Creates upper-level blocks for parent sparse members |
| **Querying / Retrieving** | ❌ No | Reading data does NOT create blocks |

## 12.2 SET CREATEBLOCKONEQ

```essbase
/* Without SET CREATEBLOCKONEQ ON: */
FIX("Forecast")
    "Revenue" = "Revenue" -> "Actual";
ENDFIX
/* If the block [Entity, Forecast, Working] does not exist,
   the assignment is SILENTLY SKIPPED — no error, no data. */

/* With SET CREATEBLOCKONEQ ON: */
SET CREATEBLOCKONEQ ON;
FIX("Forecast")
    "Revenue" = "Revenue" -> "Actual";
ENDFIX
SET CREATEBLOCKONEQ OFF;
/* Now Essbase will CREATE the target block before writing data.
   This ensures the data copy works even for new intersections. */

/* CAUTION: SET CREATEBLOCKONEQ ON can create MANY blocks.
   Use with a tight FIX to avoid block explosion. */
```

## 12.3 DATACOPY vs Assignment

```essbase
/* DATACOPY: Always creates target blocks */
DATACOPY "Actual" TO "Forecast";
/* Copies ALL data where source blocks exist.
   Creates corresponding blocks in Forecast. */

/* Assignment: Does NOT create blocks unless CREATEBLOCKONEQ is ON */
FIX("Forecast")
    "Revenue" = "Revenue" -> "Actual";
ENDFIX
/* Only assigns data if the target block already exists. */
```

# SECTION 13: RESTRUCTURING

---

## 13.1 What is a Restructure—

A restructure is when Essbase rebuilds the physical database files (index and data files) to reflect changes in the outline.

## 13.2 Types of Restructure

| Type | Trigger | Impact | Duration |
|------|---------|--------|----------|
| **Dense Restructure** | Adding/removing/reordering a dense dimension member | ALL blocks must be rewritten (block size changes) | Long — proportional to database size |
| **Sparse Restructure** | Adding/removing/reordering a sparse dimension member | Only INDEX is rebuilt (block identifiers change) | Fast — index is much smaller than data |
| **Outline-Only** | Renaming a member, changing alias, changing formula | No data restructure needed | Instant |

```
Example:

Adding a new Account member "100140: Parking Revenue" (Account is DENSE):
  → Dense Restructure
  → Every single block must be rebuilt with the new cell
  → Block size changes: from 6,000 → 6,001 cells
  → For 5,000 blocks: 5,000 blocks × 47 KB ≈ 235 MB rewritten
  → Can take minutes to hours

Adding a new Entity "E10004: Hotel Singapore" (Entity is SPARSE):
  → Sparse Restructure
  → Only the index is updated to allow blocks for E10004
  → Existing data files are untouched
  → Takes seconds

Changing the alias of "100110" from "Rooms Revenue" to "Room Revenue":
  → Outline-Only change
  → No restructure needed
  → Instant
```

## 13.3 Restructuring in EPBCS

In Oracle EPM Cloud, restructuring happens during **Refresh Database**:

```
Navigator → Application → Overview → Actions → Refresh Database

OR

EPM Automate: epmautomate refreshcube

What Refresh Database Does:
  1. Reads the current dimension metadata from Planning
  2. Compares with the existing Essbase outline
  3. Applies changes (add/remove/reorder members)
  4. Triggers restructure if needed (dense or sparse)
  5. Updates the outline file
```

# SECTION 14: CACHE MANAGEMENT

---

## 14.1 Essbase Caches

| Cache | Contents | Performance Impact |
|-------|----------|--------------------|
| **Index Cache** | Block headers and index entries | Determines how fast blocks are located |
| **Data Cache** | Recently accessed data blocks | Determines how fast data is returned from memory |
| **Data File Cache** | OS-level file system cache | Reduces disk I/O |
| **Calculator Cache** | Blocks being actively calculated | Determines calculation speed |

## 14.2 In Cloud Context

In Oracle EPM Cloud, you **cannot** directly tune cache sizes — Oracle manages infrastructure. However, understanding cache behavior helps you:

- Design applications with reasonable block sizes (< 100 KB per block)
- Avoid unnecessarily dense dimensions that inflate block size
- Use FIX statements to minimize the number of blocks loaded during calculation

# SECTION 15: ATTRIBUTE DIMENSIONS VS UDA

---

## 15.1 Attribute Dimensions

An Attribute Dimension is a separate dimension whose members are assigned to base dimension members.

```
Base Dimension: Entity
  Hotel India (Attribute: Region = "Asia", Size = "Large")
  Hotel USA (Attribute: Region = "North America", Size = "Large")  
  Hotel UK (Attribute: Region = "Europe", Size = "Medium")

Attribute Dimension: Region
  Asia
  North America
  Europe

Attribute Dimension: Size
  Large
  Medium
  Small
```

### Key Properties:
- Attribute dimensions are ALWAYS Dynamic Calc
- They do NOT create blocks or store data
- They provide cross-tabulation and filtering capability
- Users can filter forms and reports by attribute
- ASO cubes handle attribute dimensions natively

## 15.2 UDA — User-Defined Attributes

A UDA is a text tag attached to a member. It's simpler than an attribute dimension.

```
Member: 100110 (Rooms Revenue)
  UDA: "Revenue_Driver", "Taxable"

Member: 200000 (Salaries)
  UDA: "Fixed_Cost", "HR_Related"
```

### UDA vs Attribute:
| Feature | UDA | Attribute Dimension |
|---------|-----|-------------------|
| **Complexity** | Simple text tag | Full dimension with hierarchy |
| **Cross-Tab Reporting** | ❌ Cannot pivot on UDA | ✅ Can put on row/column of report |
| **Use in Calc Scripts** | ✅ `@UDA("Account", "Revenue_Driver")` | ✅ `@ATTRIBUTE("Region", "Asia")` |
| **Performance** | Lightweight | Adds dimension overhead |
| **Best For** | Grouping members in rules | Reporting/filtering |

```essbase
/* Using UDA in a calc script */
FIX(@UDA("Account", "Revenue_Driver"))
    "Forecast" = "Actual" * 1.10;
    /* Increase all Revenue_Driver accounts by 10% in Forecast */
ENDFIX

/* Using Attribute in a calc script */
FIX(@ATTRIBUTE("Region", "Asia"))
    "Forecast" = "Actual" * 1.15;
    /* Increase all Asia-region entities by 15% */
ENDFIX
```

# SECTION 16: INTERVIEW QUESTIONS

---

## 16.1 Beginner

**Q1: What is the difference between Dense and Sparse dimensions—**
> Dense dimensions have data for most intersections and form the internal structure of blocks. Sparse dimensions have data for relatively few intersections and determine which blocks exist. Block = all dense member combinations for one specific sparse member combination.

**Q2: What is a block in Essbase—**
> A block is the fundamental unit of data storage. It contains all cells from the cross-product of dense dimensions, identified by one specific combination of sparse dimension members.

**Q3: How do you calculate block size—**
> Block size = (number of stored level-0 dense members in Dim1) × (number of stored level-0 dense members in Dim2) × ... × 8 bytes. Dynamic Calc members do NOT count.

## 16.2 Intermediate

**Q4: Why should you FIX on sparse dimensions rather than dense dimensions—**
> FIX on sparse dimensions causes Essbase to load only blocks matching the filter, reducing disk I/O dramatically. FIX on dense dimensions still loads ALL blocks but only processes specific cells within each block — no I/O reduction.

**Q5: What is the difference between CALC DIM, AGG, and CALC ALL—**
> CALC ALL calculates the entire database. CALC DIM calculates one dimension including member formulas and aggregation. AGG only aggregates one dimension without executing member formulas. Always calculate dense dimensions before aggregating sparse dimensions.

**Q6: What is a Dense Restructure vs Sparse Restructure—**
> Dense restructure occurs when a dense dimension member is added/removed/reordered — it requires rewriting ALL blocks because block size changes. Sparse restructure occurs when a sparse dimension changes — only the index is rebuilt, existing data blocks are unaffected. Dense restructure is much slower.

## 16.3 Advanced

**Q7: Why do empty blocks hurt performance—**
> Empty blocks occupy disk space and memory. During calculations, Essbase loads and processes empty blocks just like full blocks — wasting I/O and CPU. CLEARBLOCK ALL removes empty blocks. Regular restructuring also cleans them up.

**Q8: Explain Two-Pass calculation. When is it needed—**
> Two-Pass is needed for members whose formulas depend on values calculated by other Dynamic Calc members. For example, "Revenue % of Total" depends on both "Revenue" and "Total Revenue" being calculated first. Without Two-Pass, Essbase might calculate "Revenue % of Total" before "Total Revenue" is ready, returning wrong results. Two-Pass forces the member to calculate in a second pass after all first-pass members are done.

**Q9: A client's database has 50,000 blocks. After a data clear operation, blocks are still 50,000 but data is gone. Why— How do you fix it—**
> The CLEARDATA command sets cells to #Missing but does NOT delete blocks. After CLEARDATA, blocks still exist as empty blocks. To remove them: use CLEARBLOCK ALL (deletes blocks for that sparse intersection) or restructure the database. This recovers disk space and improves future calculation performance.

**Q10: What is SET CREATEBLOCKONEQ and when do you need it—**
> SET CREATEBLOCKONEQ ON tells Essbase to create new blocks during calculation assignments when the target block doesn't exist. Without it, assignments to non-existent blocks are silently skipped. Use it with DATACOPY-equivalent assignments. CAUTION: use with tight FIX to avoid creating millions of unnecessary blocks.

## 📝 Summary

| Concept | Key Takeaway |
|---------|-------------|
| **OLAP vs OLTP** | Essbase is OLAP — optimized for aggregation, not transactions |
| **Dense/Sparse** | Dense dims form block internals; Sparse dims determine which blocks exist |
| **Block** | = All dense cells × one sparse intersection. Only blocks with data exist. |
| **BSO** | Block Storage — supports input, calc scripts, member formulas |
| **ASO** | Aggregate Storage — read-only, dynamic aggregation, no calc scripts |
| **Hybrid BSO** | BSO with Dynamic Calc parents for real-time aggregation |
| **CALC ALL** | Calculate entire database — all dimensions |
| **CALC DIM** | Calculate one dimension — formulas + aggregation |
| **AGG** | Aggregate one dimension — no formulas |
| **Block Creation** | Data load, DATACOPY, SET CREATEBLOCKONEQ create blocks |
| **Restructure** | Dense restructure rewrites all blocks; Sparse only rebuilds index |
| **Dynamic Calc** | Calculated on query, not stored, reduces block size |
| **Two-Pass** | Second calculation pass for members depending on other Dynamic Calcs |
