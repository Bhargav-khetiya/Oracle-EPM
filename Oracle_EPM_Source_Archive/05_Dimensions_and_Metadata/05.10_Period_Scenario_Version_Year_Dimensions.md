# 05.10 Period, Scenario, Version & Year Dimensions — Exhaustive Reference

> **Module:** 05_Metadata  
> **Topic:** 10 — Every Property of Period, Scenario, Version, and Year Dimensions  
> **Target Audience:** Developer / Architect  

---

## Introduction

The **Period, Scenario, Version, and Year** dimensions are the four "system" dimensions that every Oracle EPM Planning application has by default. Unlike Account and Entity (which can be heavily customized), these dimensions have specific system-level properties that control time periods, planning cycles, data versions, and multi-year horizons.

---

# PART 1: PERIOD DIMENSION

---

## 1.1 What is the Period Dimension?

The Period dimension represents the **time hierarchy** — months, quarters, and year totals. It is almost always a **Dense** dimension because every data block contains all periods.

### Standard Period Hierarchy:
```
YearTotal (Dynamic Calc)
├── Q1 (Dynamic Calc)
│   ├── Jan (Store)
│   ├── Feb (Store)
│   └── Mar (Store)
├── Q2 (Dynamic Calc)
│   ├── Apr (Store)
│   ├── May (Store)
│   └── Jun (Store)
├── Q3 (Dynamic Calc)
│   ├── Jul (Store)
│   ├── Aug (Store)
│   └── Sep (Store)
└── Q4 (Dynamic Calc)
    ├── Oct (Store)
    ├── Nov (Store)
    └── Dec (Store)
```

---

## 1.2 Period-Specific Properties

| Property | Description | Options | Default |
|----------|-------------|---------|---------|
| **Period Type** | Granularity of the lowest level | `Monthly`, `Quarterly`, `Weekly`, `Custom` | Set at application creation |
| **Start Month** | Which month the fiscal year starts | `January` through `December` | `January` |
| **Start Year** | First year in the application | Year (e.g., `2020`) | Set at creation |
| **End Year** | Last year in the application | Year (e.g., `2030`) | Set at creation |
| **Fiscal Year First Month** | Determines fiscal year mapping | Month name | `January` |

### Period Member Properties (per member):

| Property | Description | Options |
|----------|-------------|---------|
| **Data Storage** | How the period member stores data | `Store` (Level 0), `Dynamic Calc` (parents Q1, YearTotal) |
| **Alias** | Display name | Free text (e.g., `January`, `Quarter 1`, `Year Total`) |
| **Consolidation** | How children roll up to parent | `+` (default — sum Jan+Feb+Mar=Q1) |

---

## 1.3 BegBalance (Beginning Balance)

| Property | Description |
|----------|-------------|
| **BegBalance** | A special period member representing the starting balance before the first period |

**Use Case:** Balance Sheet accounts (Cash, Inventory) need an opening balance before January.

**Architecture:** BegBalance is a **sibling** of Q1 at the top level, not a child of any quarter:
```
YearTotal
├── BegBalance (Store, Consolidation: ~)
├── Q1
│   ├── Jan
│   ├── Feb
│   └── Mar
├── Q2
...
```

> **Consolidation = `~` (Ignore):** BegBalance does NOT add into YearTotal. It is a reference point, not a flow.

---

## 1.4 Dynamic Time Series (DTS)

| DTS Member | What It Calculates | Example |
|-----------|-------------------|---------|
| **H-T-D** (History-to-Date) | Sum from beginning of time to current period | HTD Revenue = all historical revenue |
| **Y-T-D** (Year-to-Date) | Sum from Jan to current month | YTD Revenue (Jan through Jun if current = Jun) |
| **Q-T-D** (Quarter-to-Date) | Sum from quarter start to current month | QTD Revenue (Apr + May if current = May in Q2) |
| **M-T-D** (Month-to-Date) | Current month value (essentially the member itself) | MTD Revenue = June Revenue |
| **S-T-D** (Season-to-Date) | Custom aggregation range | Configurable |

### Enabling DTS:
```
Application Settings → Dynamic Time Series → Enable → Select DTS members → 
Set "Latest Period" for each DTS → Save
```

### How It Works:
When DTS is enabled, Oracle Planning creates **virtual members** (H-T-D, Y-T-D, etc.) that dynamically calculate based on the `Latest Period` setting.

**Example:** If `Latest Period = Jun`:
- Y-T-D = Jan + Feb + Mar + Apr + May + Jun
- Q-T-D = Apr + May + Jun (Q2 start to Jun)

---

## 1.5 Period Frequency Options

| Frequency | Periods per Year | Members Created |
|-----------|-----------------|-----------------|
| **12 Months** | 12 | Jan–Dec, Q1–Q4, YearTotal |
| **Quarterly** | 4 | Q1–Q4, YearTotal |
| **Weekly (52)** | 52 | Wk01–Wk52, Monthly/Quarterly rollups |
| **Custom** | User-defined | As configured |

# PART 2: SCENARIO DIMENSION

---

## 2.1 What is the Scenario Dimension?

The Scenario dimension represents **planning scenarios** — different versions of financial reality (what happened vs. what was planned vs. what we forecast).

### Standard Scenarios:
```
Scenario Dimension:
├── Actual (Store)
├── Budget (Store)
├── Forecast (Store)
├── Plan (Store)
├── What_If (Store)
└── Baseline (Store)
```

---

## 2.2 Scenario-Specific Properties

| Property | Description | Options | Impact |
|----------|-------------|---------|--------|
| **Start Year** | First year this scenario covers | Year (e.g., `FY23`) | Controls form display and rule scope |
| **End Year** | Last year this scenario covers | Year (e.g., `FY25`) | Same |
| **Start Period** | First period (month) this scenario covers | Period member (e.g., `Jan`) | Determines which periods are editable |
| **End Period** | Last period this scenario covers | Period member (e.g., `Dec`) | Same |
| **Exchange Rate Table** | Which exchange rate table to use for currency conversion | Dropdown of configured rate tables | Different scenarios can use different FX rates |
| **Enable Process Management** | Whether this scenario participates in approval workflows | ☑️ / ☐ | Usually enabled for Budget, disabled for Actual |
| **Data Storage** | How scenario data is stored | `Store` (default) | Almost always Store |

### Scenario Design Matrix:

| Scenario | Start Year | End Year | Start Period | End Period | Process Mgmt | FX Table |
|----------|-----------|---------|-------------|-----------|-------------|----------|
| Actual | FY20 | CurrYear | Jan | CurrMonth | ❌ | Actual_Rates |
| Budget | BudgetYear | BudgetYear | Jan | Dec | ✅ | Budget_Rates |
| Forecast | CurrYear | CurrYear+1 | CurrMonth+1 | Dec | ✅ | Forecast_Rates |
| What_If | CurrYear | CurrYear+2 | Jan | Dec | ❌ | Budget_Rates |

---

## 2.3 Scenario Best Practices

| Practice | Why |
|----------|-----|
| Keep scenario count under 10 | Each scenario multiplies block count |
| Use Substitution Variables for Start/End | `&BudgetStartYear`, `&ForecastStartMonth` |
| Disable Process Management for Actual | Actuals come from ERP — no approval needed |
| Create separate FX tables per scenario | Budget may use planned rates, Actual uses real rates |

# PART 3: VERSION DIMENSION

---

## 3.1 What is the Version Dimension?

The Version dimension allows **multiple iterations** within a scenario. For example, the Budget scenario might have Draft 1, Draft 2, and Final versions.

### Standard Versions:
```
Version Dimension:
├── Working (Store) — Bottom-Up type
├── Final (Store) — Target type
├── V1 (Store)
├── V2 (Store)
└── Sandbox (Store)
```

---

## 3.2 Version-Specific Properties

| Property | Description | Options | Impact |
|----------|-------------|---------|--------|
| **Version Type** | How data flows in this version | `Bottom-Up`, `Target` | Controls data entry direction |
| **Enable Process Management** | Approval workflow for this version | ☑️ / ☐ | Determines if Submit/Approve/Reject applies |

### Version Type Deep Dive:

| Type | Data Flow | Use Case |
|------|-----------|----------|
| **Bottom-Up** | Data enters at Level 0, aggregates up | Standard budgeting — departments enter data, rolled up to total |
| **Target** | Data enters at upper level, spread down | Executive targets — CEO sets $10M revenue target, spread to departments |

### Bottom-Up vs Target Example:

**Bottom-Up (Working):**
```
Total_Company = $10M (calculated: sum of children)
├── US = $6M (user input)
├── UK = $3M (user input)
└── DE = $1M (user input)
```

**Target (Final):**
```
Total_Company = $12M (user input — executive target)
├── US = $7.2M (auto-spread: 60% of $12M)
├── UK = $3.6M (auto-spread: 30% of $12M)
└── DE = $1.2M (auto-spread: 10% of $12M)
```

# PART 4: YEAR DIMENSION

---

## 4.1 What is the Year Dimension?

The Year dimension represents the **fiscal years** in the application. It is always a **Sparse** dimension.

### Standard Year Hierarchy:
```
Year Dimension:
├── FY20 (Store)
├── FY21 (Store)
├── FY22 (Store)
├── FY23 (Store)
├── FY24 (Store)
├── FY25 (Store)
└── No_Year (Label Only, optional)
```

---

## 4.2 Year-Specific Properties

| Property | Description | Options |
|----------|-------------|---------|
| **Data Storage** | How year data is stored | `Store` (default for all) |
| **Alias** | Display name | `2024`, `Fiscal Year 2024` |
| **Consolidation** | How years roll up | `+` (if a "Total Years" parent exists) or `~` |

---

## 4.3 Year Range Configuration

| Setting | Description | Example |
|---------|-------------|---------|
| **Application Start Year** | First year in the application | `FY20` |
| **Application End Year** | Last year | `FY30` |
| **Number of Years** | Total years | `11` (FY20–FY30) |
| **Current Year (Substitution Var)** | Points to the active year | `&CurrYear = FY24` |

### Year Range Best Practices:

| Practice | Why |
|----------|-----|
| Don't create too many years (>15) | Each year multiplies block count significantly |
| Use Substitution Variables | `&CurrYear`, `&PriorYear`, `&BudgetYear` |
| Archive old years | Years > 3–5 years old should be archived to reduce database size |
| Don't create "No_Year" unless needed | Adds unnecessary blocks |

---

## 4.4 Year and Scenario Interaction

The **Scenario's Start/End Year properties** restrict which years are editable for that scenario:

| Scenario | Start Year | End Year | Editable Range |
|----------|-----------|---------|---------------|
| Actual | FY20 | FY24 | All years FY20–FY24 (historical data) |
| Budget | FY25 | FY25 | Only FY25 (the budget year) |
| Forecast | FY24 | FY25 | FY24 (remaining months) and FY25 |
| Long-Range Plan | FY25 | FY30 | FY25–FY30 |

## Interview Questions

### Intermediate
**Q: What is the difference between the Version types "Bottom-Up" and "Target"?**
> A: Bottom-Up means data is entered at the lowest level (departments) and aggregates up to the total. Target means data is entered at the top level (executive target) and can be spread down to children. The key difference is the direction of data flow and whether upper-level values are calculated (Bottom-Up) or manually entered (Target).

### Architect
**Q: Design the Scenario and Version structure for a company that does: Annual Budget (3 drafts + final), Monthly Rolling Forecast, and Quarterly What-If analysis.**

> A:
> **Scenarios:** `Actual`, `Budget`, `Forecast`, `What_If`
> **Versions:** `Working` (Bottom-Up), `Draft_1`, `Draft_2`, `Draft_3`, `Final` (Target)
>
> | Process | Scenario | Version | Year Range |
> |---------|----------|---------|------------|
> | Budget Cycle | Budget | Draft_1 → Draft_2 → Draft_3 → Final | FY25 only |
> | Monthly Forecast | Forecast | Working | FY24 remaining + FY25 |
> | What-If | What_If | Working | FY24–FY26 |
> | Actuals Load | Actual | Final | FY20–FY24 |

### Trick Question
**Q: A user enters data for "Budget, FY25, Jan" but when they check the form for "Budget, FY25, Q1", it shows #Missing. What happened?**
> A: The form is showing Q1 as a separate member that hasn't been calculated yet. If Q1 is `Dynamic Calc`, it should show the sum automatically. If Q1 is `Store`, the user needs to run a `CALC DIM("Period")` or `AGG("Period")` to aggregate Jan up to Q1. Check Q1's Data Storage property.

## Summary

| Dimension | Key Property | Critical Impact |
|-----------|-------------|-----------------|
| **Period** | Time Balance (on Account dim) | Flow vs Last — determines quarterly rollup method |
| **Period** | Dynamic Time Series | Y-T-D, Q-T-D automatic calculations |
| **Scenario** | Start/End Year + Period | Restricts data entry timeframe per scenario |
| **Scenario** | Exchange Rate Table | Different FX rates for Budget vs Actual |
| **Version** | Type (Bottom-Up vs Target) | Controls direction of data flow |
| **Year** | Range (Start/End) | Directly impacts database size (blocks per year) |
