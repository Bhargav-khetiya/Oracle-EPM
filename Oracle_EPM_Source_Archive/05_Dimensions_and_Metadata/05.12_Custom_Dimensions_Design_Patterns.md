# 05.12 Custom Dimensions — Design Patterns & Best Practices

> **Module:** 05_Metadata  
> **Topic:** 12 — Custom Dimension Architecture  
> **Target Audience:** Architect  

---

## Introduction

In addition to the 6 standard dimensions (Account, Entity, Period, Scenario, Version, Year), Oracle EPM Planning allows you to create **Custom dimensions** for business-specific categorization. Common examples include Product, Channel, Project, Department, Geography, or Business Unit. Designing custom dimensions correctly is critical — every additional dimension multiplies the potential block count exponentially.

---

# SECTION 1: WHEN TO CREATE CUSTOM DIMENSIONS

## Decision Framework

| Question | If YES → | If NO → |
|----------|----------|---------|
| Does the data need to be categorized by this attribute at the input level— | Create custom dimension | Use UDAs or Attributes on an existing dimension |
| Do users need to enter different values for different members of this attribute— | Create custom dimension | Use a member formula or attribute |
| Does this attribute have its own hierarchy for rollups— | Create custom dimension | Use Attribute Dimensions |
| Will this attribute have > 5 members— | Consider custom dimension | Consider Smart List |
| Will this attribute have > 10,000 members— | ⚠️ Carefully architect (sparse, filtered forms) | N/A |

## Custom Dimension vs Alternatives

| Approach | Best For | Example |
|----------|----------|---------|
| **Custom Dimension** | Input-level segmentation with separate data | Product, Channel, Department, Project |
| **Attribute Dimension** | Reporting-only categorization (no separate input) | Region (attribute of Entity), Industry (attribute of Customer) |
| **UDA** | Tagging for calc script targeting | "Active", "CapEx", "Allocatable" |
| **Smart List** | Dropdown selections on cells (status, category) | Approval Status, Risk Level |

# SECTION 2: CUSTOM DIMENSION PROPERTIES

Every custom dimension member has these properties:

| Property | Description | Options |
|----------|-------------|---------|
| **Member Name** | Unique identifier | Alphanumeric, underscores |
| **Alias** | Display name | Free text |
| **Data Storage** | Store/Dynamic Calc/Shared/Label Only/Never Share | Same as Account dimension |
| **Consolidation Operator** | +, -, *, /, %, ~ | Same as Account |
| **Plan Type Association** | Which cubes this member exists in | ☑️ per plan type |
| **UDA** | User Defined Attributes | Free text tags |
| **Smart List** | Associated Smart List | Dropdown |
| **Formula** | Member formula | Essbase formula syntax |
| **Two-Pass** | Enable two-pass calculation | ☑️ / ☐ |
| **Solve Order** | Calculation priority (0-127) | Numeric |

# SECTION 3: DENSE vs SPARSE — THE CRITICAL DECISION

### The Rule:
- **Dense dimensions** define the content INSIDE a block (affects block size)
- **Sparse dimensions** define WHICH blocks exist (affects block count)

### Default Dimension Density:

| Dimension | Default Density | Rationale |
|-----------|----------------|-----------|
| Account | Dense | Every block contains all accounts |
| Period | Dense | Every block contains all months |
| Entity | Sparse | Not every entity has data for every product |
| Scenario | Sparse | Budget data doesn't exist for every intersection |
| Version | Sparse | Same as Scenario |
| Year | Sparse | Same |
| **Custom Dims** | **YOU DECIDE** | See guidelines below |

### Guidelines for Custom Dimension Density:

| Factor | Make it Dense | Make it Sparse |
|--------|--------------|----------------|
| Number of members | ≤ 20 | > 20 |
| Data density (% of intersections with data) | > 50% populated | < 50% populated |
| Used in FIX statements | Rarely | Frequently |
| Combined with other dense dims | Small combined size | N/A |
| Performance priority | Block size control | Block count control |

### Block Size Calculation:
```
Block Size = Product of all Dense dimension members × 8 bytes

Example:
- Account: 500 members (Dense)
- Period: 13 members (Dense)
- Custom_Dim: 10 members (Dense)

Block Size = 500 × 13 × 10 × 8 = 520,000 bytes = 507 KB per block

If Custom_Dim is Sparse instead:
Block Size = 500 × 13 × 8 = 52,000 bytes = 50.8 KB per block
(But 10x more blocks to store — one per Custom_Dim member)
```

### The Sweet Spot:
**Block size should be between 8 KB and 200 KB.** Below 8 KB wastes I/O overhead. Above 200 KB wastes memory loading large blocks.

# SECTION 4: COMMON CUSTOM DIMENSION PATTERNS

## Pattern 1: Product Dimension
```
All_Products (Dynamic Calc)
├── Category_Electronics (Dynamic Calc)
│   ├── Laptops (Store)
│   ├── Tablets (Store)
│   └── Phones (Store)
├── Category_Software (Dynamic Calc)
│   ├── Cloud_SaaS (Store)
│   ├── On_Prem_License (Store)
│   └── Support_Services (Store)
└── No_Product (~, Store)
```

| Property | Setting | Rationale |
|----------|---------|-----------|
| Density | **Sparse** | Products are selective — not every entity sells every product |
| "No_Product" | Consolidation `~` | For accounts not broken by product (e.g., Corporate Overhead) |

## Pattern 2: Channel / Segment Dimension
```
All_Channels
├── Direct_Sales (Store)
├── Online (Store)
├── Partner (Store)
├── Retail (Store)
└── No_Channel (~)
```

| Property | Setting | Rationale |
|----------|---------|-----------|
| Density | **Dense** (if < 10 members) | Small enough to include in every block |
| "No_Channel" | `~` Ignore | For data not segmented by channel |

## Pattern 3: Project / Initiative Dimension
```
All_Projects
├── Active_Projects (Label Only)
│   ├── PRJ_001 (Store)
│   ├── PRJ_002 (Store)
│   └── PRJ_003 (Store)
├── Completed_Projects (Label Only)
│   ├── PRJ_ARCH_001 (Store)
│   └── PRJ_ARCH_002 (Store)
└── No_Project (~)
```

| Property | Setting | Rationale |
|----------|---------|-----------|
| Density | **Sparse** | Projects are highly selective — each entity has only a few projects |
| UDAs | "Active", "Completed", "On_Hold" | For calc script filtering |

## Pattern 4: Cost Center / Department (Alternative to Entity)
```
All_Departments
├── Finance
│   ├── Accounting (Store)
│   ├── FP&A (Store)
│   └── Treasury (Store)
├── HR
│   ├── Recruiting (Store)
│   └── Benefits (Store)
└── IT
    ├── Infrastructure (Store)
    └── Development (Store)
```

| Property | Setting | Rationale |
|----------|---------|-----------|
| Density | **Sparse** | Departments have selective data — HR doesn't have Revenue |
| UDAs | "Revenue_Generating", "Support_Function" | For allocation rules |

## Pattern 5: Geography (if not using Entity for it)
```
All_Regions
├── Americas
│   ├── North_America (Store)
│   └── Latin_America (Store)
├── EMEA
│   ├── Western_Europe (Store)
│   └── Middle_East (Store)
└── APAC
    ├── Japan (Store)
    └── Australia (Store)
```

# SECTION 5: CUSTOM DIMENSION LIMITS

| Limit | Value | Impact |
|-------|-------|--------|
| **Max custom dimensions per app** | ~20 (practical limit: 5-8) | Each dimension multiplies block count |
| **Max members per dimension** | ~100,000 (Essbase outline limit) | Performance degrades above 10,000 |
| **Max total intersections** | ~10 billion (theoretical) | Practical limit: ~1 billion before timeout issues |
| **Dense dimension combined members** | Keep block size < 200 KB | More dense members = larger blocks |
| **Sparse dimension combined members** | Keep block count < 10 million | More sparse members = more blocks |

# SECTION 6: THE "No_Dimension" MEMBER PATTERN

### The Problem:
If you add a Product dimension, every Account suddenly requires a Product intersection. But "Office Rent" has nothing to do with Products. Where do you store it—

### The Solution: `No_Product` (or `N/A_Product`)
- Create a member called `No_Product` at the same level as other products
- Set its Consolidation Operator to `~` (Ignore) — it should NOT roll up into `All_Products`
- Tag it with UDA `"NoProduct"` for easy identification in calc scripts
- Use it as the default intersection for accounts that don't vary by Product

### In Calc Scripts:
```essbase
/* Allocate overhead from No_Product to specific products */
FIX("Budget", "Working", "FY24", @RELATIVE("Total_Entity", 0))
    @ALLOCATE("Office_Rent" -> "No_Product", @RELATIVE("All_Products", 0), "Revenue");
ENDFIX
```

## Interview Questions

### Intermediate
**Q: How do you decide if a custom dimension should be Dense or Sparse—**
> A: The decision depends on two factors: (1) **Member count** — Dense dimensions with many members create oversized blocks. Keep dense dimensions under ~20 members. (2) **Data density** — If most intersections will have data (>50%), Dense is appropriate. If data is selective (<50%), Sparse is better because it avoids creating millions of empty blocks.

### Architect
**Q: A client wants to add a "Project" dimension with 5,000 active projects. Each Entity has at most 10 projects. How do you architect this—**
> A: (1) Make Project a **Sparse** dimension — only 10 out of 5,000 projects have data per entity, so data density is < 1%. (2) Use `No_Project` for accounts not segmented by project. (3) Use UDAs (`Active`, `Completed`) to manage project lifecycle in calc scripts. (4) On forms, never put all 5,000 projects on rows — use the Page axis with a filter, or use Valid Intersections to restrict which entities see which projects. (5) Consider splitting into an attribute dimension if projects are only for reporting (not input).

## Summary

| Design Decision | Guidance |
|----------------|----------|
| **Dense vs Sparse** | < 20 members + >50% populated = Dense; otherwise Sparse |
| **Max custom dims** | 5-8 practical maximum; each one multiplies block count |
| **"No_Dimension" member** | Always create; set consolidation to `~`; essential for non-product accounts |
| **Block size target** | 8 KB – 200 KB per block |
| **Naming convention** | Prefix-based: `PRD_`, `CHN_`, `PRJ_` for clarity |
| **UDAs** | Always use for dynamic calc script targeting |
