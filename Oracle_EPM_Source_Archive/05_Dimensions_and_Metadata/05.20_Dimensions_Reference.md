## 🏢 1. Overview of All Dimensions

Every EPBCS application has dimensions. Some are **mandatory** (OOTB — Out of the Box), and some are **optional** (Custom).

### All Dimensions in Your Project:

| # | Dimension | Type | Dense/Sparse | Purpose |
|---|-----------|------|-------------|---------|
| 1 | **Account** | OOTB | Dense | What is being measured (Revenue, Expense) |
| 2 | **Entity** | OOTB | Sparse | Which company/branch |
| 3 | **Scenario** | OOTB | Sparse | Actual vs Budget vs Forecast |
| 4 | **Version** | OOTB | Sparse | Working vs Approved draft |
| 5 | **Year** | OOTB | Sparse | FY24, FY25, FY26... |
| 6 | **Period** | OOTB | Dense | Jan, Feb, Mar... Q1, Q2... |
| 7 | **Currency** | OOTB | Sparse | INR, USD |
| 8 | **Department** | Custom | Sparse | HR, IT, Finance, Sales |
| 9 | **PlanElement** | Custom | Sparse | Load, Calculated, Adjustments |
| 10 | **Custom1** | Custom | Sparse | Planning Drivers |
| 11 | **Future** | Custom | Sparse | Future scenario tagging |

### 💡 Logic & Purpose
The standard dimensional design in EPBCS strictly separates "What happened" (Scenario) from "What iteration is this" (Version). You should never create a Scenario member called `Budget_V1` and `Budget_V2`. You create a Scenario called `Budget`, and cross it with Versions `Working`, `V1`, `V2`, and `Final`. This strict separation is what allows a single form to show a variance column comparing `Budget -> V1` against `Budget -> Final` without writing complex member formulas.

### 🌀 Confusion Resolution
> **Misconception:** "We need a way to track the Employee Name, Employee ID, Start Date, and Job Title. I will create 4 new custom dimensions for each of these."
> **Reality:** DO NOT create custom dimensions for attributes! Dimensions dictate the physical block size of the Essbase cube. Adding 4 sparse dimensions for employee details will explode the database size exponentially. Use **Smart Lists**, **Text Data Types**, or **Attributes** to track metadata properties instead of physical structural dimensions.

### 😈 Twisted Interview Question
**Question:** A developer is migrating an application from HFM (Hyperion Financial Management) to EPBCS. HFM has 12 standard dimensions. The developer decides to recreate all 12 dimensions in EPBCS as Custom dimensions because they want it to match perfectly. Why is this a catastrophic mistake—
> **Answer:** EPBCS uses Essbase (a multidimensional OLAP engine) under the hood, whereas HFM uses a relational-based financial engine. In Essbase, every Sparse dimension multiplies the potential block combinations. An application with 12+ dimensions will likely suffer from "Block Explosion", resulting in 2-hour calculation times and massive database fragmentation. You must completely redesign the dimensionality for Essbase, consolidating dimensions where possible.

## 🛠 3. Entity Dimension

The Entity dimension answers: **"WHICH company or branch—**

### Your Project's Entity Hierarchy:

```
Total Entity (Dynamic Calc — Auto-calculated)
├── E10001: Hotel Pvt Ltd (Store)
└── E10002: Manufacturing Pvt Ltd (Store)
```

### Properties:

| Member | Parent | Alias | Aggregation | Storage |
|--------|--------|-------|------------|---------|
| Total Entity | — | — | Addition | Dynamic Calc |
| E10001 | Total Entity | Hotel Pvt Ltd | Addition | Store |
| E10002 | Total Entity | Manufacturing Pvt Ltd | Addition | Store |

### How It Works:
- Users enter data at the **entity level** (E10001 or E10002)
- **Total Entity** is automatically calculated by adding E10001 + E10002
- Total Entity uses **Dynamic Calc** — no data is stored, it calculates on-the-fly

### Example:
```
                    Jan Revenue
E10001 (Hotel)    = ₹18 Cr      ← User enters this
E10002 (Mfg)      = ₹12 Cr      ← User enters this
Total Entity       = ₹30 Cr      ← Automatically calculated (18 + 12)
```

## ️ 4. Scenario Dimension

The Scenario dimension answers: **"Is this PLAN or REALITY—**

### Your Project's Scenario Members:

| Member | Purpose | Example |
|--------|---------|---------|
| **Actual** | What really happened | "January actual revenue was ₹18 Cr" |
| **Budget** | What we planned to happen | "January budgeted revenue was ₹20 Cr" |
| **Forecast** | Updated prediction based on latest info | "Revised forecast: ₹19 Cr" |
| **No Scenario** | Placeholder for data that doesn't need a scenario | Used by system |

### How They Work Together — Variance Analysis:

```
Budget Revenue (Jan):    ₹20 Cr    (what we planned)
Actual Revenue (Jan):    ₹18 Cr    (what really happened)
                         ─────────
Variance:                -₹2 Cr    (we fell short by ₹2 Cr)
```

### Edge Case — What is "No Scenario"—
Some data doesn't need a scenario context. For example, a **tax rate** of 30% is the same whether you're looking at Budget or Actual. This data goes under "No Scenario".

## 📊 5. Version Dimension

The Version dimension answers: **"WHICH draft of the data—**

### Your Project's Version Members:

| Member | Purpose | Example |
|--------|---------|---------|
| **Working** | The current work-in-progress draft | "Department is still entering numbers" |
| **Approved** | The final approved version | "CFO approved this budget" |
| **What-If** | A hypothetical scenario for analysis | "What if we cut marketing by 20%— |
| **No Version** | Placeholder | Used by system |

### Typical Workflow:

```
Working (Draft) → Review → Approved (Final)
                    ↓
              What-If (Test scenario — not submitted)
```

### Why Multiple Versions—
- Finance team enters data in **Working** version
- Manager reviews and makes changes
- Once finalized, it's moved to **Approved**
- Meanwhile, someone might run a **What-If** scenario to test alternatives

## 🏋 6. Period Dimension

The Period dimension answers: **"WHICH time period—**

### Your Project's Period Hierarchy:

```
YearTotal (Store)
├── Q1 (Store)
│   ├── Jan (Store)
│   ├── Feb (Store)
│   └── Mar (Store)
├── Q2 (Store)
│   ├── Apr (Store)
│   ├── May (Store)
│   └── Jun (Store)
├── Q3 (calculated)
│   ├── Jul
│   ├── Aug
│   └── Sep
├── Q4 (calculated)
│   ├── Oct
│   ├── Nov
│   └── Dec
└── BegBalance (Store) ← Beginning Balance
```

### Key Concepts:

| Concept | Meaning | Example |
|---------|---------|---------|
| **Monthly data** | Data entered for each month | Jan Revenue = ₹18 Cr |
| **Quarterly rollup** | Q1 = Jan + Feb + Mar | Q1 Revenue = ₹52 Cr |
| **YearTotal** | Sum of all months | YearTotal = ₹200 Cr |
| **BegBalance** | Starting balance at the beginning of the year | Opening inventory = ₹5 Cr |

### Data Storage in Periods:
- **Never Share** is the storage used for Period members
- This means each period stores its own unique value independently

## 🎓 8. Currency Dimension

The Currency dimension handles **multi-currency** applications.

### Your Project's Currency Members:

```
Currency
├── Input Currencies (what users enter data in)
│   ├── USD (US Dollar)
│   └── INR (Indian Rupee)
└── Reporting Currencies (what reports are generated in)
    ├── USD_Reporting
    └── INR_Reporting
```

### How It Works:
1. Indian users enter data in **INR**
2. US users enter data in **USD**
3. EPM converts everything to the **Reporting Currency** (e.g., USD_Reporting) using exchange rates
4. The CFO sees one consolidated report in one currency

### Exchange Rate Types (from Account properties):

| Type | When Used | Example |
|------|-----------|---------|
| **None** | No conversion needed | Data already in reporting currency |
| **Average** | For Revenue/Expense (income statement) | Average USD/INR rate for the quarter |
| **Ending** | For Assets/Liabilities (balance sheet) | USD/INR rate on March 31st |
| **Historical** | For Equity | Rate when the investment was originally made |

## 🔗 10. PlanElement Dimension (Custom)

### What It Is:
PlanElement categorizes data by **how it was created**:

```
Plan Element
└── Total (Store)
    ├── Load (Store)        ← Data loaded from external system or entered by user
    ├── Calculated (Store)  ← Data calculated by business rules
    └── Adjustments (Store) ← Manual adjustments made by planners
```

### Example:
| Data Point | PlanElement | Why— |
|-----------|-------------|------|
| January Actual Revenue = ₹18 Cr | **Load** | Loaded from ERP (actual data) |
| January Forecast Revenue = ₹19 Cr | **Calculated** | Calculated by a business rule |
| Adjustment for error correction = +₹0.5 Cr | **Adjustments** | Finance made a manual adjustment |

## 📝 11. Custom1 Dimension (Custom — Planning Drivers)

### Your Project's Custom1 Hierarchy:

```
Custom1
├── Planning_Drivers (Label Only, Ignore aggregation)
│   └── Catering_Drivers (Label Only, Ignore aggregation)
│       ├── Number_of_Meals (Store, Addition)
│       └── Selling_Price_Per_Meal (Store, Never Share)
└── No Custom1 (Store, Addition)
```

### What Are These—
These are **drivers** used in driver-based planning:

| Driver | What It Means | How It's Used |
|--------|-------------|---------------|
| **Number_of_Meals** | How many meals are planned | Revenue = Number_of_Meals × Selling_Price_Per_Meal |
| **Selling_Price_Per_Meal** | Price charged per meal | This is a rate — it should NOT be aggregated (hence "Never Share") |

### Why "Never Share" for Selling Price—
If you add prices together, you get nonsense:
- January price: ₹200
- February price: ₹200
- Q1 total: ₹400— ← **This makes no sense!**

"Never Share" prevents this. The quarterly price stays at ₹200 (or is calculated as an average), not ₹400.

## 🏋️ 14. 🎯 Hands-On Exercises — Metadata

### Exercise 1: Add a New Entity
```
1. Navigator → Dimensions
2. Select the Entity dimension
3. Select the parent member (e.g., "Total_Company")
4. Click Add Child
5. Name it "E10003", Alias "New Retail Store"
6. Set Data Storage to "Store"
7. Save and Refresh Database
```

### Exercise 2: Modify Account Properties
```
1. Select the Account dimension
2. Find a revenue account (e.g., "Product_Revenue")
3. Change its Data Type from "Currency" to "Non-Currency"
4. Try to save. (Notice how it might affect forms using currency formatting)
5. Change it back to "Currency"
6. Check the Time Balance property — is it Flow or Balance— (Should be Flow for Revenue)
```

### Exercise 3: Setting Up a Smart List
```
1. Navigator → Smart Lists
2. Create a new Smart List called "Approval_Status"
3. Add entries: 1=Draft, 2=Submitted, 3=Approved
4. Go to Dimensions → Account
5. Create a new account "Status_Flag"
6. Set Data Type to "Smart List" and select "Approval_Status"
7. Save and Refresh Database
```

### Exercise 4: Testing Implied Sharing
```
1. Create a parent member "Temp_Parent" in Entity
2. Add exactly ONE child member "Temp_Child" under it
3. Set parent to "Store" or "Dynamic Calc"
4. Refresh Database
5. Notice that Temp_Parent behaves as if it shares the data of Temp_Child (Implied Sharing)
```
