## 🏢 1. Why Account Dimension is Special

The Account dimension is the **only dimension** that has all these extra properties:
- Account Type
- Time Balance
- Exchange Rate Type
- Data Storage
- Skip Value
- Variance Reporting
- Data Type

Other dimensions only have basic properties like Aggregation and Storage.

---

## 💡 2. Account Type

The **Account Type** tells Essbase what kind of financial data this account holds. This affects how calculations work.

| Account Type | Used For | Example Accounts |
|-------------|----------|-----------------|
| **EXPENSE** | Costs and expenses | Salary, Rent, Electricity, Raw Material |
| **REVENUE** | Income or sales | Room Revenue, Catering Revenue, Food Sales |
| **ASSET** | Resources owned by the company | Cash, Inventory, Equipment, Land |
| **LIABILITY** | Amounts the company owes | Loans, Accounts Payable, Taxes Payable |
| **EQUITY** | Owner's investment and retained earnings | Share Capital, Retained Earnings |
| **SAVED ASSUMPTION** | Assumption values used in calculations | Tax Rate (30%), Growth Rate (5%), Inflation (4%) |

### Why Does Account Type Matter—

Account Types affect:
1. **Variance Reporting** — Is a positive variance good or bad—
2. **Time Balance** — How data rolls up over time
3. **Exchange Rate** — Which exchange rate to use for currency conversion

### Example — Saved Assumption:
```
Tax Rate (Saved Assumption) = 30%

Revenue = ₹100 Cr
Tax = Revenue × Tax Rate = ₹100 Cr × 30% = ₹30 Cr

If Tax Rate changes to 28%:
Tax = ₹100 Cr × 28% = ₹28 Cr (automatically recalculated)
```

## 🛠 3. Variance Reporting

**Variance** = Budget - Actual (or the other way, depending on the type)

The question is: **"Is a positive difference GOOD or BAD—**

| Type | Setting | Meaning | Example |
|------|---------|---------|---------|
| **Non-Expense** | Used for Revenue, Assets, etc. | Positive variance = FAVORABLE (good) | Revenue: Budget ₹100, Actual ₹120 → Variance +₹20 → 😊 Good! |
| **Expense** | Used for Expense accounts | Negative variance = FAVORABLE (good) — because spending LESS is good | Expense: Budget ₹50, Actual ₹40 → Variance -₹10 → 😊 Good! (we saved ₹10!) |

### Edge Case — Why This Matters:
If you mark a Revenue account with "Expense" variance reporting:
- Revenue Budget = ₹100, Actual = ₹120
- Variance = +₹20
- System would show this as **UNFAVORABLE** ❌ (which is WRONG!)

### 💡 Logic & Purpose
The Account dimension is mathematically unique because it handles the double-entry accounting sign conventions implicitly. If you build a P&L reporting hierarchy, you don't need to write negative numbers for expenses. You input expenses as positive numbers (e.g., $5,000 for Rent) and set the Account Type to `Expense`. The Essbase engine automatically knows how to subtract it from `Revenue` when rolling up to `Net Income` without you writing a single formula.

### 🌀 Confusion Resolution
> **Misconception:** "My Headcount account is rolling up to the Total Assets line, so I should set the Account Type to Asset."
> **Reality:** Headcount is NOT an Asset! Setting it to Asset will subject it to currency translation rules and financial variance logic. Non-financial drivers like Headcount, Square Footage, or Units Sold MUST be set to `Saved Assumption` (or an equivalent non-financial type) so they are excluded from automated financial logic like exchange rate conversions.

### 😈 Twisted Interview Question
**Question:** A client wants to track "Customer Satisfaction Score" on a form. They create an Account member, set the Type to `Revenue` (because a higher score is better), and enter a value of 85. The next day, the score changes to 90. When they check the Quarter total, it says the score is 175. Why—
> **Answer:** By setting the Account Type to `Revenue`, the system defaulted the `Time Balance` property to `Flow` (which adds up the months). Customer Satisfaction is a non-financial metric that should not aggregate over time. The developer should have set the Time Balance to `First`, `Last`, or `Average` so the quarterly score reflects the average or ending score, not a mathematically impossible summed score of 175.

## ️ 4. Time Balance — How Data Rolls Up Over Time

Time Balance controls what happens when **monthly data rolls up to quarterly or yearly totals**.

### Flow (Most Common for Revenue/Expense)

**Meaning:** Add up all months to get the total.

```
                Jan    Feb    Mar    Apr    May    Jun    YearTotal
Account 100110: 100    200     —     400    500    600    6800
Account 100120: 200    400    600    800   1000   1200   15600
```

**YearTotal = Jan + Feb + Mar + ... + Dec (all months added)**

**Use For:** Revenue, Expenses, Sales — anything that accumulates over time.

### First

**Meaning:** Take only the FIRST month's value as the total.

```
                Jan    Feb    Mar    Apr    May    Jun    YearTotal
Account 100110: 100    200     —     400    500    600    100  ← Takes January's value!
Account 100120: 200    400    600    800   1000   1200    200  ← Takes January's value!
```

**YearTotal = January value only**

**Use For:** Beginning balances, opening headcount. "How many employees did we START with—

### Balance

**Meaning:** Take the LAST month's value (ending balance).

```
                Jan     Feb     Mar    Q1 Total
Cash Balance:  ₹50L    ₹55L   ₹60L    ₹60L  ← Takes March value (last month)
```

**Q1 = March value (the closing/ending balance)**

**Use For:** Balance sheet items — Cash Balance, Inventory Balance, Loan Outstanding. These don't add up; you want the LATEST value.

### Edge Case — Why NOT Use Flow for Balance Sheet—
```
Cash in Jan = ₹50 Lakh
Cash in Feb = ₹55 Lakh
Cash in Mar = ₹60 Lakh

If Flow: Q1 Cash = ₹50 + ₹55 + ₹60 = ₹165 Lakh ← WRONG! 😱
If Balance: Q1 Cash = ₹60 Lakh ← CORRECT! ✅
```
You don't "add up" cash — the cash on March 31st is your actual balance.

### Average

**Meaning:** Calculate the simple average of all months.

```
                Jan     Feb     Mar    Q1 Average
Revenue:       ₹100    ₹200   ₹150    ₹150  ← (100+200+150)/3
```

**Use For:** Average price, average exchange rate.

### AVG_ACTUAL (Average Actual)

**Meaning:** Average only months that HAVE data (skip missing months).

```
                Jan     Feb     Mar    Q1 Average
Revenue:       ₹100   #MISSING  ₹150    ₹125  ← (100+150)/2, skips Feb
```

**Note:** If all months have data, AVG_ACTUAL = AVERAGE. The difference only shows when some months are #MISSING.

### AVG_365

**Meaning:** Average over a fixed 365-day year, regardless of missing data.

```
Uses 365 days as the denominator, even if some months are missing.
```

**Use For:** Annualized calculations, especially in financial services.

### FILL

**Meaning:** Carry the last entered value forward until a new value is entered.

```
                Jan     Feb     Mar    Apr    May    Jun
Account:       ₹100   ₹100   ₹100   ₹200   ₹200   ₹200
                ↑                      ↑
            Entered ₹100          Entered ₹200
         (Feb, Mar auto-filled)  (May, Jun auto-filled)
```

**Use For:** Fixed rates that change occasionally (e.g., monthly rent, exchange rate that changes quarterly).

### Summary — When to Use Each Time Balance:

| Time Balance | When to Use | Typical Account Types |
|-------------|-------------|----------------------|
| **FLOW** | Values that accumulate over time | Revenue, Expenses, Sales quantity |
| **FIRST** | Opening/beginning values | Beginning headcount, Opening balance |
| **BALANCE** | Ending/closing values | Cash balance, Loan outstanding, Inventory |
| **AVERAGE** | Simple average over time | Average price, Average rate |
| **AVG_ACTUAL** | Average excluding missing periods | Average when not all months have data |
| **AVG_365** | Fixed 365-day average | Annualized returns |
| **FILL** | Carry forward last value | Rent, Fixed rates |

## 📊 5. Data Storage — Where and How Data is Stored

| Storage Type | Meaning | Can User Enter Data— | Stored in Cube— | Example |
|-------------|---------|---------------------|-----------------|---------|
| **Store** | Data is physically saved in the cube | ✅ Yes | ✅ Yes | "Rooms Revenue" — user enters ₹18 Cr |
| **Dynamic Calc** | Calculated on-the-fly when viewed (not stored) | ❌ No | ❌ No | "Total Revenue" = sum of all revenue accounts |
| **Dynamic Calc and Store** | Calculated and then stored for faster future retrieval | ❌ No (first time), then stored | ✅ Yes (after first calc) | Used for expensive calculations |
| **Never Share** | Creates a unique block even if member name exists elsewhere | ✅ Yes | ✅ Yes | "Miscellaneous Expenses" — needs its own data |
| **Shared** | Shares data from another stored member | ❌ No (reads from source) | ❌ No (references source) | Same account appearing in two places in hierarchy |
| **Label Only** | Used only for grouping/headings — no data | ❌ No | ❌ No | "PL Accounts" — just a category header |

### From Your Project:

```
PL Accounts      → Label Only      (just a heading)
Net Profit       → Dynamic Calc    (= Income - Expense, calculated)
100000: Income   → Dynamic Calc    (= sum of all revenue accounts)
100110: Rooms Rev → Store          (user enters data here)
100120: Banquet Rev → Store        (user enters data here)
200800: Misc Exp → Never Share     (unique data, not shared)
```

### Visual — How Data Flows:

```
User enters data here (Store members):
    100110: Rooms Revenue = ₹18 Cr
    100120: Banquet Revenue = ₹8 Cr

Dynamic Calc members calculate automatically:
    100100: Hotel Revenue = ₹18 + ₹8 = ₹26 Cr (Dynamic Calc)
    100000: Income = ₹26 + other revenues = ₹50 Cr (Dynamic Calc)
    Net Profit = Income - Expense = ₹50 - ₹30 = ₹20 Cr (Dynamic Calc)
```

## 🏋 6. Aggregation (Consolidation Operators)

Aggregation controls **HOW a child member contributes to its parent**:

| Operator | Symbol | Meaning | Example |
|----------|--------|---------|---------|
| **Addition** | + | Add to parent | Revenue + Revenue = Total Revenue |
| **Subtraction** | - | Subtract from parent | Revenue - Expense = Net Profit |
| **Multiplication** | * | Multiply | Quantity × Price = Revenue |
| **Division** | / | Divide | Total / Count = Average |
| **Percent** | % | Percentage | Value × Percent |
| **Ignore** | ~ | Don't include in parent total | "Budget Drivers" are ignored in P&L total |
| **Never** | ^ | Never consolidate | Rate/Price members (should not add up) |

### From Your Project — Aggregation Example:

```
Parent: 100100 (Hotel Revenue) — Dynamic Calc, Addition
├── Child: 100110 (Rooms Revenue) — Store, Addition (+)     = ₹1715
└── Child: 100120 (Banquet Revenue) — Store, Addition (+)   = ₹1872
                                                              ──────
    100100 = 100110 + 100120                                = ₹3587 ✅
```

### Subtraction Example:

```
If 100120 had Subtraction aggregation:
    100100 = 100110 - 100120
    100100 = ₹1715 - ₹1872 = -₹157
```

This was shown in your training data:

```
        Aggregation  Child  100110  Store     1715  740   2353  540  1008  1973
        Subtraction  Child  100120  Store     1872  1691   253  1248  1596  1700
        Parent       100100 Dynamic Calc     -157  -951  2100  -708  -588   273
```

## ️ 7. Skip Value

Skip Value tells Essbase what to do with **zero or missing values** when calculating averages or other aggregations.

| Setting | What Gets Skipped | Use Case |
|---------|-------------------|----------|
| **None** | Nothing is skipped | Include everything, even zeros and missing |
| **Zeros** | Skip cells with value 0 | Average calculation should ignore zero months |
| **Missing** | Skip cells with #MISSING | Average should only consider months with data |
| **Missing and Zero** | Skip both | Most conservative — only include months with actual positive/negative data |

### Example:
```
Monthly Revenue:  Jan=₹100, Feb=#MISSING, Mar=₹0, Apr=₹200

Skip = None:     Average = (100 + 0 + 0 + 200) / 4 = ₹75
Skip = Missing:  Average = (100 + 0 + 200) / 3 = ₹100
Skip = Zeros:    Average = (100 + #MISSING + 200) / 2 = ₹150
Skip = Both:     Average = (100 + 200) / 2 = ₹150
```

## 🎓 8. Exchange Rate Type

Controls which exchange rate to use when converting this account from one currency to another.

| Type | Meaning | Used For |
|------|---------|----------|
| **None** | No currency conversion | Account already in reporting currency |
| **Average** | Average exchange rate for the period | Revenue, Expenses (P&L items) |
| **Ending** | Exchange rate on the last day of the period | Assets, Liabilities (Balance Sheet items) |
| **Historical** | Exchange rate from the original transaction date | Equity items (Share Capital) |

### Why Different Rates—

| Account | Exchange Rate | Reasoning |
|---------|--------------|-----------|
| Revenue (Jan) | Average rate for January | Revenue was earned throughout the month |
| Cash Balance (Jan 31) | Ending rate on Jan 31 | Balance is a point-in-time value |
| Share Capital | Historical rate (when shares were issued) | Equity is valued at historical cost |

## 🔗 10. Implied Sharing

**Implied Sharing** is an Essbase behavior where a parent member automatically shares its value with its only child (or vice versa).

### When Does It Happen—
- A parent has **only one child**
- The parent automatically shows the same value as the child

### Example:
```
Revenue (Parent — has only one child)
└── Product_Revenue (Child)

If Product_Revenue = ₹100 Cr
Then Revenue = ₹100 Cr (implied sharing — same value)
```

### Why Does This Matter—
- No extra calculation needed
- Saves storage space
- But it can confuse you if you don't expect it!

### Edge Case:
If you add a **second child** later, implied sharing **stops** and the parent starts calculating normally (addition of both children).
