## 🏢 1. Overview

A **Member Formula** is a calculation attached directly to a dimension member. When Essbase retrieves or calculates that member, it executes the formula.

## 🛠 3. Basic Syntax

```
// Simple formula: Net Profit = Income - Expense
"Income" - "Expense";

// Conditional formula
IF("Revenue" > 0)
  "Revenue" * 0.30;    // Tax = 30% of Revenue
ELSE
  0;
ENDIF;

// Cross-dimensional reference
"Revenue" -> "Jan";    // Get January's Revenue
"Revenue" -> "E10001"; // Get E10001's Revenue
```

## ️ 4. When to Use Member Formulas vs Business Rules

| Feature | Member Formula | Business Rule |
|---|---|---|
| **Attached to** | A specific member | Runs independently |
| **Executes when** | Member is calculated/retrieved | User runs it manually or on form save |
| **Complexity** | Simple to moderate | Can be very complex |
| **Cross-cube** | ❌ Same cube only | ✅ Can span cubes |
| **Groovy** | ❌ Not supported | ✅ Supported |

### 💡 Logic & Purpose
Member Formulas exist because not every calculation needs to be pushed through a heavy batch engine. If you just need a simple ratio like "Margin % = Profit / Revenue", running a Business Rule every time someone wants to look at a report is highly inefficient. By attaching the calculation directly to the `Margin %` member as a `Dynamic Calc` formula, the math happens instantaneously in RAM only at the moment a user requests to view that cell on a form or report.

### 🌀 Confusion Resolution
> **Misconception:** "I wrote a complex member formula to calculate Employee Bonus across 100,000 employees. I set it to `Dynamic Calc`, but now the form takes 3 minutes to load."
> **Reality:** Member formulas are strictly designed for *simple* math (ratios, variances, basic IF statements). If you embed complex cross-dimensional logic (like looking up historical rates across a massive sparse dimension) inside a Dynamic Calc formula, the Essbase engine will struggle to calculate it on-the-fly during a retrieval. Complex calculations should be moved to a Business Rule running against a `Store` member.

### 😈 Twisted Interview Question
**Question:** An admin writes a member formula: `"Net_Profit" = "Revenue" - "Expenses";`. They attach it to the `Net_Profit` account and set the storage to `Store`. They open a form, but Net Profit is showing `#MISSING`. Why—
> **Answer:** If a member is tagged as `Store`, Essbase *ignores* the member formula during a normal form retrieval! `Store` implies the data is physically saved on the disk. To force a `Store` member to evaluate its formula, you must explicitly run a Business Rule (Calc Script) that targets that member. If you want the formula to calculate automatically when the user opens the form, you MUST set the member storage to `Dynamic Calc`.

## 🏋️ 6. 🎯 Hands-On Exercises — Member Formulas

### Exercise 1: Simple Ratio Calculation
```
1. In Dimension Editor, edit Account "Gross_Margin_Pct"
2. Set Data Storage to Dynamic Calc
3. In the Member Formula box, enter:
   "Gross_Margin" / "Revenue" * 100;
4. Validate and Save
5. Refresh Database
6. Open a form to verify the calculation works on retrieval
```

### Exercise 2: Conditional Formula (IF/ELSE)
```
1. Edit Account "Bonus_Accrual" (Dynamic Calc)
2. Enter formula:
   IF("Net_Income" > 100000)
       "Net_Income" * 0.10;
   ELSEIF("Net_Income" > 50000)
       "Net_Income" * 0.05;
   ELSE
       0;
   ENDIF;
3. Validate, Save, and Refresh
4. Test with different Net Income values
```

### Exercise 3: Cross-Dimensional Reference
```
1. Edit Account "Prior_Year_Revenue" (Dynamic Calc)
2. Enter formula:
   "Revenue" -> @PRIOR("Years");
3. Validate, Save, and Refresh
4. Test in a form to see if it pulls last year's revenue
```

### Exercise 4: Using @Functions
```
1. Edit Account "YTD_Revenue" (Dynamic Calc)
2. Enter formula:
   @SUM(@CURGEN("Period"), "Revenue"); // Adjust based on your time hierarchy
   // Alternatively: @SUM(Jan:@CURGEN(Period))
3. Validate, Save, and Refresh
```
