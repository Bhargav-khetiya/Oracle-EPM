# SECTION 1: DIMENSION FUNDAMENTALS

---

## 1.1 What is a Dimension—

A **Dimension** is a structural category used to organize and analyze data in an Essbase cube. Each dimension represents a different "axis" of analysis.

```
Think of it as a spreadsheet:
  - Rows = One dimension (Account)
  - Columns = Another dimension (Period)
  - Different sheets = Another dimension (Entity)
  - Different workbooks = Another dimension (Scenario)
  
But Essbase supports 10-25+ dimensions simultaneously,
which is impossible in Excel.
```

## 1.2 Standard vs Custom Dimensions

### Standard Dimensions (System-Created)
These dimensions are automatically created when you build an EPBCS application. You CANNOT delete them.

| Dimension | Purpose | Always Present— |
|-----------|---------|----------------|
| **Account** | Financial line items (Revenue, Expense, etc.) | ✅ Yes (except Free Form) |
| **Entity** | Organizational units (companies, departments) | ✅ Yes (except Free Form) |
| **Period** | Time periods (Jan, Feb, Q1, etc.) | ✅ Yes |
| **Year** | Fiscal years (FY25, FY26, FY27) | ✅ Yes |
| **Scenario** | Data versions (Actual, Budget, Forecast) | ✅ Yes (except Free Form) |
| **Version** | Workflow stages (Working, Final) | ✅ Yes (except Free Form) |
| **Currency** | Reporting currencies (INR, USD, GBP) | Only if multi-currency |

### Custom Dimensions (User-Created)
Created by the administrator to model additional business analysis categories.

| Example | Purpose |
|---------|---------|
| **Department** | Catering, Front Office, Finance, HR |
| **Product** | Room Type, F&B Category, Event Type |
| **Channel** | Direct, OTA, Corporate |
| **Project** | CapEx projects, IT initiatives |
| **Driver** | Units, Rate, Occupancy %, Price |

### Limits:
| Application Type | Max Custom Dimensions |
|------------------|-----------------------|
| Standard | Up to 7 custom dimensions |
| Enterprise | Module-dependent (3-5 additional) |
| Free Form | Up to 20 total dimensions |

## 1.3 Dimension Terminology

```
Account (Dimension)
  │
  ├── Total P&L (Root Member / Generation 0)
  │   │
  │   ├── Revenue (Parent / Generation 1 / Level 2)
  │   │   │
  │   │   ├── 100110: Rooms Revenue (Child / Leaf / Level 0 / Generation 2)
  │   │   ├── 100120: Banquet Revenue (Child / Leaf / Level 0 / Generation 2)
  │   │   └── 100130: F&B Revenue (Child / Leaf / Level 0 / Generation 2)
  │   │
  │   └── Expense (Parent / Generation 1 / Level 2)
  │       ├── 200000: Salaries (Leaf / Level 0)
  │       ├── 200010: Benefits (Leaf / Level 0)
  │       └── 200020: Utilities (Leaf / Level 0)
  │
  └── KPIs (Parent, separate branch)
      ├── Gross Margin % (Leaf with formula)
      └── RevPAR (Leaf with formula)

Terminology:
  Root = Top-most member of the dimension
  Parent = Any member with children
  Child = Any member under a parent
  Sibling = Members sharing the same parent
  Leaf (Level 0) = Bottom member with no children
  Ancestor = Any member above in the hierarchy
  Descendant = Any member below in the hierarchy
```

# SECTION 2: ACCOUNT DIMENSION

---

## 2.1 Purpose

The Account dimension represents your **chart of accounts** — every financial line item that needs to be planned, budgeted, or reported.

## 2.2 Standard Account Hierarchy Pattern

```
Account (Dimension Root)
  ├── Income Statement
  │   ├── Revenue
  │   │   ├── Operating Revenue
  │   │   │   ├── 100110: Rooms Revenue (Store, +)
  │   │   │   ├── 100120: Banquet Revenue (Store, +)
  │   │   │   ├── 100130: F&B Revenue (Store, +)
  │   │   │   └── 100140: Parking Revenue (Store, +)
  │   │   └── Non-Operating Revenue
  │   │       ├── 110000: Interest Income (Store, +)
  │   │       └── 110010: Gain on Sale (Store, +)
  │   │
  │   ├── COGS (Cost of Goods Sold)
  │   │   ├── 200000: Raw Materials (Store, +)
  │   │   └── 200010: Direct Labor (Store, +)
  │   │
  │   ├── Gross Margin (Dynamic Calc, formula: Revenue - COGS)
  │   │
  │   ├── Operating Expense
  │   │   ├── 300000: Salaries (Store, +)
  │   │   ├── 300010: Benefits (Store, +)
  │   │   ├── 300020: Rent (Store, +)
  │   │   ├── 300030: Utilities (Store, +)
  │   │   ├── 300040: Depreciation (Store, +)
  │   │   └── 300050: Travel (Store, +)
  │   │
  │   ├── EBITDA (Dynamic Calc, formula: Gross Margin - OpEx + Depreciation)
  │   ├── EBIT (Dynamic Calc, formula: EBITDA - Depreciation)
  │   ├── Tax (Store, +)
  │   └── Net Income (Dynamic Calc, formula: EBIT - Tax)
  │
  ├── Balance Sheet
  │   ├── Assets
  │   │   ├── Current Assets
  │   │   │   ├── 400000: Cash (Store, Time Balance: Balance)
  │   │   │   ├── 400010: Accounts Receivable (Store, Time Balance: Balance)
  │   │   │   └── 400020: Inventory (Store, Time Balance: Balance)
  │   │   └── Fixed Assets
  │   │       ├── 410000: Property (Store, Time Balance: Balance)
  │   │       └── 410010: Equipment (Store, Time Balance: Balance)
  │   └── Liabilities & Equity
  │       ├── 500000: Accounts Payable (Store, Time Balance: Balance)
  │       ├── 500010: Long-Term Debt (Store, Time Balance: Balance)
  │       └── 600000: Retained Earnings (Store, Time Balance: Balance)
  │
  ├── Cash Flow
  │   ├── Operating Cash Flow (Dynamic Calc)
  │   ├── Investing Cash Flow (Dynamic Calc)
  │   └── Financing Cash Flow (Dynamic Calc)
  │
  └── Statistical Accounts (Driver Accounts)
      ├── Rooms Available (Store, ~, Account Type: Saved Assumption)
      ├── Rooms Sold (Store, ~)
      ├── Occupancy Rate (Dynamic Calc, ~, formula: Rooms Sold / Rooms Available)
      ├── Average Room Rate (Store, ~, Account Type: Saved Assumption)
      └── RevPAR (Dynamic Calc, ~, formula: Revenue / Rooms Available)
```

## 2.3 Account Properties — Complete Reference

Every Account member has these properties:

| Property | Values | What It Controls |
|----------|--------|-----------------|
| **Account Type** | Revenue, Expense, Asset, Liability, Equity, Saved Assumption | Variance reporting direction and consolidation behavior |
| **Variance Reporting** | Expense, Non-Expense | How positive/negative variances are interpreted |
| **Time Balance** | Flow, First, Balance, Average, Fill, Weighted Average | How data aggregates across time periods |
| **Skip Value** | None, #Missing, Zeros, Missing and Zeros | What values to skip during time balance aggregation |
| **Exchange Rate Type** | None, Average, Ending, Historical | Which FX rate to use for currency translation |
| **Data Storage** | Store, Dynamic Calc, Dynamic Calc and Store, Never Share, Shared, Label Only | Where/how data is stored |
| **Consolidation Operator** | +, -, *, /, ~, ^, % | How member rolls up to parent |
| **Two-Pass** | Yes / No | Whether to calculate in second pass |
| **Plan Type** | Plan1, Plan2, CapPlan, etc. | Which cubes this member belongs to |
| **Smart List** | (linked Smart List name) | Dropdown list for data entry |
| **UDA** | Free text tags | User-defined attribute tags |
| **Member Formula** | Essbase formula | Calculation formula |
| **Alias** | Alias table → display name | User-friendly display name |

All Entities (Root)

# SECTION 4: PERIOD DIMENSION

---

## 4.1 Purpose

The Period dimension defines the **time granularity** for data entry — monthly, quarterly, annually.

## 4.2 Period Hierarchy

```
YearTotal (Root — Dynamic Calc)
  ├── Q1 (Parent — Dynamic Calc)
  │   ├── Jan (Leaf — Store)
  │   ├── Feb (Leaf — Store)
  │   └── Mar (Leaf — Store)
  ├── Q2 (Parent — Dynamic Calc)
  │   ├── Apr (Leaf — Store)
  │   ├── May (Leaf — Store)
  │   └── Jun (Leaf — Store)
  ├── Q3 (Parent — Dynamic Calc)
  │   ├── Jul (Leaf — Store)
  │   ├── Aug (Leaf — Store)
  │   └── Sep (Leaf — Store)
  └── Q4 (Parent — Dynamic Calc)
      ├── Oct (Leaf — Store)
      ├── Nov (Leaf — Store)
      └── Dec (Leaf — Store)

For Indian Fiscal Year (April-March):
  FY Total
    ├── Q1: Apr, May, Jun
    ├── Q2: Jul, Aug, Sep
    ├── Q3: Oct, Nov, Dec
    └── Q4: Jan, Feb, Mar
```

## 4.3 Period and Time Balance Interaction

The Period dimension aggregation is controlled by the **Time Balance** property on the Account:

```
Account: Revenue (Time Balance: Flow)
  Jan: ₹18Cr, Feb: ₹19Cr, Mar: ₹20Cr
  Q1 = Jan + Feb + Mar = ₹57Cr  ← SUM for Flow accounts

Account: Cash Balance (Time Balance: Balance)
  Jan: ₹100Cr, Feb: ₹105Cr, Mar: ₹110Cr
  Q1 = Mar = ₹110Cr  ← LAST value for Balance accounts

Account: Headcount (Time Balance: Average)
  Jan: 500, Feb: 510, Mar: 520
  Q1 = (500 + 510 + 520) / 3 = 510  ← AVERAGE for Average accounts

Account: Opening Balance (Time Balance: First)
  Jan: ₹100Cr, Feb: ₹105Cr, Mar: ₹110Cr
  Q1 = Jan = ₹100Cr  ← FIRST value for First accounts
```

## 4.4 BegBalance and Period Mappings

```
Special Period Members:
  BegBalance: Opening balance before the first period
    → Used for Balance Sheet accounts
    → Cash BegBalance = closing balance of prior year
    
  YearTotal: Full-year aggregation
    → For Flow accounts: Sum of 12 months
    → For Balance accounts: = Dec (or last month)
```

# SECTION 5: YEAR DIMENSION

---

## 5.1 Purpose

The Year dimension holds the fiscal years. Each year is typically a separate member.

```
Year Dimension:
  ├── FY24 (Historical)
  ├── FY25 (Historical)
  ├── FY26 (Current Budget Year)
  ├── FY27 (Forecast)
  ├── FY28 (Long-Range Plan)
  └── FY29 (Long-Range Plan)
```

## 5.2 Year Properties

| Property | Description |
|----------|-------------|
| **Start Year / End Year** | Application setting — determines available years |
| **Historical Year** | Past years — typically loaded from ERP (Actuals) |
| **Plan Year** | Current and future years — open for user input |

## 5.3 Adding/Removing Years

```
Adding a new year:
  Application → Dimensions → Year → Add Member "FY30"
  → Requires Refresh Database (Sparse restructure — fast)
  
Removing a historical year:
  ⚠️ Data for that year will be DELETED
  → Must carefully plan data archival before removal
```

# SECTION 6: SCENARIO DIMENSION

---

## 6.1 Purpose

The Scenario dimension separates different **versions of reality** — what actually happened vs. what was planned.

```
Scenario Dimension:
  ├── Actual     ← Loaded from ERP (what happened)
  ├── Budget     ← Annual budget (what we planned)
  ├── Forecast   ← Re-forecast (updated expectations)
  └── Plan       ← Long-range strategic plan (3-5 years)
```

## 6.2 Scenario Properties

| Property | Options | Description |
|----------|---------|-------------|
| **Start Year** | FY24 | First year this scenario has data |
| **End Year** | FY29 | Last year this scenario has data |
| **Start Period** | Jan | First period open for data |
| **End Period** | Dec | Last period open for data |
| **Exchange Rate Table** | (table name) | Which FX rate table to use |
| **Enabled for Process Management** | Yes/No | Whether approval workflow applies |

## 6.3 Variance Analysis

```
Variance = Actual - Budget
Variance % = (Actual - Budget) / Budget × 100

For Revenue (Non-Expense variance reporting):
  Actual Revenue: ₹26Cr
  Budget Revenue: ₹25Cr
  Variance: +₹1Cr (FAVORABLE — actual > budget)
  Variance %: +4%

For Expense (Expense variance reporting):
  Actual Expense: ₹12Cr
  Budget Expense: ₹10Cr
  Variance: +₹2Cr (UNFAVORABLE — actual > budget means overspent)
  Variance %: +20%

The Account Type and Variance Reporting properties control
whether a positive variance is shown as favorable or unfavorable.
```

# SECTION 7: VERSION DIMENSION

---

## 7.1 Purpose

The Version dimension tracks **workflow stages** of the same budget/forecast data.

```
Version Dimension:
  ├── Working   ← Draft — analysts are still editing
  ├── Final     ← Approved — locked for submission
  └── v1, v2    ← Optional iterations (e.g., "Budget v1", "Budget v2")
```

## 7.2 Version Types

| Type | Behavior |
|------|----------|
| **Standard Bottom-Up** | Data entered at lowest Entity level, rolls up by sum |
| **Standard Top-Down** | Data can be entered at any Entity level, distributed down |
| **Target Bottom-Up** | Read-only target values, bottom-up consolidation |
| **Target Top-Down** | Read-only target values, top-down distribution |

```
Bottom-Up Example:
  User enters Revenue for Hotel India = ₹26Cr
  User enters Revenue for Hotel USA = ₹30Cr
  All Entities Revenue = ₹56Cr (automatic sum)

Top-Down Example:
  CFO enters Revenue for All Entities = ₹60Cr
  System distributes: Hotel India = ₹28Cr, Hotel USA = ₹32Cr
  (based on historical ratio or equal distribution)
```

# SECTION 8: CURRENCY DIMENSION

---

## 8.1 Purpose

The Currency dimension exists only in **multi-currency applications**. It allows data entry in local currency and reporting in group currency.

```
Currency Dimension:
  ├── Local        ← Data entered in entity's base currency
  ├── INR          ← Reporting in Indian Rupees (group currency)
  ├── USD          ← Reporting in US Dollars
  └── GBP          ← Reporting in British Pounds
```

## 8.2 Currency Translation Process

```
Hotel USA base currency = USD
Group reporting currency = INR

Data Entry (in Local = USD):
  Revenue [Hotel USA, Jan, Budget, Local] = $350,000

Exchange Rate (from Rate table):
  USD→INR Average Rate for Jan = 83.50

After Currency Translation Rule:
  Revenue [Hotel USA, Jan, Budget, INR] = $350,000 × 83.50 = ₹2,92,25,000

The Exchange Rate Type on the Account determines WHICH rate to use:
  Revenue → Average Rate (earned evenly throughout period)
  Cash → Ending Rate (point-in-time balance)
  Equity → Historical Rate (original investment rate)
```

---

## 9.1 Common Custom Dimensions

| Custom Dimension | Purpose | Example Members |
|-----------------|---------|-----------------|
| **Department** | Cost center / functional area | Catering, Front Office, Finance, HR, IT |
| **Product** | Product line / service | Room Type A, Room Type B, Banquet Hall |
| **Channel** | Sales/distribution channel | Direct Booking, OTA, Corporate Contract |
| **Project** | CapEx or strategic projects | Expansion Phase 1, IT Upgrade, Renovation |
| **Driver / Custom1** | Planning drivers and assumptions | Units, Rate, Occupancy %, Growth % |
| **Segment** | Business segment | Luxury, Economy, Business |

## 9.2 Design Best Practices

```
✅ DO:
  - Keep custom dimensions small (< 50 members if possible)
  - Make them Sparse (unless very small and fully populated)
  - Use meaningful member names with prefixes: D10010 Catering
  - Design complete hierarchies before building
  - Consider reporting needs: "Can I pivot on this dimension—

❌ DON'T:
  - Create custom dimensions for attributes (use UDA or Attribute Dimensions)
  - Create too many custom dimensions (each adds sparse complexity)
  - Make custom dimensions Dense (inflates block size)
  - Use custom dimensions for one-time categorization (use UDA)
```

## 9.3 "No" Members

Every custom dimension has a system-generated "No" member:

```
Department Dimension:
  Department (Root)
    ├── No Department    ← System member, always exists
    ├── D10010: Catering
    ├── D10020: Front Office
    └── D10030: Finance

"No Department" is used when an Account applies to ALL departments
or is not department-specific.

Example:
  Revenue is entered at "No Department" (company-wide revenue)
  Salaries is entered per department: Catering, Front Office, etc.
```

# SECTION 11: DATA STORAGE PROPERTIES

---

## 11.1 Complete Data Storage Reference

### Store
```
Purpose: Data is physically saved in the Essbase cube block.
User Input: ✅ Yes
Stored on Disk: ✅ Yes
Block Size Impact: ✅ Adds cells to block
Use For: Leaf-level input members, loaded data
Example: "100110: Rooms Revenue" — user enters ₹18Cr
```

### Dynamic Calc
```
Purpose: Calculated on-the-fly every time it's queried. NOT stored.
User Input: ❌ No
Stored on Disk: ❌ No  
Block Size Impact: ❌ Does NOT add cells to block
Use For: Parent members, ratios, KPIs, calculated metrics
Example: "Revenue" = sum of Rooms + Banquet + F&B (calculated when queried)

Key Benefit: Reduces block size → reduces memory → improves performance
Key Cost: Calculation overhead on every query
```

### Dynamic Calc and Store
```
Purpose: Calculated once on first query, then stored for faster future retrieval.
User Input: ❌ No
Stored on Disk: ✅ Yes (after first calculation)
Block Size Impact: ✅ Adds cells to block
Use For: Expensive calculations queried frequently
Example: Complex allocation formula that takes seconds to compute

Caution: Must CLEARBLOCK DYNAMIC to force recalculation when source data changes
```

### Never Share
```
Purpose: Forces the member to NOT participate in implied sharing.
User Input: ✅ Yes
Stored on Disk: ✅ Yes
Block Size Impact: ✅ Adds cells to block
Use For: Single-child situations where you want independent data

Example: 
  Revenue
    └── Rooms Revenue (only child)
  
  Without Never Share: Implied sharing kicks in → Revenue = Rooms Revenue (same cell)
  With Never Share on Rooms Revenue: Each stores its own independent value
```

### Shared
```
Purpose: Points to an existing member's data. No independent storage.
User Input: Via base member only
Stored on Disk: ❌ No (shares base member's cell)
Block Size Impact: ❌ Does NOT add cells
Use For: Alternate hierarchies, different roll-up views

Example:
  Primary Hierarchy:
    Revenue → Rooms Revenue → 100110 (base member, Store)
  
  Alternate Hierarchy:
    By Geography → India Revenue → 100110 (SHARED member)
    
  Both point to the SAME data cell. Change one → both change.
```

### Label Only
```
Purpose: Organizational grouping — no data storage at all.
User Input: ❌ No
Stored on Disk: ❌ No
Block Size Impact: ❌ Does NOT add cells
Use For: Grouping headers, organizational nodes

Example:
  "Statistical Accounts" (Label Only) — just a grouping header
    ├── Rooms Available (Store)
    ├── Occupancy Rate (Dynamic Calc)
    └── RevPAR (Dynamic Calc)
```

# SECTION 12: CONSOLIDATION OPERATORS

---

## 12.1 Complete Operator Reference

| Operator | Symbol | Effect on Parent | Example |
|----------|--------|-----------------|---------|
| **Addition** | `+` | Child value ADDS to parent | Revenue (+): children add to parent Revenue total |
| **Subtraction** | `-` | Child value SUBTRACTS from parent | COGS (-): subtracts from Gross Margin |
| **Multiplication** | `*` | Child value MULTIPLIES into parent | Rarely used in planning |
| **Division** | `/` | Child value DIVIDES into parent | Rarely used in planning |
| **Percentage** | `%` | Child treated as percentage of parent | Rarely used |
| **Ignore** | `~` | Child is EXCLUDED from parent aggregation | Statistical accounts (Headcount, Occupancy %) |
| **Never Consolidate** | `^` | Child has member formula — don't use operator | KPIs with formulas (Gross Margin %) |

## 12.2 Worked Example

```
Income Statement Hierarchy with Operators:

Net Income (^) ← Has formula: Revenue + (-Expense) or calculated by formula
  ├── (+) Revenue = 26,00,000
  │   ├── (+) Rooms Revenue = 18,00,000
  │   ├── (+) Banquet Revenue = 5,00,000
  │   └── (+) F&B Revenue = 3,00,000
  │
  ├── (-) Total Expense = 11,00,000    ← NOTE: Operator is MINUS
  │   ├── (+) Salaries = 8,00,000      ← Plus WITHIN Expense
  │   ├── (+) Benefits = 2,00,000
  │   └── (+) Utilities = 1,00,000
  │
  └── (~) Gross Margin % = 57.69%      ← Ignored in consolidation

Calculation:
  Revenue = 18,00,000 + 5,00,000 + 3,00,000 = 26,00,000
  Total Expense = 8,00,000 + 2,00,000 + 1,00,000 = 11,00,000
  Net Income = Revenue (+) + Expense (-) = 26,00,000 + (-11,00,000) = 15,00,000
  Gross Margin % = (~) IGNORED — has its own member formula
```

# SECTION 13: ACCOUNT TYPE PROPERTIES

---

## 13.1 All Account Types

| Account Type | Financial Category | Variance Reporting | Time Balance Default | Example |
|-------------|-------------------|-------------------|---------------------|---------|
| **Revenue** | Income Statement | Non-Expense | Flow | Sales, Service Revenue |
| **Expense** | Income Statement | Expense | Flow | Salaries, Rent, Utilities |
| **Asset** | Balance Sheet | Non-Expense | Balance | Cash, AR, Inventory, Property |
| **Liability** | Balance Sheet | Expense | Balance | AP, Loans, Bonds |
| **Equity** | Balance Sheet | Non-Expense | Balance | Retained Earnings, Common Stock |
| **Saved Assumption** | Non-Financial | Non-Expense | Flow | Headcount, Occupancy Rate, Growth % |

## 13.2 How Account Type Affects Variance Reporting

```
NON-EXPENSE variance (Revenue, Asset, Equity):
  Actual > Budget → Variance is POSITIVE → FAVORABLE (green)
  Actual < Budget → Variance is NEGATIVE → UNFAVORABLE (red)
  Logic: More revenue/assets = good

EXPENSE variance (Expense, Liability):
  Actual > Budget → Variance is POSITIVE → UNFAVORABLE (red)
  Actual < Budget → Variance is NEGATIVE → FAVORABLE (green)
  Logic: More expense = bad, less expense = good

Example:
  Revenue: Actual ₹26Cr, Budget ₹25Cr → Variance +₹1Cr → 🟢 Favorable
  Expense: Actual ₹12Cr, Budget ₹10Cr → Variance +₹2Cr → 🔴 Unfavorable
```

## 13.3 Saved Assumption

```
Saved Assumption is special:
  - Used for DRIVER accounts (Units, Rate, Occupancy %, Price)
  - These accounts are NOT part of the P&L, BS, or CF
  - They drive calculations but don't directly appear in financial statements
  - Variance Reporting = Non-Expense (more is usually neutral/good)
  - Time Balance = Flow (sums across periods by default, but you can override)

Example:
  Rooms Available (Saved Assumption, Time Balance: Flow)
    Jan: 3,000 rooms, Feb: 2,800 rooms, Mar: 3,100 rooms
    Q1: 8,900 rooms (sum)
  
  Occupancy Rate (Saved Assumption, Dynamic Calc)
    Formula: Rooms Sold / Rooms Available * 100
```

# SECTION 14: TIME BALANCE PROPERTIES

---

## 14.1 All Time Balance Options

### Flow (Default)
```
Aggregation: SUM across periods
Use For: Income statement items (Revenue, Expense)

Example:
  Revenue: Jan ₹18Cr + Feb ₹19Cr + Mar ₹20Cr = Q1 ₹57Cr
```

### First
```
Aggregation: FIRST period's value
Use For: Opening balances

Example:
  Opening Cash: Jan ₹100Cr, Feb ₹105Cr, Mar ₹110Cr
  Q1 = Jan = ₹100Cr (first period)
```

### Balance (Last)
```
Aggregation: LAST period's value
Use For: Balance sheet items (Cash, AR, AP, Debt)

Example:
  Cash Balance: Jan ₹100Cr, Feb ₹105Cr, Mar ₹110Cr
  Q1 = Mar = ₹110Cr (last period)
  
Why— A balance is a point-in-time snapshot. The Q1 balance
IS the end-of-March balance, not the sum of all months.
```

### Average
```
Aggregation: AVERAGE of periods
Use For: Headcount, FTE, statistical averages

Example:
  Headcount: Jan 500, Feb 510, Mar 520
  Q1 = (500 + 510 + 520) / 3 = 510
  
Skip Values affect the denominator:
  Headcount: Jan 500, Feb #Missing, Mar 520
  Skip = None: Q1 = (500 + 0 + 520) / 3 = 340
  Skip = #Missing: Q1 = (500 + 520) / 2 = 510  ← Correct!
```

### Fill
```
Aggregation: Parent value is COPIED to all children
Use For: Spreading a quarterly target evenly to months

Example:
  User enters Q1 Headcount = 510
  Fill: Jan = 510, Feb = 510, Mar = 510
  (Same value filled into all child periods)
```

### Weighted Average (with Weighted Average Tag)
```
Aggregation: Weighted average using another member as weight
Use For: Weighted cost per unit, blended rates

Requires: A second member tagged as the "weight" member
```

## 14.2 Skip Value Interaction with Time Balance

| Time Balance | Skip = None | Skip = #Missing | Skip = Zeros | Skip = Both |
|-------------|-------------|-----------------|-------------|-------------|
| **Flow** | Sum all (count 0 and #M as 0) | Sum non-#Missing | Sum non-zero | Sum non-zero and non-#Missing |
| **Average** | Avg all (count 0 and #M in denominator) | Avg, exclude #M from count | Avg, exclude 0 from count | Avg, exclude both |
| **Balance** | Last value (even if #Missing) | Last non-#Missing value | Last non-zero value | Last non-zero, non-#Missing |
| **First** | First value (even if #Missing) | First non-#Missing value | First non-zero value | First non-zero, non-#Missing |

```
Example: Average + Skip = #Missing

Headcount: Jan=500, Feb=#Missing, Mar=520, Apr=#Missing, May=510, Jun=530

Q1 Average (Skip None):    (500 + 0 + 520) / 3 = 340 ← WRONG
Q1 Average (Skip #Missing): (500 + 520) / 2 = 510    ← CORRECT

Q2 Average (Skip None):    (0 + 510 + 530) / 3 = 346.67 ← WRONG
Q2 Average (Skip #Missing): (510 + 530) / 2 = 520       ← CORRECT
```

# SECTION 15: SHARED MEMBERS AND ALTERNATE HIERARCHIES

---

## 15.1 What is a Shared Member—

A Shared member is a **pointer** to an existing (base) member. It shares the same data cell — any change to one reflects in the other.

```
Primary Hierarchy:
  Revenue
    ├── Rooms Revenue (BASE member — data stored here)
    ├── Banquet Revenue (BASE)
    └── F&B Revenue (BASE)

Alternate Hierarchy:
  Revenue by Type
    ├── Room Related
    │   └── Rooms Revenue (SHARED → points to base member above)
    └── Event Related
        ├── Banquet Revenue (SHARED)
        └── F&B Revenue (SHARED)
```

## 15.2 Rules for Shared Members

| Rule | Description |
|------|-------------|
| **Base member must appear FIRST** | In the outline, the base (Store) member must come before any shared references |
| **Same dimension only** | Shared members can only reference members in the SAME dimension |
| **Different parent** | Shared member must have a DIFFERENT parent than the base member |
| **Data storage** | Shared member's Data Storage is set to "Shared" |
| **No double-counting** | Essbase knows to count the data only once during aggregation |
| **Consolidation** | The consolidation operator on the SHARED member determines how it rolls to ITS parent |

## 15.3 Example: Building an Alternate Hierarchy

```
Use Case: Account dimension needs TWO roll-ups:
  1. By financial statement line (Revenue → Net Income)
  2. By nature of expense (Fixed vs Variable)

Primary:
  Net Income
    ├── Revenue (+)
    │   ├── 100110: Rooms Revenue (Store, base)
    │   └── 100120: Banquet Revenue (Store, base)
    └── Expense (-)
        ├── 200000: Salaries (Store, base)
        ├── 200010: Rent (Store, base)
        └── 200020: Utilities (Store, base)

Alternate (Shared members):
  By Cost Behavior (Label Only)
    ├── Fixed Costs (Dynamic Calc)
    │   ├── 200000: Salaries (SHARED → points to base)
    │   └── 200010: Rent (SHARED → points to base)
    └── Variable Costs (Dynamic Calc)
        └── 200020: Utilities (SHARED → points to base)

Now users can view:
  - Total Fixed Costs = Salaries + Rent = ₹10Cr
  - Total Variable Costs = Utilities = ₹1Cr
  Without duplicating data!
```

# SECTION 16: IMPLIED SHARING

---

## 16.1 What is Implied Sharing—

Implied Sharing is Essbase's automatic optimization where a parent and child share the same data cell when there's no need for separate storage.

## 16.2 When Implied Sharing Occurs

| Condition | What Happens |
|-----------|-------------|
| **Parent with ONE child** | Parent and child share the same cell (parent = child always) |
| **Parent with ONE child that is NOT "Never Share"** | Implied sharing active |
| **Parent's consolidation would just copy the child** | Essbase optimizes away the duplicate storage |

```
Example:
  Rooms Revenue (Parent)
    └── 100110: Room Revenue Detail (Only child, +)

  Since Rooms Revenue = 100110 always (only one child, + operator),
  Essbase stores data in ONE cell and shares it:
  
  Enter data in 100110 → Rooms Revenue automatically = same value
  Enter data in Rooms Revenue → 100110 automatically = same value
  (Bi-directional — they ARE the same cell)
```

## 16.3 Preventing Implied Sharing

Use **Never Share** data storage on the child to prevent implied sharing:

```
  Rooms Revenue (Parent)
    └── 100110: Room Revenue Detail (Only child, Never Share)

  Now each has its own independent cell:
  Enter data in 100110 = ₹18Cr
  Rooms Revenue must be calculated = ₹18Cr (after CALC DIM)
  But they are SEPARATE cells — no sharing
```

## 16.4 Why You Might Want Never Share

```
Scenario: You have a parent with one child TODAY, but plan to add 
more children LATER.

With Implied Sharing:
  Data entered into parent OR child goes to the shared cell.
  When you add a second child, the shared data stays with the 
  PARENT, and the original child becomes empty → data loss risk.

With Never Share:
  Data entered into the child stays with the child.
  When you add a second child, the original child keeps its data.
  Parent recalculates = child1 + child2.
```

# SECTION 17: SMART LISTS

---

## 17.1 What is a Smart List—

A Smart List is a dropdown selection list assigned to an Account member, replacing numeric data entry with predefined text options that are stored as numeric IDs internally.

```
Smart List: "YesNo"
  ID 1: "Yes"
  ID 2: "No"
  ID 0: "#Missing" (not selected)

Smart List: "Status"
  ID 1: "Not Started"
  ID 2: "In Progress"
  ID 3: "Complete"
  ID 4: "On Hold"
```

## 17.2 How Smart Lists Work

```
Account: "Project Status" (Data Type: Smart List, Smart List: "Status")

In the form, user sees a dropdown:
  [▼ Not Started ]
  
User selects "In Progress"
  → Essbase stores: 2 (the numeric ID)
  → Form displays: "In Progress" (the label)

In Calc Scripts:
  IF("Project Status" == 2)  /* In Progress */
      "Allocation %" = 0.50;
  ENDIF
```

## 17.3 Smart List Design Rules

| Rule | Detail |
|------|--------|
| IDs start at 1 | 0 = #Missing (nothing selected) |
| IDs must be unique | Within the Smart List |
| Labels must be unique | Within the Smart List |
| Maximum entries | ~500 (practical limit) |
| Account Data Type | Must be set to "Smart List" |
| Multiple accounts can share one Smart List | Yes |

# SECTION 18: UDA VS ATTRIBUTE VS SMART LIST

---

## 18.1 Comparison Matrix

| Feature | UDA | Attribute Dimension | Smart List |
|---------|-----|-------------------|------------|
| **What** | Text tag on a member | Separate dimension with hierarchy | Dropdown list on a form cell |
| **Attached To** | Any dimension member | Base dimension members | Account members (data cells) |
| **Purpose** | Categorize members for calc scripts | Categorize for reporting + calc scripts | User data entry with predefined options |
| **Report Pivot** | ❌ Cannot put on rows/columns | ✅ Can pivot as dimension | ❌ Displays in cells |
| **Calc Script Use** | `@UDA("Account", "tag")` | `@ATTRIBUTE("AttrDim", "value")` | `IF("Member" == ID)` |
| **Performance** | Lightweight | Adds dimension overhead | No performance impact |
| **Storage** | No storage | Dynamic Calc (no blocks) | Stores numeric ID in block |
| **Hierarchy** | Flat tags only | Full hierarchy possible | Flat list |

## 18.2 When to Use Which

```
Use UDA when:
  → You need to group members in a calc script
  → "Calculate all Revenue_Driver accounts with 10% growth"
  → No reporting need (won't appear in rows/columns)

Use Attribute Dimension when:
  → You need to report/filter by the attribute
  → "Show me revenue for all Large entities" (pivoting Region on rows)
  → You need a hierarchy: Region → Country → City

Use Smart List when:
  → Users need to SELECT a value from a dropdown in a form
  → "Is this project approved— [Yes/No]"
  → The selection drives a business rule (IF Status == 3...)
```

# SECTION 19: DIMENSION ORDERING AND PERFORMANCE

---

## 19.1 Outline Order Impact

The order of dimensions in the Essbase outline affects performance:

```
Best Practice Outline Order:
  1. Account (Dense)         ← Densest dimension first
  2. Period (Dense)          ← Second dense dimension
  3. Entity (Sparse)         ← Most selective sparse first
  4. Scenario (Sparse)
  5. Version (Sparse)
  6. Year (Sparse)
  7. Currency (Sparse)
  8. Department (Sparse)     ← Custom dimensions last
  9. Custom1 (Sparse)

Rule: 
  - Dense dimensions first in outline
  - Sparse dimensions ordered by SELECTIVITY (most selective first)
  - "Most selective" = the dimension you most commonly filter on
```

## 19.2 Dense/Sparse Assignment Impact

```
Impact of wrong Dense/Sparse assignment:

Scenario: Department has 12 members, currently Sparse.
What if we make Department Dense—

Before (Sparse):
  Block size = Account(500) × Period(12) = 6,000 cells = 48 KB/block
  Blocks = Entity(50) × Scenario(3) × Version(2) × Year(5) × Dept(12) × Currency(3) = 54,000
  
After (Dense):  
  Block size = Account(500) × Period(12) × Dept(12) = 72,000 cells = 576 KB/block
  Blocks = Entity(50) × Scenario(3) × Version(2) × Year(5) × Currency(3) = 4,500

Block size increased 12×! Each block is now 576 KB instead of 48 KB.
Fewer blocks (4,500 vs 54,000) but EACH block is enormous.

Problem: Most cells in the larger block will be #Missing 
(not every account exists for every department).
This wastes memory and I/O.

Rule: Keep block size < 100 KB for optimal performance.
```

# SECTION 20: DESIGN PATTERNS

---

## 20.1 Pattern: Driver-Based Account Design

```
Revenue Model:
  Statistical Accounts (Saved Assumption, ~)
    ├── Rooms Available (Store, input)
    ├── Occupancy Rate % (Store, input)
    ├── Average Room Rate (Store, input)
    └── Rooms Sold (Dynamic Calc: Rooms Available × Occupancy Rate / 100)

  Revenue (Dynamic Calc, +)
    └── Rooms Revenue (Dynamic Calc: Rooms Sold × Average Room Rate)

Business Rule:
  FIX("Budget", @DESCENDANTS("All Entities"), @CHILDREN("YearTotal"))
      "Rooms_Sold" = "Rooms_Available" * "Occupancy_Rate" / 100;
      "Rooms_Revenue" = "Rooms_Sold" * "Average_Room_Rate";
  ENDFIX
```

## 20.2 Pattern: Memo Accounts for Commentary

```
Account Hierarchy Addition:
  Revenue
    ├── 100110: Rooms Revenue (Store, Currency)
    ├── 100120: Banquet Revenue (Store, Currency)
    └── Rooms Revenue Comment (Store, Data Type: Text, ~)

The Comment account:
  - Data Type = Text (allows text entry up to 255 characters)
  - Consolidation = ~ (ignore in totals)
  - Not included in any calculation
  
Users type: "Strong Q3 due to wedding season bookings"
```

## 20.3 Pattern: Variance Accounts

```
Account Hierarchy:
  Revenue Variance (Dynamic Calc, ~)
    Formula: "Revenue" -> "Actual" - "Revenue" -> "Budget";
  
  Revenue Variance % (Dynamic Calc, ~, Two-Pass)
    Formula: 
      IF("Revenue" -> "Budget" <> 0)
          ("Revenue" -> "Actual" - "Revenue" -> "Budget") / 
          "Revenue" -> "Budget" * 100;
      ENDIF;
```

# SECTION 21: INTERVIEW QUESTIONS

---

**Q1: What is the difference between Store and Dynamic Calc—**
> Store physically saves data on disk; Dynamic Calc computes on-the-fly when queried. Store supports user input; Dynamic Calc does not. Dynamic Calc reduces block size.

**Q2: Explain Implied Sharing with an example.**
> When a parent has only one child with a + consolidation operator, Essbase shares one physical cell between them. Data entry into either the parent or child affects the same cell. Use "Never Share" on the child to prevent this.

**Q3: What is the difference between Time Balance Flow and Balance—**
> Flow sums across periods (Revenue: Jan+Feb+Mar = Q1). Balance takes the last period's value (Cash Balance: Q1 = March value). Revenue is a flow item; Cash is a balance item.

**Q4: When would you use a Smart List vs a UDA—**
> Smart List is for user data entry in forms (dropdown selection stored as a number). UDA is for categorizing members in calc scripts (text tag for grouping, not visible in forms).

**Q5: Why is the order of dimensions in the outline important—**
> Dimension order affects calculation efficiency. Dense dimensions should come first. Sparse dimensions should be ordered by selectivity (most commonly filtered first). Wrong ordering can degrade calculation performance.

**Q6: Explain Shared Members. When and why do you use them—**
> Shared members point to a base member's data cell, enabling alternate hierarchies without duplicating data. Example: Account dimension has a primary P&L hierarchy and an alternate "Fixed vs Variable cost" hierarchy using shared members.

**Q7: How does Account Type affect variance reporting—**
> For Revenue/Asset/Equity (Non-Expense), Actual > Budget = Favorable. For Expense/Liability (Expense), Actual > Budget = Unfavorable. This ensures variance reports correctly show green/red color coding.

**Q8: What happens during a Dense Restructure vs Sparse Restructure—**
> Adding a dense dimension member changes block size, requiring ALL blocks to be rewritten (slow). Adding a sparse dimension member only requires an index update (fast). Dense restructure time is proportional to database size; sparse is nearly instant.
