# 12.01 — Security and Roles: Complete Guide

> **Module:** 12_Security | **Topic:** Roles, Permissions, Security Model
> **Audience:** Service Administrator

---

## 1. WHY — What Real-World Problem Does This Solve—

**The problem:** Without proper security, a Mumbai planner can see Delhi's confidential salary data. An intern can accidentally delete the entire forecast. A contractor can run business rules that corrupt the cube. Security isn't optional — it's the foundation of trust in the system.

**The solution:** EPBCS has a **layered security model**: Application Roles → Dimension Security → Form Permissions. Each layer adds a level of control.

---

## 2. THE SECURITY LAYERS

```
Layer 1: IDENTITY DOMAIN (Oracle Cloud — User Authentication)
  → Who can log into Oracle Cloud at all—
  → Managed by Identity Domain Admin
  
Layer 2: APPLICATION ROLES (EPBCS — What Can They Do—)
  → What features can the user access— (Admin, Power User, Planner, Viewer)
  → Managed by Service Admin
  
Layer 3: DIMENSION SECURITY (Data Access)
  → Which entities/accounts/scenarios can they see/edit—
  → Managed by Service Admin
  
Layer 4: FORM/FOLDER PERMISSIONS (UI Access)
  → Which forms can they open— Read or Write—
  → Managed by Service Admin

All four layers work TOGETHER. A user needs:
  ✅ Layer 1: Can log in
  ✅ Layer 2: Has a role (Planner, Viewer, etc.)
  ✅ Layer 3: Has access to the data (Entity, Account)
  ✅ Layer 4: Has access to the form (Read/Write)
```

---

## 3. APPLICATION ROLES — COMPLETE LIST

| Role | Access Level | Can Do | Can't Do |
|------|-------------|--------|----------|
| **Service Administrator** | Full access | Everything — dimensions, forms, rules, security, maintenance | N/A — god mode |
| **Power User** | Advanced | Create forms, run rules, manage some settings | Manage security, application settings |
| **Planner** | Standard | Open forms, enter data, submit, run attached rules | Create forms, modify dimensions |
| **Viewer** | Read-only | View forms, run reports | Enter data, run rules |
| **Approvals Administrator** | Approval workflow | Manage approval units, promote/approve | Not a data access role |
| **Ad Hoc User** | Smart View | Ad hoc analysis in Smart View | May not have form access |

### Role Hierarchy

```
Service Administrator ─────────────────── Full Access
  │
  ├── Power User ────────────────────── Create artifacts + Data entry
  │     │
  │     ├── Planner ──────────────────── Data entry + Run rules
  │     │     │
  │     │     └── Viewer ──────────────── Read-only
  │     │
  │     └── Approvals Administrator ──── Manage approvals
  │
  └── Ad Hoc User ───────────────────── Smart View access
```

## 4. DIMENSION SECURITY

### How It Works

For each dimension member, you assign access to users/groups:

| Access Level | Can See— | Can Edit— | Inherited— |
|-------------|---------|----------|------------|
| **Write** | ✅ | ✅ | Yes — children inherit |
| **Read** | ✅ | ❌ | Yes — children inherit |
| **None** | ❌ | ❌ | Yes — children inherit |
| **No Access** | ❌ | ❌ | No — explicit denial |

### Setting Dimension Security

```
Navigator → Create and Manage → Dimensions → Select dimension → Security

Entity: All_Hotels
├── Mumbai_Hotel     → Mumbai_Team: Write | Delhi_Team: None | CFO: Read
├── Delhi_Hotel      → Delhi_Team: Write | Mumbai_Team: None | CFO: Read
├── Bangalore_Hotel  → Bangalore_Team: Write | Others: None | CFO: Read
├── Kolkata_Hotel    → Kolkata_Team: Write | Others: None | CFO: Read
└── Chennai_Hotel    → Chennai_Team: Write | Others: None | CFO: Read

All_Hotels (parent)  → CFO: Read (sees consolidated total)
```

### Security Inheritance

```
If you set:
  All_Hotels → Mumbai_Team: None

Result:
  Mumbai_Hotel → None (inherited)
  Delhi_Hotel → None (inherited)
  All children → None (inherited)

Override:
  All_Hotels → Mumbai_Team: None
  Mumbai_Hotel → Mumbai_Team: Write (explicit override)
  
Result:
  Mumbai_Hotel → Write (override wins)
  Delhi_Hotel → None (inherited from parent)
```

## 6. SECURITY GROUPS — BEST PRACTICE

### Always Use Groups, Never Individual Users

```
❌ BAD: Assign permissions to individual users
  Mumbai_Hotel → Ramesh: Write
  Mumbai_Hotel → Priya: Write
  Mumbai_Hotel → Arjun: Write
  (If Ramesh leaves → must update everywhere)

✅ GOOD: Create groups, assign permissions to groups
  Group: Mumbai_Planners → Members: Ramesh, Priya, Arjun
  Mumbai_Hotel → Mumbai_Planners: Write
  (If Ramesh leaves → remove from group only)
```

### Hotel Pvt Ltd Group Structure

```
Groups:
  Admin_Group           → Service Administrators
  Finance_Controllers   → CFO, Finance VPs
  Hotel_GMs             → 5 hotel general managers
  Mumbai_Planners       → 3 Mumbai finance team members
  Delhi_Planners        → 3 Delhi finance team members
  Bangalore_Planners    → 2 Bangalore team members
  Kolkata_Planners      → 2 Kolkata team members
  Chennai_Planners      → 2 Chennai team members
  HR_Team               → HR managers (Workforce cube access)
  Viewer_Group          → Board members, auditors (read-only)
```

## 8. COMMON MISTAKES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Assigning to users instead of groups | Maintenance nightmare | Always use groups |
| Forgetting to set dimension security | Users see all data | Set explicit None on sensitive entities |
| Admin role for power users | Too much access, accidental damage | Use Power User role instead |
| No security on Actual scenario | Planners can overwrite actuals | Set Actual to Read for non-admins |
| Inheritance not understood | Child entities have wrong access | Review parent → child inheritance chain |

## 9. INTERVIEW QUESTIONS

### Beginner
**Q: What are the four security layers in EPBCS—**
> (1) **Identity Domain** — user authentication (can they log in—). (2) **Application Roles** — feature access (Admin, Power User, Planner, Viewer). (3) **Dimension Security** — data access (which entities/accounts can they see/edit—). (4) **Form Permissions** — UI access (which forms can they open, read or write—). All four must align — a user needs proper access at every layer to interact with data.

### Architect
**Q: Design the complete security model for Hotel Pvt Ltd with 5 hotels, each having a GM and 2-3 planners, plus a central CFO and finance team.**
> **Groups (10):** Admin_Group, Finance_Controllers, 5 Hotel_X_Planners groups, HR_Team, Viewer_Group. **Roles:** Admins=Service Administrator, CFO=Power User, GMs=Planner, Hotel Planners=Planner, HR=Planner (WFP only), Board=Viewer. **Entity Security:** Each hotel group gets Write on their hotel + None on others. CFO gets Read on All_Hotels. **Scenario Security:** Actual=Read for all non-admins (no edits to actuals). Budget/Forecast=Write for planners. **Account Security:** Salary details=None for non-HR (confidential). **Form Security:** Folder-level — Data Entry folders=Write for planners, Summary folders=Read for planners, Admin folder=Write for admin only.
