## 🏢 Overview

Security in Oracle EPBCS operates at multiple layers: **Identity Domain** (who can log in), **Application Roles** (what features they can access), and **Data Access** (what data they can see/edit). A well-designed security model ensures the right users see the right data with the right permissions.

---

## 🔒 Security Architecture — 3 Layers

```
Layer 1: Identity Domain (Oracle Cloud Identity / IDCS)
├── User accounts, SSO, password policies
│
Layer 2: Application Roles (EPM Cloud Provisioning)
├── Service Admin, Power User, User, Viewer
│
Layer 3: Data Access Security (Planning Application)
├── Dimension-level access (Read, Write, None)
├── Form access
├── Task list access
├── Business rule access
```

## 📌 Layer 2: Pre-Defined Application Roles

| Role | Permissions | Typical User |
|------|-------------|-------------|
| **Service Administrator** | Full control — create apps, manage security, run all rules | EPM Admin, IT |
| **Power User** | Create forms, rules, task lists, manage metadata | Lead Analyst, Senior Consultant |
| **User** | Enter data in assigned forms, run assigned rules | Budget Preparers, Cost Center Managers |
| **Viewer** | View data only — no editing | Executives, Auditors |

### Role Hierarchy

```
Service Administrator (can do everything)
├── Power User (can do most things except admin)
│   ├── User (can enter data in assigned forms)
│   │   └── Viewer (can only view)
```

### Provisioning Users

```
Navigation: Home → Tools → Access Control → Manage Roles
OR: Home → Navigator → Security → Assign Roles
```

Steps:
1. Search for the user by email
2. Select the role to assign
3. Click Assign
4. User receives email notification

## 🔒 Layer 3: Data Access Security

### Dimension Security (Access Control)

Data security is set at the **dimension member** level. You control who can Read/Write/None for each member.

| Permission | Description |
|-----------|-------------|
| **Read** | User can view data but NOT edit |
| **Write** | User can view AND edit data |
| **None** | User cannot see the member or its data |
| **Inherit** | Takes permission from parent member |

### Assigning Data Access

```
Navigation: Home → Navigator → Security → Assign Access
```

| Step | Action |
|------|--------|
| 4 | Choose permission (Read/Write/None) |
| 5 | Set inheritance (Children/Descendants) |

### 💡 Logic & Purpose
Security in EPM is evaluated as a mathematical overlay on top of the dimension structure. If a user tries to submit data, Essbase checks the exact intersection (e.g., `Entity -> Account -> Scenario -> Version`). The user must have explicitly inherited `Write` access to all components of that intersection. If even one dimension evaluates to `Read` or `None`, the entire intersection is locked and the cell renders as gray/read-only.

### 🌀 Confusion Resolution
> **Misconception:** "I gave John 'Write' access to the `Revenue` account, and 'None' access to the `Hardware_Revenue` child under it. But John can still see Hardware Revenue on his form!"
> **Reality:** In EPBCS security, **Explicit assignments override Inherited assignments**, but when two explicit assignments conflict, the **least restrictive** (most open) permission wins! Since both rules apply to John, `Write` (the more open permission) overrides `None`. To successfully block a child while allowing the parent, you must assign the `Write` access at the parent level as `@IChildren` (which sets explicit on the parent and inherited on the children), and then explicitly set the child to `None`.

### 😈 Twisted Interview Question
**Question:** A user is assigned to a group called "Sales Planners" and another group called "Sales Reviewers". The Planners group has `Write` access to `Entity_100`. The Reviewers group has `Read` access to `Entity_100`. The user logs in to enter data into `Entity_100`. What happens?
> **Answer:** The user CAN enter data! When a user inherits conflicting permissions from multiple groups for the same member, the EPM security engine evaluates them and grants the **highest level of access** available across all groups (None < Read < Write). Since `Write` is higher than `Read`, the user is granted Write access.

### Security Assignment Example

```
Entity Dimension:
├── All Entities → None (default)
│   ├── E10001: Hotel Pvt Ltd → Write (for Hotel team)
│   │   ├── E10001_01: Mumbai → Write (inherits)
│   │   └── E10001_02: Delhi → Write (inherits)
│   └── E10002: Manufacturing → Write (for Manufacturing team)

Scenario Dimension:
├── Actual → Read (everyone — actuals are loaded, not entered)
├── Budget → Write (preparers)
└── Forecast → Write (preparers)

Version Dimension:
├── Working → Write (preparers)
├── Approved → Read (everyone after approval)
```

### Groups — Best Practice

**Always assign security to GROUPS, not individual users.**

```
Group: "Hotel_Budget_Preparers"
├── Members: user1@company.com, user2@company.com
├── Entity Access: E10001 → Write
├── Scenario Access: Budget → Write
└── Version Access: Working → Write

Group: "Manufacturing_Budget_Preparers"
├── Members: user3@company.com, user4@company.com
├── Entity Access: E10002 → Write
├── Scenario Access: Budget → Write
└── Version Access: Working → Write

Group: "Finance_Reviewers"
├── Members: cfo@company.com, controller@company.com
├── Entity Access: All Entities → Read
├── Scenario Access: All → Read
└── Version Access: All → Read
```

## 🔒 Common Security Mistakes

| Mistake | Risk | Fix |
|---------|------|-----|
| Assigning security to individuals | Maintenance nightmare | Use groups |
| Giving Write to Actuals | Users can overwrite loaded data | Actuals = Read only |
| Not testing security setup | Users see wrong data | Test with a test user account |
| Everyone as Service Admin | No data protection | Follow least-privilege principle |
| Not using None for parent entities | Users see consolidated data they shouldn't | Set None and grant specific children |

## 🎓 Interview Questions

**Q: What are the 3 layers of security in EPBCS?**
> A: (1) Identity Domain — user authentication and SSO, (2) Application Roles — feature-level access (Admin, Power User, User, Viewer), (3) Data Access Security — dimension member-level Read/Write/None permissions.

**Q: What is the difference between Read and Write security?**
> A: Read allows viewing data but not editing. Write allows both viewing and editing. None hides the member entirely — the user doesn't even know it exists.

**Q: Why should you assign security to groups instead of individuals?**
> A: Groups simplify management. When a new employee joins, you add them to a group and they automatically inherit all permissions. When someone leaves, remove them from the group. Individual assignments don't scale.

**Q: How do you prevent budget preparers from editing Actuals?**
> A: Set the Actual scenario member to Read access for the budget preparer group. Actuals should only be loaded via data integration, never manually edited.

**Q: What is the approval workflow and how does security relate to it?**
> A: The approval workflow routes budget submissions through Preparer → Reviewer → Approver. Each role has different permissions — Preparers can edit and submit, Reviewers can approve or reject, Approvers give final sign-off. Once approved, data becomes read-only for preparers.
