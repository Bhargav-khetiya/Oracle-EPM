## 📌 Layer 1: Identity Management — Every Detail

### User Lifecycle

```
1. CREATE user in IDCS → user receives email invitation
2. USER activates account → sets password
3. ADMIN assigns EPM role → user can access application
4. ADMIN assigns data access → user sees specific data
5. USER departs → ADMIN deactivates in IDCS
```

### Identity Provider Options

| Provider | Type | When to Use |
|----------|------|-------------|
| **IDCS** | Oracle's cloud identity | Default, simple setup |
| **Azure AD** | Microsoft federation | Company uses Microsoft |
| **Okta** | 3rd party SSO | Company uses Okta |
| **ADFS** | On-premise AD | Company has Active Directory |
| **Oracle Access Manager** | On-premise OAM | Legacy Oracle infrastructure |

### SAML 2.0 Federation Setup

```
1. Configure IDCS as Service Provider
2. Configure corporate IdP (Azure AD/Okta/ADFS) as Identity Provider
3. Exchange SAML metadata between both
4. Test SSO: User logs in with corporate credentials
5. Result: Single sign-on — one login for ERP + EPM + HCM
```

## 📌 Layer 3: Data Access — Every Scenario

```
Navigation: Application → Dimensions → [Dimension] → Security
OR: Tools → Access Control → Permissions
```

### Permission Types

| Permission | What User Can Do | Cell Appearance |
|-----------|-----------------|-----------------|
| **Write** | View AND edit data | White cell |
| **Read** | View only, cannot edit | Light blue/gray cell |
| **None** | Cannot see the member AT ALL | Member is invisible |

### Inheritance Rules

├── Child1: (inherits Write) → Write
├── Child2: None (explicitly set) → None  
└── Child3: Read (explicitly set) → Read

Key Rule: Explicit overrides inherited
```

### 💡 Logic & Purpose
Oracle's security engine evaluates cell access dynamically at runtime based on the multidimensional intersection. A cell is essentially a matrix equation of permissions: `Entity(Access) * Account(Access) * Scenario(Access) * Version(Access)`. The lowest permission dictates the final cell state. `None` forces invisibility, `Read` forces lock, and only a matrix of 100% `Write` permits data entry.

### 🌀 Confusion Resolution
> **Misconception:** "I want to hide the 'Bonus' account from the HR department, but I want the Finance department to see it. I'll just apply dimension security on the Account."
> **Reality:** Dimension security applies globally across the entire cube! If you set `None` for the HR group on the 'Bonus' account, they can never see 'Bonus' anywhere, regardless of the Entity. If you need security that says "HR can see Bonus for Entity A but not Entity B," you must use **Valid Intersections** or **Cell-Level Security**. Standard dimension security cannot perform complex conditional cross-dimensional logic.

### 😈 Twisted Interview Question
**Question:** An administrator creates a Cell-Level Security rule that explicitly DENIES access to `Actual -> January`. However, the user belongs to the "Admins" group, which has explicit `Write` access to the Scenario and Period dimensions. Does the user see the data—
> **Answer:** NO. Cell-Level Security is a specialized override layer evaluated *after* standard dimension security. Even if standard security grants `Write` across all dimensions, a matching Cell-Level Security rule that enforces a denial will completely override the standard permission matrix and block the data.
Key Rule: If Parent = None, ALL children = None (regardless of child settings)
```

### Cross-Dimensional Security (Effective Access)

```
If Entity "Mumbai" = Write AND Scenario "Actual" = Read
Then: Mumbai × Actual = READ (most restrictive wins)

If Entity "Mumbai" = Write AND Scenario "Budget" = Write  
Then: Mumbai × Budget = WRITE

If Entity "Mumbai" = None AND Scenario "Budget" = Write
Then: Mumbai × Budget = NONE (None always wins)
```

### Security Assignment via Groups

```
Best Practice: NEVER assign security to individual users
Always use GROUPS

Example Groups:
├── GRP_Budget_Preparers_Mumbai
│   ├── user1@company.com
│   └── user2@company.com
├── GRP_Budget_Preparers_Delhi
│   ├── user3@company.com
│   └── user4@company.com

│   ├── manager1@company.com
│   └── manager2@company.com
└── GRP_Executives
    ├── cfo@company.com

```

## 📌 Audit Trail — Complete Reference

```
Navigation: Tools → Audit
```

### What Gets Audited

| Audit Type | What It Records | Enabled By Default— |
|-----------|----------------|-------------------|
| **Data Audit** | Cell value changes (old → new, who, when) | No — must enable |
| **Security Audit** | Permission changes | Yes |
| **Login Audit** | User login/logout activity | Yes |
| **Rule Audit** | Business rule executions | Yes |

### Enabling Data Audit

```
1. Application → Settings → Enable Data Audit = ON
2. Application → Dimensions → Account → select members to audit
3. For each audited member: Properties → Enable for Audit = YES
4. Note: Auditing every member impacts performance — only audit critical members
```

### 🎯 Hands-On: Complete Security Setup

```
Exercise 1: Create Groups and Assign Roles
1. Navigate to Tools → Access Control
2. Create 3 groups:
   - GRP_Preparers (assign 2 test users)
   - GRP_Reviewers (assign 1 test user)
   - GRP_Executives (assign 1 test user)
3. Assign roles: Preparers=User, Reviewers=Power User, Executives=Viewer

Exercise 2: Configure Data Access
1. Navigate to Dimensions → Entity → Security
2. Set: E10001 → GRP_Preparers = Write, GRP_Reviewers = Read
3. Set: E10002 → GRP_Preparers = None, GRP_Reviewers = Read
4. Test: Login as Preparer → verify E10001 visible, E10002 hidden
5. Test: Login as Reviewer → verify both visible as Read-only

Exercise 3: Scenario Security
1. Navigate to Dimensions → Scenario → Security
2. Set: Actual → ALL groups = Read (nobody edits actuals)
3. Set: Budget → GRP_Preparers = Write, others = Read
4. Test: Login as Preparer → can edit Budget but not Actual

Exercise 4: Form Security
1. Edit "Revenue Input" form → Access Control tab
2. Assign: GRP_Preparers, GRP_Reviewers
3. Remove: GRP_Executives
4. Test: Login as Executive → form is NOT visible in their navigation

Exercise 5: Audit Setup
1. Enable Data Audit in Application Settings
2. Select 3 key Account members for auditing
3. Make data changes
4. Navigate to Tools → Audit → Data
5. Verify: Old value, new value, user, timestamp are all recorded

Exercise 6: Security Design Exercise
Design complete security for a company with:
- 10 entities across 3 regions (APAC, EMEA, Americas)
- 4 user groups: Regional Preparers (3 groups), Global Reviewers, CFO
- Scenarios: Actual (load only), Budget (editable), Forecast (editable)
- Requirements: Each region can only see their own entities
  CFO can see everything but cannot edit
Document: Group names, role assignments, entity permissions, scenario permissions
```

## 🎓 Interview Questions (Oracle Official)

**Q: Explain the 3 layers of EPM Cloud security.**
> Layer 1: Identity (IDCS/SSO — authentication). Layer 2: Application Roles (Admin/Power User/User/Viewer — feature access). Layer 3: Data Access (Read/Write/None per dimension member — data visibility). All 3 must be configured for complete security.

**Q: How does cross-dimensional security work—**
> Effective access is the MOST RESTRICTIVE across all dimensions. If Entity=Write and Scenario=Read, effective = Read. If any dimension = None, effective = None. This is evaluated at every cell intersection.

**Q: Why should you use groups instead of individual user assignments—**
> Scalability and maintainability. If 50 users need the same access, assign to a group once. When a user joins/leaves, just add/remove from the group — no need to touch 20 dimension security settings.

**Q: A user says they can't see a form. What do you check—**
> (1) Is the user provisioned with a role— (2) Does the form have access control restrictions— (3) Does the user have Read or Write on the dimensions used in the form— (4) Are Navigation Flows hiding the form from their role—

## 📝 Summary

| Key Point | Detail |
|-----------|--------|
| **3 Layers** | Identity (who) → Roles (what features) → Data Access (what data) |
| **Roles** | Service Admin > Power User > User > Viewer |
| **Permissions** | Write (edit), Read (view only), None (invisible) |
| **Cross-Dim** | Most restrictive wins at every intersection |
| **Groups** | ALWAYS use groups, NEVER individual assignments |
| **Audit** | Data audit must be explicitly enabled per member |
