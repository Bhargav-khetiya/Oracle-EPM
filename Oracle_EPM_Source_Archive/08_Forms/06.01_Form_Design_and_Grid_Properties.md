# 06.01 — Form Design and Grid Properties: Complete Guide

> **Module:** 06_Forms | **Topic:** Form Layout Architecture, Axes, and Grid Design
> **Audience:** Service Administrator / Consultant

---

## 1. WHY — What Real-World Problem Does This Solve—

**The problem:** An Essbase cube is n-dimensional (8-12 dimensions). Humans can only see data in 2 dimensions (rows × columns). Forms are the bridge — they project an n-dimensional cube onto a 2D grid that users can interact with.

**The solution:** Forms are 2D windows into multi-dimensional cubes. Designing a form means choosing: which dimensions go on rows, which on columns, which on the page dropdown, and which are fixed in the Point of View (POV). Getting this right is the difference between a 2-second and a 30-second form.

---

## 2. WHAT — The Four Axes of a Form

Every dimension in the cube MUST be placed on exactly one axis:

```
┌── Form: Revenue Entry ──────────────────────────────────────────────┐
│                                                                      │
│  POV:  Scenario=[Budget]  Version=[Working]  Year=[FY2026]          │
│  ────────────────────────────────────────────────────────────────    │
│  Page: Entity=[Mumbai_Hotel ▾]  Department=[F&B ▾]                 │
│  ════════════════════════════════════════════════════════════════    │
│                 │ Jan      │ Feb      │ Mar      │ Q1 Total   │    │
│  ───────────────┼──────────┼──────────┼──────────┼────────────│    │
│  Room Revenue   │ ₹85,000  │ ₹90,000  │ ₹88,000  │ ₹2,63,000 │    │
│  F&B Revenue    │ ₹22,000  │ ₹24,000  │ ₹21,000  │ ₹67,000   │    │
│  Spa Revenue    │ ₹5,000   │ ₹6,000   │ ₹5,500   │ ₹16,500   │    │
│  ───────────────┼──────────┼──────────┼──────────┼────────────│    │
│  Total Revenue  │ ₹1,12,000│ ₹1,20,000│ ₹1,14,500│ ₹3,46,500 │    │
│  COLUMNS ──────── Period dimension ────────────────────────────     │
│  ROWS ──────────── Account dimension                                │
└──────────────────────────────────────────────────────────────────────┘
```

### The Four Axes Explained

| Axis | Behavior | Best For | Dimension Limit |
|------|----------|----------|-----------------|
| **Point of View (POV)** | Fixed — user sees one member, usually can't change | Dimensions the user doesn't need to toggle: Scenario, Version, Year | Unlimited |
| **Page** | Dropdown — user toggles between members | Dimensions the user needs to switch: Entity, Department | 1-3 dims recommended |
| **Rows** | Vertical axis of the grid — main data display | Account, line items | 1-2 dims max |
| **Columns** | Horizontal axis of the grid | Period/time | 1-2 dims max |

## 3. HOW — Dimension Placement Rules

### The Golden Rules

```
RULE 1: Account dimension → ROWS (always)
RULE 2: Period dimension → COLUMNS (always)
RULE 3: Entity dimension → PAGE (user toggles hotels)
RULE 4: Scenario/Version/Year → POV (rarely changes)
RULE 5: Custom dimensions → PAGE or POV (never rows if sparse+large)
```

### Why These Rules—

```
Performance reason:
  Account (Dense) + Period (Dense) = form reads single Essbase blocks
  Entity (Sparse) on rows = cross-join with Account = block explosion
  
  Dense × Dense on rows/columns = FAST (within-block read)
  Sparse × Dense on rows = OKAY (one block per sparse member)
  Sparse × Sparse on rows = SLOW (cross-join explosion)
```

### Dimension Placement Decision Tree

```
Is the dimension Dense—
├── YES → Rows or Columns (either is fine)
│         Account → Rows, Period → Columns (convention)
│
└── NO (Sparse) → How many members does the user need to see—
    ├── ONE at a time → Page axis (dropdown)
    │   (Entity, Department, Custom dims)
    │
    ├── DON'T CHANGE → POV (fixed)
    │   (Scenario, Version, Year)
    │
    └── MULTIPLE on screen → Rows (carefully!)
        Only if member count < 20
        AND no other sparse dim on rows
```

## 4. FORM CREATION WORKFLOW

```
Step 1: PROPERTIES TAB
  → Name, Description, Cube selection
  
Step 2: LAYOUT TAB (most important)
  → Assign dimensions to axes
  → Select members per dimension
  → Set Grid Properties (suppression, sizing)
  → Set Segment Properties (per-row/column)
  → Set Dimension Properties (display, drill)
  → Set Display Properties (read-only, missing values)
  → Set Smart View Options (flex, formatting)
  → Add Formula Rows/Columns
  → Add Format Rules / Validation Rules
  
Step 3: OTHER OPTIONS TAB
  → Precision settings
  → Context menu association
  → Instructions text
  
Step 4: BUSINESS RULES TAB
  → Attach rules (On Load, On Save, Manual)
  → Configure RTPs
  
Step 5: SAVE & TEST
```

## 5. MEMBER SELECTION — WHAT APPEARS ON THE FORM

For each dimension on rows/columns, you choose which members to display:

### Selection Methods

| Method | Description | Example |
|--------|-------------|---------|
| **Individual members** | Pick specific members | "Room_Revenue", "F&B_Revenue" |
| **IDescendants(parent)** | All descendants of a parent | IDescendants("Total_Revenue") |
| **IChildren(parent)** | Immediate children only | IChildren("All_Hotels") |
| **Level0(parent)** | Leaf members only (no parents) | Level0("All_Hotels") |
| **Siblings(member)** | Same-level members | Siblings("Jan") = all months |
| **User Variables** | Dynamic per-user | [UserEntity] |
| **Substitution Variables** | Global admin-managed | &CurrMonth |
| **Attribute-based** | Filter by attribute | UDA = "Luxury_Hotel" |

### Member Selection Best Practices

```
DO:
  ✅ Use IChildren/IDescendants for dynamic membership
  ✅ Use User Variables for entity selection
  ✅ Use Substitution Variables for time selection
  ✅ Exclude members that shouldn't be on this form

DON'T:
  ❌ Select "All Members" on a large dimension (1000+ members = crash)
  ❌ Use hardcoded member lists (hard to maintain)
  ❌ Forget to exclude shared members (causes duplicates)
```

## 6. SHOW ME — Hotel Pvt Ltd: Three Form Designs

### Form 1: Revenue Data Entry

```
Purpose: GMs enter monthly revenue by category
Cube: OEP_FS

POV: Scenario=Budget, Version=Working, Year=FY2026
Page: Entity=[UserEntity] (each GM sees their hotel)
Rows: Account = IChildren("Operating_Revenue")
Columns: Period = IChildren("Q1"), IChildren("Q2"), IChildren("Q3"), IChildren("Q4")

Grid Properties:
  ☐ Suppress Missing Data (GMs need blank rows for data entry)
  ☑ Display Missing as Blank
  ☑ Enable Grid Spread

Business Rules:
  On Save: "Calculate_Revenue_Totals"
```

### Form 2: P&L Summary (Read-Only)

```
Purpose: CFO reviews consolidated P&L
Cube: OEP_FS

POV: Version=Final, Year=FY2026
Page: Entity=[UserEntity], Scenario=[Budget, Actual, Forecast]
Rows: Account = IDescendants("Net_Income") — full P&L hierarchy
Columns: Period = IChildren("YearTotal") + [Jan, Feb, ..., Dec]

Grid Properties:
  ☑ Suppress Missing Data
  ☑ Suppress Missing Blocks
  Make Form Read-Only: ☑

Format Rules:
  Negative variance → Red background
  Positive variance → Green background
  Total rows → Bold + Blue background
```

### Form 3: KPI Dashboard Entry

```
Purpose: Hotel managers enter operational KPIs
Cube: HotelOps (FreeForm)

POV: Scenario=Actual, Version=Working, Year=FY2026
Page: Entity=[UserEntity], Room_Type=[All_Room_Types]
Rows: Account = Occupancy_Rate, ADR, RevPAR, Guest_Satisfaction
Columns: Period = IChildren(&CurrYear)  

Grid Properties:
  ☑ Display Missing as Blank
  Precision: Percentage = 1 decimal, Currency = 0 decimals

Validation Rules:
  Occupancy_Rate > 100 → Error: "Cannot exceed 100%"
  ADR < 0 → Error: "ADR cannot be negative"
```

## 7. COMMON MISTAKES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Account on columns | Doesn't work — Account must be on rows | Move Account to rows; Period to columns |
| Entity + Account both on rows | 100 × 200 = 20,000 rows, slow | Move Entity to Page |
| No members selected for a dimension | Form shows "no data" | Select members for every dimension |
| Hardcoded member list | New members not visible on form | Use IChildren/IDescendants instead |
| Forgot to assign a dimension | Form validation error | Every dim must be on exactly one axis |
| Suppress Missing on data entry form | Users can't see empty rows | Disable suppression for entry forms |

## 8. INTERVIEW QUESTIONS

### Beginner
**Q: What are the four axes of a form and which dimensions typically go on each—**
> **POV (Point of View):** Fixed dimensions — Scenario, Version, Year. User sees one value. **Page:** Dropdown dimensions — Entity, Department. User toggles between values. **Rows:** Vertical axis — Account/line items (dense dimension). **Columns:** Horizontal axis — Period/time (dense dimension). The key principle: Dense dimensions on rows/columns (fast), Sparse dimensions on Page/POV (minimal data retrieval).

### Intermediate  
**Q: Why should Account always go on rows and never on columns—**
> Two reasons: (1) **Oracle restriction** — Account, Version, and Scenario dimensions cannot be assigned to the column axis in standard Planning forms. (2) **Logical convention** — accounts represent line items (revenue, expenses) that read naturally as rows, while time periods (Jan, Feb, Mar) read naturally as columns. Entity can go on any axis. Period is typically on columns but can go on rows for time-series analysis.

### Architect
**Q: Design the form architecture for Hotel Pvt Ltd with 5 hotels, 200 accounts, 12 months, 3 scenarios, 3 versions. How many forms do you need—**
> Minimum 6-8 forms covering the core workflows: (1) Revenue Entry — per hotel, per month. (2) Expense Entry — per hotel, per month. (3) P&L Summary — read-only consolidated view. (4) Variance Analysis — Actual vs Budget comparison. (5) Forecast Entry — same as Revenue/Expense but for Forecast scenario. (6) KPI Dashboard — composite form combining KPIs from multiple cubes. Design principle: Use the SAME form for all 5 hotels via User Variable on Entity (1 form, not 5). Use the SAME form for Budget and Forecast via Page on Scenario (1 form, not 2). User Variables and Page dropdowns multiply coverage without multiplying forms.
