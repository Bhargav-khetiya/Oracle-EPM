## WHY — What Real-World Problem Does This Solve?

A single data grid (a simple form) provides only one perspective. A planner entering room revenue might need to simultaneously see their historical occupancy trends or the corporate average to make an informed decision. 

**The goal is unified context on a single screen.**

Historically, Oracle solved this with **Composite Forms** — sticking two or three forms together on one page. However, modern users expect visual analytics (charts, KPIs). Oracle introduced **Dashboards 2.0** to solve this, combining forms with rich visualizations.

For Hotel Pvt Ltd, the CFO doesn't want to open three different forms to see Revenue, Expenses, and Headcount. They want one screen with a Revenue grid, an Expense pie chart, and Headcount KPI tiles, all interactively linked.

---

## WHAT — Plain English Definition

### Simple Form
A single grid of data (rows and columns) tied to one specific query against the Essbase cube.

### Composite Form (Legacy)
A container that holds multiple simple forms on the same screen (e.g., Form A on top, Form B on the bottom). The key feature was linking the POVs so changing "Entity" on Form A updated Form B. 
**Status:** Deprecated by Oracle.

### Dashboards 2.0 (Modern)
A highly customizable canvas where you can drag and drop Forms, Charts (Bar, Line, Pie, Waterfall), KPI Tiles, and external URLs. It completely replaces Composite Forms and adds interactivity.

---

## HOW — The Evolution and Migration

### Why Were Composite Forms Deprecated?

Composite forms suffered from severe limitations:
1. **No Visuals:** Only rows and columns of numbers. No native charting.
2. **Rigid Layout:** Fixed grids (Top/Bottom, Left/Right). No modern responsive design.
3. **Performance:** Every form in the composite fired a synchronous query to Essbase. 
4. **Poor Mobile Experience:** The dense grids were unusable on tablets.

*Oracle officially recommends migrating all existing Composite Forms to Dashboards 2.0.*

### How to Migrate: Rebuilding for the Modern Era

If you have a legacy Composite Form at Hotel Pvt Ltd containing:
- Form A: Room Revenue Input
- Form B: F&B Revenue Input
- Form C: Total Revenue Summary

**Step-by-Step Dashboard 2.0 Rebuild:**

```
1. PREPARE THE FORMS
   → Dashboards use the exact same underlying simple forms.
   → Ensure Form A, B, and C have Suppress Missing Blocks enabled.
   → Optimize the rows/columns for smaller visual spaces.

2. CREATE THE DASHBOARD
   → Navigator → Dashboards → Create.
   → Name: "Revenue_Input_Dashboard".

3. DESIGN THE CANVAS
   → Drag Form A (Room Revenue) to the top left.
   → Drag Form B (F&B Revenue) to the bottom left.
   → *Architect Trick:* Instead of showing Form C as a grid, drag a 
     Pie Chart object, link it to Form C, and place it on the right!

4. CONFIGURE MASTER-DETAIL LINKING (The replacement for POV linking)
   → In Composite Forms, you linked POVs.
   → In Dashboards, use Master-Detail linking.
   → Select Form A → Properties → "Tag as Master".
   → Link to the Pie Chart (Target).
   → When user clicks a specific hotel in Form A, the Pie Chart updates.

5. ADD KPI TILES
   → Add 3 Tile components at the very top for instant context:
     "Total Rooms Booked", "ADR", "RevPAR".
```

### Dashboard Master-Detail Linking Explained

This is the most powerful UI feature for complex planning, replacing the old Composite Form POV linking.

```
THE SCENARIO:
You have a summary grid (Total Salaries, Total Travel) and a detailed grid
(Employee 1, Employee 2).

THE CONFIGURATION:
1. Dashboard Canvas has both forms.
2. Form 1 (Summary) is tagged as "Master".
3. Form 2 (Detail) is the "Target".
4. Dimension Map: Link the "Account" dimension.

USER EXPERIENCE:
1. User clicks "Total Salaries" in Form 1.
2. Form 2 instantly refreshes to show the employees making up that salary.
3. User clicks "Total Travel" in Form 1.
4. Form 2 instantly refreshes to show travel expense details.
```

## SHOW ME — Hotel Pvt Ltd Migration Scenario

**The Legacy State:**
The General Manager of the Mumbai Taj was using a Composite Form:
- Top Grid: Revenue Entry (Room, F&B, Events)
- Bottom Grid: Reference Data (Last Year Actuals)

**The Problem:**
It was ugly, hard to read, and gave no visual indication of how far they were from their target.

**The New Dashboard 2.0 Design:**
```text
┌─────────────────────────────────────────────────────────────┐
│  Mumbai Taj — Revenue Planning Dashboard                    │
│                                                             │
│  [TILE: Rev Target]   [TILE: Rev Input]   [TILE: Variance]  │
│  [ ₹2.5Cr         ]   [ ₹2.2Cr        ]   [ -₹0.3Cr (Red)]  │
│                                                             │
│  ┌─────────────────────────┐  ┌──────────────────────────┐  │
│  │ DATA ENTRY FORM         │  │ VARIANCE WATERFALL CHART │  │
│  │ Room Rev:  [ 1.5Cr ]    │  │                          │  │
│  │ F&B Rev:   [ 0.5Cr ]    │  │ Shows gap between Target │  │
│  │ Events:    [ 0.2Cr ]    │  │ and Current Input        │  │
│  │                         │  │                          │  │
│  │ [Save Data Button]      │  │ (Auto-refreshes on save) │  │
│  └─────────────────────────┘  └──────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**The Result:** The GM enters data and instantly sees the waterfall chart bridge the gap to their target. EPM becomes a true planning tool, not just a data entry grid.

## MISTAKES — Common Errors & Fixes

| # | Mistake | Symptom | Fix |
|---|---------|---------|-----|
| 1 | Creating new Composite Forms | Client complains UI looks like 2010 | Train users on Dashboards 2.0; enforce policy of no new composites. |
| 2 | Heavy forms on Dashboards | Dashboard takes 15 seconds to load | A dashboard fires simultaneous queries. Ensure all underlying forms use Suppress Missing Blocks. Limit to 4-6 components. |
| 3 | Forgetting Smart Push | User saves data, chart doesn't update | Chart is reading ASO, Form is writing to BSO. Enable Smart Push "Run After Save" on the form. |
| 4 | Master-Detail not working | Clicking grid does nothing | Ensure the Master form is properly tagged in Dashboard properties and the target dimension is mapped. |

## TEST ME — Interview Questions

### 🟢 Beginner
**Q: A client asks you to build a Composite Form so they can see two data grids at once. What should you recommend instead?**
> A: You should strongly recommend building a Dashboard 2.0. Composite Forms are a legacy feature deprecated by Oracle. Dashboards can display multiple grids side-by-side, but also offer modern visualizations (charts, tiles) and better responsiveness.

### 🟡 Intermediate
**Q: How do you replicate the old Composite Form behavior where changing a member in one grid updates the other grid?**
> A: Use Master-Detail linking in Dashboards 2.0. You tag one grid as the "Master", set the target component, and map the dimensions. When a user clicks a row/column in the Master, the target component dynamically updates its POV.

### 🔴 Architect
**Q: You built a Dashboard with a data entry Form and a Pie Chart. The Pie Chart reads from the ASO reporting cube for performance. When the user types a new number in the form and clicks Save, the Pie Chart does not update. Explain the technical architecture of why this happens and how to fix it.**
> A: The data entry Form writes to the BSO (Block Storage) cube. The Pie Chart queries the ASO (Aggregate Storage) cube. The Essbase save action only commits data to BSO. Since the data hasn't moved to ASO, the chart remains stale. 
> **The Fix:** Open the underlying data entry Form, attach a Smart Push data map, and configure it to "Run After Save". This automatically copies the data from BSO to ASO instantly upon saving. Finally, ensure the Dashboard component is set to refresh on save.
