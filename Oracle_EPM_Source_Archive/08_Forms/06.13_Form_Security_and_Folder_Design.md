# 06.13 — Form Security and Folder Design: Complete Guide

> **Module:** 06_Forms | **Topic:** Form Access Permissions, Folder Organization
> **Audience:** Service Administrator

---

## 1. WHY — What Real-World Problem Does This Solve—

**The problem:** Hotel Pvt Ltd has 50 forms. Without organization, the "Forms" listing is a chaotic flat list. Without security, a Mumbai planner can open Delhi's salary entry form and potentially see/edit wrong data. The admin spends hours assigning permissions one form at a time.

**The solution:**
- **Form Folders:** Organize forms into a hierarchical folder structure (by department, by process, by role)
- **Form Security:** Control who can see, open, and edit each form with Read/Write/None permissions
- **Folder-Level Security:** Set permissions on folders that cascade to all forms inside

## 3. FORM ACCESS PERMISSIONS

### Three Permission Levels

| Permission | Can See Form— | Can Open— | Can Edit Data— |
|-----------|-------------|-----------|---------------|
| **Write** | ✅ | ✅ | ✅ (subject to dimension security) |
| **Read** | ✅ | ✅ | ❌ (view-only) |
| **None** | ❌ (hidden) | ❌ | ❌ |

> ⚠️ **Key:** Form permissions work WITH dimension security — not instead of. A user with "Write" on a form but "None" on an entity still can't see that entity's data.

### Setting Form Permissions

```
Navigator → Create and Manage → Forms
→ Select form → Actions → Assign Access (or right-click → Permissions)

┌── Assign Access: Room_Revenue_Entry ─────────────────────────────┐
│                                                                   │
│  User/Group           │ Permission │ Inherited From              │
│───────────────────────┼────────────┼─────────────────────────────│
│  Mumbai_Planners      │ Write ▾    │ —                           │
│  Delhi_Planners       │ Write ▾    │ —                           │
│  Finance_Controllers  │ Read ▾     │ Revenue (folder)            │
│  Hotel_GMs            │ Write ▾    │ Revenue (folder)            │
│  Viewer_Group         │ Read ▾     │ Hotel Forms (root folder)   │
│                                                                   │
│  [+ Add User/Group]  [Remove]  [Save]                           │
└───────────────────────────────────────────────────────────────────┘
```

### Folder-Level Permissions (Cascading)

Set permissions on a folder — they inherit to all forms inside:

```
📁 Revenue (folder) → Assign Access:
  Hotel_GMs: Write
  Finance_Controllers: Read
  Admin: Write
  
  Result: ALL forms inside Revenue folder inherit these permissions
  → Room_Revenue_Entry: GMs=Write, Controllers=Read
  → F&B_Revenue_Entry: GMs=Write, Controllers=Read
  → Revenue_Summary: GMs=Write, Controllers=Read

Override at form level:
  Revenue_Summary → Set Hotel_GMs to Read (override folder's Write)
  → GMs can view summary but not edit it
```

## 4. SECURITY DESIGN PATTERNS

### Pattern 1: Role-Based Folders

```
📁 Planner_Forms (Planners=Write, GMs=Read, Viewers=Read)
├── 📋 Revenue_Entry
├── 📋 Expense_Entry
└── 📋 Headcount_Entry

📁 Manager_Forms (GMs=Write, Planners=None, Viewers=Read)
├── 📋 Budget_Approval
├── 📋 Forecast_Adjustment
└── 📋 P&L_Review

📁 Executive_Forms (CFO=Write, GMs=Read, Planners=None)
├── 📋 Consolidated_P&L
├── 📋 KPI_Dashboard
└── 📋 Board_Report
```

### Pattern 2: Entity-Based Folders

```
📁 Mumbai_Forms (Mumbai_Team=Write, Others=None)

📁 Delhi_Forms (Delhi_Team=Write, Others=None)
```

## 5. HIDDEN FORMS

Forms can be hidden from the form listing while still being accessible via dashboards, action menus, or task lists:

```
Form Designer → Display Properties:
  ☑ Hide form

Use cases:
  - Sub-forms in composite forms (don't need standalone access)
  - Forms accessed only via dashboards or task lists
  - Test/development forms not ready for users
  - Admin-only forms embedded in navigation flows
```

## 7. COMMON MISTAKES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Flat form list (no folders) | Users can't find their forms | Create logical folder hierarchy |
| Permissions on each form individually | Hours of admin work, inconsistencies | Use folder-level permissions + override at form level |
| Forgot to hide test forms | Users see and get confused | Set Hide Form = ☑ for test forms |
| Planner has Write on form + None on entity | Planner sees form but no data | Align form permissions with dimension security |
| No naming convention | Random form names, hard to manage | Establish naming standard before building |

## 8. INTERVIEW QUESTIONS

### Beginner
**Q: What's the difference between form permissions (Read/Write/None) and dimension security—**
> Form permissions control whether a user can **see and access** the form at all. Dimension security controls which **data** the user can see/edit within the form. Both work together: A user needs Write on the form AND Write on the entity/account to edit data. If they have Write on the form but None on an entity, that entity's data is hidden even though they can open the form.

### Intermediate
**Q: Hotel Pvt Ltd has 50 forms. How would you organize them to minimize admin overhead—**
> Use Process-Based Folders with folder-level inheritance: (1) "Data_Entry" folder → Planners=Write, GMs=Read. (2) "Review" folder → GMs=Write, Planners=Read. (3) "Approval" folder → GMs=Write, Planners=None. (4) "Admin" folder → Admin=Write, All=None. Set permissions on folders — they cascade to all forms inside. Override only when specific forms need different access (e.g., P&L_Summary → force Read for GMs even though folder says Write). This reduces permission assignments from 50 (per form) to 4 (per folder) + a few overrides.
