# 06.15 Form Layout Tab — Exhaustive Reference

> **Module:** 06_Forms  
> **Topic:** 15 — Every Option in the Form Layout Tab  
> **Target Audience:** Administrator / Consultant / Architect  

---

## Introduction

The **Layout** tab is where you physically design the 2D grid of the form — deciding which dimensions go on Rows, Columns, Page (dropdowns), and Point of View (fixed context). This is the most architecturally important tab because layout decisions directly impact Essbase query performance, user experience, and data entry workflow.

---

## Navigation Path
```
Navigator → Forms → [Edit Form] → Layout Tab
```

---

# SECTION 1: THE FOUR AXES

Every dimension in the cube must be assigned to exactly one axis:

| Axis | Location on Form | User Interaction | Essbase Impact | Best For |
|------|-----------------|------------------|----------------|----------|
| **Point of View (POV)** | Top bar (usually hidden or minimal) | Fixed — user may or may not be able to change it | Acts as a FIX scope | Dimensions that rarely change per session (Year, Scenario) |
| **Page** | Dropdown(s) above the grid | User toggles via dropdown | Each selection = new Essbase query | Dimensions the user needs to pivot through (Entity, Product) |
| **Rows** | Vertical axis of the grid | User sees all selected members as row labels | Each row member = additional cell rendering | Account/Line Items — the primary data dimension |
| **Columns** | Horizontal axis of the grid | User sees all selected members as column headers | Each column = additional data in each block | Period (Jan–Dec) — the most common column dimension |

### Axis Placement Strategy:

| Dimension Type | Recommended Axis | Why |
|---------------|------------------|-----|
| Account | Rows | Users read financial data vertically (P&L layout) |
| Period | Columns | Monthly columns feel natural (spreadsheet-like) |
| Entity / Department | Page | Users toggle to their own entity — reduces grid size |
| Scenario | POV | Usually fixed per task (Budget OR Actual, not both simultaneously on a data entry form) |
| Version | POV | Same reasoning as Scenario |
| Year | POV | Usually one year per form |
| Product | Page or Rows | Depends on use case (entry vs review) |
| Currency | POV | Fixed for single-currency entry |
| Custom dimensions | Page or POV | Depends on cardinality and user interaction needs |

# SECTION 2: ROW DIMENSION OPTIONS — EVERY FIELD

When you place a dimension on Rows and configure its members:

## 2.1 Member Selection

| Field | Description | Options |
|-------|-------------|---------|
| **Member Selector** | Open the member selection dialog | Click to open tree selector |
| **Selected Members** | List of members that will appear as rows | Individual members, functions, variables |
| **Member Functions** | Dynamic member lists | `Children of`, `Descendants of`, `IDescendants of`, `Level 0 Descendants of`, `Siblings of`, `Parent of`, `Ancestors of`, `All Members` |
| **Substitution Variables** | Use admin-defined variables | `&VarName` (e.g., `&CurrMonth`) |
| **Cross Product** | Create cross-join of two row dimensions | See Section 5 below |

## 2.2 Member Selection Functions — Complete Reference

| Function | What It Returns | Example | Result |
|----------|----------------|---------|--------|
| `Children of "X"` | Immediate children of X | Children of "Total_Revenue" | Revenue_Product_A, Revenue_Product_B, Revenue_Services |
| `Descendants of "X"` | All levels below X | Descendants of "Total_Revenue" | All revenue accounts at every level |
| `IDescendants of "X"` | All descendants + X itself | IDescendants of "Total_Revenue" | Total_Revenue, Revenue_Product_A, ... |
| `Level 0 Descendants of "X"` | Only leaf members below X | Level 0 Descendants of "Total_Revenue" | Only input-level revenue accounts |
| `Siblings of "X"` | Members with the same parent (excluding X) | Siblings of "Revenue_Product_A" | Revenue_Product_B, Revenue_Services |
| `Parent of "X"` | The parent member | Parent of "Revenue_Product_A" | Total_Revenue |
| `Ancestors of "X"` | All ancestors up to root | Ancestors of "Revenue_Product_A" | Total_Revenue, Total_Accounts |
| `All Members` | Every member in the dimension | All Members of Account | All 500 accounts |

## 2.3 Row Display Properties

| Property | Description | Options | Default |
|----------|-------------|---------|---------|
| **Start Expanded** | Whether hierarchy trees are expanded when the form loads | ☑️ / ☐ | ☐ (Collapsed) |
| **Show Alias** | Display alias instead of member name | ☑️ / ☐ | ☑️ (On) |
| **Sort Order** | How rows are ordered | `None (Outline Order)`, `Ascending by Member Name`, `Descending by Member Name`, `Ascending by Alias`, `Descending by Alias` | `None` |
| **Indent Style** | How hierarchy indentation appears | `Indented`, `Subtotals Above`, `Subtotals Below`, `Flat` | `Indented` |

### Indent Style Deep Dive:

| Style | Appearance | Use Case |
|-------|-----------|----------|
| `Indented` | Children are indented under parents | Standard hierarchical view (like a file explorer) |
| `Subtotals Above` | Parent appears above children with indentation | Financial reporting style |
| `Subtotals Below` | Parent appears below children (summary at bottom) | Accounting statement style |
| `Flat` | No indentation — all members at same level | Simple lists, non-hierarchical data |

# SECTION 3: COLUMN DIMENSION OPTIONS — EVERY FIELD

Column options are identical to Row options (Member Selection, Functions, Display) with these additional considerations:

| Column-Specific Property | Description | Options | Default |
|-------------------------|-------------|---------|---------|
| **Enable Column Grouping** | Group columns by parent members | ☑️ / ☐ | ☐ (Off) |
| **Freeze Columns** | Number of columns frozen on the left when scrolling | `0` to `n` | `0` |

### Column Best Practices:

| Scenario | Recommended Column Members |
|----------|---------------------------|
| Monthly data entry | `Children of "YearTotal"` (Jan–Dec) or `IDescendants of "YearTotal"` (includes Q1–Q4 and YearTotal) |
| Quarterly reporting | `Q1, Q2, Q3, Q4, YearTotal` |
| Scenario comparison | `Actual, Budget, Forecast` (3 columns) |
| Variance analysis | `Actual, Budget, Variance_$, Variance_%` (4 columns) |

# SECTION 4: PAGE DIMENSION OPTIONS — EVERY FIELD

| Field | Description | Options | Default |
|-------|-------------|---------|---------|
| **Selected Members** | Which members appear in the Page dropdown | Same as Row member selection | (empty) |
| **Default Member** | Which member is pre-selected when the form opens | Any selected member or variable | First member |
| **Show All** | Include "All" option in the dropdown | ☑️ / ☐ | ☐ (Off) |

### Page Dimension Architecture:

| Consideration | Guidance |
|--------------|----------|
| Number of members in dropdown | Keep under 100 — too many slows the dropdown and confuses users |
| Default member | Set to the user's most common selection (e.g., their own department) |
| Use variables for default | `&CurrEntity` auto-selects the user's entity based on a substitution variable |
| Multiple page dimensions | Up to 4 dimensions on Page — each becomes a separate dropdown |

# SECTION 5: POINT OF VIEW (POV) OPTIONS — EVERY FIELD

| Field | Description | Options | Default |
|-------|-------------|---------|---------|
| **Selected Member** | The fixed member for this dimension | Single member, variable, or function | (empty) |
| **User-Modifiable** | Whether the user can change the POV | ☑️ / ☐ | ☑️ (Modifiable) |
| **Hidden** | Whether the POV dimension is visible to the user | ☑️ / ☐ | ☐ (Visible) |

### POV Best Practices:

| Design Pattern | When to Use |
|---------------|-------------|
| Fixed + Hidden POV | When the value should NEVER change (e.g., `Local` currency for data entry) |
| Fixed + Visible POV | When the user should see what's fixed but not change it |
| Modifiable POV | When different users need different POV values |
| Variable-based POV | When an admin controls the global context (e.g., `&BudgetYear`) |

# SECTION 6: ASYMMETRIC GRIDS (CROSS-PRODUCTS)

## What is an Asymmetric Grid?
A standard form shows the same columns for every row. An asymmetric grid allows **different column selections per row section**.

### Example:
| Row (Account) | Jan | Feb | Mar | Q1 | YearTotal |
|--------------|-----|-----|-----|----|-----------|
| Revenue | ✅ | ✅ | ✅ | ✅ | ✅ |
| COGS | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Margin %** | ❌ | ❌ | ❌ | ✅ | ✅ |

In this example, `Margin %` only shows Q1 and YearTotal (not monthly detail — because monthly margins are meaningless in isolation).

### How to Create:
1. **Layout tab** → Select "Asymmetric" option for the rows/columns
2. Create **separate row segments** with different column member selections
3. Each segment independently defines its column members

### When to Use Asymmetric:
| Scenario | Use Asymmetric? |
|----------|-----------------|
| All rows need the same columns | ❌ No — standard grid |
| Some rows need quarterly rollups, others need monthly detail | ✅ Yes |
| Revenue needs Actual + Budget columns, Headcount needs only Budget | ✅ Yes |
| Dashboard combining financial and operational metrics | ✅ Yes |

# SECTION 7: MULTIPLE DIMENSIONS ON SAME AXIS

You can place **2+ dimensions on the same axis** (e.g., Account AND Product both on Rows).

### How it Renders:
Each cell becomes the intersection of ALL row dimensions × ALL column dimensions.

**Example:** Account AND Entity on Rows, Period on Columns:
```
Row Labels                  | Jan    | Feb    | Mar
Account: Revenue / Entity: US  | 1,000  | 1,200  | 1,100
Account: Revenue / Entity: UK  | 800    | 900    | 850
Account: COGS / Entity: US     | 400    | 450    | 420
Account: COGS / Entity: UK     | 350    | 380    | 360
```

### Cross-Product Warning:
If Account has 500 members and Entity has 100 members, the cross-product creates **50,000 rows**. The form will crash.

**Rule of Thumb:** Never cross-join two large dimensions on the same axis. Use Page dropdowns to filter one of them.

## Interview Questions

### Intermediate
**Q: A form has Account (500 members) on Rows and Entity (100 members) on Rows (cross-product). The form takes 10 minutes to load. How do you fix it?**
> A: Move Entity from Rows to the Page axis (dropdown). This reduces the grid from 50,000 rows (500 × 100) to 500 rows. The user selects their Entity from the dropdown, sees only 500 account rows, and the form loads in seconds.

### Architect
**Q: Design a form for a rolling forecast where users enter monthly data for the remaining months of the year, and the YTD actuals are shown as read-only for completed months.**
> A: Create an asymmetric grid: (1) **Segment 1 (Read-only):** Columns = Actual months (Jan through `&ActualMonth`) — set to Read-Only. (2) **Segment 2 (Editable):** Columns = Forecast months (`&ActualMonth+1` through Dec) — editable. POV: Scenario = Forecast, Year = &CurrYear. Page: Entity. Rows: Accounts. Use substitution variables for the month boundaries so the form auto-adjusts each month when the admin updates `&ActualMonth`.

---

## Summary

The Layout tab is where performance is won or lost:
- **Rows:** Keep under 500 members. Use member functions for dynamic lists.
- **Columns:** Keep under 24 members (12 months + parents is ideal).
- **Page:** Put high-cardinality dimensions here (Entity, Product) as dropdowns.
- **POV:** Fix everything that doesn't change per user action.
- **Never cross-join** two large dimensions on the same axis.
