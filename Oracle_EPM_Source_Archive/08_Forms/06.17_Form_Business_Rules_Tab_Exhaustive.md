# 06.17 Form Business Rules Tab — Exhaustive Reference

> **Module:** 06_Forms  
> **Topic:** 17 — Every Option in the Form Business Rules Tab  
> **Target Audience:** Administrator / Consultant / Architect

## Introduction

The **Business Rules** tab on the Form Designer controls which business rules are associated with the form, when they execute (on load, on save, or manually), and how Runtime Prompts are handled. This is where the form transitions from a static data grid to a dynamic calculation engine.

---

## Navigation Path
```
Navigator → Forms → [Edit Form] → Business Rules Tab
```

---

# SECTION 1: RULE ASSOCIATION

## 1.1 Adding Rules to a Form

| Action | How | Result |
|--------|-----|--------|
| **Add Rule** | Click "Add Rule" button → Browse available rules → Select → OK | Rule appears in the form's rule list |
| **Remove Rule** | Select rule from list → Click "Remove" | Rule is detached from the form |
| **Reorder Rules** | Select rule → Use Up/Down arrows | Changes execution order for "Run on Save" |

## 1.2 Available Rule Types

| Rule Type | Can Be Attached? | Behavior |
|-----------|-----------------|----------|
| **Essbase Calc Script Rule** | ✅ Yes | Standard calc script execution |
| **Groovy Business Rule** | ✅ Yes | Groovy script execution |
| **Rule Set** | ✅ Yes | Sequential execution of multiple rules |
| **Template** | ❌ No (must be embedded in a rule first) | Templates are components, not standalone |

# SECTION 2: EXECUTION TIMING — EVERY OPTION

For each rule attached to the form, you configure WHEN it runs:

## 2.1 Run Rule Properties (Per Rule)

| Property | Description | Options | Default |
|----------|-------------|---------|---------|
| **Run on Load** | Execute the rule when the form opens | ☑️ / ☐ | ☐ (Off) |
| **Run on Save** | Execute the rule when the user clicks Save | ☑️ / ☐ | ☐ (Off) |
| **Run Manually** | User must explicitly click "Rules" menu → select rule → Run | Always available | ✅ (Always) |
| **Run in Background** | Execute the rule as a background job (non-blocking) | ☑️ / ☐ | ☐ (Off) |
| **Hide Rule** | Don't show the rule in the user's manual Rules menu | ☑️ / ☐ | ☐ (Off) |

### Execution Timing Decision Matrix:

| Scenario | Run on Load | Run on Save | Manual | Background |
|----------|------------|------------|--------|------------|
| Pre-populate form with calculated values | ✅ | ❌ | ❌ | ❌ |
| Recalculate totals after data entry | ❌ | ✅ | ❌ | ❌ |
| Heavy allocation rule (>30 seconds) | ❌ | ❌ | ✅ | ✅ |
| Data validation before save (Groovy) | ❌ | ✅ | ❌ | ❌ |
| Month-end consolidation | ❌ | ❌ | ✅ | ✅ |
| Groovy cell-level formatting | ✅ | ❌ | ❌ | ❌ |

---

## 2.2 Run on Load — Deep Dive

**What Happens:**
1. User opens the form
2. Before the grid renders, the rule executes
3. The grid displays the rule's output (calculated values)

**Best Practices:**
| Practice | Why |
|----------|-----|
| Keep load rules under 3 seconds | Users won't wait for a slow-loading form |
| Use for read-only calculated fields | Pre-populate Variance %, Margin %, etc. |
| Use Groovy for conditional formatting | Color cells based on thresholds |
| Don't use for heavy calculations | Use background + refresh instead |

**Groovy on Load Example:**
```groovy
// Color cells red if variance is negative
operation.grid.dataCellIterator("Variance_Pct").each { DataCell cell ->
    if (!cell.isMissing() && cell.data < 0) {
        cell.addValidationError(0xFF0000, "Unfavorable")
    }
}
```

## 2.3 Run on Save — Deep Dive

**What Happens:**
1. User clicks Save
2. Data is written to Essbase
3. The attached rule(s) execute in order
4. The form refreshes with recalculated values
5. User sees updated grid

**Execution Order:**
If multiple rules are attached as "Run on Save", they execute in the order shown in the rules list (top to bottom).

**Critical Architecture:**

| Rule Duration | User Experience | Recommendation |
|--------------|-----------------|----------------|
| < 2 seconds | Seamless — form refreshes instantly | ✅ Perfect for Save rules |
| 2–10 seconds | User sees a "Processing..." spinner | ⚠️ Acceptable if necessary |
| 10–30 seconds | User thinks the form is broken | ⚠️ Consider background execution |
| > 30 seconds | User closes browser / calls IT support | ❌ Move to background or optimize |

**Groovy Save Data vs Groovy Calculate:**

| Groovy Rule Type | When It Fires | Can Access Grid? | Can Cancel Save? |
|-----------------|---------------|-----------------|-----------------|
| **Save Data** | BEFORE data is committed to Essbase | ✅ Yes (`operation.grid`) | ✅ Yes (`throwVetoException`) |
| **Calculate** | AFTER data is committed to Essbase | ❌ No (data already saved) | ❌ No |

### The "Veto Save" Pattern (Groovy Save Data):
```groovy
// Prevent save if Revenue is negative
boolean hasErrors = false
operation.grid.dataCellIterator("Revenue").each { DataCell cell ->
    if (cell.isEdited() && cell.data < 0) {
        cell.addValidationError(0xFF0000, "Revenue cannot be negative!")
        hasErrors = true
    }
}
if (hasErrors) {
    throwVetoException("Save cancelled: Please correct highlighted errors.")
}
```

## 2.4 Run in Background — Deep Dive

**What Happens:**
1. User clicks "Run" on the rule
2. The system immediately returns control to the user (form is usable)
3. The rule executes as a background job
4. User can check status in the Job Console
5. When complete, user manually refreshes the form to see results

**When to Use Background:**
- Any rule that takes > 10 seconds
- Aggregation rules
- Allocation rules
- Cross-cube data pushes
- Month-end close processes

# SECTION 3: RUNTIME PROMPT (RTP) HANDLING ON FORMS

## 3.1 How RTPs Interact with Forms

When a business rule with RTPs is attached to a form, the admin configures how each RTP is handled:

| RTP Handling Option | Description | User Experience |
|--------------------|-------------|-----------------|
| **Prompt User** | Show the standard RTP dialog to the user | User sees a pop-up with the RTP fields |
| **Use Form Members** | Auto-populate the RTP from the form's current POV/Page/Row/Column | No prompt — RTP is silently filled |
| **Use Default** | Use the RTP's configured default value | No prompt — default value used |
| **Hidden** | Pass a fixed value without showing anything | No prompt — invisible to user |

## 3.2 Context Variables (Auto-Population)

When "Use Form Members" is selected, these context variables are available:

| Variable | What It Contains | Example |
|----------|-----------------|---------|
| `{$POV$}` | All Point of View selections | If POV has Year=FY24, Scenario=Budget → RTP gets "FY24" |
| `{$ROW$}` | The current row member(s) | If user clicked on a Revenue row → RTP gets "Revenue" |
| `{$COL$}` | The current column member(s) | If user is in Jan column → RTP gets "Jan" |
| `{$PAGE$}` | The current Page dropdown selection | If Page shows Entity=US → RTP gets "US" |

### Context Variable Example:

**Scenario:** A rule calculates tax for a specific entity. The RTP expects the entity name.

**Configuration:**
| RTP | Handling | Maps To |
|-----|---------|---------|
| `RTP_Entity` | Use Form Members | `{$PAGE$}` (Entity is on the Page axis) |
| `RTP_Year` | Use Form Members | `{$POV$}` (Year is in the POV) |

**Result:** When the user saves the form, the rule automatically receives the entity from the page dropdown and the year from the POV. No pop-up appears.

# SECTION 4: MULTIPLE RULES ON A SINGLE FORM

## 4.1 Rule Ordering

Rules execute in the order they appear in the list. Use Up/Down arrows to reorder.

**Example Order for a Budget Form:**
| Order | Rule | Timing | Purpose |
|-------|------|--------|---------|
| 1 | `Validate_Data` (Groovy Save Data) | On Save | Check for negatives, validate data |
| 2 | `Calculate_Tax` (Calc Script) | On Save | Calculate derived values |
| 3 | `Aggregate_Entity` (Calc Script) | On Save | Roll up to parent entities |
| 4 | `Push_to_Reporting` (Groovy) | On Save | Smart Push to reporting cube |

**Execution Flow:**
```
User clicks Save → 
  1. Validate_Data runs → if errors, save is cancelled (Veto)
  2. Calculate_Tax runs → Tax = Revenue * 0.25
  3. Aggregate_Entity runs → Total = US + UK + DE
  4. Push_to_Reporting runs → Data pushed to ASO cube
→ Form refreshes with updated values
```

## Interview Questions

### Intermediate
**Q: What is the difference between a Groovy "Save Data" rule and a Groovy "Calculate" rule when attached to a form's "Run on Save"?**
> A: Save Data fires BEFORE the data is committed to Essbase. It can access the grid (`operation.grid`), read which cells were edited, validate data, and cancel the save (`throwVetoException`). Calculate fires AFTER data is committed. It cannot access the grid or cancel the save. Use Save Data for validation and pre-processing; use Calculate for post-save aggregation and data pushes.

### Architect
**Q: A form has 5 rules attached to "Run on Save". Three are calc scripts (3 seconds each) and two are Groovy validation scripts (1 second each). The total execution time is 11 seconds, and users complain. How do you optimize?**
> A: (1) Combine the 3 calc scripts into 1 rule with 3 sequential script components — reduces the overhead of launching 3 separate Essbase sessions. (2) Combine the 2 Groovy validations into 1 script — reduces JVM startup overhead. (3) Ensure the Groovy validation runs FIRST (order 1) so invalid saves are rejected before the 9-second calculation runs. (4) If the calc script can be made sub-second by tightening FIX scope using form context variables (`{$PAGE$}`), do that. Target: < 3 seconds total.

## Summary

| Feature | Key Insight |
|---------|------------|
| **Run on Load** | Pre-populate calculated fields; keep under 3 seconds |
| **Run on Save** | Validation + recalculation; order matters (validate first) |
| **Run in Background** | Heavy rules that would freeze the browser |
| **Groovy Save Data** | Can cancel the save (validation); runs BEFORE commit |
| **Groovy Calculate** | Cannot cancel the save; runs AFTER commit |
| **Context Variables** | Auto-populate RTPs from form POV/Page/Row/Column |
| **Rule Ordering** | Top-to-bottom execution; validate before calculate |
