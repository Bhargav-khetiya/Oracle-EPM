# 06.25 — Form Best Practices Bible

> **Module:** 06_Forms | **Topic:** Form Design Standards, Naming, Organization
> **Audience:** Service Administrator / Architect

---

## 1. WHY — Why Codify Best Practices—

An enterprise EPBCS application can have 50-200 forms. Without standards, you get: inconsistent naming, duplicate forms, performance nightmares, and a maintenance burden that grows exponentially. This guide codifies the **rules that top consultants follow**.

---

## 2. NAMING CONVENTIONS

### Form Naming Standard

```
Pattern: [Module]_[Process]_[View]_[Version]
Example: FIN_Revenue_Entry_v2
         WF_Headcount_Summary_ReadOnly
         CP_CapEx_Approval_Form
```

| Prefix | Module | Example |
|--------|--------|---------|
| FIN_ | Financial Planning | FIN_Revenue_Entry |
| WF_ | Workforce | WF_Salary_Entry |
| CP_ | Capital Planning | CP_CapEx_Budget |
| OPS_ | Operations (FreeForm) | OPS_Room_Inventory |
| RPT_ | Reporting | RPT_PnL_Dashboard |
| ADM_ | Admin/Test | ADM_Test_Form |

| Suffix | Meaning | Example |
|--------|---------|---------|
| _Entry | Data entry form | FIN_Revenue_Entry |
| _Summary | Read-only summary | FIN_PnL_Summary |
| _Dashboard | Dashboard view | RPT_GM_Dashboard |
| _Approval | Approval workflow | FIN_Budget_Approval |
| _Test | Admin testing only | ADM_Calc_Test |

### Folder Organization

```
📁 01_Revenue (Planners=Write, GMs=Read)
📁 02_Expenses (Planners=Write, GMs=Read)
📁 03_PnL_Review (GMs=Write, Planners=Read)
📁 04_Workforce (HR=Write, GMs=Read)

📁 06_Dashboards (All=Read)
📁 07_Approval (GMs=Write)
📁 99_Admin (Admin=Write, All=None)
```

## 3. THE 15 GOLDEN RULES

### Layout Rules

```
RULE 1:  Account → Rows (always). Period → Columns (always).
RULE 2:  Entity → Page or POV. Never on rows with Account.
RULE 3:  Maximum 2 dimensions on rows. Maximum 2 on columns.
RULE 4:  Scenario + Version + Year → POV (unless user toggles them).
RULE 5:  Use User Variables for entity personalization.
```

### Performance Rules

```
RULE 6:  Enable Suppress Missing Data on ALL forms.
RULE 7:  Enable Suppress Missing Blocks on summary/reporting forms.
RULE 8:  Never put 2 sparse dimensions on rows.
RULE 9:  Limit visible cells to < 5,000 (rows × columns).
RULE 10: Limit On Save rules to 1-2 per form. Use Rulesets.
```

### User Experience Rules

```
RULE 11: Display Missing as Blank (always — users hate #MISSING).
RULE 12: Enable Grid Spread on data entry forms.
RULE 13: Use format rules for traffic-light variance display.
RULE 14: Add instructions text for complex entry forms.
RULE 15: Set meaningful precision (₹ = 0 decimals, % = 1 decimal).
```

## 4. FORM DESIGN PATTERNS

### Pattern 1: Standard Data Entry Form

```
Cube: OEP_FS
POV: Scenario, Version, Year
Page: Entity (User Variable)
Rows: Account = IChildren("Revenue_Accounts") — 10-20 members
Columns: Period = Jan through Dec
Suppression: OFF (users need blank rows for entry)
Display Missing: Blank
Grid Spread: Enabled
Business Rules: "Calculate_Totals" on Save
Precision: Currency = 0 decimals
```

### Pattern 2: Read-Only Summary Form

```
Cube: OEP_FS
POV: Version=Final, Year=FY2026
Page: Entity (User Variable), Scenario (Budget/Actual/Forecast)
Rows: Account = IDescendants("Net_Income") — full P&L tree
Columns: Period = YearTotal + Quarters
Suppression: Missing + Missing Blocks = ON
Display: Read-Only, Missing as Blank
Format Rules: Traffic light on variance rows
Business Rules: "Full_Aggregation" on Load
```

### Pattern 3: Variance Analysis Form

```
Cube: OEP_FS
POV: Version=Final, Year=FY2026
Page: Entity
Rows: Account = Key P&L lines
Columns: 
  Segment A: Period (months) for Actual
  Segment B: Period (months) for Budget
  Formula Column C: Variance = A - B
  Formula Column D: Variance% = C / B * 100
Read-Only: Yes
Format Rules:
  Variance% < -5 → Red
  Variance% between -5 and 5 → Yellow
  Variance% > 5 → Green
```

### Pattern 4: Multi-Scenario Comparison

```
Cube: OEP_FS
POV: Version=Final, Year=FY2026
Page: Entity
Rows: Account = Key metrics
Columns: Period stacked with Scenario:
  Segment A: Actual + Jan-Dec → Read-Only
  Segment B: Budget + Jan-Dec → Read-Only
  Segment C: Forecast + Jan-Dec → Editable
Show Separator between segments: ☑
```

## 5. ANTI-PATTERNS (NEVER DO)

| Anti-Pattern | Why It's Bad | Better Approach |
|-------------|-------------|-----------------|
| One mega-form with everything | Slow, confusing, 50,000+ cells | Split into focused forms by process |
| Separate form per entity | 5 hotels = 5 identical forms to maintain | 1 form + User Variable on Entity |
| Hardcoded member lists | New members require form redesign | Use IChildren/IDescendants functions |
| All dimensions visible | Form has 10 dropdowns, user overwhelmed | Move stable dims to POV, leave 1-2 on Page |
| No suppression anywhere | Forms show 500 empty rows | Enable Suppress Missing Data everywhere |
| Business logic in formula columns | Hard to maintain, can't be reused | Use member formulas in Essbase (reusable) |
| No naming convention | "Form1", "Copy of Form1", "test" | Establish naming standard on Day 1 |
| Same rule on Load AND Save | Rule runs twice (redundant) | Choose one trigger |
| Precision left at default | Shows 6 decimal places for currency | Set Currency=0, Percentage=1, Rates=4 |

## 7. FORM LIFECYCLE MANAGEMENT

```
Development:
  1. Build form in DEV environment
  2. Test with sample data
  3. Validate security and rules
  
Migration:
  4. Export via LCM (Lifecycle Management)
  5. Import to TEST environment
  6. UAT (User Acceptance Testing)
  
Production:
  7. Import to PROD
  8. Assign permissions
  9. Monitor performance (Jobs Console)
  
Maintenance:
  10. Monthly: Review form usage reports
  11. Quarterly: Remove unused forms
  12. Annually: Redesign based on feedback
```

## 8. INTERVIEW QUESTIONS

### Intermediate
**Q: You're starting a new EPBCS implementation. What form design standards do you establish on Day 1—**
> (1) Naming convention with prefixes (FIN_, WF_, CP_) and suffixes (_Entry, _Summary, _Dashboard). (2) Folder structure matching business processes with numbered prefixes for ordering. (3) Standard dimension placement: Account→Rows, Period→Columns, Entity→Page/UserVariable, everything else→POV. (4) Mandatory settings: Display Missing as Blank ☑, Suppress Missing Data ☑ on all summary forms. (5) Precision standards per data type. (6) Maximum cell count guideline: < 5,000 cells per form. (7) Template forms for common patterns that designers clone instead of building from scratch.

### Architect
**Q: A client says "We need 200 forms for 200 cost centers." What do you say—**
> Absolutely not — you need 5-10 forms maximum, using User Variables. Create one "Cost_Center_Revenue_Entry" form with UserEntity variable on the Page axis. Each cost center manager sets their User Variable to their cost center and sees only their data on the same form. 1 form serves all 200 cost centers. If some cost centers have unique accounts, use attribute-based member selection or create 2-3 form variants at most. 200 forms would be a maintenance nightmare — any change (add a column, fix formatting) would need to be replicated 200 times.
