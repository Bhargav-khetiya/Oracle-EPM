# SECTION 1: FORM FUNDAMENTALS

---

## 1.1 What is a Form—

A **Form** is a **data entry and display screen** in Oracle EPBCS. It is a structured grid view of the Essbase cube where users can:
- **Enter** budget/forecast numbers
- **View** actual data
- **Compare** scenarios (Budget vs Actual)
- **Run** business rules
- **Drill down** into details
- **Add commentary** and supporting detail

## 1.2 Form = Slice of the Cube

```
The Essbase cube has millions of cells across 10+ dimensions.
A form shows a SPECIFIC SLICE — a carefully selected subset.

Full Cube:
  Account (500) × Entity (50) × Period (12) × Year (5) × 
  Scenario (3) × Version (2) × Currency (3) × Department (12)
  = 3.24 billion possible cells

Form "Revenue Budget Entry":
  Rows: 5 Revenue accounts (Account dimension)
  Columns: 12 months (Period dimension)
  POV: Budget, Working, FY26, INR (fixed context)
  Page: One entity at a time (user selects)
  
  Visible cells: 5 × 12 = 60 cells ← Manageable for a user!
```

## 1.3 Form Lifecycle

```
Step 1: Admin DESIGNS the form (layout, properties, rules)
Step 2: Admin ASSIGNS security (who can see/edit the form)
Step 3: User OPENS the form
Step 4: Essbase RETRIEVES data for the form's intersections
Step 5: User ENTERS or MODIFIES data
Step 6: User clicks SAVE
Step 7: Data is WRITTEN back to the Essbase cube
Step 8: Business rules may RUN automatically (if configured)
Step 9: Smart Push may PUSH data to other plan types (if configured)
```

# SECTION 2: FORM ARCHITECTURE — HOW FORMS READ FROM THE CUBE

---

## 2.1 The Retrieval Process

When a user opens a form:

```
1. Planning layer reads the form definition
   → Which dimensions on Rows, Columns, POV, Pages
   → Which members selected for each dimension
   → Grid properties (suppress missing, read-only, etc.)

2. Planning generates an Essbase MDX query
   → SELECT {[Jan], [Feb], [Mar], ...} ON COLUMNS,
     {[Revenue], [Expense], [Net Income]} ON ROWS
     FROM [Plan1]
     WHERE ([Budget], [Working], [FY26], [Hotel India], [INR])

3. Essbase executes the query
   → Locates relevant blocks using sparse member filter
   → Reads dense cells within those blocks
   → Returns data grid to Planning

4. Planning applies formatting
   → Cell colors, read-only cells, validation rules
   → Displays the form to the user
```

## 2.2 The Save Process

When a user clicks Save:

```
1. Planning identifies CHANGED cells only
   → Only modified cells are sent to Essbase (not the entire grid)

2. Planning writes changed cells to Essbase
   → Direct cell update to the appropriate blocks

3. Post-Save actions trigger:
   → Business Rules (if "Run on Save" configured)
   → Smart Push (if configured to push on save)
   → Validation Rules (if defined)

4. Form REFRESHES
   → Essbase re-retrieves the data
   → Calculated members show updated values
   → User sees the result
```

# SECTION 3: THE 4 LAYOUT AREAS

---

## 3.1 Overview

Every form has exactly 4 layout areas. Every dimension must be assigned to ONE area.

```
┌──────────────────────────────────────────────────────┐
│  POV:  [Scenario: Budget ▼] [Version: Working ▼]    │
│        [Year: FY26 ▼]       [Currency: INR ▼]        │
├──────────────────────────────────────────────────────┤
│  Page: [Entity: E10001 - Hotel India ▼]              │
│        [Department: D10010 - Catering ▼]             │
├──────────────────────────────────────────────────────┤
│               │    Jan    │    Feb    │    Mar    │   │
│               │ (Column)  │ (Column)  │ (Column)  │   │
├───────────────┼───────────┼───────────┼───────────┤   │
│ Revenue (Row) │  ₹18Cr   │  ₹19Cr   │  ₹20Cr   │   │
│ Expense (Row) │  ₹12Cr   │  ₹13Cr   │  ₹14Cr   │   │
│ Net Inc (Row) │   ₹6Cr   │   ₹6Cr   │   ₹6Cr   │   │
└──────────────────────────────────────────────────────┘
```

## 3.2 POV (Point of View)

| Aspect | Detail |
|--------|--------|
| **Purpose** | Fixed context — sets the "background" for the entire form |
| **Visibility** | Shown as dropdowns at the TOP of the form |
| **Interactivity** | User CAN change POV selections (unless admin restricts) |
| **Data Impact** | Changing POV re-retrieves the entire form for new context |
| **Best For** | Dimensions where users rarely switch (Year, Currency, Version) |
| **Members Shown** | ONE member at a time per dimension |

```
Example POV:
  Scenario: Budget ← user sees data for Budget only
  Version: Working ← user sees Working version only
  Year: FY26 ← user sees FY26 only
  Currency: INR ← user sees INR only

If user changes Scenario to "Actual" → entire form refreshes with Actual data
```

## 3.3 Pages

| Aspect | Detail |
|--------|--------|
| **Purpose** | Switchable context — like tabs/pages within the form |
| **Visibility** | Dropdown above the grid, below POV |
| **Interactivity** | User can switch between page members freely |
| **Data Impact** | Switching pages re-retrieves grid data for new page |
| **Best For** | Dimensions where users frequently switch (Entity, Department) |
| **Members Shown** | ONE member at a time, but easy dropdown switching |

```
Example Pages:
  Entity: [Hotel India ▼] ← user can switch to Hotel USA, Hotel UK
  Department: [Catering ▼] ← user can switch to Front Office, Finance

Switching to "Hotel USA" → grid refreshes with Hotel USA data
Each "page" is like a separate spreadsheet tab
```

## 3.4 Rows

| Aspect | Detail |
|--------|--------|
| **Purpose** | Vertical axis of the data grid |
| **Visibility** | Left side of the grid |
| **Interactivity** | Visible members determined by admin's member selection |
| **Best For** | Account dimension (financial line items) |
| **Members Shown** | ALL selected members visible simultaneously |
| **Multiple Dims** | Can stack multiple dimensions on rows (nested) |

```
Single dimension on rows:
  Revenue
  COGS
  Gross Margin
  Operating Expense
  Net Income

Multiple dimensions on rows (nested):
  Hotel India
    Revenue
    Expense
    Net Income
  Hotel USA
    Revenue
    Expense
    Net Income
```

## 3.5 Columns

| Aspect | Detail |
|--------|--------|
| **Purpose** | Horizontal axis of the data grid |
| **Visibility** | Top of the grid |
| **Best For** | Period dimension (months/quarters) |
| **Members Shown** | ALL selected members visible simultaneously |
| **Multiple Dims** | Can stack multiple dimensions on columns (nested) |

```
Single dimension on columns:
  Jan  |  Feb  |  Mar  |  Apr  |  May  |  Jun

Multiple dimensions on columns (nested):
  Budget          |  Actual         |  Variance
  Jan | Feb | Mar | Jan | Feb | Mar | Jan | Feb | Mar
```

## 3.6 Dimension Assignment Rules

| Rule | Description |
|------|-------------|
| **Every dimension must be assigned** | Each dimension goes to exactly one area |
| **Only 1 member visible in POV/Page** | POV and Page show one member at a time |
| **All members visible in Row/Column** | Rows and Columns display all selected members |
| **Nested dimensions** | Multiple dimensions can be stacked on Rows or Columns |
| **Account on Rows (best practice)** | Users expect financial line items on the left |
| **Period on Columns (best practice)** | Users expect months across the top |

# SECTION 6: GRID PROPERTIES — EVERY CHECKBOX

---

## 6.1 Display Options

| Property | Default | Effect |
|----------|---------|--------|
| **Suppress Missing Data - Rows** | ❌ Off | Hides rows where ALL cells are #Missing |
| **Suppress Missing Data - Columns** | ❌ Off | Hides columns where ALL cells are #Missing |
| **Suppress Missing Blocks** | ✅ On | Skips Essbase blocks with no data (performance) |
| **Suppress Invalid Data** | ❌ Off | Hides intersections that don't exist in the cube |
| **Suppress Zero Data - Rows** | ❌ Off | Hides rows where ALL cells are zero |
| **Suppress Zero Data - Columns** | ❌ Off | Hides columns where ALL cells are zero |

```
⚠️ Critical Edge Case: Suppress Missing Data

Form has these rows: Revenue, Expense, Net Income
Entity: Brand New Hotel (no data yet)

Suppress Missing Rows = OFF:
  Revenue      #Missing  #Missing  #Missing
  Expense      #Missing  #Missing  #Missing
  Net Income   #Missing  #Missing  #Missing
  → User sees the form but with empty cells → CAN enter data

Suppress Missing Rows = ON:
  (empty form — all rows suppressed!)
  → User sees NOTHING → CANNOT enter data for new entity!
  → This is a common deployment mistake!

FIX: For data entry forms, keep Suppress Missing Rows = OFF
     For reporting forms, turn it ON for cleaner display
```

## 6.2 Data Entry Options

| Property | Default | Effect |
|----------|---------|--------|
| **Enable Cell-Level Read-Only** | ❌ Off | Allows marking specific cells as read-only |
| **Read-Only Cells** | (color setting) | Background color for read-only cells (e.g., light gray) |
| **Dirty Cell Color** | Yellow | Color of changed (unsaved) cells |
| **Enable Spreading** | ✅ On | Allow users to spread values across periods |
| **Enable Grid Spread** | ❌ Off | Allow proportional spreading |

## 6.3 Spreading Mechanics

```
Mass Allocate (Grid Spread):
  User enters YearTotal Revenue = ₹3,00,00,000
  → System spreads to months based on existing pattern

Spread Options:
  Proportional: Spread based on existing monthly ratios
  Evenly: Divide equally (₹3,00,00,000 / 12 = ₹25,00,000/month)
  Fill: Copy ₹3,00,00,000 to every month

Example — Proportional Spread:
  Current monthly data: Jan=8%, Feb=7%, Mar=8%, ... = 100%
  New YearTotal = ₹3,00,00,000
  Jan = ₹3,00,00,000 × 8% = ₹24,00,000
  Feb = ₹3,00,00,000 × 7% = ₹21,00,000
  Mar = ₹3,00,00,000 × 8% = ₹24,00,000
  ...and so on
```

# SECTION 7: BUSINESS RULES TAB

---

## 7.1 Rule Attachment Points

| Attachment Point | When It Fires | Use Case |
|-----------------|---------------|----------|
| **Run on Load** | When user opens the form | Pre-calculate values, apply rates |
| **Run on Save** | When user clicks Save | Calculate derived values, aggregate, validate |
| **Run on Demand** | User manually selects from menu | Ad hoc operations, data copy |
| **Associated Rule** | Linked but not auto-triggered | Appears in right-click menu |

## 7.2 Example: Form with Run on Save Rule

```
Form: "Revenue Budget Entry"
  Business Rule: "Calculate_Revenue" (Run on Save)
  
  Script:
  FIX({RTP_Entity}, "Budget", "Working", &CurrYear)
      "Rooms_Sold" = "Rooms_Available" * "Occupancy_Rate" / 100;
      "Rooms_Revenue" = "Rooms_Sold" * "Avg_Room_Rate";
      "Total_Revenue" = "Rooms_Revenue" + "Banquet_Revenue" + "FnB_Revenue";
  ENDFIX

  User Flow:
  1. User opens form → sees Rooms_Available, Occupancy_Rate, Avg_Room_Rate
  2. User enters/modifies driver values
  3. User clicks Save
  4. "Calculate_Revenue" runs automatically
  5. Form refreshes → Rooms_Sold, Rooms_Revenue, Total_Revenue are calculated
  6. User sees updated totals
```

## 7.3 Rule Launch Options

| Option | Description |
|--------|-------------|
| **Hide Prompt** | Don't show RTP dialog to user (use form context) |
| **Use Form Members** | RTP values auto-filled from form's current POV/Page |
| **Launch as Background** | Run in background (for long-running rules) |

# SECTION 8: MEMBER SELECTION DEEP DIVE

---

## 8.1 Static Selection

Selecting specific named members:
```
Rows (Account): Revenue, COGS, Gross Margin, Operating Expense, Net Income
Columns (Period): Jan, Feb, Mar, Apr, May, Jun, Jul, Aug, Sep, Oct, Nov, Dec
```

## 8.2 Function-Based Selection

Using Essbase functions to dynamically select members:

| Function | Returns | Example |
|----------|---------|---------|
| `@CHILDREN("Revenue")` | Immediate children of Revenue | Rooms Revenue, Banquet Revenue, F&B Revenue |
| `@DESCENDANTS("Revenue")` | ALL descendants (recursive) | All revenue accounts at every level |
| `@ICHILDREN("Revenue")` | Revenue + its children | Revenue, Rooms Revenue, Banquet Revenue, F&B Revenue |
| `@IDESCENDANTS("Revenue")` | Revenue + all descendants | Revenue + all nested members |
| `@SIBLINGS("Rooms Revenue")` | Same-level siblings | Rooms Revenue, Banquet Revenue, F&B Revenue |
| `@LEVMBRS("Account", 0)` | All level 0 members | All leaf accounts (input members) |
| `@UDA("Account", "Revenue_Driver")` | Members with UDA tag | All accounts tagged "Revenue_Driver" |
| `@ATTRIBUTE("Region", "Asia")` | Members with attribute | All entities in Asia region |

## 8.3 Variable-Based Selection

```
Substitution Variables:
  &CurrYear → FY26 (admin sets this centrally)
  &CurrPeriod → Jul (changes monthly)
  &CurrScenario → Budget

In Form Layout:
  Columns (Period): &CurrPeriod to Dec
  → Shows: Jul, Aug, Sep, Oct, Nov, Dec (remaining months)
  
  When admin updates &CurrPeriod to "Aug":
  → Form automatically shows: Aug, Sep, Oct, Nov, Dec
```

## 8.4 Dynamic Member Selection with Variables

```
Pattern: Rolling 6-Month Form

POV: Year = &CurrYear, Scenario = Budget
Columns: @RELATIVE("Period", 0)  [with start/end using variables]

When &CurrPeriod = "Jul":
  Form shows: Jul | Aug | Sep | Oct | Nov | Dec

When &CurrPeriod = "Oct":
  Form shows: Oct | Nov | Dec | Jan | Feb | Mar (crosses year!)
  → Requires cross-year handling with Year dimension
```

|---------|--------|

| Feature | Detail |
|---------|--------|

```
Need simple data entry— → Simple Form
Need to see 2+ grids side by side— → Composite Form
```

# SECTION 11: RUNTIME PROMPTS ON FORMS

---

## 11.1 How RTPs Work with Forms

When a business rule has Runtime Prompts (RTPs) and is attached to a form:

```
Rule: "Calculate_Revenue"
RTP: Entity (type: Member, dimension: Entity)
RTP: Year (type: Member, dimension: Year)
Attached to Form: Run on Save

Option 1: "Use Form Members" = YES
  → Entity RTP is auto-filled from the form's Page/POV Entity
  → Year RTP is auto-filled from the form's POV Year
  → No popup dialog — seamless experience

Option 2: "Use Form Members" = NO  
  → User sees a popup asking for Entity and Year
  → User manually selects → rule runs

Option 3: "Hide Prompt" = YES
  → RTP dialog is hidden, values come from form context
  → Cleanest user experience
```

## 11.2 RTP Type Reference

| RTP Type | User Input | Example |
|----------|-----------|---------|
| **Member** | Select member from dimension | Entity: Hotel India |
| **String** | Type free text | Comment: "Adjusted for season" |
| **Number** | Type a number | Growth Rate: 10 |
| **Date** | Select date | Start Date: 01-Jan-2026 |
| **Member Range** | Select start and end member | From: Jan, To: Jun |
| **Smart List** | Select from dropdown | Status: Approved |
| **Cross Dimension** | Select member from multiple dims | Account, Entity pair |

# SECTION 12: VALIDATION RULES

---

## 12.1 What Are Validation Rules—

Validation rules run on form Save to check data integrity. They can display warnings or errors.

## 12.2 Validation Rule Components

```
IF [condition] THEN [action]

Conditions:
  - Cell value > threshold
  - Cell value < threshold
  - Cell value = specific value
  - Cell is #Missing
  - Cross-cell comparison

Actions:
  - Show Warning (yellow — allows save)
  - Show Error (red — blocks save)
  - Set cell color
  - Set cell text message
```

## 12.3 Examples

```
Rule 1: "Revenue Cannot Be Negative"
  IF [Revenue] < 0
  THEN Error: "Revenue must be a positive number"
  → Blocks save if user enters negative revenue

Rule 2: "Expense Exceeds Budget Warning"
  IF [Expense Actual] > [Expense Budget] * 1.10
  THEN Warning: "Expense is >10% over budget. Please verify."
  → Shows warning but allows save

Rule 3: "Mandatory Entry"
  IF [Revenue] IS #Missing AND [Entity] IS Level 0
  THEN Error: "Revenue must be entered for all operating entities"
  → Forces revenue entry for leaf entities

Rule 4: "Cross-Cell Check"
  IF [Occupancy Rate] > 100
  THEN Error: "Occupancy Rate cannot exceed 100%"
  → Prevents invalid percentage entry
```

# SECTION 15: FORM PERFORMANCE

---

## 15.1 Performance Best Practices

| Practice | Why |
|----------|-----|
| **Limit rows to < 200** | Large grids are slow to render and confuse users |
| **Limit columns to < 30** | Wide forms are hard to read and slow |
| **Use Suppress Missing Rows** | Skip empty rows (for reporting forms) |
| **Use Suppress Missing Blocks** | Avoids loading blocks with no data |
| **Minimize Dynamic Calc members in grid** | Each Dynamic Calc cell computes on retrieval |
| **Avoid cross-dim references in member formulas on form** | Cross-dim lookups in Dynamic Calc slow retrieval |
| **Use separate forms for entry vs reporting** | Entry forms: few rows, no suppression. Reporting forms: many rows, suppression on |
| **Avoid nested dimensions on both rows AND columns** | Cross-product explosion: 50 entities × 500 accounts on rows × 12 months = 300,000 cells |
| **Use Composite forms instead of one giant form** | Split complex views into focused grids |

## 15.2 Common Performance Problems

```
Problem 1: Form takes 30+ seconds to open
  Cause: 500 accounts on rows × 12 months × 3 scenarios on columns = 18,000 cells
  Fix: Reduce to 50 key accounts + use separate detail forms

Problem 2: Form shows all #Missing
  Cause: Suppress Missing = OFF with no data entered
  Fix: Load sample data or turn off suppression for entry forms

Problem 3: Form save takes 60 seconds
  Cause: 5 business rules set to "Run on Save" 
  Fix: Consolidate rules into one optimized rule set

Problem 4: Dynamic Calc members show stale values
  Cause: Dynamic Calc member has complex cross-dim formula
  Fix: Simplify formula or convert to Stored + business rule
```

# SECTION 18: INTERVIEW QUESTIONS

---

**Q1: What are the 4 layout areas of a form—**
> POV (Point of View), Pages, Rows, and Columns. POV provides fixed context. Pages allow switching between members. Rows and Columns display all selected members in the data grid.

**Q2: What is the difference between Suppress Missing Rows and Suppress Missing Blocks—**
> Suppress Missing Rows hides rows in the displayed grid where ALL cells are #Missing. Suppress Missing Blocks prevents Essbase from loading blocks that have no data at all, improving retrieval performance. Suppress Missing Blocks is an optimization at the Essbase level; Suppress Missing Rows is a display-level filter.

**Q3: When should you NOT suppress missing data on a form—**
> On data ENTRY forms where users need to enter data for new intersections. If all rows are #Missing (new entity with no data) and suppression is on, the user sees an empty form and cannot enter data.

**Q4: What is a Composite Form—**
> A Composite Form displays 2-4 grids on one screen. Grids can connect to different plan types (BSO and ASO). Dimensions can be shared across grids (synchronized POV) or independent per grid.

**Q5: Explain how Runtime Prompts work with forms.**
> When a business rule with RTPs is attached to a form, you can set "Use Form Members" to auto-fill RTP values from the form's current POV and Page context, eliminating the RTP dialog popup. Alternatively, "Hide Prompt" hides the dialog entirely.

**Q6: What is Smart Push on form save—**
> Smart Push copies data from one plan type to another (typically BSO to ASO) when a form is saved. It can push "Changed Data Only" for speed or "All Data" for completeness. This keeps reporting cubes in sync with input cubes.

**Q7: How would you design a form for a brand new entity with no historical data—**
> Suppress Missing Data = OFF (so the grid displays even with all #Missing). Read-Only Dynamic Calc = YES. Enable Spreading = YES for easy bulk entry. Pre-populate with seed data using a "Run on Load" business rule that copies baseline from a template entity.

**Q8: What is the maximum number of grids in a Composite Form—**
> Up to 4 grids can be placed on a single Composite Form.
