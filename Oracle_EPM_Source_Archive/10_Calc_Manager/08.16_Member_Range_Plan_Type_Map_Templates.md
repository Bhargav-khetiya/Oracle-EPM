# 08.16 Member Range & Plan Type Map Templates — Exhaustive Deep Dive

> **Module:** 08_Calculation_Manager  
> **Topic:** 16 — Member Range and Plan Type Map Templates  
> **Target Audience:** Administrator / Architect / Developer  

---

## Introduction

While Condition, Loop, and Formula are flow-control building blocks, **Member Range** and **Plan Type Map** are scope-control and data-movement templates. Member Range defines the exact slice of the database your rule operates on. Plan Type Map moves data between different cubes (plan types) within the same application.

---

# PART 1: THE MEMBER RANGE TEMPLATE

---

## 1. What is the Member Range Template—

The Member Range template generates a `FIX` statement in the compiled script. It defines which specific members (and therefore which Essbase data blocks) should be included in the calculation scope.

**Key Distinction:** While a Loop generates *sequential* FIX blocks (one per member), a Member Range generates a *single* FIX block containing all selected members.

### Where to Find It
- **Graphical Designer:** New Objects palette → drag **Member Range** onto the canvas
- **Script Mode:** Type `FIX(...) ENDFIX` directly

---

## 2. Member Range Properties Dialog — Every Field

| Property | Description | Options / Values | Default |
|----------|-------------|------------------|---------|
| **Range Name** | Display label on canvas | Free text (e.g., `Fix_Budget_FY24`) | `MemberRange1` |
| **Dimension** | Each row represents one dimension | Auto-populated from the cube's outline | All dimensions listed |
| **Member Selection** | How to pick members for this dimension | `Specific Members`, `Function`, `Variable`, `All` | `All` (no restriction) |
| **Members** | The specific member(s) selected | Member selector — pick one or more | (empty = no FIX on this dim) |
| **Function** | A member function for dynamic selection | See function table below | (none) |
| **Variable** | A Runtime Prompt, Substitution Variable, or Global/Local Variable | Variable selector | (none) |

### Key Rule: Only dimensions with explicit member selections appear in the generated FIX statement. Dimensions left as "All" are NOT included in the FIX.

---

## 3. Member Selection Methods — All Options

### Method 1: Specific Members
Manually select one or more members from the member selector dialog.

**Example:** Selecting `Budget` from the Scenario dimension and `FY24` from the Year dimension.

**Generated Script:**
```essbase
FIX("Budget", "FY24")
    /* content */
ENDFIX
```

**Member Selector Dialog Options:**
| Feature | Description |
|---------|-------------|
| Search | Type-ahead search for member names |
| Tree Navigation | Expand/collapse hierarchy to find members |
| Multi-Select | Hold Ctrl/Shift to select multiple members |
| Select by Level | Select all members at a specific level |
| Select by Generation | Select all members at a specific generation |
| Show Aliases | Toggle between member names and alias names |
| Filter by Plan Type | Show only members enabled for specific cubes |

### Method 2: Function-Based Selection
Use an `@` function to dynamically select members at runtime.

**All Available Functions for Member Range:**

| Function | Syntax | What It Returns | Example | Generated FIX |
|----------|--------|-----------------|---------|---------------|
| `@CHILDREN` | `@CHILDREN("parent")` | Immediate children only | `@CHILDREN("Total_Entity")` | `FIX(@CHILDREN("Total_Entity"))` |
| `@DESCENDANTS` | `@DESCENDANTS("parent")` | All descendants at all levels | `@DESCENDANTS("Total_Entity")` | `FIX(@DESCENDANTS("Total_Entity"))` |
| `@IDESCENDANTS` | `@IDESCENDANTS("parent")` | All descendants + the parent itself | `@IDESCENDANTS("Q1")` | `FIX(@IDESCENDANTS("Q1"))` |
| `@RELATIVE` | `@RELATIVE("parent", level)` | Descendants at a specific level | `@RELATIVE("Total_Entity", 0)` | `FIX(@RELATIVE("Total_Entity", 0))` |
| `@SIBLINGS` | `@SIBLINGS("member")` | Members sharing the same parent (excluding self) | `@SIBLINGS("East")` | `FIX(@SIBLINGS("East"))` |
| `@ISIBLINGS` | `@ISIBLINGS("member")` | Siblings + self | `@ISIBLINGS("East")` | `FIX(@ISIBLINGS("East"))` |
| `@ANCESTORS` | `@ANCESTORS("member")` | All ancestors up to root | `@ANCESTORS("P_100")` | `FIX(@ANCESTORS("P_100"))` |
| `@UDA` | `@UDA("dim", "uda_value")` | All members with a specific UDA | `@UDA("Entity", "Allocatable")` | `FIX(@UDA("Entity", "Allocatable"))` |
| `@ATTRIBUTE` | `@ATTRIBUTE("attr_dim", "value")` | Members with a specific attribute value | `@ATTRIBUTE("Region_Attr", "EMEA")` | `FIX(@ATTRIBUTE("Region_Attr", "EMEA"))` |
| `@LIST` | `@LIST("m1", "m2", "m3")` | Explicit list of members | `@LIST("Jan", "Feb", "Mar")` | `FIX(@LIST("Jan", "Feb", "Mar"))` |
| `@REMOVE` | `@REMOVE(set1, set2)` | Set1 minus Set2 | `@REMOVE(@CHILDREN("Q1"), "Mar")` | `FIX(@REMOVE(@CHILDREN("Q1"), "Mar"))` |
| `@MERGE` | `@MERGE(set1, set2)` | Union of Set1 and Set2 | `@MERGE(@CHILDREN("Q1"), @CHILDREN("Q2"))` | Combines both sets |

### Level vs Generation — Critical Difference

| Concept | Numbering | Direction | Example (3-level hierarchy) |
|---------|-----------|-----------|----------------------------|
| **Level** | Starts at **0** at the **bottom** | Bottom → Up | L0 = Leaf, L1 = Mid, L2 = Top |
| **Generation** | Starts at **1** at the **top** | Top → Down | G1 = Top, G2 = Mid, G3 = Leaf |

**Example Hierarchy:**
```
Total_Entity (Level 2, Gen 1)
├── North_America (Level 1, Gen 2)
│   ├── US (Level 0, Gen 3)
│   └── Canada (Level 0, Gen 3)
└── Europe (Level 1, Gen 2)
    ├── UK (Level 0, Gen 3)
    └── Germany (Level 0, Gen 3)
```

- `@RELATIVE("Total_Entity", 0)` → US, Canada, UK, Germany (Level 0 = bottom)
- `@RELATIVE("Total_Entity", 1)` → North_America, Europe (Level 1 = one up from bottom)
- `@CHILDREN("Total_Entity")` → North_America, Europe (immediate children only)
- `@DESCENDANTS("Total_Entity")` → North_America, US, Canada, Europe, UK, Germany (ALL below)

### Method 3: Variable-Based Selection
Use a Runtime Prompt (RTP), Substitution Variable, or Global/Local variable.

**Generated Script:**
```essbase
FIX({RTP_Entity}, &CurrYear, {var_Scenario})
    /* content */
ENDFIX
```

| Variable Type | Syntax in Script | Set By | Example |
|--------------|-----------------|--------|---------|
| Runtime Prompt (RTP) | `{RTP_VarName}` | End user at rule execution | `{RTP_Entity}` |
| Substitution Variable | `&VarName` | Administrator in Application Settings | `&CurrYear` |
| Global Variable | `{var_Name}` | Developer in Calc Manager | `{var_Scenario}` |

### Method 4: Combined/Nested Functions
You can combine functions for complex member selections:

```essbase
FIX(@REMOVE(@RELATIVE("Total_Entity", 0), @UDA("Entity", "Inactive")))
```
This selects all Level 0 entities EXCEPT those tagged with the "Inactive" UDA.

---

## 4. Multiple Dimensions in a Single Member Range

You can set member selections on multiple dimensions simultaneously within a single Member Range object. All selections are combined into one FIX statement.

**Example Configuration:**
| Dimension | Selection |
|-----------|-----------|
| Scenario | `Budget` |
| Version | `Working` |
| Year | `&CurrYear` (Substitution Variable) |
| Entity | `@RELATIVE("Total_Entity", 0)` |
| Period | `@CHILDREN("Q1")` |
| Account | (All — no restriction) |
| Product | (All — no restriction) |

**Generated Script:**
```essbase
FIX("Budget", "Working", &CurrYear, @RELATIVE("Total_Entity", 0), @CHILDREN("Q1"))
    /* content */
ENDFIX
```

> **Best Practice: Dimension Order in FIX**
> While Essbase doesn't require a specific order, best practice is:
> 1. **Sparse dimensions first** (Entity, Product, Custom dims)
> 2. **Dense dimensions last** (Account, Period)
> 
> Why— Essbase uses sparse dimensions to identify which blocks to load. Putting sparse dims first helps the engine's block-scanning algorithm find the right blocks faster.

---

## 5. Nested Member Ranges

You can drag a Member Range inside another Member Range to create nested FIX statements.

**Generated Script:**
```essbase
FIX("Budget", "Working")
    FIX(@RELATIVE("Total_Entity", 0))
        /* inner logic */
    ENDFIX
ENDFIX
```

> **When to nest vs. combine:**
> - **Combine** (single FIX) when all dimensions are used for the same scope
> - **Nest** when you need different logic at different scope levels (e.g., outer FIX for scenario, inner FIX loops through entities with per-entity calculations)

---

## 6. Member Range Best Practices

| # | Best Practice | Why |
|---|--------------|-----|
| 1 | **Always FIX on Sparse dimensions** | Sparse dims define blocks. FIX on sparse = fewer blocks to process |
| 2 | **Avoid FIX on Dense dimensions when possible** | FIX on dense members still loads the entire block — no performance benefit |
| 3 | **Use `@RELATIVE(parent, 0)` instead of `@DESCENDANTS`** | `@DESCENDANTS` includes upper-level members which you rarely need to write to |
| 4 | **Use `@UDA` for dynamic scoping** | When metadata changes frequently, UDA-based FIX auto-adapts |
| 5 | **Always include Scenario, Version, Year, and Entity in FIX** | These are almost always sparse — omitting them means processing ALL scenarios/years |
| 6 | **Test generated script before deployment** | Click "Validate" → "View Script" to see exactly what FIX statement is generated |
| 7 | **Use `@REMOVE` to exclude edge cases** | Cleaner than adding Conditions inside the FIX |

---

## 7. Common Errors

| Error | Cause | Fix |
|-------|-------|-----|
| `"No blocks found for FIX statement"` | FIX scope is too narrow — no data exists at the intersection | Verify member names and that data has been loaded |
| `"Member not found: xxx"` | Typo in member name or member doesn't exist in selected Plan Type | Check spelling, check Plan Type assignment |
| `"FIX on dense dimension has no effect"` | You FIXed on a dense member expecting performance gain | Move to a Condition (IF) inside the block, or accept that dense FIX just filters output |
| Rule runs too long | FIX is too wide — missing key sparse dimension constraints | Add Scenario, Version, Year, Entity to the FIX |

# PART 2: THE PLAN TYPE MAP TEMPLATE

---

## 1. What is the Plan Type Map Template—

The Plan Type Map template moves data between different **Plan Types (Cubes)** within the same EPBCS application. Unlike Smart Push (which is real-time and form-triggered), Plan Type Map is batch-oriented and runs as part of a business rule.

### Terminology
- **Plan Type** = **Cube** in Essbase (e.g., `OEP_FS` = Financial Statement, `OEP_WFP` = Workforce, `OEP_CAPEX` = Capital)
- **Source Cube** = Where data is read from
- **Target Cube** = Where data is written to

### Where to Find It
- **Graphical Designer:** New Objects palette → drag **Plan Type Map** onto the canvas
- **Script Mode:** Generates `PLANTYPE_MAP` commands

---

## 2. Plan Type Map Wizard — Every Step, Every Field

### Step 1: Source and Target Plan Types

| Field | Description | Options |
|-------|-------------|---------|
| **Source Plan Type** | The cube to read data FROM | Dropdown: All plan types in the application (e.g., OEP_FS, OEP_WFP, OEP_CAPEX, Custom cubes) |
| **Target Plan Type** | The cube to write data TO | Dropdown: All plan types in the application |

> **Note:** Source and Target cannot be the same cube.

### Step 2: Data Mapping (Dimension Mapping)

For each dimension that exists in BOTH the source and target cubes, you specify how members map:

| Field | Description | Options |
|-------|-------------|---------|
| **Dimension** | The dimension name (auto-populated) | Read-only |
| **Mapping Type** | How members translate between cubes | `Same Name`, `Specific Member`, `Function`, `Variable` |
| **Source Member** | The member(s) to read from in the source cube | Member selector |
| **Target Member** | The member(s) to write to in the target cube | Member selector |

**Mapping Type Details:**

| Mapping Type | Description | Use Case |
|-------------|-------------|----------|
| `Same Name` | Source member name = Target member name (e.g., `"Jan"` → `"Jan"`) | Shared dimensions like Period, Year |
| `Specific Member` | Map from one member to a different member | `"WFP_Salary"` → `"FS_Salary_Expense"` |
| `Function` | Use `@CHILDREN`, `@DESCENDANTS`, etc. | Map all children of a source parent |
| `Variable` | Use RTP/Substitution variable | Dynamic mapping at runtime |

### Step 3: Options

| Field | Description | Options | Default |
|-------|-------------|---------|---------|
| **Clear Target Before Map** | Delete existing data in target before copying | `Yes` / `No` | `No` |
| **Aggregate Source Before Map** | Run aggregation on source data before reading | `Yes` / `No` | `No` |
| **Merge vs Replace** | If target already has data, merge or replace— | `Merge` / `Replace` | `Merge` |

---

## 3. Smart Push vs Plan Type Map — Complete Comparison

| Feature | Smart Push | Plan Type Map |
|---------|-----------|---------------|
| **Trigger** | Automatic on form save | Manual (run as business rule) |
| **Scope** | Only data changed on the form | Entire mapped scope (batch) |
| **Direction** | Source → Target (one-way) | Source → Target (one-way) |
| **Performance** | Fast (incremental) | Slower (batch — reads all blocks in scope) |
| **Where Configured** | Form → Smart Push tab | Calc Manager → Business Rule |
| **Groovy Access** | `operation.grid.getSmartPush()` | Part of a calc script |
| **Use Case** | Real-time sync on user saves | Month-end batch transfers |
| **Dimension Mapping** | Simple (same name mapping) | Complex (different member names) |
| **Can Clear Target** | No | Yes |
| **Can Aggregate Source** | No | Yes |

### When to Use Which

| Scenario | Recommendation |
|----------|---------------|
| User enters Headcount in Workforce cube, needs to see it instantly in Financial cube | **Smart Push** |
| Month-end process copies finalized Actuals from Finance to Reporting cube | **Plan Type Map** |
| Data needs complex member mapping (different names in source vs target) | **Plan Type Map** |
| Need to clear target data before copying | **Plan Type Map** |
| Real-time sync during form data entry | **Smart Push** |
| Batch sync during overnight job | **Plan Type Map** |

---

## 4. Plan Type Map Best Practices

| # | Best Practice | Why |
|---|--------------|-----|
| 1 | Always aggregate source data before mapping if reading upper-level members | Source parents may not be calculated yet |
| 2 | Clear target data before mapping if replacing (not merging) | Prevents stale data in target intersections not covered by source |
| 3 | Map at Level 0 whenever possible | Level 0 data is always stored; upper levels may be Dynamic Calc |
| 4 | Use Smart Push for form-level sync; Plan Type Map for batch-level sync | Right tool for the right job |
| 5 | Test with a small scope first | Map one entity/one period first to verify data integrity before full batch |
| 6 | Document all mappings in a design document | Complex member mappings across cubes are impossible to debug without documentation |

---

## 5. Plan Type Map vs @XREF / @XWRITE

| Feature | Plan Type Map | @XREF | @XWRITE |
|---------|--------------|-------|---------|
| **Direction** | Source → Target (copy) | Read from another cube (no write) | Write to another cube |
| **Data Movement** | Physically copies data | Reads value in-memory (no copy) | Physically writes data |
| **Performance** | Batch — good for large data | Per-cell — slow for large data | Per-cell — slow for large data |
| **Use Case** | Bulk data transfer | Reference a rate from another cube | Push allocation results to another cube |
| **Block Creation** | Creates blocks in target | Does not create blocks | Creates blocks in target |

## 6. Complete Example

### Scenario: Copy Headcount from Workforce Cube to Finance Cube

**Configuration:**
| Step | Setting |
|------|---------|
| Source Plan Type | `OEP_WFP` (Workforce) |
| Target Plan Type | `OEP_FS` (Financial Statements) |
| Account Mapping | `WFP_FTE_Count` → `FS_Headcount` (Specific Member) |
| Entity Mapping | Same Name |
| Period Mapping | Same Name |
| Scenario Mapping | Same Name |
| Version Mapping | Same Name |
| Year Mapping | Same Name |
| Clear Target | Yes |
| Aggregate Source | Yes |

**Generated Script Equivalent:**
```essbase
/* Aggregate source cube first */
SET PLANTYPE "OEP_WFP";
CALC DIM("Entity");

/* Map data */
PLANTYPE_MAP
  SOURCE "OEP_WFP"
  TARGET "OEP_FS"
  MEMBER_MAP("Account", "WFP_FTE_Count", "FS_Headcount")
  CLEAR_TARGET YES;
```

## Interview Questions

### Intermediate
**Q: When would you use a Plan Type Map instead of Smart Push—**
> A: Plan Type Map is used for batch data transfers during scheduled processes (e.g., month-end close), when complex member mapping is needed between cubes (different member names in source vs target), or when you need to clear the target data before copying. Smart Push is for real-time, incremental data sync triggered by form saves.

### Architect
**Q: You have a Workforce cube and a Finance cube. Headcount is entered in Workforce, but the Finance cube needs to use it for salary calculations. The finance team complains that Headcount is always one month behind in their forms. What is wrong and how do you fix it—**
> A: The most likely issue is that the system relies on a nightly Plan Type Map batch job to copy Headcount from Workforce to Finance. This means any changes made during the day won't appear until the next morning. The fix is to add a **Smart Push** on the Workforce data entry form that pushes Headcount data to the Finance cube in real-time when the user saves. The nightly Plan Type Map should still run as a safety net for bulk reconciliation, but Smart Push provides the real-time sync the finance team expects.

### Trick Question
**Q: Can a Plan Type Map move data from a BSO cube to an ASO cube—**
> A: No, not directly via the Plan Type Map template. Plan Type Maps operate between BSO cubes within Planning. To move data from BSO to ASO (Reporting cube), you use **Data Maps** or **Smart Push to Reporting** (a different mechanism configured at the form level or via Groovy). Alternatively, you can use a Groovy script with DataGridDefinitionBuilder to read from BSO and write to ASO.

## Summary

| Template | What It Generates | Primary Purpose | Key Advantage |
|----------|-------------------|-----------------|---------------|
| **Member Range** | `FIX(...) ENDFIX` | Define calculation scope | Block-level scoping = maximum performance |
| **Plan Type Map** | `PLANTYPE_MAP` | Move data between cubes | Complex member mapping + batch processing |

The Member Range is the **most important performance tool** in Calc Manager — a well-scoped FIX can turn a 60-minute rule into a 60-second rule. The Plan Type Map is essential for **multi-cube architectures** where data flows between Workforce, Finance, CapEx, and custom cubes.
