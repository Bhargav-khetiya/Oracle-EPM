## 🏢 Overview

A **Business Rule** is an automated calculation or data manipulation task executed within Oracle EPBCS. Business rules are the backbone of any Planning application — they perform calculations, allocate data, copy data between scenarios, clear data, and automate complex financial logic.

---

## 🎯 Business Purpose

Without business rules, users would need to manually calculate every derived value, allocation, and consolidation. Business rules automate:
- Revenue = Units × Price
- Cost Allocation across departments
- Currency translation
- Data copy (Actuals → Budget baseline)
- Rolling forecasts

---

## 📋 Types of Business Rules

| Type | Language | Use Case | Performance |
|------|----------|----------|-------------|
| **Calc Script** | Essbase native | Standard calculations, allocations, aggregations | Fast for BSO |
| **Groovy** | Java-based | Complex logic, REST API calls, data movement, conditional flows | Flexible |
| **Template** | Graphical | Reusable components (loops, conditions) | Medium |
| **Script** | Direct Essbase | Raw calc script for advanced users | Direct control |

## 📌 Calc Script Fundamentals

### The FIX Statement

The most important concept in calc scripts. `FIX` limits which data cells a calculation operates on — dramatically improving performance.

```
FIX("Budget", "Working", "FY26", "Local")
    "Net Revenue" = "Gross Revenue" - "Discounts";
FIX END
```

**Why FIX matters:**
- Without FIX: Essbase calculates across ALL members of ALL dimensions → millions of unnecessary cells
- With FIX: Essbase calculates only the target intersection → fast and efficient

### FIX Rules
1. FIX can only contain **Sparse** dimension members (Entity, Scenario, Version, Year)
2. You cannot FIX on **Dense** dimensions (Account, Period) — use IF instead
3. FIX statements can be nested
4. Always FIX as narrowly as possible

### Common Calc Script Commands

| Command | Purpose | Example |
|---------|---------|---------|
| `FIX...ENDFIX` | Limit calculation scope | `FIX("Budget") ... ENDFIX` |
| `IF...ENDIF` | Conditional logic | `IF("Jan" > 0) ... ENDIF` |
| `SET AGGMISSG ON/OFF` | Include/exclude missing in aggregation | `SET AGGMISSG OFF;` |
| `SET UPDATECALC ON/OFF` | Recalculate only changed blocks | `SET UPDATECALC ON;` |
| `AGG(dimension)` | Aggregate a dimension | `AGG("Entity");` |
| `CALC DIM(dimension)` | Calculate a dimension | `CALC DIM("Account");` |
| `CALC ALL` | Calculate entire cube | `CALC ALL;` |
| `CLEARDATA` | Remove all data in scope | `CLEARDATA "Budget";` |
| `DATACOPY` | Copy data between members | `DATACOPY "Actual" TO "Budget";` |
| `@RETURN` | Exit the script | `@RETURN;` |

### SET Commands

```
SET UPDATECALC OFF;        /* Recalculate all blocks, not just dirty */
SET CREATEBLOCKONEQ ON;    /* Create blocks for assignment operations */
SET AGGMISSG ON;           /* Treat missing as zero in aggregation */
SET MSG SUMMARY;           /* Show only summary messages in log */
SET LOCKBLOCK OFF;         /* Allow concurrent block access */
```

### 💡 Logic & Purpose
By default, Essbase only calculates blocks that already exist. This is a massive performance optimization. If you write `A = B + C;` and there is no block for that intersection, Essbase ignores it. `SET CREATEBLOCKONEQ ON;` forces the calculation engine to explicitly create a brand new physical data block on the hard drive *if* the right-side equation evaluates to a real number, ensuring data is not lost.

### 🌀 Confusion Resolution
> **Misconception:** "I want to make sure my calc script calculates every single member, so I'm going to put `SET CREATEBLOCKONEQ ON;` at the top of every rule I write just to be safe."
> **Reality:** NEVER do this! `CREATEBLOCKONEQ` is highly dangerous if used globally. If you use it on a formula like `A = 0;` inside a broad `FIX`, it will force Essbase to create millions of physical data blocks containing zeros, instantly bloating your database and destroying performance. It should only be used tightly wrapped around the specific equation that requires block creation.

### 😈 Twisted Interview Question
**Question:** A developer writes a calc script: 
`FIX("Budget", "Working")`
`  "Bonus" = "Salary" * 0.10;`
`ENDFIX`
The script runs in 1 second, but when the user checks the form, the Bonus account is completely blank. They check the logs, and no errors occurred. Why did the script fail to calculate the bonus?
> **Answer:** The "Bonus" intersection was likely empty (`#MISSING`), meaning a physical block did not exist for it yet. Because `SET CREATEBLOCKONEQ ON;` was not used, Essbase skipped the calculation entirely. To fix it, the developer must either add `SET CREATEBLOCKONEQ ON;` before the equation, or use the `DATACOPY` command to seed the block first.

## 📌 Cross-Dimensional References (CrossDim)

Used to reference a value from a DIFFERENT member intersection within a formula.

```
/* Syntax */
"TargetMember"->member1->member2;

/* Example: Copy Jan Actual to Jan Budget */
FIX("Budget", "Working", "FY26")
    "Revenue" = "Revenue"->"Actual"->"Final";
ENDFIX
```

### Advanced CrossDim Patterns

```
/* Percentage allocation */
FIX("Budget", "Working", "FY26")
    "Marketing Expense" = "Total Revenue" * "Marketing %" -> "Saved Assumption";
ENDFIX

/* Prior year reference */
FIX("Budget", "Working", "FY27")
    "Revenue" = "Revenue" -> "Actual" -> "FY26" * (1 + "Growth Rate");
ENDFIX
```

## 📌 Runtime Prompts (RTP)

Runtime Prompts are pop-up dialogs that ask the user for input before a rule runs.

### RTP Variable Types

| Type | Description | Example |
|------|-------------|---------|
| **Member** | User selects dimension member(s) | Select Entity |
| **String** | User types free text | Enter comment |
| **Number** | User enters a numeric value | Enter growth rate |
| **Date** | User picks a date | Select start date |
| **Checkbox** | User toggles yes/no | Include adjustments? |
| **Smart List** | User picks from dropdown | Select allocation method |

### RTP Syntax in Calc Scripts

```
/* Declare RTP at the top */
/* Runtime Prompt: {RTP_Entity} Type: Member Dimension: Entity */

FIX({RTP_Entity}, "Budget", "Working", "FY26")
    CALC DIM("Account");
ENDFIX
```

### RTP in Groovy Rules

```groovy
// Get runtime prompt values
String selectedEntity = rtps.RTP_Entity.getEssbaseMember()
String selectedYear = rtps.RTP_Year.getEssbaseMember()

// Use in operations
operation.grid.pov = ['Entity': selectedEntity, 'Year': selectedYear]
```

## 🏗️ Rule Architecture & Design Patterns

### Pattern 1: Data Copy (Seed Budget from Actuals)

```
SET CREATEBLOCKONEQ ON;
FIX("Budget", "Working", "FY27", @RELATIVE("Entity", 0))
    DATACOPY "Actual"->"Final"->"FY26" TO "Budget"->"Working"->"FY27";
ENDFIX
```

### Pattern 2: Allocation (Distribute Total to Children)

```
FIX("Budget", "Working", "FY26")
    "Marketing Expense"(
        @RELATIVE("Department", 0)  /* Level 0 departments */
    ) = "Total Marketing" * 
        "Headcount" / "Headcount"->"All Departments";
ENDFIX
```

### Pattern 3: Currency Translation

```
FIX("Budget", "Working", "FY26", @RELATIVE("Entity", 0))
    /* Revenue uses Average rate */
    FIX(@ATTRIBUTE("Account", "Exchange_Rate", "Average"))
        "USD" = "Local" * "Avg Rate"->"Exchange Rates";
    ENDFIX
    
    /* Balance Sheet uses Ending rate */
    FIX(@ATTRIBUTE("Account", "Exchange_Rate", "Ending"))
        "USD" = "Local" * "End Rate"->"Exchange Rates";
    ENDFIX
ENDFIX
```

### Pattern 4: Rolling Forecast

```
FIX("Forecast", "Working", "FY26")
    /* Months already passed → copy Actuals */
    FIX(@RANGE("Period", "Jan", &CurrentMonth))
        DATACOPY "Actual"->"Final" TO "Forecast"->"Working";
    ENDFIX
    
    /* Future months → keep forecast */
    /* No action needed */
ENDFIX
```

### Pattern 5: Clear and Calculate

```
/* Always clear before recalculating to avoid stale data */
FIX("Budget", "Working", "FY26")
    CLEARDATA "Calculated_Revenue";
ENDFIX

FIX("Budget", "Working", "FY26")
    "Calculated_Revenue" = "Units" * "Price";
ENDFIX
```

## 📌 Rule Sets

A **Rule Set** is a container that executes multiple business rules in a defined sequence.

```
Rule Set: "Monthly Close Process"
├── Rule 1: Clear Prior Calculations
├── Rule 2: Load Exchange Rates  
├── Rule 3: Calculate Revenue
├── Rule 4: Allocate Overhead
├── Rule 5: Currency Translation
├── Rule 6: Aggregate Entity
└── Rule 7: Calculate Variances
```

### Rule Set Properties

| Property | Description |
|----------|-------------|
| **Sequential** | Rules run one after another (default) |
| **Parallel** | Rules run simultaneously (for independent rules) |
| **Stop on Error** | Halt if any rule fails |
| **Runtime Prompts** | Shared across all rules in the set |

## 📌 Deployment & Validation

### Deployment Steps
1. Design rule in Calculation Manager
2. **Validate** — checks syntax errors
3. **Deploy** — pushes rule to the Planning application
4. Test with a small FIX scope first
5. Assign to forms or task lists

### Validation vs Deployment

| Action | What It Does |
|--------|-------------|
| **Validate** | Checks syntax, member names, dimensions — does NOT execute |
| **Deploy** | Makes the rule available in Planning — does NOT execute |
| **Launch** | Actually RUNS the rule against data |

## ⚡ Performance Optimization

| Technique | Impact |
|-----------|--------|
| Use narrow FIX statements | ⬆️ High — reduces cells calculated |
| Use `SET UPDATECALC ON` | ⬆️ High — skips unchanged blocks |
| Avoid `CALC ALL` | ⬆️ High — calculates EVERYTHING |
| Use `SET AGGMISSG OFF` | ⬆️ Medium — skips missing values |
| Split large rules into smaller ones | ⬆️ Medium — easier debugging |
| Use bottom-up calculation order | ⬆️ Medium — natural aggregation |

---

## 📌 Common Mistakes

| Mistake | Impact | Fix |
|---------|--------|-----|
| FIX on Dense dimension | Rule fails or ignores | Use IF for Dense dims |
| Missing `SET CREATEBLOCKONEQ ON` | Data silently lost | Always include for assignments |
| Not clearing before recalculating | Stale data remains | Clear target before calc |
| Using `CALC ALL` in production | Extremely slow | Use targeted FIX + AGG |
| Hardcoding member names | Breaks when metadata changes | Use substitution variables |
| Not testing with realistic data | Slow in production | Test with production volume |

## 🔧 Troubleshooting

| Issue | Diagnosis | Solution |
|-------|-----------|----------|
| Rule takes too long | Check FIX scope — too broad | Narrow the FIX statement |
| Data not appearing after rule | Missing blocks | Add `SET CREATEBLOCKONEQ ON` |
| Rule shows validation error | Member name changed | Check dimension outline |
| Rule calculates wrong values | Cross-dim reference wrong | Test formula in Smart View first |
| Rule set stops mid-way | One rule errored | Check individual rule logs |

## 🎓 Interview Questions

**Q: What is the difference between a Business Rule and a Member Formula?**
> A: A Member Formula is permanently attached to a specific dimension member and runs automatically during aggregation/retrieval. A Business Rule is an on-demand calculation that runs when explicitly launched (from a form, task list, or schedule).

**Q: Why do we use FIX statements?**
> A: FIX limits the calculation scope to specific sparse member combinations, dramatically reducing the number of cells Essbase must process. Without FIX, a rule would calculate across every possible combination — potentially millions of unnecessary intersections.

**Q: Can you FIX on a Dense dimension like Account?**
> A: No. FIX only works on Sparse dimensions. For Dense dimensions, use IF statements inside the FIX block.

**Q: What happens if you forget SET CREATEBLOCKONEQ ON?**
> A: If your rule assigns values to sparse combinations that don't have existing data blocks, the blocks won't be created and the data will be silently lost. This is one of the most common bugs in EPBCS implementations.

**Q: How do you handle a rolling forecast calculation?**
> A: Use substitution variables like `&CurrentMonth` with @RANGE to split periods into "actual months" (copy from Actuals) and "forecast months" (keep forecast values). This ensures the forecast always blends YTD actuals with future projections.

**Q: What is a Rule Set and when would you use one?**
> A: A Rule Set is a container that executes multiple business rules in sequence (or parallel). Use it for complex multi-step processes like month-end close, where you need to clear data → load rates → calculate → allocate → translate → aggregate in a specific order.

## 🎯 Hands-On Exercises — Business Rules

### Exercise 1: Your First Business Rule
```
1. Open Calc Manager → right-click FinPlan → New Rule → "BR_Test_Simple"
2. Add Script component → type:
   FIX("Budget", "Working", "FY27", "E10001", "Jan")
       "Revenue" = 100000;
   ENDFIX
3. Validate → Deploy → Launch
4. Open form → verify Revenue for E10001/Jan/Budget = 100,000
```

### Exercise 2: Revenue = Units × Price
```
1. Create accounts: "Units" (Non-Currency, Store) and "Price" (Non-Currency, Store)
2. Enter data: Units=500, Price=2000 for Jan-Mar
3. Create rule "BR_Calculate_Revenue":
   FIX("Budget", "Working", &BudgetYear, @RELATIVE("Entity", 0))
       "Revenue" = "Units" * "Price";
   ENDFIX
4. Run → verify Revenue = 1,000,000 for each month
5. Change Price to 2500 → rerun → Revenue = 1,250,000
```

### Exercise 3: DATACOPY — Seed Budget from Actuals
```
1. Create rule "BR_Seed_Budget":
   SET CREATEBLOCKONEQ ON;
   FIX(@RELATIVE("Entity", 0), @RELATIVE("Account", 0))
       DATACOPY "Actual"->"Final"->&PriorYear TO "Budget"->"Working"->&BudgetYear;
   ENDFIX
2. Enter Actual data for FY26
3. Run rule → verify Budget FY27 = copy of Actual FY26
4. IMPORTANT: Remove SET CREATEBLOCKONEQ → rerun → budget is empty
5. Add it back → rerun → data appears
6. Document: "CREATEBLOCKONEQ is CRITICAL for DATACOPY to new intersections"
```

### Exercise 4: Allocation (Distribute Overhead)
```
1. Create overhead account: "Corporate_Overhead" = 10,000,000 at Corporate entity
2. Create "Headcount" account with values per entity: E10001=100, E10002=50, E10003=50
3. Create rule "BR_Allocate_Overhead":
   FIX("Budget", "Working", &BudgetYear, @RELATIVE("Entity", 0))
       "Allocated_Overhead" = "Corporate_Overhead"->"Corporate" *
           "Headcount" / "Headcount"->"Total_Company";
   ENDFIX
4. Run → verify:
   E10001 gets 50% (5,000,000 — 100/200 headcount)
   E10002 gets 25% (2,500,000)
   E10003 gets 25% (2,500,000)
5. Change E10001 headcount to 200 → rerun → allocation shifts
```

### Exercise 5: Currency Translation
```
1. Enable Multi-Currency in your application
2. Create exchange rate members: "USD_Rate", "EUR_Rate"
3. Enter rates: USD_Rate = 83.50 (INR per USD), EUR_Rate = 90.00
4. Create rule "BR_Currency_Translation":
   FIX("Budget", "Working", &BudgetYear, @RELATIVE("Entity", 0))
       "Revenue"->"USD" = "Revenue"->"Local" / "USD_Rate"->"Exchange_Rates";
       "Revenue"->"EUR" = "Revenue"->"Local" / "EUR_Rate"->"Exchange_Rates";
   ENDFIX
5. Enter Revenue in Local (INR) = 8,350,000
6. Run → verify USD Revenue = 100,000 (8,350,000 / 83.50)
```

### Exercise 6: Clear and Recalculate Pattern
```
1. Create rule "BR_Clear_And_Calc":
   SET CREATEBLOCKONEQ ON;
   FIX("Budget", "Working", &BudgetYear, @RELATIVE("Entity", 0))
       /* Step 1: Clear old calculated values */
       CLEARDATA "Revenue";
       
       /* Step 2: Recalculate */
       "Revenue" = "Units" * "Price";
       
       /* Step 3: Aggregate */
       AGG("Entity");
   ENDFIX
2. Run → verify: Revenue is freshly calculated, parent entities aggregated
3. Why clear first? To avoid stale data if members were removed
```

### Exercise 7: Conditional Business Rule
```
1. Create rule "BR_Conditional_Calc":
   FIX("Budget", "Working", &BudgetYear, @RELATIVE("Entity", 0))
       IF("Revenue" > 1000000)
           "Bonus_Pool" = "Revenue" * 0.05;  /* 5% bonus if revenue > 1M */
       ELSEIF("Revenue" > 500000)
           "Bonus_Pool" = "Revenue" * 0.03;  /* 3% if 500K-1M */
       ELSE
           "Bonus_Pool" = 0;  /* No bonus if < 500K */
       ENDIF
   ENDFIX
2. Enter different Revenue values for different entities
3. Run → verify correct bonus tier applied to each entity
```

### Exercise 8: Runtime Prompt (RTP) Rule
```
1. Create rule with Runtime Prompt:
   - Variable: {RTP_Entity} → Type: Member, Dimension: Entity
   - Variable: {RTP_Scenario} → Type: Member, Dimension: Scenario
2. Script:
   FIX({RTP_Scenario}, "Working", &BudgetYear, {RTP_Entity})
       "Revenue" = "Units" * "Price";
   ENDFIX
3. Deploy → launch from form → user selects Entity and Scenario
4. Run for different entities → verify each calculates independently
5. Map RTPs to form: Edit form → Business Rules → Map RTP to form POV
```

### Exercise 9: Rolling Forecast Rule
```
1. Create rule "BR_Rolling_Forecast":
   FIX("Forecast", "Working", &CurrentYear, @RELATIVE("Entity", 0))
       /* Copy actuals for past months */
       FIX(@RANGE("Period", "Jan", &CurrentMonth))
           DATACOPY "Actual"->"Final" TO "Forecast"->"Working";
       ENDFIX
       
       /* Apply growth for future months */
       FIX(@RANGE("Period", @NEXTSIBLING(&CurrentMonth), "Dec"))
           "Revenue" = "Revenue"->@PRIOR("Period") * (1 + "Growth_Rate"->"Saved Assumption");
       ENDFIX
   ENDFIX
2. Set &CurrentMonth = Jun
3. Run → verify Jan-Jun = Actual, Jul-Dec = forecast with growth
4. Update &CurrentMonth = Jul → rerun → Jul also becomes Actual
```

### Exercise 10: Complete Rule Set
```
1. Create 5 individual rules:
   - BR_Clear_Budget (CLEARDATA)
   - BR_Seed_From_Actuals (DATACOPY)
   - BR_Apply_Growth (Revenue × growth rate)
   - BR_Calculate_Expenses (salary + rent + utilities)
   - BR_Calculate_PnL (Revenue - Expenses = Profit)
2. Create Rule Set "RS_Annual_Budget":
   - Add all 5 in sequence
   - Share RTP: Entity across all rules
   - Stop on Error = Yes
3. Deploy → launch → runs all 5 automatically
4. Verify: Complete budget generated from actuals + growth
5. Monitor in Job Console → note total duration
```
