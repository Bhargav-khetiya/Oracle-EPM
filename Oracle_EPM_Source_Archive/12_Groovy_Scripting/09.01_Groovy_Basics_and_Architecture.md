# SECTION 1: WHY GROOVY EXISTS

---

## The Limitation of Calc Scripts

Calc scripts can only do math on data inside the cube. They cannot:

```
❌ Read which cells the user just edited on a form
❌ Show a custom error message to the user
❌ Send an email notification
❌ Call an external API (e.g., fetch live exchange rates)
❌ Validate data types (e.g., "this cell must be a positive number")
❌ Create/delete members dynamically
❌ Read metadata (e.g., "what Smart List is on this cell—)
❌ Conditionally run different rules based on user's form context
```

## What Groovy Can Do

```
✅ Read the exact cells the user edited on a form (operation.grid)
✅ Throw error messages that stop a save ("Budget must be positive!")
✅ Build dynamic calc scripts based on runtime context
✅ Make REST API calls to external systems
✅ Send email notifications
✅ Read/write data across plan types
✅ Access metadata (member properties, Smart List values)
✅ Loop through members and make conditional decisions
✅ Generate calc scripts that are perfectly optimized for the user's POV
```

## The Mental Model

```
Calc Script = A calculator (does math on numbers in the cube)
Groovy      = A programmer (reads the user's screen, makes decisions,
               builds calc scripts, talks to external systems)

Best Practice:
  Groovy READS the context → BUILDS a calc script → SENDS it to Essbase
  Essbase EXECUTES the math (because Essbase is the math engine)
  
  DON'T use Groovy to loop through 100,000 cells doing math
  DO use Groovy to generate the perfect FIX statement dynamically
```

## You Need to Know This Much Java (And No More)

Groovy is based on Java. Here are the 10 Java concepts you need:

### 1. Variables

```groovy
// Groovy is like Java but simpler
String name = "Hotel India"       // Text
int rooms = 200                   // Whole number
double rate = 3200.50             // Decimal number
boolean isApproved = true         // True or False

// Groovy shortcut: you can skip the type
def name2 = "Hotel London"       // Groovy figures out the type
```

### 2. If/Else

```groovy
if (occupancy > 80) {
    println "High season - raise rates!"
} else if (occupancy > 50) {
    println "Normal season"
} else {
    println "Low season - run promotions!"
}
```

### 3. Loops

```groovy
// Loop through a list
def hotels = ["Hotel India", "Hotel London", "Hotel NYC"]
for (hotel in hotels) {
    println "Processing: ${hotel}"
}

// Loop with index
for (int i = 0; i < 12; i++) {
    println "Month ${i + 1}"
}
```

### 4. Lists and Maps

```groovy
// List (array)
def months = ["Jan", "Feb", "Mar", "Apr"]
println months[0]    // "Jan"
println months.size() // 4

// Map (dictionary/key-value pairs)
def rates = ["INR": 1, "USD": 83.5, "GBP": 105.2]
println rates["USD"]  // 83.5
```

### 5. String Interpolation

```groovy
def entity = "Hotel India"
def year = "FY26"

// Use ${} to embed variables in strings
String script = "FIX(\"${entity}\", \"${year}\")"
println script  // FIX("Hotel India", "FY26")
```

### 6. Try/Catch (Error Handling)

```groovy
try {
    def result = revenue / expense
} catch (Exception e) {
    println "Error: ${e.message}"
}
```

### 7. Methods (Functions)

```groovy
def calculateRevPAR(double roomRevenue, int roomsAvailable) {
    if (roomsAvailable == 0) return 0
    return roomRevenue / roomsAvailable
}

def revpar = calculateRevPAR(12000000, 6200)
println "RevPAR: ${revpar}"  // RevPAR: 1935.48...
```

That's it. You now know enough Java/Groovy syntax to write EPM rules.

# SECTION 3: THE EPM GROOVY API OBJECT MODEL

---

## The Key Objects

```
Oracle provides these objects inside the Groovy sandbox:

operation     → The current rule execution context
  .grid       → The data grid (form) the user is working on
  .application → The EPBCS application
  .cube       → The current plan type (cube)

rtps          → Runtime Prompts (user-provided values)
  .RTP_Entity → Whatever the user selected

rule          → The current rule object
  .execute()  → Run an Essbase calc script

messageBundle → Display messages to users

DataGridBuilder → Build a data grid to read/write data
```

### Object Hierarchy Diagram

```
operation
├── .application
│   ├── .name                    → "HotelBudget"
│   └── .getSubstitutionVariable("CurrYear") → "FY26"
│
├── .grid
│   ├── .pov                     → [Scenario, Version, Year, Entity]
│   ├── .rows                    → List of row headers
│   ├── .columns                 → List of column headers
│   ├── .dataCellIterator        → Loop through ALL cells
│   └── .getCellValue(row, col)  → Read a specific cell
│
├── .cube
│   ├── .name                    → "Plan1"
│   └── .essCalcScript           → Reference to calc engine
│
└── .planType                    → Current plan type name
```

# SECTION 5: READING FORM DATA

---

## Reading What the User Sees on a Form

```groovy
/* GR_Read_Form_Data — Read data from the current form */

// Get the grid (the form the user has open)
def grid = operation.grid

// Read the POV (Point of View) — what the user selected
grid.pov.each { dimName, memberName ->
    println "POV: ${dimName} = ${memberName}"
}
// Output:
//   POV: Scenario = Budget
//   POV: Version = Working
//   POV: Year = FY26
//   POV: Entity = Hotel India

// Loop through every cell on the form
grid.dataCellIterator().each { cell ->
    if (cell.edited) {  // Only process cells the user just changed
        println "EDITED: ${cell.memberNames} = ${cell.data}"
        // Output: EDITED: [Revenue, Jan] = 12000000
    }
}
```

## Reading Specific Cells

```groovy
/* Read data from specific intersections */

// Method 1: Using DataGridDefinitionBuilder to read from the cube
DataGridDefinitionBuilder builder = new DataGridDefinitionBuilder()
builder.addPov(["Scenario": "Budget", "Version": "Working", 
                "Year": "FY26", "Entity": "Hotel India"])
builder.addColumn(["Period": ["Jan", "Feb", "Mar"]])
builder.addRow(["Account": ["Revenue", "Expense", "Net_Income"]])

DataGridDefinition dgd = builder.build()
DataGrid dataGrid = operation.application.getDataGrid(dgd, "Plan1")

// Now loop through the result
dataGrid.dataCellIterator().each { cell ->
    println "${cell.getMemberName("Account")} / ${cell.getMemberName("Period")} = ${cell.data}"
}
// Output:
//   Revenue / Jan = 12000000
//   Revenue / Feb = 12500000
//   Expense / Jan = 8000000
//   ...
```

# SECTION 6: WRITING DATA WITH DATAGRIDBUILDER

---

## Writing Data to the Cube

```groovy
/* GR_Write_Data — Write calculated values back to the cube */

DataGridBuilder grid = new DataGridBuilder("Plan1")

// Set the POV
grid.addPov("Scenario", "Forecast")
grid.addPov("Version", "Working")
grid.addPov("Year", "FY26")
grid.addPov("Entity", "Hotel India")
grid.addPov("Currency", "INR")

// Set the columns (periods)
grid.addColumn("Period", "Jan")
grid.addColumn("Period", "Feb")
grid.addColumn("Period", "Mar")

// Add data rows
grid.addRow(["Account": "Revenue"], [15000000, 16000000, 17000000])
grid.addRow(["Account": "Expense"], [9000000, 9500000, 10000000])

// Submit to the cube
grid.build(true)  // true = suppress missing values

println "Data written successfully!"
```

## Important: Read vs Write

```
READING data:  DataGridDefinitionBuilder → getDataGrid()
WRITING data:  DataGridBuilder → build()

Common mistake: Using DataGridBuilder to try to READ data
→ DataGridBuilder is WRITE-ONLY
→ To read, use DataGridDefinitionBuilder + getDataGrid()
```

# SECTION 7: GENERATING DYNAMIC CALC SCRIPTS

---

## The Most Powerful Groovy Pattern

```groovy
/* GR_Dynamic_Revenue_Calc — Generate and execute a calc script dynamically */

// Step 1: Read user's selections from Runtime Prompts
def entity = rtps.RTP_Entity.getEssbaseMemberName()
def scenario = rtps.RTP_Scenario.getEssbaseMemberName()
def growthRate = rtps.RTP_GrowthRate.toString()

// Step 2: Read the current year substitution variable
def currYear = operation.application.getSubstitutionVariable("CurrYear", "Plan1")

// Step 3: Build a perfectly optimized calc script
String calcScript = """
SET UPDATECALC OFF;
SET CREATEBLOCKONEQ ON;

FIX("${entity}", "${scenario}", "Working", "${currYear}", @LEVMBRS("Department", 0))
    @CHILDREN("YearTotal")(
        "Revenue" = "Revenue" * (1 + ${growthRate} / 100);
        "Net_Income" = "Revenue" - "Expense";
    )
ENDFIX

SET CREATEBLOCKONEQ OFF;
"""

println "Generated Calc Script:"
println calcScript

// Step 4: Execute it on Essbase
operation.planType.essCalcScript = calcScript
operation.planType.execute()

println "Calculation completed for ${entity}!"
```

### Why This Is Powerful

```
Without Groovy:
  You write ONE calc script that processes ALL entities, ALL scenarios
  → Slow (processes data you don't need)

With Groovy:
  Groovy reads the user's form POV → "They're looking at Hotel India, Budget"
  Groovy generates: FIX("Hotel India", "Budget") ... ENDFIX
  → ONLY processes the data the user cares about
  → 10x-100x faster than a generic calc script
```

# SECTION 9: DATA VALIDATION AND VETOING SAVES

---

## Preventing Bad Data

```groovy
/* GR_Validate_Revenue — Runs on form Save, BEFORE data goes to cube */
/* Rule Properties: Set as "Before Save" rule on the form */

def hasErrors = false

operation.grid.dataCellIterator().each { cell ->
    if (cell.edited) {
        def account = cell.getMemberName("Account")
        def value = cell.data
        
        // Rule 1: Revenue must be positive
        if (account == "Revenue" && value < 0) {
            cell.addValidationError(0xFF0000, 
                "Revenue cannot be negative! You entered: ${value}")
            hasErrors = true
        }
        
        // Rule 2: Occupancy Rate must be 0-100
        if (account == "Occupancy_Rate" && (value < 0 || value > 100)) {
            cell.addValidationError(0xFF0000,
                "Occupancy Rate must be between 0 and 100. You entered: ${value}")
            hasErrors = true
        }
        
        // Rule 3: Headcount must be a whole number
        if (account == "Headcount" && value != Math.floor(value)) {
            cell.addValidationError(0xFFA500,
                "Headcount must be a whole number. You entered: ${value}")
            hasErrors = true
        }
    }
}

if (hasErrors) {
    // VETO the save — data does NOT go to the cube
    throwVetoException("Validation failed. Please fix the highlighted cells.")
}
```

### What the User Sees

```
User types Revenue = -500000 → clicks Save
┌─────────────────────────────────────────────┐
│  ⚠️ Validation failed.                     │
│  Revenue cannot be negative!                │
│  You entered: -500000                       │
│                                             │
│  Please fix the highlighted cells.          │
│  [OK]                                       │
└─────────────────────────────────────────────┘
The cell turns RED. Data is NOT saved.
```

# SECTION 10: REST API CALLS FROM GROOVY

---

```groovy
/* GR_Fetch_Exchange_Rate — Call external API from Groovy */

import java.net.HttpURLConnection
import java.net.URL

// Call an exchange rate API
def url = new URL("https://api.exchangerate.host/latest—base=USD&symbols=INR")
HttpURLConnection conn = (HttpURLConnection) url.openConnection()
conn.setRequestMethod("GET")
conn.setConnectTimeout(5000)

if (conn.responseCode == 200) {
    def response = conn.inputStream.text
    println "API Response: ${response}"
    
    // Parse the rate (simplified — real API returns JSON)
    // In production, use JsonSlurper to parse JSON
    def jsonSlurper = new groovy.json.JsonSlurper()
    def json = jsonSlurper.parseText(response)
    def usdToInr = json.rates.INR
    
    println "USD to INR rate: ${usdToInr}"
    
    // Write the rate to the cube
    DataGridBuilder grid = new DataGridBuilder("Plan1")
    grid.addPov("Scenario", "Actual")
    grid.addPov("Version", "Working")
    grid.addPov("Year", "FY26")
    grid.addPov("Entity", "HSP_Rates")
    grid.addColumn("Period", "Jan")
    grid.addRow(["Account": "USD_Rate"], [usdToInr])
    grid.build(true)
    
    println "Exchange rate loaded to cube!"
} else {
    println "API call failed: ${conn.responseCode}"
}
```

# SECTION 12: PERFORMANCE AND MEMORY

---

## Memory Limits

```
Each Groovy rule runs in the Planning web server's JVM (Java Virtual Machine).

Memory Limit: ~50MB per rule execution
Cell Limit: DataGridBuilder can handle ~500,000 cells before memory issues

RULE OF THUMB:
  < 10,000 cells → Groovy can handle directly
  10,000 - 100,000 cells → Use Groovy to generate Essbase calc scripts
  > 100,000 cells → MUST use Essbase calc scripts (not Groovy)
```

## Performance Best Practices

| Practice | Why |
|----------|-----|
| Use Groovy to BUILD calc scripts, not DO calculations | Essbase is 100x faster at math |
| Minimize DataGrid reads | Each read = network round trip |
| Use targeted FIX in generated scripts | Narrow scope = fast execution |
| Avoid nested loops over large member lists | O(n²) kills performance |
| Close connections in try/finally blocks | Prevent memory leaks |

# SECTION 13: COMMON MISTAKES

---

| Mistake | Problem | Fix |
|---------|---------|-----|
| Using Groovy to loop through 1M cells | JVM memory crash | Generate a calc script instead |
| Not checking for null before accessing objects | NullPointerException | Always use `—.` (safe navigation) |
| Forgetting `getEssbaseMemberName()` on RTP | Returns object, not string | Always call `.getEssbaseMemberName()` |
| Hard-coding member names in Groovy | Breaks when members change | Use RTPs and substitution variables |
| Not using `throwVetoException()` for validation | Bad data saves to cube | Always veto on validation failure |
| Writing too much data with DataGridBuilder | Slow, may timeout | Batch writes into chunks of 10,000 |
| Not handling API timeouts | Rule hangs forever | Set `conn.setConnectTimeout(5000)` |

# SECTION 15: INTERVIEW QUESTIONS

---

### Beginner

**Q1: What is Groovy in EPM Cloud—**
> Groovy is a Java-based scripting language embedded in EPBCS. It extends business rule capabilities beyond what Essbase calc scripts can do — including UI validation, REST API calls, dynamic script generation, and metadata operations.

**Q2: Can Groovy replace Calc Scripts—**
> No. Groovy should not be used for heavy math calculations — that's Essbase's job. Groovy's role is to build context-aware, dynamic calc scripts and handle logic that calc scripts can't (validation, API calls, emails).

### Intermediate

**Q3: How does `throwVetoException()` work—**
> When called in a "Before Save" Groovy rule, it prevents the form save from completing. The data is NOT written to the cube, and the user sees an error message. Use it for data validation — e.g., preventing negative revenue.

**Q4: What is the difference between DataGridBuilder and DataGridDefinitionBuilder—**
> DataGridBuilder is for WRITING data to the cube (build → submit). DataGridDefinitionBuilder is for READING data from the cube (build definition → getDataGrid → iterate). Common mistake: trying to use DataGridBuilder to read data.

**Q5: How do you read Runtime Prompts in Groovy—**
> Use the `rtps` object. For member RTPs: `rtps.RTP_Entity.getEssbaseMemberName()`. For numeric: `rtps.RTP_Rate.toDouble()`. For string: `rtps.RTP_Comment.toString()`.

### Architect

**Q6: A Groovy rule crashes with "Exceeded Memory Limit" when processing 500K cells. How do you fix it—**
> Stop processing data in Groovy. Instead, use Groovy to read the user's POV (a few strings), generate a targeted FIX statement as an Essbase calc script string, and execute it on Essbase. Essbase handles the 500K cells natively without memory issues. Only use DataGrid for small, targeted reads/writes.

**Q7: How do you implement a multi-step budget workflow in Groovy—**
> Use a master Groovy rule that orchestrates: (1) Validate data with `throwVetoException`, (2) Generate and execute a calc script for calculations, (3) Trigger Smart Push to move data to the reporting cube, (4) Update approval status via DataGridBuilder, (5) Send email notification. All in one rule, executed in sequence.

## 📝 Summary

| Concept | Key Takeaway |
|---------|-------------|
| **Groovy** | Java-based scripting for logic beyond calc scripts |
| **Use For** | Validation, dynamic calc scripts, API calls, emails |
| **Don't Use For** | Heavy math on large datasets — use Essbase instead |
| **DataGridBuilder** | Write data to cube |
| **DataGridDefinitionBuilder** | Read data from cube |
| **throwVetoException** | Block form save on validation failure |
| **rtps** | Access runtime prompt values |
| **operation.grid** | Access the current form and its cells |
| **essCalcScript** | Generate and execute calc scripts dynamically |
| **Memory Limit** | ~50MB per rule — keep data processing small |
