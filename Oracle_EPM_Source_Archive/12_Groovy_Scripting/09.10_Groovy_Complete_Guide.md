## 🏢 Overview

**Groovy** is a Java-based scripting language used in Oracle EPBCS to write advanced business rules that go beyond what traditional calc scripts can do. Groovy rules can call REST APIs, manipulate metadata, send emails, perform complex conditional logic, and interact with external systems.

---

## 📌 Why Groovy Over Calc Scripts—

| Feature | Calc Script | Groovy |
|---------|------------|--------|
| Simple calculations | ✅ Fast, native | ✅ Works but heavier |
| Conditional logic | ❌ Limited IF/ENDIF | ✅ Full if/else/switch |
| Loops | ❌ No native loops | ✅ for, while, each |
| REST API calls | ❌ Not possible | ✅ Native support |
| Send emails | ❌ Not possible | ✅ Built-in |
| Access metadata | ❌ Very limited | ✅ Full access |
| String manipulation | ❌ None | ✅ Full Java string API |
| Error handling | ❌ Basic | ✅ try/catch/finally |
| Custom functions | ❌ None | ✅ Define methods |

## 📌 EPM Groovy API — Core Classes

### 1. Operation Class

The `Operation` class is your entry point to the EPM Groovy API.

```groovy
// Get the current application
def app = operation.application

// Get the current cube
def cube = operation.application.getCube("FinPlan")

// Get substitution variable
String currentMonth = operation.application.getSubstitutionVariable("CurrentMonth")
String budgetYear = operation.application.getSubstitutionVariable("BudgetYear")
```

### 💡 Logic & Purpose
Traditional Calc Scripts are confined inside the Essbase engine—they cannot talk to the outside world, and they struggle with dynamic string manipulation. The Groovy API wraps the Essbase engine in Java. It allows developers to reach out to external REST APIs (like exchange rate websites), dynamically build Essbase calculation strings on the fly based on user input, and construct grids to read and write data surgically without running full block calculations.

### 🌀 Confusion Resolution
> **Misconception:** "Groovy replaces Calc Scripts. I should write all my calculations in Groovy from now on."
> **Reality:** No! Groovy is terrible at mass block aggregation compared to the native Essbase engine. If you need to aggregate 10,000 entities up a hierarchy, a native Calc Script (`AGG("Entity");`) will do it in 2 seconds. A Groovy script iterating through 10,000 entities to add them up will crash the server. Groovy is for *orchestration, dynamic logic, and external connections*. Essbase is for *heavy math*. The best Groovy scripts actually use Groovy to dynamically generate a fast, native Essbase Calc Script string and submit it to the engine.

### 😈 Twisted Interview Question
**Question:** A developer writes a Groovy script to calculate Employee Bonus. The script iterates through every single employee, calculates `Salary * 0.10`, and uses `DataGridBuilder` to write the bonus back to the cube. The client complains the rule takes 45 minutes to run. How do you fix it—
> **Answer:** Never use Groovy's `DataGridBuilder` to perform bulk mathematical calculations cell-by-cell! The massive API overhead of iterating and saving thousands of individual cells via Groovy grids causes extreme latency. The correct fix is to rewrite the script: use Groovy *only* to read the RTP (Runtime Prompt) variables, dynamically build a native Essbase `FIX` statement as a String, and execute that string on the Essbase engine, reducing the 45-minute runtime to 2 seconds.

### 2. DataGridDefinitionBuilder (Reading Data)

```groovy
// Build a data grid to READ data
def gridDef = new DataGridDefinitionBuilder()
gridDef.setSuppressMissing(true)
gridDef.addPov(["Year": "FY26", "Scenario": "Actual", "Version": "Final", "Entity": "E10001"])
gridDef.addColumn(["Period": ["Jan", "Feb", "Mar", "Apr", "May", "Jun"]])
gridDef.addRow(["Account": ["Revenue", "COGS", "Gross Profit"]])

// Execute the grid
def dataGrid = operation.application.getCube("FinPlan").loadGrid(gridDef.build(), false)

// Read values
dataGrid.dataCellIterator().each { cell ->
    println "${cell.getMemberName("Account")} | ${cell.getMemberName("Period")} = ${cell.data}"
}
```

### 3. DataGridBuilder (Writing Data)

```groovy
// Build a grid to WRITE data
DataGridBuilder grid = new DataGridBuilder(operation.application.getCube("FinPlan"))
grid.addPov(["Year": "FY26", "Scenario": "Budget", "Version": "Working", "Currency": "Local"])

// Define columns
grid.addColumn(["Period": ["Jan", "Feb", "Mar"]])

// Add rows with data
grid.addRow(["Account": "Revenue", "Entity": "E10001"], [1000.0, 1100.0, 1200.0])
grid.addRow(["Account": "Revenue", "Entity": "E10002"], [500.0, 550.0, 600.0])

// Submit the data
operation.application.getCube("FinPlan").saveGrid(grid.build())
```

## 📌 Common Groovy Patterns

### Pattern 1: Copy Data Between Scenarios

```groovy
def cube = operation.application.getCube("FinPlan")
def entityDim = operation.application.getDimension("Entity", "FinPlan")
def entities = entityDim.getEvaluatedMembers("ILvl0Descendants(Entity)", "FinPlan")

entities.each { entity ->
    // Read Actuals
    def readGrid = new DataGridDefinitionBuilder()
    readGrid.addPov(["Year": "FY26", "Scenario": "Actual", "Version": "Final", 
                     "Entity": entity.name, "Currency": "Local"])
    readGrid.addColumn(["Period": ["Jan", "Feb", "Mar", "Apr", "May", "Jun",
                                    "Jul", "Aug", "Sep", "Oct", "Nov", "Dec"]])
    readGrid.addRow(["Account": "ILvl0Descendants(PL_Accounts)"])
    
    def sourceGrid = cube.loadGrid(readGrid.build(), false)
    
    // Write to Budget
    DataGridBuilder writeGrid = new DataGridBuilder(cube)
    writeGrid.addPov(["Year": "FY27", "Scenario": "Budget", "Version": "Working",
                      "Entity": entity.name, "Currency": "Local"])
    writeGrid.addColumn(["Period": ["Jan", "Feb", "Mar", "Apr", "May", "Jun",
                                     "Jul", "Aug", "Sep", "Oct", "Nov", "Dec"]])
    
    sourceGrid.dataCellIterator("Jan").each { cell ->
        String account = cell.getMemberName("Account")
        List<Double> values = []
        ["Jan","Feb","Mar","Apr","May","Jun","Jul","Aug","Sep","Oct","Nov","Dec"].each { period ->
            values << (cell.crossDimCell("Period": period).data —: 0.0)
        }
        writeGrid.addRow(["Account": account], values)
    }
    
    cube.saveGrid(writeGrid.build())
}
```

### Pattern 2: REST API Call from Groovy

```groovy
// Call an external REST API
HttpURLConnection connection = new URL("https://api.exchangerate.host/latest—base=USD")
    .openConnection() as HttpURLConnection
connection.requestMethod = "GET"

if (connection.responseCode == 200) {
    def response = new groovy.json.JsonSlurper().parse(connection.inputStream)
    double eurRate = response.rates.EUR
    double inrRate = response.rates.INR
    
    // Write rates to EPM
    DataGridBuilder grid = new DataGridBuilder(operation.application.getCube("FinPlan"))
    grid.addPov(["Year": "FY26", "Scenario": "Actual", "Version": "Final",
                 "Period": "Jan", "Entity": "Exchange_Rates"])
    grid.addColumn(["Currency": ["EUR", "INR"]])
    grid.addRow(["Account": "Exchange_Rate"], [eurRate, inrRate])
    operation.application.getCube("FinPlan").saveGrid(grid.build())
}
```

## ⚡ Performance Tips

| Tip | Reason |
|-----|--------|
| Use `setSuppressMissing(true)` | Avoid processing empty cells |
| Batch writes in one `saveGrid` | Multiple small saves are slow |
| Avoid nested API calls | HTTP latency adds up fast |
| Use `ILvl0Descendants` not `IDescendants` | Skip parent members |
| Keep grid size under 500K cells | Large grids cause memory issues |

## 📌 Common Mistakes

| Mistake | Impact | Fix |
|---------|--------|-----|
| Not checking for null/missing | NullPointerException | Use `cell.data —: 0.0` |
| Writing to a read-only cube | Rule fails | Use BSO cube for writes |
| Infinite loops | Rule hangs, times out | Add loop counters and break conditions |
| Large grids without suppress | Memory overflow | Always suppress missing |
| Hardcoded member names | Breaks with metadata changes | Use substitution variables |

## 🎓 Interview Questions

**Q: When would you use Groovy instead of Calc Scripts—**
> A: Use Groovy when you need REST API integration, complex conditional logic, string manipulation, email notifications, metadata access, or any logic that goes beyond simple mathematical calculations. Use Calc Scripts for straightforward aggregation and calculation tasks where performance is critical.

**Q: What is DataGridBuilder used for—**
> A: DataGridBuilder is used to WRITE data to the Essbase cube. You define the POV, columns, and rows with values, then call `saveGrid()` to push the data. It's the Groovy equivalent of submitting a form.

**Q: How do you read data in Groovy—**
> A: Use `DataGridDefinitionBuilder` to define what data you want to read, then call `cube.loadGrid()` to retrieve it. Iterate over cells using `dataCellIterator()`.

**Q: How do you handle errors in Groovy rules—**
> A: Use try/catch blocks. Log errors with `println` (visible in Job Console). Re-throw exceptions to mark the rule as failed. Always validate inputs before processing.

**Q: Can Groovy rules call external APIs—**
> A: Yes. Groovy supports `HttpURLConnection` and `URL` classes natively. You can call REST APIs to fetch exchange rates, send notifications, or integrate with external systems. However, the EPM Cloud instance must have network access to the target endpoint.
