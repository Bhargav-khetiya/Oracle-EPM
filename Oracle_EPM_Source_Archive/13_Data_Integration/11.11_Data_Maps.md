## 🏢 1. The Challenge of Moving Data

EPM does not generate its own financial actuals; it relies on source systems (like Oracle ERP, SAP, or flat files). But source systems don't format data exactly the way EPM expects it.

**Example Problem:**
- **ERP System says:** `Account: 4001, Dept: Sales_North`
- **EPM System expects:** `Account: 100110, Department: D10040`

How do we translate this— We use **Data Integration**.

---

## 🔌 2. Data Integration (formerly Data Management / FDMEE)

**Data Integration** is the primary tool in EPM Cloud to map, transform, and load data from external systems into your EPM cubes.

### Key Components of Data Integration:

1. **Source Connection:** Where the data is coming from (e.g., Oracle Financials Cloud, or a CSV file).
2. **Target Application:** Where the data is going (e.g., the FinPlan cube).
3. **Import Format:** Defines how to read the source data (e.g., Column 1 = Account, Column 2 = Amount).
4. **Data Mappings:** The translation dictionary.
   - *Example Mapping:* Source `4001` → Target `100110`.
   - *Mapping Types:* Explicit (Exact match), Like (Wildcard match like `40*` → `100100`), Multi-Dimensional.
5. **Data Load Rule:** The actual job that executes the pull, transform, and push.

### The EPM Integration Agent
What if your source data is in an old, on-premises SQL database behind your company firewall—
Oracle provides the **EPM Integration Agent** — a lightweight program installed on your local server that securely pulls data from your on-premise database and sends it to the EPM Cloud.

## 🛠 3. Moving Data WITHIN EPM: Data Maps & Smart Push

Once data is in EPM, you often need to move it from one cube to another. 

**Example:** You finish planning salaries in the **Manpower Cube**, and now you need to push that total Salary Expense to the **FinPlan Cube** so you can calculate Net Profit.

### A. Data Maps
A **Data Map** defines how dimensions in Cube A map to dimensions in Cube B.
- *Example:* Manpower `Employee` dimension doesn't exist in FinPlan. The Data Map tells the system to aggregate all employees and push the total to the `No Employee` placeholder in FinPlan.

### B. Smart Push
**Smart Push** is the *action* of running a Data Map, often attached directly to a Form.
- *Workflow:* A user opens the Salary Planning Form, enters new salaries, clicks "Save", and **Smart Push** automatically triggers in the background, instantly updating the FinPlan cube with the new numbers.

## ️ 4. Valid Intersections

Not all combinations of dimensions make business sense.

**Example Problem:**
- You have a department called `D10061: HR`.
- You have a revenue account called `100110: Rooms Revenue`.
- *Does the HR department generate Rooms Revenue— No.*

If a user accidentally enters ₹10 Cr of Rooms Revenue into the HR department, it messes up the reports.

### The Solution: Valid Intersections
Administrators set up **Valid Intersection Rules** to define what combinations are allowed.
- *Rule:* If Account = Revenue, then Department cannot be HR, IT, or Finance.
- *Result:* When a user opens a form for the HR department, the Revenue rows become read-only or disappear entirely. This prevents garbage data from entering the system.

### 💡 Logic & Purpose
Valid Intersections are fundamentally a user-interface constraint designed to protect data integrity. In a multi-dimensional system, users are given a matrix. Without Valid Intersections, a user could accidentally enter "Bonus Expense" against the "No Employee" member, permanently throwing off variance reports. Valid Intersections lock the UI so users are physically prevented from making impossible business entries.

### 🌀 Confusion Resolution
> **Misconception:** "I set up a Valid Intersection so that 'Revenue' cannot be entered into the 'IT Department'. But when I loaded data overnight via Data Management, $10,000 of Revenue ended up in the IT Department anyway!"
> **Reality:** Valid Intersections primarily govern the **User Interface** (Web Forms and Smart View). They do NOT automatically block backend data loads, business rules, or Data Maps! If your Data Management load file contains invalid intersections, Essbase will happily load the data. To block invalid data during loads, you must explicitly enforce the Valid Intersection rules inside your Data Management mappings or use specific load parameters.

### 😈 Twisted Interview Question
**Question:** An administrator creates a Valid Intersection rule: `Account = Salary` is only valid for `Department = HR`. The admin attaches a Data Map (Smart Push) to a form to move Salary data to a reporting cube. The user enters data correctly in HR and clicks Save. The Smart Push triggers but fails with an error: "Data Map execution failed due to invalid intersections." Why—
> **Answer:** The administrator forgot to map the Unmapped dimensions properly in the Data Map. If the reporting cube does not have the `Department` dimension, the Data Map might be trying to push `Salary -> HR` into `Salary -> No Department` in the target cube. If the target cube *also* has Valid Intersections enforced, pushing data to an unmapped or restricted target intersection will cause the Smart Push to violently reject the transfer.
