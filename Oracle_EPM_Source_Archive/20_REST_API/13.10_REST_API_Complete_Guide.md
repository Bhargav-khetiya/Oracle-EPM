## 🏢 Overview

The **Oracle EPM Cloud REST API** allows external systems and scripts to programmatically interact with EPM Cloud — running rules, loading data, exporting data, managing metadata, executing jobs, and automating administrative tasks. It uses standard HTTP methods (GET, POST, DELETE) with JSON payloads.

---

## 📌 Authentication

All REST API calls require authentication via **Basic Auth** (Base64-encoded credentials) or **OAuth 2.0** tokens.

### Basic Authentication

```
Header: Authorization: Basic <base64(username:password)>

Example:
Username: admin@company.com
Password: SecurePass123

Base64: YWRtaW5AY29tcGFueS5jb206U2VjdXJlUGFzczEyMw==

Header: Authorization: Basic YWRtaW5AY29tcGFueS5jb206U2VjdXJlUGFzczEyMw==
```

### Base URL Format

```
https://<instance>.pbcs.us2.oraclecloud.com/HyperionPlanning/rest/v3/

Example:
https://mycompany.pbcs.us2.oraclecloud.com/HyperionPlanning/rest/v3/
```

## 📌 Core API Endpoints

### 1. Application Management

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | `/applications` | List all applications |
| GET | `/applications/{appName}` | Get application details |
| GET | `/applications/{appName}/plantypes` | List cubes (plan types) |

```json
// GET /applications
// Response:
{
    "items": [
        {
            "name": "Vision",
            "type": "Planning",
            "status": "Active"
        }
    ]
}
```

### 2. Running Business Rules

| Method | Endpoint | Purpose |
|--------|----------|---------|
| POST | `/applications/{appName}/plantypes/{planType}/rules/{ruleName}` | Launch a business rule |

```json
// POST /applications/Vision/plantypes/FinPlan/rules/Calculate_Revenue
// Request Body (with Runtime Prompts):
{
    "parameters": {
        "RTP_Entity": "E10001",
        "RTP_Scenario": "Budget",
        "RTP_Year": "FY26"
    }
}

// Response:
{
    "status": 0,
    "details": "Rule launched successfully",
    "jobId": 12345
}
```

### 💡 Logic & Purpose
The REST API fundamentally changes EPM from a closed web-interface tool to an open programmable engine. By wrapping EPM logic into API endpoints, architects can trigger heavy calculation engines from external orchestrators like Control-M, Python scripts, or OCI Data Factory. This decouples the EPM system from manual human intervention.

### 🌀 Confusion Resolution
> **Misconception:** "My Python script fired the POST request to run the business rule. The response came back with `status: 0`. Excellent, the rule finished calculating and I can now export the data!"
> **Reality:** `status: 0` on a POST request does NOT mean the rule finished! It simply means the server successfully *received* the instruction and placed it in the job queue. Business rules are asynchronous. You must extract the `jobId` from the response (e.g., `12345`) and enter a `While` loop, repeatedly pinging the `/jobs/12345` endpoint with GET requests until its `status` changes to `Completed` (or -1/1). Only then can you proceed to export.

### 😈 Twisted Interview Question
**Question:** A developer writes a PowerShell script that sends 10 REST API requests simultaneously to launch 10 different Business Rules across the same application. The API responds with success (`jobId` generated) for all 10 requests, but users immediately complain that the Planning application has frozen and forms will not save. Why—
> **Answer:** The developer triggered a massive lock contention event in Essbase. REST APIs execute blindly. By launching 10 rules simultaneously without orchestration, the script flooded the EPM Job Console. If those rules touched overlapping blocks in the Essbase database, they all queued up waiting for database locks, resulting in gridlock. The developer should have queued the jobs sequentially, waiting for one `jobId` to complete before triggering the next.

### 5. Job Management

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | `/applications/{appName}/jobs` | List recent jobs |
| GET | `/applications/{appName}/jobs/{jobId}` | Get job status |

```json
// GET /applications/Vision/jobs/12345
// Response:
{
    "jobId": 12345,
    "jobType": "RULES",
    "status": "COMPLETED",
    "executionStatus": "SUCCESS",
    "startTime": "2026-07-22T10:30:00Z",
    "endTime": "2026-07-22T10:30:45Z"
}
```

**Job Status Values:**
| Status | Meaning |
|--------|---------|
| `PROCESSING` | Job is running |
| `COMPLETED` | Job finished (check executionStatus) |
| `SUCCESS` | Execution was successful |
| `FAILED` | Execution had errors |

## 📌 Common Automation Patterns

### Pattern 1: Daily Data Load Script (PowerShell)

```powershell
$baseUrl = "https://mycompany.pbcs.us2.oraclecloud.com/HyperionPlanning/rest/v3"
$cred = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("admin@company.com:Password"))
$headers = @{ "Authorization" = "Basic $cred"; "Content-Type" = "application/json" }

# Step 1: Upload file
$filePath = "C:\data\actuals.csv"
$uploadUrl = "$baseUrl/applications/Vision/files/inbox/actuals.csv"
Invoke-RestMethod -Uri $uploadUrl -Method Post -Headers $headers -InFile $filePath

# Step 2: Import data
$importBody = @{
    jobType = "IMPORT_DATA"
    jobName = "DailyActualsLoad"
} | ConvertTo-Json
$importUrl = "$baseUrl/applications/Vision/jobs"
$job = Invoke-RestMethod -Uri $importUrl -Method Post -Headers $headers -Body $importBody

# Step 3: Check status
do {
    Start-Sleep -Seconds 10
    $status = Invoke-RestMethod -Uri "$baseUrl/applications/Vision/jobs/$($job.jobId)" -Headers $headers
} while ($status.status -eq "PROCESSING")

Write-Host "Job completed: $($status.executionStatus)"
```

### Pattern 2: Python Automation

```python
import requests
import base64
import time

base_url = "https://mycompany.pbcs.us2.oraclecloud.com/HyperionPlanning/rest/v3"
credentials = base64.b64encode(b"admin@company.com:Password").decode()
headers = {"Authorization": f"Basic {credentials}", "Content-Type": "application/json"}

# Run a business rule
response = requests.post(
    f"{base_url}/applications/Vision/plantypes/FinPlan/rules/Calculate_Revenue",
    headers=headers,
    json={"parameters": {"RTP_Entity": "E10001", "RTP_Year": "FY26"}}
)

job_id = response.json()["jobId"]

# Poll for completion
while True:
    status = requests.get(f"{base_url}/applications/Vision/jobs/{job_id}", headers=headers).json()
    if status["status"] != "PROCESSING":
        print(f"Result: {status['executionStatus']}")
        break
    time.sleep(10)
```

## 📌 Error Handling

| HTTP Code | Meaning | Action |
|-----------|---------|--------|
| 200 | Success | Process response |
| 400 | Bad request | Check JSON payload syntax |
| 401 | Unauthorized | Check credentials |
| 403 | Forbidden | User lacks permissions |
| 404 | Not found | Check endpoint URL |
| 500 | Server error | Check EPM Cloud status, retry |
| 503 | Service unavailable | Instance under maintenance |

## 🎓 Interview Questions

**Q: What is the EPM Cloud REST API used for—**
> A: It allows external systems and scripts to programmatically interact with EPM — running rules, loading data, managing metadata, automating administration tasks, and integrating with CI/CD pipelines.

**Q: How do you authenticate to the REST API—**
> A: Using Basic Authentication (Base64-encoded username:password) or OAuth 2.0 tokens. The credentials are the same as the EPM Cloud login.

**Q: How do you check if a job completed successfully via API—**
> A: After launching a job (which returns a jobId), poll the job status endpoint (`GET /jobs/{jobId}`) until the status changes from PROCESSING to COMPLETED, then check the executionStatus field for SUCCESS or FAILED.

**Q: Can you load data via REST API—**
> A: Yes. First upload the data file to the inbox using the files endpoint, then trigger an IMPORT_DATA job to load it into the cube.
