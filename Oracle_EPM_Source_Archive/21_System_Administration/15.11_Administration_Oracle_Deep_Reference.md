## 🔬 Job Console — Deep Dive

```
Navigation: Tools → Job Console
```

### Job Types

| Job Type | Description |
|----------|-------------|
| **Cube Refresh** | Restructure database after metadata changes |
| **Business Rule** | Calc script or Groovy execution |
| **Import Data** | Data load into cube |
| **Export Data** | Data export from cube |
| **Import Metadata** | Dimension member load |
| **Export Metadata** | Dimension member export |
| **Maintenance** | Backup, restore, clear |
| **Smart Push** | Data map execution |

### Job Status Values

| Status | Meaning | Action |
|--------|---------|--------|
| **Processing** | Currently running | Wait |
| **Completed** | Finished successfully | Verify results |
| **Completed with Errors** | Finished but had issues | Check error details |
| **Error** | Failed completely | Check error log, fix, re-run |

### 💡 Logic & Purpose
The Job Console is the central nervous system of EPM Cloud operations. Because EPBCS is a multi-tenant cloud application, Oracle strictly limits background processing time. The Job Console tracks these async threads. When an administrator triggers a Cube Refresh, the web UI immediately returns control to the admin, but the *real* heavy lifting happens asynchronously in the Job Console, protecting the UI from timing out.

### 🌀 Confusion Resolution
> **Misconception:** "I kicked off a Data Load rule, and the Job Console immediately showed `Completed`. That means the data is perfectly loaded into the cube."
> **Reality:** A `Completed` status in the EPM Job Console merely means the *job orchestration* finished without a fatal system crash. It does NOT mean the data loaded successfully! If the Data Management mapping rejected 100% of the rows, the load job itself still "Completed" successfully because the engine successfully processed the rejection logic. Always click the job details and check the Data Management logs to verify row-level success!

### 😈 Twisted Interview Question
**Question:** An administrator triggers a "Cube Refresh" from the Application module. The Job Console shows the refresh is "Processing". Five minutes later, users complain that they are getting booted out of Smart View and web forms are throwing errors. Did the Cube Refresh crash the system?
> **Answer:** No, the system is behaving normally. A Cube Refresh requires an exclusive system lock on the Essbase database to restructure the blocks and index files. When the refresh executes, it forcefully terminates all active user sessions and locks the application to prevent data corruption. Admins should NEVER run a Cube Refresh during active business hours!

### Filtering Jobs

| Filter | Options |
|--------|---------|
| Job Type | All, Rules, Import, Export, etc. |

| Date Range | Today, Last 7 days, Custom |

### 🎯 Hands-On: Job Console Mastery

```
Exercise 1: Monitor Jobs

5. Click on any failed job → read the error message

Exercise 2: Rule Execution Tracking
1. Go to a form → run a business rule
2. Immediately switch to Job Console
3. Watch the rule appear as "Processing"
4. Wait for completion → click to see duration and details
5. Note the execution time → baseline for performance comparison
```

## 📌 Migration (LCM) — Complete Reference

```
Navigation: Tools → Migration
```

### What Can Be Migrated

| Artifact Type | Exportable | Importable |
|---------------|-----------|------------|
| **Dimensions/Members** | ✅ | ✅ |
| **Forms** | ✅ | ✅ |
| **Business Rules** | ✅ | ✅ |
| **Task Lists** | ✅ | ✅ |
| **Smart Lists** | ✅ | ✅ |
| **Security/Access** | ✅ | ✅ |
| **Navigation Flows** | ✅ | ✅ |
| **Reports** | ✅ | ✅ |
| **Data** | ❌ (use snapshots) | ❌ |
| **Substitution Variables** | ✅ | ✅ |

### Migration Steps: DEV → PROD

```
Step 1: In DEV — Select artifacts to export
  Tools → Migration → Select components → Export
  
Step 2: Download the export file (.zip)
  
Step 3: In PROD — Upload the file
  Tools → Migration → Upload → Select zip file
  
Step 4: Import selected artifacts
  Review → select what to import → Import

Step 5: Verify in PROD
  Check forms, rules, members are correct
```

### Migration Best Practices

| Practice | Reason |
|----------|--------|
| Export specific components, not everything | Avoid overwriting PROD-specific settings |
| Always backup PROD before import | Safety net |
| Don't migrate data via LCM | Use snapshots or data loads instead |
| Document what was migrated | Audit trail |
| Test import in TEST first | Catch issues before PROD |

### 🎯 Hands-On: Perform a Migration

```
Exercise 5: LCM Export/Import
1. In your application: Tools → Migration
2. Select: Forms → select one form
3. Click Export → name it "Form_Export_Test"
4. Download the zip file
5. Navigate to Migration → Import
6. Upload the zip → select the form → Import
7. Verify the form exists and works correctly

Exercise 6: Full Component Export
1. Export ALL of these together:
   - All dimensions
   - All forms
   - All business rules
   - All task lists
   - Substitution variables
2. Save the export as "Full_Backup_[date].zip"
3. Document what was exported for future reference
```

## 📌 Snapshots — Backup & Restore

### Snapshot Types

| Type | What's Included | Size |
|------|----------------|------|
| **Maintenance Snapshot** | Everything (data + metadata + artifacts + security) | Large (GBs) |
| **LCM Export** | Selected artifacts only (no data) | Small (MBs) |

### Snapshot Operations

```
# Create snapshot
Navigation: Application → Overview → Actions → Export Snapshot
OR: epmautomate exportSnapshot "BackupName"

# Restore snapshot
Navigation: Application → Overview → Actions → Import Snapshot
OR: epmautomate importSnapshot "BackupName"

# List snapshots
Navigation: Application → Overview → Snapshots tab
OR: epmautomate listFiles
```

### 🎯 Hands-On: Backup & Restore

```
Exercise 7: Complete Backup/Restore Cycle
1. Export snapshot: Application → Actions → Export → name it "Backup_Exercise"
2. Verify snapshot appears in Snapshots list
3. Make a change: delete a member or form
4. Import snapshot: Application → Actions → Import → select "Backup_Exercise"
5. Verify: The deleted member/form is restored
6. Document the backup/restore time for capacity planning
```

## 📌 Cube Refresh (Database Restructure)

```
Navigation: Application → Overview → Actions → Refresh Database
OR: Application → Cubes → [Select Cube] → Refresh
```

### When to Refresh

| Action | Refresh Needed? |
|--------|----------------|
| Add/remove dimension members | ✅ Yes |
| Change member properties | ✅ Yes |
| Change Dense/Sparse | ✅ Yes (full restructure) |
| Change consolidation operators | ✅ Yes |
| Create/modify forms | ❌ No |
| Create/modify rules | ❌ No (just deploy) |
| Load data | ❌ No |

### Refresh Options

| Option | Description |
|--------|-------------|
| **Refresh** | Apply metadata changes (standard) |
| **Full Restructure** | Rebuild entire database (needed for Dense/Sparse changes) |
| **Create/Refresh** | Create cube if it doesn't exist |

### 🎯 Hands-On: Cube Refresh

```
Exercise 8: Metadata Change Workflow
1. Add a new member to Account dimension: "200150 — Travel Expense"
2. Try opening a form → notice the new member doesn't appear
3. Navigate to Application → Overview → Refresh Database
4. Wait for refresh to complete (check Job Console)
5. Reopen the form → select the new member → it now appears
6. Enter data → verify the member works correctly
```

## 📌 System Maintenance

### Daily Checks (15 Minutes)

```
1. [ ] Job Console → check overnight jobs
2. [ ] Activity Reports → review performance
3. [ ] Check user support tickets
4. [ ] Verify data loads completed
```

### Monthly Tasks (1 Hour)

```
1. [ ] Update substitution variables (&CurrentMonth)
2. [ ] Export full snapshot backup
3. [ ] Review user access (deactivate departed users)
4. [ ] Review Oracle Readiness document for next update
5. [ ] Compare performance metrics with prior month
```

### Oracle Monthly Updates

```
Timeline:
1. Oracle publishes Readiness document → 2 weeks before update
2. Non-production environments update first → 1 week before
3. Production updates → scheduled maintenance window
4. Post-update verification → same day

Action Items:
- Read Readiness document for breaking changes
- Test in non-prod after it updates
- Backup PROD before update
- Verify after PROD updates
```

## 🎓 Interview Questions

**Q: What are the main admin tools in EPM Cloud?**
> Job Console (job monitoring), Activity Reports (performance), Access Control (users/roles), Migration (LCM), Audit (change tracking), and Application settings (dimensions, cubes, variables).

**Q: How do you promote changes from DEV to PROD?**
> Use Migration (LCM): Export selected artifacts from DEV → download zip → upload to PROD → import. Always backup PROD first and test in TEST/UAT before PROD. Don't migrate data — use snapshots for that.

**Q: When do you need to refresh the database?**
> After any metadata change: adding/removing members, changing member properties, changing Dense/Sparse assignment. You do NOT need refresh for form changes, rule deployment, or data loads.

**Q: How do Oracle's monthly updates work?**
> Updates are mandatory. Non-prod updates first (1 week early), then PROD. Review the Readiness document for breaking changes, test in non-prod, backup PROD, verify after update.
