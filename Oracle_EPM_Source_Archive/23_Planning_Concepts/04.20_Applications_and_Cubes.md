## 🏢 1. What is an Application in EPM?

An **Application** is a container that holds everything needed for a specific planning process:
- Cubes (databases)
- Dimensions and their members
- Forms (data entry screens)
- Business Rules (calculations)
- Security settings

> **Think of it like this:** An Application is like a **project folder** that contains all the files needed for one planning task.

---

## 💡 2. Application Types

EPBCS offers **three types** of applications:

### A. Custom Application
| Feature | Detail |
|---------|--------|
| **What it is** | You build everything from scratch |
| **Dimensions** | You choose which dimensions to create |
| **Total Dimensions** | Up to **32** (7 OOTB + 25 Custom) |
| **OOTB Dimensions** | Account, Entity, Scenario, Version, Year, Period, Currency (7 total) |
| **Custom Dimensions** | Up to 25 more (Department, Product, Custom1, etc.) |
| **Best For** | When your planning needs don't fit any pre-built module |

### B. Freeform Application
| Feature | Detail |
|---------|--------|
| **What it is** | Maximum flexibility — even OOTB rules are relaxed |
| **Dimensions** | Minimal restrictions |
| **Total Dimensions** | Up to **29** (3 OOTB + 26 Custom) |
| **OOTB Dimensions** | Only Account, Entity, and Period are required (3 total) |
| **Custom Dimensions** | Up to 26 more |
| **Best For** | When you want full control with minimal Oracle restrictions |

### C. OOTB (Out of the Box) Application
| Feature | Detail |
|---------|--------|
| **What it is** | Pre-built by Oracle — ready to use with minimal setup |
| **Dimensions** | Comes with pre-defined dimensions and members |
| **Total Dimensions** | Up to **32** (7 OOTB + 25 Custom) |
| **Modules** | FinPlan, Workforce (Manpower), Capital, Projects, Strategic Modeling |
| **Best For** | Standard financial planning — fastest to implement |

### Comparison:

| Feature | Custom | Freeform | OOTB (Standard) |
|---------|--------|----------|-----------------|
| **Total Max Dimensions** | 32 | 29 | 32 |
| **OOTB Dimensions** | 7 | 3 | 7 |
| **Custom Dimensions** | 25 | 26 | 25 |
| **Pre-built Modules** | ❌ | ❌ | ✅ |
| **Setup Time** | Long | Long | Short |
| **Oracle Best Practices** | Manual | Manual | Built-in |

### 💡 Logic & Purpose
Oracle designed three distinct application types because no two clients are identical. OOTB (Out of the Box) enforces strict Oracle best practices and standard dimensions, drastically reducing implementation time. However, if a client has a radically different business model (e.g., a university planning by courses and semesters instead of standard financial accounts and months), OOTB's rigid structures will fail, necessitating a Custom or Freeform build.

### 🌀 Confusion Resolution
> **Misconception:** "We have 10 custom dimensions, so we have to use a Freeform application because Standard/Custom only gives us a few."
> **Reality:** A Standard/Custom EPBCS application gives you 7 required dimensions *plus* up to 25 custom dimensions (for a total of 32). A Freeform application is actually *less* about getting "more dimensions" and more about dropping Oracle's mandatory requirements. Freeform applications do NOT require Scenario, Version, or Year dimensions. They only require Account, Entity, and Period.

### 😈 Twisted Interview Question
**Question:** A client wants to migrate an old Essbase BSO cube into EPM Cloud. This cube only has 4 dimensions: "Region", "Product", "Account", and "Time". Can you migrate this directly into a standard EPBCS Custom Application?
> **Answer:** No! A standard EPBCS Custom Application strictly enforces 7 required dimensions (Account, Entity, Scenario, Version, Year, Period, Currency). Since the legacy cube only has 4, the migration will fail unless you artificially create and map the missing dimensions. The correct approach is to migrate this into a **Freeform** application, which natively supports custom 4-dimension cubes without forcing you to add Version or Scenario.

## 🛠 3. OOTB Cubes in EPBCS

When you create an OOTB application, Oracle provides **pre-built cubes** for each module:

### The Three Main OOTB Cubes:

| Cube Name | Module | Purpose | Key Dimensions |
|-----------|--------|---------|---------------|
| **FinPlan** | Financials | P&L, Balance Sheet, Cash Flow planning | Account, Entity, Scenario, Version, Year, Period, PlanElement, Department, Custom1, Future, Currency |
| **Manpower** | Workforce | Employee headcount, salary, benefits | Account, Entity, Scenario, Version, Year, Period, Employee, Department, Currency |
| **Capital** | Capital | Asset planning, depreciation | Account, Entity, Scenario, Version, Year, Period, AssetClass, AssetDetail, Department, Currency |

## ️ 4. Dimension Validity — Which Dimension Belongs Where

Some custom dimensions are **valid only for specific cubes**:

| Dimension | Valid For (Cube) | Meaning |
|-----------|-----------------|---------|
| PlanElement | F (FinPlan only) | Only used in financial planning cube |
| Department | F, M, C (All three) | Used across all cubes |
| Custom1 | F (FinPlan only) | Planning drivers, only in FinPlan |
| Future | F (FinPlan only) | Future scenarios, only in FinPlan |
| Employee | M (Manpower only) | Only in workforce planning |
| AssetClass | C (Capital only) | Only in capital planning |
| AssetDetail | C (Capital only) | Only in capital planning |

### "No" Members:
When a dimension is NOT valid for a cube, Oracle creates a placeholder member:

| Dimension | FinPlan Uses | Manpower Gets | Capital Gets |
|-----------|-------------|---------------|--------------|
| PlanElement | ✅ Full members | "No PlanElement" | "No PlanElement" |
| Employee | "No Employee" | ✅ Full members | "No Employee" |
| AssetClass | "No AssetClass" | "No AssetClass" | ✅ Full members |

> **Think of it like this:** If Manpower cube doesn't need "PlanElement", Oracle puts a dummy member "No PlanElement" as a placeholder. This keeps the cube structure consistent.

## 📊 5. Block Set

### What is a Block Set?
A **Block Set** is a concept related to how BSO organizes data blocks in memory.

### In Simple Words:
> When you run a calculation in BSO, Essbase needs to decide **which blocks to process**. A Block Set is the group of blocks that Essbase will work on during a particular calculation.

### Key Points:
| Point | Explanation |
|-------|-------------|
| **Created automatically** | Essbase creates block sets when processing calculations |
| **Performance impact** | Larger block sets = more memory needed, slower processing |
| **Optimization** | Proper Dense/Sparse assignment helps optimize block set size |

## 💡 6. Dynamic Calc vs Store — A Critical Concept

From your project's Excel data, this is one of the most important things to understand:

### Scenario: Two Accounts with Different Storage

```
Acc1 → Data Storage = Dynamic Calc → Value shown = 200
Acc2 → Data Storage = Store         → Value shown = 200
```

### What's the Difference?

| Aspect | Dynamic Calc (Acc1) | Store (Acc2) |
|--------|-------------------|-------------|
| **Data physically saved?** | ❌ No — calculated on-the-fly each time you view it | ✅ Yes — saved in the cube |
| **When is it calculated?** | At the moment you open the form/report | When the business rule runs or data is loaded |
| **Disk space used?** | None (saves storage) | Yes (uses storage) |
| **Speed** | May be slightly slower (calculates each time) | Faster retrieval (already stored) |
| **Can user enter data?** | ❌ No (it's calculated, not entered) | ✅ Yes |

### Another Example — "Dynamic Calc and Store":

```
Acc1 → Dynamic Calc and Store → Value = 200
```

This means:
- First time: Calculated dynamically and then **stored** for future retrieval
- Next time: Retrieved from storage (faster)
- If children change: Recalculated and stored again

## 📝 7. Summary

| Concept | Key Takeaway |
|---------|-------------|
| **Application** | A container for cubes, forms, rules, dimensions |
| **Custom App** | Build everything from scratch (32 dimensions max) |
| **Freeform App** | Maximum flexibility, minimal restrictions (29 dimensions max) |
| **OOTB App** | Pre-built modules, fastest to set up (32 dimensions max) |
| **FinPlan Cube** | Financial planning (Revenue, Expenses, P&L) |
| **Manpower Cube** | Workforce planning (Employees, Salaries) |
| **Capital Cube** | Asset planning (Buildings, Vehicles, Depreciation) |
| **Block Set** | Group of data blocks processed during calculations |
| **Dynamic Calc** | Calculated on-the-fly, not stored |
| **Store** | Data physically saved in the cube |
