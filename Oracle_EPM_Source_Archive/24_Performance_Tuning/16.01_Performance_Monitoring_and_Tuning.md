# 16.01 — Performance Monitoring and Tuning: Complete Guide

> **Module:** 16_Performance | **Topic:** Monitoring Tools, Bottleneck Identification, Tuning
> **Audience:** Architect / Service Administrator

---

## 1. WHY — Why Performance Matters

Oracle's SLA for form load: **< 5 seconds**. For business rules: **< 30 seconds** (most rules should be < 5 seconds). Users who wait more than 10 seconds lose focus. Users who wait 30+ seconds switch to Excel. Performance is NOT a "nice to have" — it's the #1 determinant of EPM adoption.

## 3. THE PERFORMANCE DIAGNOSTIC FRAMEWORK

```
User reports: "The form is slow"
           │
           ▼
Step 1: MEASURE — What is the actual load time—
  → Open Jobs Console → check form load/rule execution time
  → Open browser DevTools (F12) → Network tab → measure total page load
           │
           ▼
Step 2: IDENTIFY — Which layer is slow—
  → Form rendering— (browser-side)
  → Essbase query— (server-side data retrieval)
  → Business rule— (calc execution)
  → Network— (latency between client and cloud)
           │
           ▼
Step 3: DIAGNOSE — What's the root cause—
  → Too many cells on the form— (>5,000)
  → No suppression enabled—
  → Heavy On Load rule—
  → Block explosion (check block count)—
  → High fragmentation—
  → Cross-dim on sparse = Top-Down—
           │
           ▼
Step 4: FIX — Apply the right optimization
  → Form optimization (move dims, suppress, reduce cells)
  → Rule optimization (tight FIX, Bottom-Up, LOCKBLOCK)
  → Cube optimization (restructure, CLEARBLOCK)
           │
           ▼
Step 5: VERIFY — Re-measure after fix
  → Did load time improve—
  → Compare before/after metrics
```

## 4. FORM PERFORMANCE TUNING

### Quick Wins (Fix These First)

| Check | Action | Impact |
|-------|--------|--------|
| Cell count > 5,000 | Reduce rows/columns or move dims to Page | 50-80% improvement |
| Suppress Missing off | Enable Suppress Missing Data + Blocks | 40-70% improvement |
| 2+ sparse dims on rows | Move one to Page axis | 60-90% improvement |
| Heavy On Load rule | Move to On Save or batch job | 50-90% improvement |
| Formula columns + DB suppression | Switch to regular suppression | 30-50% improvement |
| 15+ format rules | Reduce to 5-8 rules | 20-30% improvement |

## 5. BUSINESS RULE PERFORMANCE TUNING

### Quick Wins

| Check | Action | Impact |
|-------|--------|--------|
| No FIX statement | Add tight FIX | 90%+ improvement |
| Cross-dim on sparse | Use two-pass pattern | 80-95% improvement |
| Multiple On Save rules | Combine into Ruleset | 2-3× faster |
| CALCPARALLEL not set | Add SET CALCPARALLEL 4 | 2-4× faster |
| LOCKBLOCK OFF | SET LOCKBLOCK ON | 20-40% improvement |
| AGG on all dims | AGG only changed dims | 50% improvement |

## 6. CUBE/DATABASE PERFORMANCE TUNING

### Block Count Management

```
Healthy:       Existing blocks < 10% of potential blocks
Warning:       Existing blocks = 10-30% of potential blocks
Critical:      Existing blocks > 30% → likely block explosion

Action: CLEARBLOCK ALL (removes empty blocks)
        Restructure database (optimizes storage)
```

### Fragmentation Management

```
Healthy:       < 20% fragmentation
Warning:       20-40% fragmentation
Critical:      > 40% fragmentation

Action: Export data → Clear → Restructure → Reimport
        OR: epmautomate compactcube "OEP_FS"
```

### Dense/Sparse Optimization

```
Rule: Dense dimensions should have HIGH usage density (>20%)
      Sparse dimensions should have LOW member count

If block density < 5%:
  → Move the least-populated Dense dimension to Sparse
  → This reduces block size and increases density

If block size > 200KB:
  → Too many Dense members → move some to Sparse
```

## 7. SHOW ME — Hotel Pvt Ltd Performance Audit

```
BEFORE optimization:
  Revenue form load:         15.2 seconds ❌
  P&L form load:             22.4 seconds ❌
  Monthly Close rule:        8.5 minutes ❌
  Cube fragmentation:        35% ⚠️
  Existing blocks:           45,000 (expected: 500) ❌ BLOCK EXPLOSION
  
ROOT CAUSES:
  1. Revenue form: Entity + Department on rows (sparse × sparse)
  2. P&L form: No suppression, 500 account rows, On Load AGG rule
  3. Monthly Close: No FIX, cross-dim on Entity, no CALCPARALLEL
  4. Block explosion: Old rule had CREATEBLOCKONEQ ON left active

AFTER optimization:
  Revenue form load:         2.8 seconds ✅ (Entity to Page)
  P&L form load:             3.5 seconds ✅ (suppress + remove On Load)
  Monthly Close rule:        12 seconds ✅ (tight FIX + 4 threads)
  Cube fragmentation:        8% ✅ (restructured)
  Existing blocks:           520 ✅ (CLEARBLOCK ALL)
```

## 9. INTERVIEW QUESTIONS

### Intermediate
**Q: Walk me through diagnosing a form that takes 20 seconds to load.**
> (1) **Measure:** Check Jobs Console for the form's data retrieval time. Open browser F12 → Network tab to see total page load. (2) **Identify the slow layer:** Is it the Essbase query (check job duration), On Load rule (check rule execution), or browser rendering (check row count)— (3) **Diagnose:** Count cells (rows × columns). Check for sparse-sparse cross-join on rows. Check suppression settings. Check if On Load rules exist. (4) **Fix:** If too many cells → move a dimension to Page. If no suppression → enable it. If On Load rule is heavy → optimize or move to batch. (5) **Verify:** Re-open the form, confirm load time < 5 seconds.

### Architect
**Q: Design the performance monitoring strategy for Hotel Pvt Ltd's production EPBCS environment.**
> **Automated monitoring:** (1) EPM Automate script that runs nightly, checks block count and fragmentation via Application Statistics, emails admin if thresholds exceeded. (2) Weekly Activity Report review — identify forms with > 10 second load times. (3) Monthly performance dashboard (Excel + Smart View) that tracks: average form load time, average rule execution time, block count trend, fragmentation trend. **Proactive tuning:** (1) After every metadata import → check block count. (2) Before month-end close → run CLEARBLOCK ALL and compact. (3) After deploying new rules → compare execution time to baseline. **Thresholds:** Form load > 8 seconds → investigate. Rule > 30 seconds → optimize. Block count > 2× baseline → alert.
