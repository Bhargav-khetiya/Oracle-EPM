# 16.02 — BSO vs ASO Performance Patterns: Complete Guide

> **Module:** 16_Performance | **Topic:** BSO, ASO, Hybrid Performance Characteristics
> **Audience:** Architect

---

## 1. WHY — Choosing the Right Storage

**The problem:** The reporting cube (ASO) loads data in 2 seconds but can't accept user input. The input cube (BSO) accepts input but queries on 500 entities take 30 seconds. The Hybrid BSO cube promises both — but only if configured correctly. Understanding storage engine performance is essential for cube design.

---

## 2. BSO vs ASO vs HYBRID — COMPLETE COMPARISON

| Feature | BSO | ASO | Hybrid BSO |
|---------|-----|-----|-----------|
| **User Input** | ✅ Read/Write | ❌ Load only | ✅ Read/Write |
| **Calc Scripts** | ✅ Full support | ❌ Not supported | ✅ Full support |
| **Aggregation** | Manual (AGG command) | ✅ Automatic on query | Dynamic Calc members |
| **Query Speed (10K members)** | 🐌 Slow | ⚡ Fast | ⚡ Fast (Dynamic Calc) |
| **Query Speed (100 members)** | ⚡ Fast | ⚡ Fast | ⚡ Fast |
| **Write-back** | ✅ Native | ❌ Not supported | ✅ Native |
| **Block Explosion Risk** | ⚠️ Yes | ❌ No blocks | ⚠️ Reduced |
| **Dense/Sparse Design** | Critical | N/A (auto) | Important |
| **Max Dimensions** | ~20 practical | ~100+ | ~20 practical |
| **EPBCS Typical Use** | Input cubes | Reporting cube | Default for new cubes |

## 3. BSO PERFORMANCE PATTERNS

### When BSO is Fast

```
1. Small cube (< 50 entities, < 200 accounts)
2. Dense dimensions on Rows/Columns (Account, Period)
3. Tight FIX statements in rules
4. Bottom-Up calculations
5. Pre-aggregated data (AGG ran after data load)
```

### When BSO is Slow

```
1. Large sparse cross-joins (Entity × Department × Product)
2. No FIX statements in rules
3. Cross-dimensional on sparse dimensions (Top-Down)
4. No suppression on forms
5. Block explosion (100× more blocks than expected)
6. High fragmentation (>30%)
```

### BSO Optimization Checklist

```
☐ Block density > 20%—
☐ Fragmentation < 20%—
☐ Block count within expected range—
☐ All rules have FIX statements—
☐ No cross-dim on sparse without two-pass—
☐ SET LOCKBLOCK ON in rules—
☐ SET CALCPARALLEL 4 in rules—
☐ CLEARBLOCK ALL run after data clears—
☐ Dense dims: Account, Period, Currency (high cardinality within blocks)
☐ Sparse dims: Entity, Scenario, Version, Year (define blocks)
```

## 4. ASO PERFORMANCE PATTERNS

### Why ASO is Fast for Queries

```
ASO aggregation is AUTOMATIC:
  User queries "All_Hotels, Q1, Total_Revenue"
  → ASO dynamically aggregates from stored leaf-level data
  → No need to run AGG — it happens on-the-fly
  → Result in < 1 second even for millions of cells

BSO aggregation is MANUAL:
  User queries "All_Hotels, Q1, Total_Revenue"
  → BSO looks for a stored block for All_Hotels
  → If AGG hasn't run → #MISSING!
  → Must run AGG("Entity") first → takes 30 seconds
```

### ASO Limitations

```
❌ No calc scripts (no FIX, AGG, DATACOPY, IF/ENDIF)
❌ No write-back (users can't enter data)
❌ No SET commands
❌ Data can only be loaded via data loads
❌ Cannot attach business rules to forms

Use ASO only for:
  ✅ Reporting/dashboard cubes (read-only)
  ✅ Large-dimension analysis (100+ entities)
  ✅ Consolidation aggregation
```

## 5. HYBRID BSO — THE MODERN DEFAULT

### What Makes It "Hybrid"

```
Hybrid BSO = Regular BSO + ASO-like Dynamic Calc members

In traditional BSO:
  Parent member "Total_Revenue" → needs AGG to calculate
  If AGG not run → shows #MISSING

In Hybrid BSO:
  Parent member "Total_Revenue" → Data Storage = Dynamic Calc
  → Calculates automatically on query (like ASO!)
  → No AGG needed for Dynamic Calc members
  → Users see correct totals INSTANTLY

  Leaf member "Room_Revenue" → Data Storage = Store
  → Users enter data here (traditional BSO input)
```

### Hybrid Performance Best Practices

```
1. All PARENT members → Dynamic Calc
   (Account parents, Entity parents, Period parents)
   → Aggregation happens automatically on query

2. All LEAF (Level-0) members → Store
   (Input accounts, leaf entities)
   → Users enter data here

3. Calculated accounts → Dynamic Calc
   (Profit Margin = Net Income / Revenue)
   → Calculates on-the-fly, never stale

4. Result: No AGG command needed!
   → Form loads show correct totals instantly
   → No waiting for aggregation rules
```

### Performance Comparison

```
Query: "Show me All_Hotels, Q1, Total_Revenue"

BSO (traditional):
  Step 1: Run AGG("Entity") → 30 seconds
  Step 2: Open form → reads stored parent → instant
  Total: 30 seconds (if AGG ran)
  Risk: If AGG didn't run → #MISSING

Hybrid BSO:
  Step 1: Open form → Dynamic Calc parent aggregates on-the-fly
  Total: 2 seconds (no AGG needed)
  Risk: None — always correct

ASO (reporting cube):
  Step 1: Data must be loaded (Smart Push from BSO) → 5 seconds
  Step 2: Open form → automatic aggregation → instant
  Total: 5 seconds + instant query
```

## 7. COMMON MISTAKES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Store on parent members (BSO) | Must run AGG constantly | Set parents to Dynamic Calc (Hybrid) |
| Using BSO for large reporting | Slow queries, must pre-aggregate | Use ASO cube for reporting |
| Using ASO for data entry | Users can't enter data | Use BSO/Hybrid for input |
| Not using Smart Push to ASO | ASO cube has stale data | Configure Smart Push from BSO on save |
| Dynamic Calc on every member | Slow reads (too much on-the-fly calc) | Only parents + calculated accounts |

## 8. INTERVIEW QUESTIONS

### Beginner
**Q: What is the difference between BSO, ASO, and Hybrid BSO—**
> **BSO (Block Storage):** Read-write, supports calc scripts, manual aggregation (AGG command). Best for data input cubes. **ASO (Aggregate Storage):** Read-only (data loaded via imports), automatic aggregation, extremely fast queries. Best for reporting cubes with many dimensions. **Hybrid BSO:** BSO + Dynamic Calc members that aggregate automatically like ASO. Modern default — users can enter data AND see correct parent totals without running AGG. EPBCS uses Hybrid BSO for input cubes and ASO for the reporting cube.

### Architect
**Q: Design the cube architecture for Hotel Pvt Ltd.**
> **OEP_FS (FinPlan):** Hybrid BSO. Account/Period = Dense, Entity/Scenario/Version/Year = Sparse. Account parents and Entity parents = Dynamic Calc (auto-aggregate). Account leaves = Store (user input). No AGG needed — parents calculate on-the-fly. **OEP_WFP (Workforce):** Hybrid BSO, same pattern. Only HR team has access. **OEP_CP (Capital):** Hybrid BSO, smaller cube for CapEx. **OEP_REP (Reporting):** ASO. Receives data via Smart Push from all 3 input cubes. Executives query this cube for consolidated views — instant aggregation across 500+ member combinations. Smart Push configured as On Save rule on key forms.
