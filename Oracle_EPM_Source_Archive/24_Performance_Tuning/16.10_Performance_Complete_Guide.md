## 🏢 Overview

Performance in Oracle EPBCS depends on three pillars: **Database Design** (how the cube is structured), **Calculation Performance** (how rules are written), and **Retrieval Performance** (how forms/reports fetch data). A poorly designed application can take hours for what should take seconds.

---

## ⚡ Pillar 1: Database Design Performance

### Dense/Sparse Assignment

**The single most impactful design decision.**

| Guideline | Reason |
|-----------|--------|
| Account → Dense | Almost every entity/scenario has all accounts |
| Period → Dense | Every entity has all 12 months |
| Entity → Sparse | Not every entity has every account |
| Scenario → Sparse | Budget, Actual, Forecast are few |
| Version → Sparse | Working, Approved — few members |
| Year → Sparse | FY25, FY26, FY27 — few members |
| Custom dimensions → Analyze | Depends on data density |

### Block Size Optimization

```
Block Size = Product of all Dense dimension member counts (Level 0 only)

Example:
Account: 200 Level 0 members
Period: 12 members

Block Size = 200 × 12 = 2,400 cells
Cell Size = 8 bytes

Block Memory = 2,400 × 8 = 19,200 bytes = ~19 KB ✅ Good

Target: Keep block size between 10 KB and 100 KB
```

| Block Size | Rating | Action |
|-----------|--------|--------|
| < 10 KB | ❌ Too small | Too many blocks, high index overhead |
| 10–100 KB | ✅ Optimal | Good balance of size and count |
| 100–500 KB | ⚠️ Getting large | Consider if Dense members can be reduced |
| > 500 KB | ❌ Too large | Slow retrieval, high memory usage |

### 💡 Logic & Purpose
The Essbase engine is fundamentally a block-storage system. When a user requests data for `Q1 -> Revenue`, Essbase doesn't just read that one cell; it pulls the entire Block from the hard drive into RAM. If your Block Size is optimally 50KB, that memory swap is instantaneous. If your Block Size is 5MB, pulling a single block into RAM takes significantly longer, crippling system performance.

### 🌀 Confusion Resolution
> **Misconception:** "My block size is 2MB, which is too big. I will change my Custom 1 dimension from Dense to Sparse to reduce it."
> **Reality:** Changing a dimension from Dense to Sparse will definitely shrink your Block Size (which is good), but it will simultaneously explode your Block Count (which could be worse)! If Custom 1 has 1,000 members, making it Sparse creates 1,000 times more blocks. The index file will become massively bloated, and retrievals will slow down. You must analyze the *density* of the data before shifting dimensions.

### 😈 Twisted Interview Question
**Question:** A developer realizes their Block Size is 1.2MB because the `Account` dimension (Dense) has 15,000 members. They decide they cannot make Account sparse, so they choose to change the `Period` dimension (12 members) from Dense to Sparse to shrink the block size by a factor of 12. Why is this a terrible idea—
> **Answer:** `Period` should NEVER be Sparse! Essbase calculations (like Time Balance and Quarter/Year-To-Date aggregations) rely on the Period members existing within the same physical block to calculate efficiently in memory. If you make Period sparse, Essbase has to perform cross-block (hard drive I/O) reads to calculate Q1 from Jan, Feb, and Mar. This will destroy calculation performance.

### Block Count Estimation

```
Block Count = Product of all Sparse dimension Level 0 member counts
              (Only for combinations where data exists)

Example:
Entity: 50 Level 0
Scenario: 3 (Actual, Budget, Forecast)
Version: 2 (Working, Approved)
Year: 3 (FY25, FY26, FY27)

Maximum Blocks = 50 × 3 × 2 × 3 = 900 blocks
Actual Blocks = ~60% density = ~540 blocks (typical)
```

### Data Storage Properties Impact

| Storage Type | Performance Impact |
|-------------|-------------------|
| **Store** | Uses disk space, fast retrieval |
| **Dynamic Calc** | No disk, calculated on-the-fly — can be slow for complex formulas |
| **Dynamic Calc & Store** | Calculated once, then cached |
| **Label Only** | No impact — no data |
| **Shared** | Minimal — points to existing data |
| **Never Share** | Creates unique blocks for members that would normally share |

**Rule of thumb:**
- Level 0 (leaf) accounts → **Store**
- Parent accounts → **Dynamic Calc** (aggregation on retrieval)
- Ratios/percentages → **Dynamic Calc** + Two-Pass
- Grouping headers → **Label Only**

## ⚡ Pillar 2: Calculation Performance

### FIX Scope Optimization

```
❌ BAD: No FIX — calculates everything
"Revenue" = "Units" * "Price";

✅ GOOD: Narrow FIX
FIX("Budget", "Working", "FY26", @RELATIVE("Entity", 0))
    "Revenue" = "Units" * "Price";
ENDFIX

✅ BEST: FIX + SET optimization
SET UPDATECALC ON;
SET CREATEBLOCKONEQ ON;
FIX("Budget", "Working", "FY26", @RELATIVE("Entity", 0))
    "Revenue" = "Units" * "Price";
ENDFIX
```

### SET Command Performance Impact

| SET Command | Effect | When to Use |
|-------------|--------|-------------|
| `SET UPDATECALC ON` | Only recalculate "dirty" blocks | After incremental data changes |
| `SET UPDATECALC OFF` | Recalculate ALL blocks | After full data reload |
| `SET CREATEBLOCKONEQ ON` | Create blocks for new assignments | When writing to new sparse combinations |
| `SET AGGMISSG OFF` | Skip missing values in aggregation | When missing = truly no data |
| `SET CACHE HIGH` | Allocate more memory to calc | Large calculations |
| `SET MSG SUMMARY` | Reduce log verbosity | Production (less I/O) |

### Calculation Order

```
Optimal Order (Bottom-Up):
1. Calculate Level 0 formulas first
2. Aggregate up the hierarchy
3. Calculate parent-level formulas (Dynamic Calc or Two-Pass)

Avoid:
- Calculating parents before children (causes recalculation)
- Mixing aggregation with member formulas (evaluation order conflicts)
```

### Common Calc Performance Killers

| Problem | Impact | Fix |
|---------|--------|-----|
| `CALC ALL` | Calculates EVERYTHING | Use targeted FIX + AGG |
| Broad FIX scope | Millions of unnecessary cells | Narrow to Level 0, specific scenarios |
| Nested cross-dim references | Slow cell-by-cell lookup | Pre-calculate intermediate results |
| Too many Dynamic Calc members | Slow form retrieval | Convert some to Store |
| Large data copies without FIX | Copies all dimensions | FIX to specific entities/scenarios |

## ⚡ Pillar 3: Form/Retrieval Performance

### Form Design for Speed

| Optimization | Impact |
|-------------|--------|
| **Suppress Missing Data** | ⬆️ High — skips empty rows |
| **Suppress Missing Blocks** | ⬆️ High — skips blocks with no data |
| **Suppress Zero** | ⬆️ Medium — hides zero-value rows |
| **Limit member selections** | ⬆️ High — fewer cells to retrieve |
| **Use Page dimensions wisely** | ⬆️ Medium — lazy-load on page change |
| **Avoid too many business rules on load** | ⬆️ High — rules add load time |

### Form Size Guidelines

| Metric | Guideline |
|--------|-----------|
| Rows × Columns | Keep under 5,000 cells per form |
| Maximum rows | ~500 visible rows |
| Maximum columns | ~50 columns |
| POV dimensions | 5+ dimensions in POV (fixed) |
| Page dimensions | 1-2 dimensions as pages (switchable) |

### Smart View Performance

| Tip | Reason |
|-----|--------|
| Use forms over ad-hoc for regular work | Forms are pre-optimized |
| Close unused connections | Each consumes a server session |
| Use HsGetValue sparingly | Each call = a round trip to server |
| Avoid large ad-hoc grids | > 10,000 cells = slow |
| Refresh specific sheets, not all | Targeted refresh = faster |

## 📌 Monitoring & Diagnostics

### Activity Reports

```
Navigation: Home → Tools → Activity Reports

What to monitor:
├── Top 10 slowest forms (load time > 5 seconds = investigate)
├── Top 10 slowest rules (execution time patterns)
├── Data load times (increasing trend = problem)
├── User concurrency (peak usage patterns)
└── Failed operations (errors indicate issues)
```

### Key Metrics to Track

| Metric | Target | Action if Exceeded |
|--------|--------|-------------------|
| Form load time | < 5 seconds | Check suppression, reduce members |
| Rule execution | < 60 seconds for common rules | Optimize FIX scope |
| Data load | < 5 minutes for daily loads | Check file size, mapping efficiency |
| Smart View refresh | < 10 seconds | Check grid size, network latency |

## ⚡ Performance Checklist

```
Database Design:
□ Dense/Sparse assignment follows data patterns
□ Block size is between 10-100 KB
□ Block count is manageable (< 100K blocks)
□ Level 0 = Store, Parents = Dynamic Calc
□ Label Only for grouping members
□ Never Share for rates/percentages

Calculations:
□ All rules use FIX statements
□ SET CREATEBLOCKONEQ ON where needed
□ No CALC ALL in production
□ Substitution variables instead of hardcoded values
□ Rule sets for multi-step processes

Forms:
□ Suppress Missing Data enabled
□ Suppress Missing Blocks enabled
□ Cell count under 5,000
□ Minimal rules on form load
□ Pages used for frequently-switched dimensions

Monitoring:
□ Activity Reports reviewed weekly
□ Slow forms/rules identified and optimized
□ Data load trends tracked
```

## 🎓 Interview Questions

**Q: What are the 3 pillars of EPM performance—**
> A: Database design (Dense/Sparse, block size), Calculation performance (FIX scope, SET commands), and Retrieval performance (form design, suppression settings).

**Q: How do you determine optimal block size—**
> A: Multiply all Level 0 members of Dense dimensions. Multiply by 8 bytes per cell. Target 10-100 KB per block. If too large, consider moving a Dense dimension to Sparse.

**Q: Why is CALC ALL bad for performance—**
> A: CALC ALL recalculates every cell in every block across all dimensions. In a production application with millions of intersections, this can take hours. Use targeted FIX statements instead.

**Q: How do you optimize a slow form—**
> A: (1) Enable Suppress Missing Data and Suppress Missing Blocks, (2) reduce the number of rows/columns, (3) move dimensions to POV that don't need to be on the grid, (4) remove on-load business rules, (5) check if Dynamic Calc members are causing slow retrieval.

**Q: What is SET UPDATECALC and when should you use it—**
> A: SET UPDATECALC ON tells Essbase to only recalculate blocks that have been modified since the last calculation. Use it after incremental updates (e.g., user entered data in one form). Turn it OFF after a full data reload to ensure everything is recalculated.
