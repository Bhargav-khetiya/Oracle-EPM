## 🏢 Overview

Production support for Oracle EPBCS involves daily monitoring, scheduled maintenance, incident response, backup management, and environment administration. A well-run production environment requires proactive monitoring and documented runbooks.

## 📌 Daily Checklist

| # | Task | How | Priority |
|---|------|-----|----------|
| 1 | Check overnight data loads | Job Console → filter by Import | 🔴 Critical |
| 2 | Verify scheduled rule completions | Job Console → filter by Rules | 🔴 Critical |
| 3 | Review Activity Reports | Tools → Activity Reports | 🟡 Important |
| 4 | Check disk space / database size | Application → Statistics | 🟡 Important |
| 5 | Verify user login issues | Check support tickets | 🟡 Important |
| 6 | Monitor form performance | Activity Reports → Form Load Times | 🟢 Regular |

### 💡 Logic & Purpose
Production Support isn't just about fixing broken things; it's about detecting degradation *before* it becomes an outage. By establishing a baseline for rule runtimes and form load times, admins can spot when the database needs restructuring. The daily checklist ensures the core mechanics (data flow and calculations) succeeded overnight so users don't start their day with stale data.

### 🌀 Confusion Resolution
> **Misconception:** "I check the EPM Automate log every morning. If the batch script returns `Exit Code 0`, I know the data loaded successfully and I don't need to check anything else."
> **Reality:** An `Exit Code 0` from EPM Automate merely means the REST API call didn't crash. It does NOT guarantee data integrity! The `importData` job could have successfully executed, but Data Management might have rejected 100% of the rows due to an unmapped account. Admins must spot-check actual data intersections in a form (e.g., checking `Total Revenue` against the ERP source) to verify true success.

### 😈 Twisted Interview Question
**Question:** A Junior Admin notices that the overnight "Calculate Actuals" business rule, which normally takes 5 minutes, took 45 minutes last night. The rule did not fail, it just ran slowly. The admin checks the Job Console and sees no other rules were running at the same time. What is the most likely structural cause of this sudden performance degradation?
> **Answer:** The database likely requires a restructure due to excessive block fragmentation or a massive metadata hierarchy change the day before. When new dimension members are added (especially Sparse ones) and data is loaded, Essbase creates new physical blocks. Over time, these blocks become fragmented on the disk, drastically slowing down calculation I/O. A simple "Cube Refresh" or running a database Restructure usually resolves this immediately.

## 📌 Incident Management

### Severity Levels

| Severity | Definition | Response Time | Examples |
|----------|-----------|---------------|---------|
| **P1 — Critical** | System down, all users affected | 15 minutes | EPM Cloud unreachable, data corruption |
| **P2 — High** | Major feature broken, many users affected | 1 hour | Data load failing, key forms not working |
| **P3 — Medium** | Feature degraded, some users affected | 4 hours | Slow performance, specific rule failing |
| **P4 — Low** | Minor issue, workaround available | Next business day | Cosmetic form issue, minor report error |

### Incident Response Flow

```
1. IDENTIFY → User reports issue or monitoring alerts
2. ASSESS → Determine severity (P1-P4)
3. COMMUNICATE → Notify stakeholders
4. DIAGNOSE → Use DRILL method (see Debugging guide)
5. RESOLVE → Fix the issue
6. VERIFY → Confirm fix with user
7. DOCUMENT → Update runbook, write RCA
8. PREVENT → Add monitoring or automation to prevent recurrence
```

### Root Cause Analysis (RCA) Template

```markdown
## 📌 Incident: [Title]
- **Date:** YYYY-MM-DD
- **Severity:** P1/P2/P3/P4
- **Duration:** X hours
- **Affected Users:** N users / All users

## 📌 Timeline
- HH:MM — Issue reported by [user]
- HH:MM — Investigation started
- HH:MM — Root cause identified
- HH:MM — Fix applied
- HH:MM — Verified and closed

## 📌 Root Cause
[What actually caused the problem]

## 📌 Resolution
[What was done to fix it]

## 📌 Prevention
[What changes will prevent recurrence]
```

## 📌 Backup & Recovery

### Backup Strategy

| Type | Frequency | Tool | Retention |
|------|-----------|------|-----------|
| **Daily Snapshot** | Every night | EPM Automate | 7 days |
| **Weekly Snapshot** | Every Sunday | EPM Automate | 4 weeks |
| **Monthly Snapshot** | First of month | EPM Automate | 12 months |
| **Pre-change Snapshot** | Before any major change | Manual | Until verified |

### Backup Script

```batch
@echo off
SET SNAPSHOT_NAME=Daily_%DATE:~-4%_%DATE:~4,2%_%DATE:~7,2%

epmautomate login %EPM_USER% %EPM_PWD% %EPM_URL% %EPM_KEY%
epmautomate exportSnapshot %SNAPSHOT_NAME%

:: Clean old snapshots (keep last 7)
epmautomate listFiles | findstr "Daily_" > snapshots.txt
:: Manual cleanup or scripted retention
epmautomate logout
```

### Recovery Procedure

```
1. Assess impact and decide recovery point
2. Login to EPM Cloud
3. List available snapshots: epmautomate listFiles
4. Import snapshot: epmautomate importSnapshot "SnapshotName"
5. Verify data integrity
6. Notify users
```

## 📌 Environment Management

### Environments

| Environment | Purpose | Data |
|-------------|---------|------|
| **DEV** | Development and testing | Test data |
| **TEST/UAT** | User acceptance testing | Subset of production data |
| **PROD** | Production | Real data |

### Environment Refresh Flow

```
PROD → Export Snapshot → Copy to TEST → Recreate → Import
TEST → Export Snapshot → Copy to DEV → Recreate → Import
```

### Migration Promotion Flow

```
DEV → Test changes → Promote to TEST → UAT sign-off → Promote to PROD
```

What to migrate (via LCM/Snapshot):
- Metadata changes
- Business rules
- Forms
- Task lists
- Security settings

What NOT to migrate:
- Data (usually)
- Substitution variable values
- User-specific settings

## 🎓 Interview Questions

**Q: What does a typical daily support routine look like for an EPM admin?**
> A: Check overnight job status (data loads, scheduled rules) in Job Console, review Activity Reports for performance issues, verify user login issues, check disk usage, and address any open support tickets.

**Q: How do you handle a P1 incident where EPM is down?**
> A: Immediate response within 15 minutes. Communicate to all stakeholders. Check Oracle Cloud Status page first. If it's an Oracle infrastructure issue, raise an SR (Service Request). If it's application-level, check Job Console and recent changes. Apply fix and verify.

**Q: How do you manage backups in EPM Cloud?**
> A: Schedule daily snapshots via EPM Automate, keep weekly and monthly backups with different retention periods. Always take a pre-change snapshot before any major modification. Test restore procedures periodically.

**Q: How do you refresh TEST from PROD?**
> A: Export snapshot from PROD → Use `copySnapshotFromInstance` to copy to TEST → Run `recreate -f` on TEST → Import snapshot. Reset passwords for test users. Update substitution variables if needed.
