### ðŸŽ¯ Logic & Purpose
The Oracle Cloud release cycle is aggressive. Oracle pushes mandatory updates to the TEST environment on the 1st Friday of the month, and to PROD on the 3rd Friday. The gap between these dates is your critical testing window. Monthly administrative tasks must align with this cycle. If an update breaks a custom business rule in TEST, you have exactly two weeks to log an SR (Service Request) and halt the PROD push.

### ðŸŽ¯€ Confusion Resolution
> **Misconception:** "Oracle Cloud is SaaS (Software as a Service), so Oracle handles all the patching and updates. I don't need to test anything; Oracle guarantees it won't break."
> **Reality:** Oracle guarantees that *their* core software won't break, but they DO NOT guarantee that *your* highly customized Groovy scripts, complex Data Management SQL mappings, or bespoke Business Rules will survive an underlying engine change! You must perform regression testing on your most critical business processes in the TEST environment every month before PROD gets patched.

### ðŸ˜ˆ Twisted Interview Question
**Question:** It's the second week of the month. An admin notices that a critical calculation script is failing in the TEST environment, but it still works perfectly in PROD. The admin traces the issue to a change Oracle made in the monthly patch (which hit TEST last Friday). The admin opens an SR with Oracle to fix it, but Oracle says the fix will take 30 days. What MUST the admin do immediately to prevent disaster—
> **Answer:** The admin must immediately request a **Skip Update** (or "Hold") for the PROD environment via the SR! If they do not explicitly halt the PROD patch, Oracle will automatically push the broken update to PROD on the 3rd Friday, crashing the live production system. Oracle allows clients to defer a PROD patch for up to two months in the event of a regression bug.

## ðŸŽ¯ Oracle Monthly Updates — Complete Guide

### Update Timeline

```
Week 1: Oracle publishes Readiness document
         → Download from Oracle Cloud Readiness
         → Review ALL changes — especially "Changed Behavior"
         → Identify any impact on your application

Week 2: Non-production environments update (automatic)
         → Test your application in non-prod
         → Run key forms, rules, data loads
         → Report any issues to Oracle (SR)

Week 3: Production update (automatic, scheduled window)
         → Backup before update (export snapshot)
         → After update: verify key functionality
         → Communicate to users if any changes

Week 4: Post-update stabilization
         → Monitor for any issues
         → Update documentation if needed
```

## ðŸŽ¯ Backup Strategy — Complete

### Backup Types

| Type | What's Included | How to Create | Frequency |
|------|----------------|---------------|-----------|
| **Maintenance Snapshot** | Everything (data + metadata + forms + rules + security) | `epmautomate exportSnapshot` | Daily |
| **LCM Export** | Selected artifacts (no data) | Tools → Migration → Export | Before deployments |
| **Data Export** | Data only (CSV format) | `epmautomate exportData` | As needed |
| **Metadata Export** | Dimension members only | `epmautomate exportMetadata` | Before metadata changes |

### Backup Automation Script

```batch
@echo off
REM Daily Backup — Schedule at 11:00 PM
SET DATE_STAMP=%date:~-4%%date:~4,2%%date:~7,2%
SET SNAP_NAME=Daily_Backup_%DATE_STAMP%

epmautomate login %USER% %PWD% %URL% %KEY%
IF ERRORLEVEL 1 (echo Backup FAILED: login error & exit /b 1)

REM Create snapshot
epmautomate exportSnapshot "%SNAP_NAME%"
IF ERRORLEVEL 1 (echo Backup FAILED: snapshot error & exit /b 2)

REM Keep only last 7 snapshots (delete older ones)
REM (Manual step — review and delete old snapshots weekly)

epmautomate logout
echo Backup %SNAP_NAME% created successfully
```

### Recovery Procedures

| Scenario | Recovery Method | Estimated Time |
|----------|----------------|---------------|
| Accidental data overwrite | Restore from daily snapshot | 15-60 min |
| Bad rule deployment | Redeploy previous version via LCM | 5-10 min |
| Metadata corruption | Restore from snapshot | 30-60 min |
| Full application recovery | Recreate + import snapshot | 1-2 hours |
| Cross-environment refresh | Copy snapshot from source | 1-2 hours |

## ðŸŽ¯ Interview Questions

**Q: Describe your daily admin routine for an EPM application.**
> (1) Check Job Console for overnight failures. (2) Review EPM Automate batch logs. (3) Spot-check key data points. (4) Check user support queue. (5) Review Activity Reports for performance issues. Takes ~15 minutes every morning.

**Q: How do you handle Oracle's monthly updates—**
> (1) Read the Readiness document as soon as it's published. (2) Identify any breaking changes. (3) Test in non-prod when it updates first. (4) Backup PROD before update. (5) Run verification checklist after PROD updates. (6) Communicate any changes to users.

**Q: A user says data was lost. What do you do—**
> (1) Verify the data is actually missing (check POV, security). (2) Check Audit log — who changed what, when— (3) Check if CLEARDATA was run. (4) If data is truly lost — restore from the most recent snapshot backup. (5) Document the incident and implement prevention.
