## 📌 Beginner

**Q1: What are dimensions in EPBCS—**
> Dimensions are business categories that classify data — Account, Entity, Period, Year, Scenario, Version, Currency. Each dimension contains members (individual items). Together, dimensions form the multi-dimensional cube structure.

**Q2: What is the difference between a standard dimension and a custom dimension—**
> Standard dimensions are pre-built by Oracle and are mandatory (Account, Entity, Period, Year, Scenario, Version, Currency). Custom dimensions are user-defined and added based on business needs (Department, Product, Channel).

**Q3: What are the 6 Data Storage properties—**
> (1) Store — physically saves data, (2) Dynamic Calc — calculated on-the-fly, never stored, (3) Dynamic Calc and Store — calculated once then cached, (4) Label Only — no data, used for grouping, (5) Shared Member — points to another member's data, (6) Never Share — forces unique block, prevents implied sharing.

**Q4: What is an alias in EPBCS—**
> An alias is a user-friendly display name for a dimension member. Example: Member code `100110` has alias `Rooms Revenue`. Aliases are stored in alias tables (Default, Reporting, etc.) and appear in forms/reports instead of codes.

**Q5: What is a Smart List—**
> A Smart List is a custom dropdown menu in data forms that maps text selections to numbers. Example: "Yes"=1, "No"=0. The user sees text, but Essbase stores the number. Used for status tracking, approval flags, etc.

## 📌 Intermediate

**Q6: What is the difference between Generation and Level—**
> Generation counts top-down (Root = Gen 1, children = Gen 2, etc.). Level counts bottom-up (Leaf/Level 0, parent = Level 1, etc.). Both identify hierarchy position but from opposite directions. Level 0 members are where data is entered.

**Q7: What are consolidation operators and when do you use each—**
> (+) Addition — default, adds child to parent. (-) Subtraction — subtracts from parent (e.g., Expenses). (~) Ignore — excluded from aggregation (used for Label Only, ratios). (^) Never consolidate — similar to Ignore but prevents all aggregation.

**Q8: Explain Time Balance property with examples.**
> Time Balance controls how monthly values roll up to quarters/years. Flow (default) = sum all months. First = take first month's value (e.g., opening balance). Balance = take last month's value (e.g., closing balance). Average = average of months.

**Q9: What is a Shared Member and when would you use one—**
> A Shared Member exists in an alternate hierarchy but points to the same stored data as its primary instance. Use case: Revenue member appears under both "Total Revenue" (primary) and "Hotel Revenue" (alternate grouping) — no data duplication.

**Q10: What is implied sharing and when does it occur—**
> When a parent has exactly one child, Essbase automatically shares the value between them (parent = child). This is "implied sharing." Adding a second child breaks it — the parent starts aggregating. Use Never Share to prevent it for rate/price members.

### 😈 Twisted Interview Question
**Question:** A developer uses a business rule to clear data at a parent member level: `CLEARDATA "Total_Revenue";`. The rule runs successfully. However, the user complains that the single child member `"Product_Revenue"` under it was also wiped out! Why did clearing the parent clear the Level 0 child—
> **Answer:** Because of Implied Sharing! Since the parent had only one child, Essbase treated the parent and the child as the *exact same physical memory pointer*. When the developer told Essbase to wipe the parent, Essbase wiped the shared pointer, instantly destroying the child's data. To fix this, the developer must set the parent to `Never Share` so they maintain distinct physical blocks.

**Q11: What are Attribute Dimensions—**
> Attribute dimensions classify members of standard dimensions by characteristics. Example: Account dimension with an attribute "Account Category" (Revenue, Expense, Asset). Used for filtering and analysis — "show me all Revenue accounts."

**Q12: What is Two-Pass Calculation—**
> Two-Pass forces a member to be recalculated AFTER all other members are aggregated. Essential for ratios and percentages. Without Two-Pass, "Profit Margin %" would be calculated at each entity, then those percentages would be summed (meaningless). With Two-Pass, it recalculates at the parent level after aggregation.

## 📌 Advanced

**Q13: How do you design an Account dimension for a real project—**
> (1) Map to Chart of Accounts from ERP. (2) Use hierarchical grouping with Label Only parents. (3) Set Account Types correctly (Revenue, Expense, Asset, Liability). (4) Set Time Balance (Flow for P&L, Balance for BS). (5) Set Variance Reporting (Expense vs Non-Expense). (6) Use Never Share for rates/percentages. (7) Mark calculated accounts as Dynamic Calc.

**Q14: What is the Evaluation Order in Essbase and why does it matter—**
> Essbase calculates in this order: (1) Member formulas first, (2) Consolidation operators second, (3) Two-Pass calculations last. If you have both a formula and a consolidation operator on the same member, the formula takes precedence. Understanding this prevents wrong totals.

**Q15: How do you handle a situation where a member needs different parents in different hierarchies—**
> Use Shared Members. The primary instance sits under one parent with Store data storage. The shared instance sits under the alternate parent with Shared data storage. Both point to the same data — no duplication.

**Q16: What is Skip Value and when should you use it—**
> Skip Value controls how missing/zero values affect Time Balance calculations. Options: None (include everything), Missing (skip missing), Zeros (skip zeros), Missing and Zeros (skip both). Critical for Balance accounts — if March has no entry, should Q1 show February's closing balance or zero—

**Q17: How would you optimize a dimension with 5,000 members for performance—**
> (1) Set parents as Dynamic Calc (aggregate on-the-fly). (2) Use Label Only for pure grouping. (3) Minimize dense dimension members to control block size. (4) Use Never Share where needed. (5) Consider attribute dimensions instead of deeply nested hierarchies. (6) Remove unused members.

## 📌 Scenario-Based

**Q18: A client says their P&L report shows Expenses as positive numbers but they want negative. What do you check—**
> Check the Variance Reporting property on expense accounts. If set to "Expense," positive variance means favorable (actual < budget). For display, check the consolidation operator — expenses should use (+) to add up, but the Variance property controls sign convention in reports.

**Q19: After adding a new entity, data doesn't appear on forms. What's wrong—**
> Possible causes: (1) Cube not refreshed after metadata change. (2) Security not assigned for new entity. (3) Data not loaded for new entity. (4) Form member selection doesn't include the new member. (5) Substitution variable not updated.

**Q20: A rate member (Tax Rate = 30%) is showing 90% at the parent level. What happened—**
> The parent is summing the child rates: 3 children × 30% = 90%. Fix: Set the Tax Rate member to Never Share data storage with Ignore (~) consolidation operator. This prevents meaningless aggregation of rates.

## 📌 Expert

**Q21: Explain the difference between UDA, Attribute Dimension, and Smart List. When would you use each—**
> UDA: A text tag on a member for calc script filtering (@UDA). Use when you need to group members for calculation purposes. Attribute: A separate dimension that classifies members for analysis/reporting. Use for cross-dimensional analysis. Smart List: A dropdown in forms for user input. Use when users need to select predefined options.

**Q22: How do you handle multi-currency in EPBCS—**
> (1) Enable Currency dimension. (2) Set Exchange Rate Type per account (Average for P&L, Ending for Balance Sheet, Historical for Equity). (3) Load exchange rates to a rates table/dimension. (4) Create currency translation business rules. (5) Use Local currency for input, Reporting currency for consolidated views.

**Q23: What is the impact of making a Dense dimension Sparse (or vice versa) on an existing application—**
> It triggers a full database restructure. Dense→Sparse: Blocks get smaller (good for retrieval), more blocks created (higher index). Sparse→Dense: Blocks get larger (may exceed optimal size), fewer blocks. Always analyze data patterns and test in DEV first. Requires application offline during restructure.

**Q24: How do you implement alternate rollups in the Entity dimension—**
> Use Shared Members. Primary hierarchy: Geographic (Americas → US → NY). Alternate hierarchy: Business Line (Retail → US-Retail). US is stored under Americas (primary, Store). US is shared under Retail (secondary, Shared). Both report the same data.

**Q25: Design the dimension structure for a company with 100 entities, 500 accounts, 5 departments, 3 scenarios, across 5 years.**
> Account (500 L0) → Dense. Period (12) → Dense. Block size = 500×12 = 6,000 cells = ~47KB ✅. Entity (100 L0) → Sparse. Scenario (3) → Sparse. Version (2) → Sparse. Year (5) → Sparse. Department (5) → Sparse (if data density is low) or Dense (if every entity has all departments). Max blocks = 100×3×2×5×5 = 15,000. Total data = 15,000 × 47KB = ~690 MB. Acceptable for EPBCS.
