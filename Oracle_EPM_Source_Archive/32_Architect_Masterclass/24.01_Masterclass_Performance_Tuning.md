# Architect Masterclass: Advanced Performance Tuning

This masterclass goes beyond basic block optimization and explores the deepest levels of Essbase BSO performance tuning.

## 1. The Two-Pass Calculation Trap

The "Two-Pass" property is a checkbox on Account dimension members. It tells Essbase: "Calculate the entire database normally, then go back and calculate this member a second time."

*   **Why use it?** It is mandatory for ratio accounts (e.g., Gross Margin %). If you don't calculate the % *after* the raw dollars roll up to the parent entity, your parent entity will just add up the percentages of its children (e.g., 50% + 50% = 100% Gross Margin), which is mathematically wrong.
*   **The Trap:** If you tag hundreds of members as Two-Pass, the default Essbase aggregation script (`CALC ALL;`) will grind to a halt. It literally runs the entire database calculation twice.
*   **The Masterclass Solution:** Never use `CALC ALL`. Always write custom aggregation scripts. Use `CALC DIM(Entity);` to roll up the dollars, and rely on Dynamic Calc (or Hybrid BSO) for your ratio accounts so they calculate instantly on query rather than consuming batch calculation time.

## 2. Optimizing the FIX Statement (Top-Down vs Bottom-Up)

By default, Essbase calculations are Bottom-Up. It finds existing data blocks at Level 0 and calculates them.

*   **The Issue:** If you want to allocate $100,000 from a Parent Cost Center down to its children based on headcount, Essbase struggles because the children might not have blocks yet.
*   **The Fix:** You must force a Top-Down calculation.
    ```essbase
    /* Force Essbase to look at the parent first, then push down */
    SET UPDATECALC OFF;
    FIX ("Parent_Cost_Center")
        "Allocated_Expense" (
            @ALLOCATE("Rent", @CHILDREN("Parent_Cost_Center"), "Headcount", , share);
        )
    ENDFIX
    ```

## 3. Parallel Calculation (`SET CALCPARALLEL`)

This command allows Essbase to split a task across multiple CPU cores.

*   **The Rule of Thumb:** If your server has 8 cores, set it to `SET CALCPARALLEL 6;`. Never max it out, or the OS will choke.
*   **The Constraint:** CalcParallel only works on *Sparse* dimensions. Essbase takes the sparse blocks and divides them among the threads. If your `FIX` statement only contains Dense dimensions, `CALCPARALLEL` will be ignored entirely. Ensure you are fixing on large sparse hierarchies (like Entity or Product) to get the multi-threading benefit.
