## 1. WHY — What Problem Do Member Properties Solve—

**The problem:** Each dimension member isn't just a name — it has behaviors. How does it aggregate— Is it stored or calculated on-the-fly— What alias does it show— What data type is it— These properties control how Essbase processes and displays each member.

**The solution:** Member Properties are **configuration attributes** for every dimension member that control storage, calculation, display, and behavior.

## 3. COMPLETE MEMBER PROPERTIES — ALL DIMENSIONS

### 3.1 Properties Common to ALL Members

| Property | Options | Default | Description |
|----------|---------|---------|-------------|
| **Member Name** | Text (unique) | — | Internal name (no duplicates across ALL dims) |
| **Alias** | Text | Same as name | Display name shown to users (alias table) |
| **Description** | Text | Empty | Optional description |
| **Data Storage** | Store, Dynamic Calc, Dynamic Calc and Store, Never Share, Label Only, Shared | Store | How data is stored/calculated |
| **Aggregation** | +, -, *, /, %, ~, Never | + | How child rolls up to parent |
| **Two Pass Calculation** | ☑/☐ | ☐ | Recalculate after initial pass (for ratios) |
| **Smart List** | [Select] / None | None | Attach dropdown for text-based input |
| **Data Type** | Currency, Non-currency, Percentage, Smart List, Date, Text | Currency | How data is formatted/processed |
| **Plan Type (Cube)** | ☑ per cube | All checked | Which cubes this member belongs to |
| **UDA (User Defined Attribute)** | Text tags | None | Custom tags for filtering/formulas |
| **Member Formula** | Essbase formula | None | Custom calculation formula |

### 3.2 Data Storage Options — CRITICAL KNOWLEDGE

| Storage Option | Data Stored— | Calculated— | Blocks Created— | When to Use |
|---------------|-------------|-------------|----------------|-------------|
| **Store** | ✅ Yes | ❌ No | ✅ Yes | Leaf members (data entry points) |
| **Dynamic Calc** | ❌ No | ✅ On-the-fly | ❌ No | Parent members, ratios, KPIs |
| **Dynamic Calc and Store** | ✅ After calc | ✅ First time | ✅ After calc | Rarely used — complex scenarios |
| **Never Share** | ✅ Yes | ❌ No | ✅ Yes | Prevent implied sharing |
| **Label Only** | ❌ No | ❌ No | ❌ No | Hierarchy organizers (no data) |
| **Shared** | ❌ (points to base) | ❌ | ❌ | Alternate hierarchies |

### 3.3 Aggregation Options

| Operator | Symbol | Meaning | Example |
|----------|--------|---------|---------|
| **Addition** | + | Child adds to parent | Revenue = Room_Rev + F&B_Rev + Spa_Rev |
| **Subtraction** | - | Child subtracts from parent | Net = Revenue - Expense |
| **Multiplication** | * | Child multiplies | Rarely used |
| **Division** | / | Child divides | Rarely used |
| **Percentage** | % | Child is percentage of parent | Rarely used |
| **Ignore** | ~ | Child ignored in aggregation | For comment/text members |
| **Never** | Never | No aggregation | For input-only members |

## 4. ACCOUNT-SPECIFIC PROPERTIES

| Property | Options | Description |
|----------|---------|-------------|
| **Account Type** | Revenue, Expense, Asset, Liability, Equity, Saved Assumption | Controls time balance and variance reporting |
| **Time Balance** | Flow, First, Balance, Average, Fill | How data aggregates across time periods |
| **Skip Value** | None, Missing, Zeros, Missing and Zeros | Which values to skip in time balance |
| **Variance Reporting** | Expense, Non-Expense | How variance is calculated (positive = good or bad) |
| **Exchange Rate Type** | None, Average, Ending, Historical | Which exchange rate to use for currency conversion |
| **Source Plan Type** | [Cube selection] | Which cube provides data for this account |

### Time Balance Explained

| Time Balance | Meaning | Example |
|-------------|---------|---------|
| **Flow** | Values add across periods | Revenue: Jan(100) + Feb(150) + Mar(120) = Q1(370) |
| **First** | Parent = first child's value | Opening Balance: Q1 = Jan value |
| **Balance** (Last) | Parent = last child's value | Closing Balance: Q1 = Mar value |
| **Average** | Parent = average of children | Avg Headcount: Q1 = (Jan+Feb+Mar)/3 |
| **Fill** | Parent value fills all children | Exchange Rate: Q1 rate fills Jan, Feb, Mar |

### Account Type + Variance Reporting Interaction

| Account Type | Variance Reporting | Positive Variance Means |
|-------------|-------------------|----------------------|
| Revenue | Non-Expense | Actual > Budget = GOOD (favorable) |
| Expense | Expense | Actual < Budget = GOOD (favorable) |
| Asset | Non-Expense | Higher = GOOD |
| Liability | Expense | Lower = GOOD |

## 9. COMMON MISTAKES AND FIXES

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Parent set to "Store" instead of "Dynamic Calc" | Blocks explode, performance degrades | Change to Dynamic Calc, refresh database |
| Wrong Account Type (Revenue vs Expense) | Variance shows wrong direction | Change Account Type, verify Variance Reporting |
| Time Balance = "Flow" for a balance sheet account | Q1 = Sum of Jan+Feb+Mar (wrong — should be Mar closing) | Change to "Balance" (Last) |
| Missing "Two Pass" on ratio members | Ratio calculated before aggregation, shows wrong | Enable Two Pass Calculation |
| Shared member not pointing to correct base | Data doesn't match between hierarchies | Delete and recreate shared member correctly |
| Smart List assigned but Data Type not changed | Dropdown doesn't appear in forms | Set Data Type to "Smart List" |

## 10. INTERVIEW QUESTIONS

### Beginner
**Q: What is the difference between "Store" and "Dynamic Calc" data storage—**
> **A:** **Store** means the data value is physically saved in the Essbase database (occupies block space). Use it for leaf members where users enter data. **Dynamic Calc** means the value is calculated on-the-fly every time it's queried — it's never stored. Use it for parent members (aggregation) and calculated KPIs (like ratios). Dynamic Calc saves space and improves performance because no blocks are created for those members.

### Intermediate
**Q: ADR (Average Daily Rate) = Room Revenue / Occupied Rooms. Both are aggregated from 5 hotels. When you view the All Hotels total, ADR shows a wrong number. What's wrong—**
> **A:** ADR needs **Two Pass Calculation** enabled. Without it, Essbase calculates ADR before Revenue and Rooms are aggregated to the All Hotels level. With Two Pass, Essbase first aggregates Revenue and Rooms to All Hotels, THEN recalculates ADR = Aggregated Revenue / Aggregated Rooms. Also, ADR's Time Balance should be "Average" (not "Flow") and Account Type should be "Saved Assumption" (not Revenue). The member formula is: `"Room_Revenue" / "Occupied_Rooms";`

### Architect
**Q: A client has 250 Account members. 80% are level 0 (Store), 20% are parents. They report slow form loads. What member property changes would you recommend—**
> **A:** (1) Set ALL parent Account members to **Dynamic Calc** — this eliminates block creation for parents, dramatically reducing block count. (2) Enable **Hybrid Mode** at the app level — this automatically handles most parent calculations. (3) For any ratio/KPI members (like ADR, Occupancy%), set **Two Pass = ☑** and **Data Storage = Dynamic Calc**. (4) If any parents are "Label Only," keep them — they create no blocks. (5) Review the Account dimension's **Density setting** — Account should be Dense (it's the most common dense dimension). (6) After all changes, **Refresh Database** is required.
