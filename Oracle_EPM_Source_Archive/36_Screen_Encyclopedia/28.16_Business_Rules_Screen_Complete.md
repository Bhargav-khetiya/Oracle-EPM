## 1. WHY — What Problem Does Calculation Manager Solve—

**The problem:** Raw data entered into EPBCS forms is just the starting point. You need to:
- Roll up children to parents (aggregation)
- Calculate KPIs (Revenue per Room = Total Revenue / Total Rooms)
- Allocate costs across entities
- Perform currency conversions
- Run complex financial models (cash flow, balance sheet)
- Validate data (prevent negative headcount, enforce minimum wage)

**The solution:** Calculation Manager is the **rule engine** for EPBCS. It lets you create, validate, deploy, and run multidimensional calculations called **Business Rules**. Rules execute against the Essbase cube and manipulate data based on formulas, scripts, and conditions.

**Consultant importance:** After forms, business rules are the second most critical skill. Every EPBCS implementation has at least 10-50 business rules. You MUST know this screen.

---

## 2. WHAT — Plain English Definition

Calculation Manager is a **visual rule builder** embedded in EPBCS that produces:
- **Business Rules** — Individual calculations (formula-based or script-based)
- **Business Rulesets** — Groups of rules that run together (sequentially or simultaneously)
- **Components** — Building blocks: formulas, scripts, conditions, loops, ranges
- **Templates** — Reusable calculation patterns (system-provided or custom)

**Two types of rules:**
| Type | Description | Use Case |
|------|-------------|----------|
| **Calc Script Rules** | Traditional Essbase calculation scripts built via graphical designer | Standard aggregation, allocation, data copy |
| **Groovy Rules** | Rules written in Groovy scripting language | Complex logic, data validation, REST API calls, EPM Automate commands |

## 5. RULE DESIGNER — EVERY SECTION

### 5.1 Flow Chart Area (Graphical Mode)

The rule is shown as a **flow chart** from BEGIN to END:

```
BEGIN ──→ [Formula1] ──→ [Condition] ──→ [Script1] ──→ END
                            │
                            ├──→ [True: Formula2]
                            └──→ [False: Formula3]
```

**What you can drag into the flow chart:**

| Object | Category | Description |
|--------|----------|-------------|
| **Formula** | New Object | Visual formula builder with member selector |
| **Script** | New Object | Free-form Essbase calc script or Groovy script |
| **Condition** | New Object | IF-THEN-ELSE branching |
| **Fixed Loop** | New Object | Loop that runs a fixed number of times |
| **Metadata Loop** | New Object | Loop over dimension members |
| **Member Block** | New Object | FIX statement targeting specific members |
| **Member Range** | New Object | Data range specification |
| **DTP Assignment** | New Object | Design-Time Prompt assignment |
| **Existing Rule** | Existing Object | Embed another rule inside this rule |
| **Existing Template** | Existing Object | Use a system or custom template |

### 5.2 Properties Tabs (Below Flow Chart)

| Tab | Contents |
|-----|----------|
| **Properties** | General: Name, Description, Comments. Location: Application, Cube. Options: Create/Delete Dynamic Members, Enable Notifications |
| **Global Range** | Define common dimensions (FIX members) that apply to ALL components in the rule |
| **Variables** | Runtime prompt variables — appears only when rule has runtime prompts |
| **Script** | Read-only view of the generated Essbase calc script |
| **Usages** | Which rules, rulesets, and forms reference this rule |
| **Errors and Warnings** | Run diagnostics: validation errors, warnings, block estimates |

### 5.3 Designer vs Edit Script Mode

| Mode | How to Access | When to Use |
|------|---------------|-------------|

## 6. COMPONENT TYPES — COMPLETE REFERENCE

### Formula Component
**What it does:** Visual builder for Essbase formulas. Point-and-click member selection.
```
Example:
  "Room Revenue" = "ADR" * "Occupied Rooms";
  
Built visually:
  Source: ADR [Account dim → ADR member]
  Operator: * (multiply)
  Source: Occupied_Rooms [Account dim → Occupied_Rooms member]
  Target: Room_Revenue [Account dim → Room_Revenue member]
```

### Script Component
**What it does:** Free-form calc script or Groovy script. Maximum flexibility.
```
Example (Calc Script):
FIX("Budget", "Working", "FY2026")
  "Total Revenue" = "Room Revenue" + "F&B Revenue" + "Spa Revenue";
ENDFIX

Example (Groovy):
/* RTPS: {rtpEntity} */
def entity = rtps.rtpEntity.getEssbaseMemberName()
operation.grid.dataCellIterator().each { cell ->
  if (cell.data < 0) {
    cell.addValidationError(0xFF0000, "Negative values not allowed")
  }
}
```

### Condition Component
**What it does:** IF-THEN-ELSE branching in the flow chart.
```
Flow Chart:
  [Condition: Is Revenue > 0—]
       │
       ├── TRUE → [Formula: Calculate Profit Margin]
       └── FALSE → [Formula: Set Margin to 0]
```

### Fixed Loop Component
**What it does:** Runs a component a specified number of times.
```
Example: Run allocation 3 times for iterative allocation convergence
  Loop Count: 3
  Loop Body: [Allocation Formula]
```

### Metadata Loop Component
**What it does:** Loops over dimension members.
```
Example: Loop over all Entity members
  Dimension: Entity
  Members: IDescendants("All Hotels")
  Loop Body: [Per-entity calculation]
```

### Member Block Component (FIX)
**What it does:** Creates a FIX statement — restricts which members the calculation applies to.
```
Example:
  FIX("Budget", "Working", "FY2026", @CHILDREN("All Hotels"))
    ... calculation here ...
  ENDFIX
```

## 7. TOP 10 BEST PRACTICES FOR BUSINESS RULES (from Oracle)

1. **SET Commands:** Do NOT use `SET CREATEBLOCKONEQ ON` at the top of rules. Do NOT use `SET CLEARBLOCK EMPTY` in end-user rules.

2. **Block Creation:** Use `DATACOPY` or sparse member assignment for block creation. Use `@CREATEBLOCK` only as a last resort inside a limited FIX.

3. **Missing Dimension References:** Never omit dimensions from a FIX statement in Data Copy rules — this wastes processing time and creates unnecessary blocks.

4. **No Parallel in Form Rules:** `CALC PARALLEL` / `FIX PARALLEL` should ONLY be in admin/batch rules, NOT in rules attached to forms.

5. **Avoid Creating Zeros:** If `"Earned Premium" <> 0` — always add IF conditions. Zeros lead to block and data explosion.

6. **Eliminate Multiple Passes:** Don't loop over the same blocks repeatedly. Set a proper outer FIX and combine IF statements.

7. **Cross-Dim on Left Side:** Avoid cross-dimensional references on the LEFT side of equations. Performance impact.

8. **Aggregation Order:** Aggregate dimensions from MOST blocks to LEAST blocks: `AGG(Entity, Department, Product)`.

9. **Use Runtime Prompts:** Instead of creating 5 similar rules, create ONE rule with runtime prompts for Scenario, Version, Entity.

10. **Use Templates for Reuse:** Break business logic into templates. But templates should NOT contain full FIX/ENDFIX — the parent rule should manage the FIX.

## 8. GROOVY RULES — KEY CONCEPTS

### What Groovy Rules Can Do That Calc Scripts Cannot

| Capability | Calc Script | Groovy |
|-----------|-------------|--------|
| Data validation (prevent save) | ❌ | ✅ |
| Dynamic calc script generation | ❌ | ✅ |
| REST API calls | ❌ | ✅ |
| EPM Automate commands | ❌ | ✅ |
| Email notifications | ❌ | ✅ |
| Cross-cube data operations | Limited | ✅ |
| Smart List value manipulation | Limited | ✅ |
| Form context awareness | ❌ | ✅ |

### Groovy Rule Header
**Every Groovy rule MUST start with:**
```groovy
/* RTPS: */
```
**If it has runtime prompts:**
```groovy
/* RTPS: {rtpYear}, {rtpScenario} */
```

### Two Types of Groovy Rules
```
Type 1: Generate calc scripts dynamically
  → Groovy builds a calc script string and returns it to Essbase for execution

Type 2: Pure Groovy (no calc script)
  → Groovy directly manipulates data via Java API
  → Used for: data validation, grid iteration, cell-level operations
```

## 10. VALIDATE → DEPLOY → LAUNCH WORKFLOW

```
Step 1: CREATE the rule (Designer or Script mode)
    ↓
Step 2: SAVE the rule (Ctrl+S or Save button)
    ↓
Step 3: VALIDATE the rule
    → Right-click rule → Validate
    → Checks syntax, member names, FIX statements
    → Shows Errors, Warnings, Block estimates
    ↓
Step 4: DEPLOY the rule
    → Deployment View → Check the rule → Deploy
    → Makes rule available to end users in Planning
    → Without deployment, rule exists only in Calc Manager
    ↓
Step 5: LAUNCH the rule
    → From Calc Manager: Open rule → Run
    → From Planning: Rules page / Form / Task List / Dashboard
    → User fills in runtime prompts → Launch
```

> ⚠️ **Critical:** A rule can be saved but NOT deployed. Users will NOT see undeployed rules.

## 11. ERRORS AND WARNINGS TAB — DIAGNOSTICS

When you run diagnostics (Errors and Warnings tab → click run):

| Section | What It Shows |
|---------|-------------|
| **Summary** | # of data cells affected, # of passes through data, dimensions used incorrectly |
| **Warnings** | Missing sparse dimensions in cell references, cross-block assignments |
| **Blocks** | For each FIX: potential and estimated # of blocks affected |
| **Validation Errors** | Syntax errors, invalid member names, formula errors |

**Fix errors:** Right-click error → "Show in Script" or "Show in Designer" to jump to the problem.

## 12. HOTEL PVT LTD EXAMPLE

### Rule: Calculate Hotel P&L

```
Rule Name: Hotel_FinPlan_Rollup
Cube: OEP_FS
Type: Calc Script (Graphical)

Flow Chart:
BEGIN → [Member Block: FIX] → [Aggregation Template] → END

Member Block (FIX):
  Scenario: {rtpScenario}     ← Runtime Prompt
  Version: {rtpVersion}       ← Runtime Prompt
  Year: {rtpYear}             ← Runtime Prompt
  Entity: @CHILDREN("All Hotels")

Aggregation Template:
  Full Sparse Aggregation: Entity, Department
  Dense Aggregation: (empty — Account parents are Dynamic Calc)
  Aggregate missing values: Yes

Runtime Prompts:
  rtpScenario: Member type, Dimension = Scenario, Default = Budget
  rtpVersion: Member type, Dimension = Version, Default = Working
  rtpYear: Member type, Dimension = Year, Default = FY2026
```

### Groovy Rule: Validate Revenue Entry

```groovy
/* RTPS: */
// Prevent saving if any Revenue account has negative values
boolean hasErrors = false

operation.grid.dataCellIterator("Room_Revenue", "F&B_Revenue", "Spa_Revenue").each { cell ->
  if (cell.data < 0) {
    cell.addValidationError(0xFF0000, "Revenue cannot be negative: ₹${cell.data}")
    hasErrors = true
  }
}

if (hasErrors) {
  operation.grid.addValidationError("Please correct negative revenue values before saving.")
}
```

## 13. INTERVIEW QUESTIONS

### Beginner
**Q: You created a business rule in Calculation Manager and saved it. But when users go to the Rules page in Planning, they don't see it. Why—**
> **A:** The rule has been saved but NOT deployed. In Calculation Manager, go to the Deployment View, find the rule, check the checkbox to make it deployable, then right-click the application and select "Deploy". Only deployed rules are visible in Planning. Also check: (1) The rule's "Show on Rules Page" setting in Calculation Manager. (2) Users need "Launch" permissions on the rule.

### Intermediate
**Q: What is the difference between a Formula Component and a Script Component— When do you use each—**
> **A:** A **Formula Component** is a visual, point-and-click builder where you select members from dropdowns and the system generates the calc script automatically. It's best for simple, single-line calculations (e.g., `"Revenue" = "ADR" * "Rooms"`). A **Script Component** is a free-text editor where you write raw Essbase calc script (or Groovy). It's best for complex logic with FIX statements, IF conditions, loops, and multiple calculations. In practice: use Formula for simple calculations, Script for anything complex. Most production rules end up as Script components because they need FIX statements and IF conditions that are easier to write in script than to configure visually.

### Architect
**Q: A Hotel Pvt Ltd batch rule runs every night but takes 45 minutes. The rule aggregates Entity, Department, and Account dimensions. The application has 8 entities, 15 departments, and 250 accounts. How would you optimize it—**
> **A:** (1) **Set Account parent members to Dynamic Calc** — if Account is dense, parents should be Dynamic Calc. This eliminates the need for dense aggregation entirely (saves the biggest calculation). (2) **Use AGG instead of CALC DIM** — AGG is faster for sparse dimensions. Aggregate in order of most blocks to least: `AGG(Entity, Department)`. (3) **Add FIX PARALLEL** — since it's a batch rule (not form-attached), use `SET CALCPARALLEL 4;` to leverage multi-threaded calculation. (4) **Limit the FIX scope** — if aggregation only needs to run for specific Scenarios/Versions, add a FIX to limit which blocks are processed. (5) **Check for block explosion** — run Errors and Warnings diagnostics to see how many blocks the FIX creates. If the number is too high, review dimension hierarchies for unnecessary members. (6) **Consider Hybrid Aggregation** — if the cubes are Hybrid BSO, much of the aggregation may happen automatically via the dynamic hierarchy features without needing an explicit AGG rule.

## 14. DO's AND DON'Ts

### ✅ DO
- **DO** always Validate before Deploying — catch errors before users see them
- **DO** use runtime prompts for Scenario, Version, Year, Entity — makes rules reusable
- **DO** start Groovy scripts with `/* RTPS: */` — even if no runtime prompts
- **DO** use AGG for sparse aggregation instead of CALC DIM
- **DO** add IF conditions to avoid creating unnecessary zeros
- **DO** test rules in a sandbox/dev environment before deploying to production

### ❌ DON'T
- **DON'T** use CALC PARALLEL in rules attached to forms — only for batch/admin rules
- **DON'T** use SET CREATEBLOCKONEQ ON at the top of rules — creates blocks everywhere
- **DON'T** put cross-dimensional references on the LEFT side of equations
- **DON'T** open a graphical rule in "Edit Script" mode and save — destroys the graphical structure
- **DON'T** create multiple rules for the same logic with different parameters — use runtime prompts
- **DON'T** run Groovy rules in composite forms — not supported
