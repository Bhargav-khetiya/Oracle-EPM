## 1. WHY — What Problem Do Smart Lists Solve—

**The problem:** Financial data isn't always numeric. Sometimes users need to enter text-based selections: "Approved/Pending/Rejected," "Full-Time/Part-Time/Contract," or "Cash/Accrual." But Essbase is a numeric database — it can only store numbers.

**The solution:** Smart Lists are **dropdown menus** that display text labels to users but store numeric IDs in Essbase. Each text entry maps to an integer value. Users see "Full-Time" in the cell, but Essbase stores `1`. This bridges the gap between human-readable text and numeric storage.

**Hotel Pvt Ltd use case:** Employee Type: 1=Full-Time, 2=Part-Time, 3=Contract. HR managers select from a dropdown instead of typing numbers.

---

## 2. WHAT — Plain English Definition

A Smart List is a **named list of text-value pairs** that:
- Appears as a **dropdown** in form cells
- Stores a **numeric ID** (integer) in Essbase
- Is assigned to **Account members** or **dimension members** via the "Smart List" property
- Can be used in **member formulas** and **business rules** (reference by ID)
- Can be shared across cubes

```
Smart List: "Employee_Type"
┌─────────────────────┬──────────┐
│ Display Label       │ Value ID │
├─────────────────────┼──────────┤
│ #MISSING (default)  │ -1       │
│ Full-Time           │ 1        │
│ Part-Time           │ 2        │
│ Contract            │ 3        │
│ Intern              │ 4        │
└─────────────────────┴──────────┘
```

## 5. PROPERTIES TAB — EVERY OPTION

| Property | Description | Example |
|----------|-------------|---------|
| **Name** | Unique identifier (no spaces) | Employee_Type |
| **Label** | Display name shown to users | Employee Type |
| **Cube** | Which cube(s) the Smart List is available for | OEP_WFP or All Cubes |
| **#MISSING Label** | What to show when no value is selected | "Unassigned" or blank |
| **Start ID** | Starting ID for auto-numbering entries (default: 1) | 1 |

---

## 6. ENTRIES TAB — HOW TO BUILD THE LIST

Each entry has:

| Field | Description | Rules |
|-------|-------------|-------|
| **ID** | Numeric value stored in Essbase | Auto-incremented from Start ID; CANNOT be changed after creation |
| **Name** | Internal name (no spaces) | Used in formulas and rules |
| **Label** | Display text shown to users | Can contain spaces, shown in dropdown |

> ⚠️ **CRITICAL:** The ID is stored in Essbase. If you change the ID mapping (delete entry 2 and recreate it), ALL existing data for that entry is lost. IDs are permanent.

### #MISSING Display Behavior

| Setting | What Users See |
|---------|----------------|
| **#MISSING Label = blank** | Cell shows as blank |
| **#MISSING Label = "Unassigned"** | Cell shows "Unassigned" |
| **#MISSING Label = "#MISSING"** | Cell shows "#MISSING" |

## 7. LINKING SMART LISTS TO MEMBERS

Smart Lists are linked to dimension members via the member's **Smart List** property:

```
Step 1: Create the Smart List (Navigator → Smart Lists → Create)
Step 2: Go to Dimension Editor (Dimensions → Account or Custom dim)
Step 3: Select a member (e.g., "Employee_Type")
Step 4: In member properties, set:
         Data Type: Smart List
         Smart List: Employee_Type (select from dropdown)
Step 5: Save → Refresh Database
```

**After linking:**
- Any form cell at the intersection of that member shows a dropdown
- Users pick from the dropdown instead of typing numbers
- The selected text's ID is stored in Essbase

## 8. USING SMART LISTS IN FORMULAS AND RULES

### In Member Formulas
```
/* If Employee_Type = Full-Time (ID=1), benefit rate is 25% */
IF("Employee_Type" == 1)
  "Benefit_Cost" = "Base_Salary" * 0.25;
ELSEIF("Employee_Type" == 2)
  "Benefit_Cost" = "Base_Salary" * 0.15;
ELSE
  "Benefit_Cost" = 0;
ENDIF
```

### In Business Rules (Calc Script)
```
FIX("Budget", "Working", "FY2026")
  IF("Employee_Type" == 1)    /* Full-Time */
    "Annual_Leave_Days" = 24;
  ELSEIF("Employee_Type" == 2)  /* Part-Time */
    "Annual_Leave_Days" = 12;
  ELSEIF("Employee_Type" == 3)  /* Contract */
    "Annual_Leave_Days" = 0;
  ENDIF
ENDFIX
```

### In Groovy Rules
```groovy
/* RTPS: */
operation.grid.dataCellIterator("Employee_Type").each { cell ->
  int empType = (int) cell.data
  if (empType == 1) {
    println "Full-Time employee found"
  }
}
```

## 10. DO's AND DON'Ts

### ✅ DO
- **DO** plan Smart List IDs carefully — they are permanent
- **DO** use the #MISSING Label to provide meaningful default text
- **DO** name entries without spaces (use underscores)
- **DO** set the member's Data Type to "Smart List" in the Dimension Editor
- **DO** refresh the database after linking a Smart List to a member

### ❌ DON'T
- **DON'T** delete Smart List entries that have been used — data loss
- **DON'T** change the ID-to-label mapping after data entry — breaks existing data
- **DON'T** create overlapping Smart Lists (same entries in multiple lists for the same dim)
- **DON'T** forget to refresh the database after assigning Smart List to a member
- **DON'T** use Smart Lists for dimensions that need aggregation — Smart List values don't aggregate

## 11. INTERVIEW QUESTIONS

### Beginner
**Q: How does a Smart List work behind the scenes— What does Essbase actually store—**
> **A:** Essbase stores only **numeric integer values**. When a Smart List dropdown shows "Full-Time" (ID=1), "Part-Time" (ID=2), and "Contract" (ID=3), Essbase stores the IDs (1, 2, 3) in the data cells. The EPBCS application layer translates these IDs back to display labels when showing the form. This is why you can reference Smart List values in calc scripts using numbers: `IF("Employee_Type" == 1)` means "if Employee_Type is Full-Time."

### Intermediate
**Q: A client wants to add a new entry "Freelancer" to an existing Smart List that already has entries 1-4. What ID will it get, and are there any risks—**
> **A:** The new entry "Freelancer" will get ID=5 (auto-incremented). There are NO risks to existing data — IDs 1-4 remain unchanged, and all cells storing values 1-4 continue to work correctly. The only thing to verify: (1) Any business rules with IF conditions for Smart List values should be updated to handle the new ID=5 case. (2) Any member formulas that check for specific IDs may need to include the new ID. (3) Any reports that filter on Smart List values need to include the new entry.

### Architect
**Q: A Hotel Pvt Ltd application needs to track "Room Status" (Available, Occupied, Under Maintenance, Reserved, Out of Order) across 500 rooms for 365 days. Should you use a Smart List or an alternate approach—**
> **A:** A Smart List is the **correct approach** for this. Create a Smart List with 5 entries (1=Available through 5=Out of Order). Link it to a "Room_Status" account member in the workforce/operations cube. However, consider the data volume: 500 rooms × 365 days × 1 account = 182,500 cells. This is manageable. The alternative approaches would be: (1) Separate members for each status (less flexible, harder to maintain), (2) A text dimension (not supported in Essbase). The Smart List approach is standard. For reporting, you'd use business rules that count the number of rooms with each status: `IF("Room_Status" == 1) "Available_Count" = "Available_Count" + 1;`
