## 1. WHY — What Problem Do Valid Intersections Solve—

**The problem:** In a multidimensional cube, every combination of dimension members creates a potential data intersection. With 250 accounts × 8 entities × 12 months × 3 scenarios = 72,000 intersections. But not ALL intersections make business sense. "Spa Revenue" for a hotel that doesn't have a spa creates meaningless cells. Users might accidentally enter data there, wasting time and storage.

**The solution:** Valid Intersections (also called Valid Combinations) let administrators define which combinations of dimension members are valid. Invalid intersections become **read-only** on forms — users can't enter data there. This enforces data quality at the structural level.

**Hotel Pvt Ltd use case:** Mumbai Hotel has a spa, but Delhi Hotel doesn't. Define a valid intersection rule: "Spa Revenue" is valid ONLY for Entity = Mumbai_Hotel. Delhi Hotel planners won't see editable Spa Revenue cells.

---

## 2. WHAT — Plain English Definition

Valid Intersections are **rules that restrict which dimension member combinations are valid for data entry**. They work by:
1. Defining groups of members (Anchor + Target dimensions)
2. Any intersection NOT covered by a valid intersection rule = **invalid = read-only**
3. Invalid cells show on forms but cannot be edited (grayed out)
4. Business rules skip invalid intersections

**How EPBCS handles validity:**
```
Without Valid Intersections:
  ALL combinations are valid → users can enter data everywhere

With Valid Intersections:
  Only DEFINED combinations are valid → undefined = read-only
  
  Example rule: Account = "Spa_Revenue" is valid ONLY when Entity = "Mumbai_Hotel"
  → Spa_Revenue + Mumbai_Hotel = VALID (editable)
  → Spa_Revenue + Delhi_Hotel = INVALID (read-only, grayed out)
```

## 5. KEY CONCEPTS

### Anchor Dimension vs Target Dimension

| Term | Definition | Example |
|------|-----------|---------|
| **Anchor Dimension** | The PRIMARY dimension whose members define the restriction | Account |
| **Target Dimension** | The SECONDARY dimension(s) that the anchor is validated against | Entity, Department |
| **Valid Combination** | A row in the rules grid — specific anchor + target members = VALID | Spa_Revenue + Mumbai = Valid |
| **Invalid Combination** | Any combination NOT listed in the rules grid | Spa_Revenue + Delhi = Invalid |

### How Validity is Determined

```
If a Valid Intersection group exists for Account × Entity:
  → ONLY the combinations explicitly listed as "Enabled = Yes" are valid
  → ALL other Account × Entity combinations become INVALID

If NO Valid Intersection group exists for Account × Entity:
  → ALL Account × Entity combinations are valid (default behavior)
```

> ⚠️ **CRITICAL:** Once you create a valid intersection group for a pair of dimensions, ALL unlisted combinations become invalid. This is **exclusionary** by default — you must explicitly list EVERY valid combination.

### Multiple Target Dimensions

You can have MULTIPLE target dimensions in one group:

```
Group: Revenue_Account_Entity_Dept
  Anchor: Account
  Target 1: Entity
  Target 2: Department

  Rule: Spa_Revenue → Mumbai_Hotel → Spa_Department = Valid
  Rule: Spa_Revenue → Mumbai_Hotel → Rooms_Department = Invalid
  Rule: Spa_Revenue → Delhi_Hotel → (any) = Invalid
```

## 6. VALID INTERSECTION EFFECTS

### On Forms
| Behavior | Description |
|----------|-------------|
| **Invalid cells** | Grayed out, read-only — users cannot enter data |
| **Suppress invalid data** | If "Suppress invalid data" is enabled on the form, invalid rows/columns are hidden entirely |
| **Cell tip** | Hovering over an invalid cell may show "Invalid intersection" tooltip |
| **Smart View** | Invalid cells are locked in Smart View too |

### On Business Rules
| Behavior | Description |
|----------|-------------|
| **Skip invalid** | Business rules automatically skip invalid intersections |
| **No data creation** | Rules cannot create data at invalid intersections |
| **Runtime prompts** | Member selectors in runtime prompts can filter out invalid members |

### On Data Loading
| Behavior | Description |
|----------|-------------|
| **Load rejection** | Data loads reject records at invalid intersections |
| **Error logging** | Rejected records appear in the data load error log |

## 7. STEP-BY-STEP: CREATING A VALID INTERSECTION

### Scenario: Restrict Spa accounts to hotels with spas

```
1. Navigate: Application → Overview → Valid Intersections tab
2. Click [+ Create]
3. Group Name: "Spa_Account_By_Entity"
4. Anchor Dimension: Account
5. Target Dimension: Entity
6. Valid for Cubes: ☑ OEP_FS (FinPlan)

7. In the Rules Grid, add rows:
   Anchor = Spa_Revenue, Target = Mumbai_Hotel → Enabled ☑
   Anchor = Spa_Revenue, Target = Bangalore_Hotel → Enabled ☑
   (Delhi, Kolkata, Chennai don't have spas — NOT listed)

   Anchor = Spa_Expense, Target = Mumbai_Hotel → Enabled ☑
   Anchor = Spa_Expense, Target = Bangalore_Hotel → Enabled ☑

8. Click Save
9. Go to Application → Overview → Actions → Refresh Database

Result:
  Forms showing Spa_Revenue for Delhi_Hotel → cells are grayed out (invalid)
  Forms showing Spa_Revenue for Mumbai_Hotel → cells are editable (valid)
```

## 8. HOTEL PVT LTD EXAMPLE

### Valid Intersection Rules for Hotel Chain

**Business Logic:**
| Account Group | Valid Entities | Reason |
|--------------|---------------|--------|
| Spa_Revenue, Spa_Expense | Mumbai, Bangalore | Only these hotels have spas |
| Casino_Revenue | Mumbai | Only Mumbai has gaming license |
| Convention_Revenue | Delhi, Bangalore | Only these have conference halls |
| Room_Revenue | All Hotels | All hotels have rooms |
| F&B_Revenue | All Hotels | All hotels have restaurants |

**Implementation:**
```
Valid Intersection Group 1: "Spa_Accounts"
  Anchor: Account (Spa_Revenue, Spa_Expense)
  Target: Entity (Mumbai_Hotel, Bangalore_Hotel)
  Cubes: OEP_FS

Valid Intersection Group 2: "Casino_Accounts"
  Anchor: Account (Casino_Revenue, Casino_Expense)
  Target: Entity (Mumbai_Hotel)
  Cubes: OEP_FS

Valid Intersection Group 3: "Convention_Accounts"
  Anchor: Account (Convention_Revenue, Convention_Expense)
  Target: Entity (Delhi_Hotel, Bangalore_Hotel)
  Cubes: OEP_FS
```

> **Note:** Room_Revenue and F&B_Revenue don't need valid intersection rules because they are valid for ALL entities (default behavior = all valid when no rule exists).

## 9. DO's AND DON'Ts

### ✅ DO
- **DO** plan valid intersections BEFORE building forms — invalid cells appear on forms immediately after refresh
- **DO** test valid intersections in a dev environment first — once created, ALL unlisted combinations become invalid
- **DO** refresh the database after creating/modifying valid intersections
- **DO** use "Suppress invalid data" on forms to hide meaningless rows
- **DO** document all valid intersection groups — they're invisible to users but affect their experience

### ❌ DON'T
- **DON'T** create a valid intersection group and forget to list all valid combinations — everything unlisted becomes invalid immediately
- **DON'T** use valid intersections for simple account suppression — use form design (member selection) instead for cosmetic hiding
- **DON'T** create overlapping valid intersection groups for the same dimension pair — behavior becomes unpredictable
- **DON'T** forget to refresh the database — valid intersections don't take effect until refresh
- **DON'T** use valid intersections for security — use access control (dimension security) for restricting who can see data

## 10. INTERVIEW QUESTIONS

### Beginner
**Q: After creating a valid intersection rule, a user complains that some cells on their form are now grayed out. What happened—**
> **A:** The valid intersection rule made those cells "invalid" — meaning the combination of Account × Entity at those cells is not in the valid intersection list. For example, if you created a rule that "Spa_Revenue" is valid only for "Mumbai_Hotel", then Spa_Revenue cells for Delhi_Hotel are now grayed out (read-only). This is by design — it prevents entering data at meaningless intersections. If the cells SHOULD be editable, add those combinations to the valid intersection group.

### Intermediate
**Q: You want to prevent users from entering "Salary" data in the "F&B" department because F&B staff are outsourced. But you also have Salary data in the "Rooms" department that should be editable. How do you configure this—**
> **A:** Create a Valid Intersection group:
> - Group Name: "Salary_By_Department"
> - Anchor Dimension: Account
> - Target Dimension: Department
> - Add rows for EVERY valid combination:
>   - Salary → Rooms = Enabled ☑
>   - Salary → Maintenance = Enabled ☑
>   - Salary → HR = Enabled ☑
>   - Salary → Finance = Enabled ☑
>   - (Do NOT add Salary → F&B — it will become invalid)
> - Refresh Database
> 
> **Important caveat:** Once you create this group, you MUST list ALL valid Account × Department combinations, not just the ones you want to restrict. If you only list Salary rows, ALL other accounts (Revenue, Expense, etc.) for ALL departments become invalid too. The cleaner approach is to list Salary for all departments EXCEPT F&B, and leave all other accounts unrestricted (by not including them in the anchor list).

### Architect
**Q: A Hotel Pvt Ltd client has 5 hotels, 15 departments, and 250 accounts. They want to restrict 20 accounts to specific hotel-department combinations. How many valid intersection rows would this require, and is there a better approach—**
> **A:** With 20 restricted accounts × (valid hotel-dept combinations for each), you might need 100-200 rows. This is manageable. However, there are architectural considerations:
> (1) **Performance:** Valid intersections add overhead to form rendering (each cell is checked). 200 rows is fine; 10,000 rows would slow forms.
> (2) **Maintenance:** Every time a new entity or department is added, ALL valid intersection groups must be updated. With 3 groups × 200 rows, this is significant maintenance.
> (3) **Alternative approach:** Instead of valid intersections, consider:
> - Using **separate forms** per hotel type (Spa Hotels form vs Non-Spa Hotels form) with different account member selections
> - Using **member formulas** with IF conditions to zero out invalid data after entry
> - Using **Groovy validation rules** to prevent saving invalid data with a user-friendly error message
> (4) **Best practice:** Use valid intersections for structural restrictions (accounts that truly don't apply to certain entities), use form design for cosmetic restrictions, and use Groovy for business validation.
