## 1. WHY — What Problem Do Data Maps Solve?

**The problem:** EPBCS applications often have multiple cubes — FinPlan (OEP_FS), Workforce (OEP_WFP), Capital (OEP_CP), Reporting (OEP_REP). A user enters headcount in the Workforce cube, but the salary expense needs to appear in the FinPlan cube. How does data move between cubes?

**The solution:** Data Maps (also called Smart Push) define **cross-cube data movement rules** — which data to copy, from which cube to which cube, and how dimensions map between the source and target cubes.

---

## 2. TWO TYPES OF CROSS-CUBE DATA MOVEMENT

| Type | Trigger | Speed | Use Case |
|------|---------|-------|----------|
| **Smart Push** | Automatic — runs when user saves a form | Fast (selected data only) | Real-time cross-cube updates during data entry |
| **Data Map (Push Data)** | Manual — admin runs explicitly | Slower (bulk operation) | Batch data movement, nightly jobs |

## 5. DIMENSION MAPPING TYPES

| Mapping Type | Description | Example |
|-------------|-------------|---------|
| **Same (Shared)** | Dimension exists in both cubes with same members | Entity, Scenario, Version, Year, Period |
| **Member-to-Member** | Map specific source members to target members | Source: Basic_Salary → Target: Salary_Expense |
| **Fixed** | Target dimension always uses a single fixed member | Source has no Department dim → Target: Department = "HR" |
| **Aggregate** | Source dimension aggregated (summed) before push | Source: Employee dim aggregated (all employees) → no Employee dim in target |
| **Unmapped** | Dimension exists only in one cube — ignored or aggregated | Source-only dims → aggregated |

### Smart Push Trigger Options

| Trigger | Description |
|---------|-------------|
| **On Save** | Smart Push runs automatically when user saves the form |
| **On Load** | Smart Push runs when form loads (rare — performance impact) |
| **Manual** | User must click Actions → Smart Push to trigger |

## 7. HOTEL PVT LTD EXAMPLE

### Workforce → FinPlan Data Map

```
Scenario: Employee salary data is entered in the Workforce cube (OEP_WFP).
          Salary expense needs to appear in the FinPlan cube (OEP_FS) for P&L reporting.

Data Map: "WF_to_FinPlan_Salary"
  Source: OEP_WFP (Workforce)
  Target: OEP_FS (FinPlan)

  Dimension Mappings:
    Account: Basic_Salary → Salary_Expense (member mapping)
    Account: Benefits → Benefits_Expense (member mapping)
    Entity: Same (shared — Mumbai, Delhi, etc.)
    Scenario: Same (shared — Budget, Actual)
    Year/Period: Same (shared)
    Employee: Aggregated (sum all employees → single total)
    Department: Same (shared — if exists in both cubes)

  Smart Push: Enabled on "Salary Entry" form → On Save
  
  Result: When HR enters salary data in the Workforce form and saves,
          the total salary expense automatically appears in the FinPlan cube.
          The P&L form shows updated Salary Expense without any manual step.
```

## 8. DO's AND DON'Ts

### ✅ DO
- **DO** validate data maps before running (catches mapping errors)
- **DO** use Smart Push for real-time cross-cube updates during data entry
- **DO** use "Changed Data Only" scope for performance (don't push everything)
- **DO** test data maps in a sandbox before production
- **DO** document all data maps and their schedules

### ❌ DON'T
- **DON'T** create circular data maps (Cube A → B → A = infinite loop)
- **DON'T** use "On Load" trigger for Smart Push — it slows form loading
- **DON'T** forget about unmapped dimensions — data gets aggregated/lost
- **DON'T** run bulk data maps during business hours — performance impact
- **DON'T** enable Smart Push on every form — only where cross-cube push is needed

## 9. INTERVIEW QUESTIONS

### Beginner
**Q: What is the difference between a Data Map and Smart Push?**
> **A:** A **Data Map** is the definition (blueprint) of how data moves between cubes — which members map to which, which dimensions are shared, aggregated, or fixed. **Smart Push** is the mechanism that triggers a Data Map automatically when a user saves a form. A Data Map can be run manually (like a batch job) or via Smart Push (real-time on form save). Think of it as: Data Map = what to push, Smart Push = when to push.

### Intermediate  
**Q: Hotel Pvt Ltd has 500 employees in the Workforce cube. When salary data pushes to FinPlan, should each employee appear as a separate row, or should they be aggregated?**
> **A:** They should be **aggregated**. The FinPlan cube doesn't have an Employee dimension — it has Salary_Expense as a single account. The Data Map should map the Employee dimension as "Aggregate" — this sums all 500 employees' salaries into one total that maps to Salary_Expense in FinPlan. If FinPlan needed employee-level detail, you'd need to add an Employee dimension to FinPlan (which would significantly increase cube size). The standard approach is: detailed data in Workforce cube, aggregated totals in FinPlan cube.
