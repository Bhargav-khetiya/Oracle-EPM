## 1. WHY — What Problem Does Access Control Solve—

**The problem:** An EPBCS application has multiple user types — planners who enter data, managers who review, admins who build — each needing different levels of access to forms, dimensions, rules, and data. Without proper security, a planner could delete dimensions or a manager could edit another team's data.

**The solution:** Access Control provides a **multi-layer security model** with predefined roles, artifact-level permissions, and dimension-level data security — ensuring each user sees and edits only what they should.

---

## 2. SECURITY MODEL — THREE LAYERS

```
Layer 1: ROLES (who can do what type of work)
  ├── Service Administrator → full access
  ├── Power User → design forms/rules, enter data
  ├── Planner → enter data only
  └── Viewer → read-only

Layer 2: ARTIFACT PERMISSIONS (who sees which objects)
  ├── Forms → Read / Write / None per user/group
  ├── Rules → Launch / None per user/group
  ├── Task Lists → Launch / Manage / None
  └── Dashboards → Read / None

Layer 3: DATA SECURITY (who sees which data)
  ├── Dimension Security → Read / Write / None per member
  │   Example: Mumbai_GM gets Write to Mumbai_Hotel, None to Delhi_Hotel
  ├── Valid Intersections → Structural data restrictions
  └── Cell-Level Security → Fine-grained cell restrictions
```

## 3. PREDEFINED ROLES — COMPLETE REFERENCE

| Role | Description | Key Capabilities |
|------|-------------|-----------------|
| **Service Administrator** | Full application access | Everything: create apps, manage users, design, data entry, deploy rules, migration |
| **Power User** | Design + Data entry | Create/edit forms, rules, dimensions, dashboards; enter data; launch rules; no migration/user management |
| **Planner** | Data entry only | Enter data in forms, launch allowed rules, view dashboards; no design access |
| **Viewer** | Read-only | View forms, dashboards, reports; cannot enter data; cannot launch rules |
| **Task Manager Admin** | Task Manager management | Full Task Manager access (schedules, tasks, templates) |
| **Task Manager Analyst** | Task Manager analysis | Create/view reports and dashboards in Task Manager |
| **Task Manager Contributor** | Task Manager user | Complete assigned tasks, add comments |

## 4. DIMENSION SECURITY — DATA ACCESS

### How It Works

Dimension security controls which **members** a user can see/edit in each dimension:

```
Entity dimension security for Mumbai_GM:
  All_Hotels → None (can't see or edit consolidated data)
  Western_Region → Read (can view regional total but not edit)
  Mumbai_Hotel → Write (can enter data for Mumbai)
  Delhi_Hotel → None (can't see Delhi data at all)
  Bangalore_Hotel → None (hidden)
```

### Access Types for Members

| Access | Meaning |
|--------|---------|
| **Write** | User can read AND write data for this member |
| **Read** | User can view data but cannot edit |
| **None** | User cannot see this member at all — hidden from forms, selectors |
| **Inherited** | Inherits access from parent member (default) |

### Setting Member Security

```
Path: Dimensions → Select dimension → Select member → Access tab
  Or: Navigator → Create and Manage → Dimensions → [dim] → [member] → Assign Access

Dialog:
  Member: Mumbai_Hotel
  User/Group: Mumbai_Planners_Group
  Access: Write
  
  Member: Delhi_Hotel
  User/Group: Mumbai_Planners_Group
  Access: None
```

### Effective Access Rules

| Parent Access | Child Access Setting | Effective Child Access |
|--------------|---------------------|----------------------|
| Write | Inherited | Write |
| Write | Read | Read |
| Write | None | None |
| Read | Inherited | Read |
| Read | Write | Write (child overrides) |
| None | Inherited | None |
| None | Write | Write (child overrides) |

> ⚠️ **Key Rule:** Child member access can **override** parent access. If a parent is "None" but a child is "Write," the user sees ONLY that child — not the parent or other children.

## 5. ARTIFACT PERMISSIONS

### Form Permissions

| Permission | What User Can Do |
|-----------|-----------------|
| **Read** | View form, see data (cannot edit even if dimension security allows) |
| **Write** | View and edit data in the form |
| **None** | Cannot see the form at all |

### Rule Permissions

| Permission | What User Can Do |
|-----------|-----------------|
| **Launch** | Can run the rule (from Rules page or form) |
| **None** | Cannot see or run the rule |

### Setting Artifact Permissions

```
Path: Navigator → Create and Manage → Forms → [select form] → Permissions tab

Dialog:
  User/Group: [Mumbai_Planners ▾]
  Permission: [Write ▾]
  
  User/Group: [Finance_Controllers ▾]
  Permission: [Read ▾]
```

## 6. GROUPS — SIMPLIFYING SECURITY

Instead of assigning permissions to individual users, create **Groups** and assign permissions to groups:

```
Groups (created in Identity Domain / OCI IAM):
  Hotel_Mumbai_Planners → [user1, user2, user3]
  Hotel_Delhi_Planners → [user4, user5]
  Finance_Controllers → [user6, user7]
  Hotel_GMs → [user8, user9, user10, user11, user12]
  
Security Assignment:
  Form "Mumbai_Revenue_Entry":
    Hotel_Mumbai_Planners → Write
    Finance_Controllers → Read
    
  Entity "Mumbai_Hotel":
    Hotel_Mumbai_Planners → Write
    Finance_Controllers → Read
    Hotel_Delhi_Planners → None
```

**Best Practice:** Always use groups, never individual users. When employees change roles, just move them between groups.

## 9. DO's AND DON'Ts

### ✅ DO
- **DO** always use Groups, not individual users
- **DO** use the principle of least privilege — start with None, grant as needed
- **DO** test security by logging in as a test user
- **DO** document your security design before implementing
- **DO** review access regularly — run Access Control reports quarterly

### ❌ DON'T
- **DON'T** grant Service Administrator to everyone — it bypasses all security
- **DON'T** rely only on form permissions — add dimension security too (defense in depth)
- **DON'T** assign permissions to individual users — use groups
- **DON'T** forget to test with the Viewer role — ensure read-only users see what they should
- **DON'T** use Cell-Level Security unless absolutely necessary — significant performance impact

## 10. INTERVIEW QUESTIONS

### Beginner
**Q: What is the difference between a Planner role and a Viewer role—**
> **A:** A **Planner** can enter data in forms, launch rules (if granted launch access), and view dashboards/reports. A **Viewer** can only view data — they cannot enter, edit, or launch anything. Both roles are restricted from designing forms, rules, or dimensions (that requires Power User or Service Administrator).

### Intermediate
**Q: A Mumbai planner says they can see Delhi Hotel data on a shared form. How do you prevent this—**
> **A:** Set up dimension security on the Entity dimension: (1) Go to Dimensions → Entity → Delhi_Hotel → Assign Access. (2) For the Mumbai_Planners group, set Delhi_Hotel access to "None." (3) This hides Delhi_Hotel from all forms, member selectors, and reports for Mumbai planners. The form itself doesn't need to change — dimension security automatically filters which entity data each user can see. Also verify that the form's POV/Page uses a User Variable (UserEntity) so each user automatically sees their own hotel.

### Architect
**Q: Design a security model for Hotel Pvt Ltd where: (a) Each hotel GM can enter data for their hotel only, (b) Regional Directors can view but not edit their region's hotels, (c) The CFO can view and edit all hotels, (d) Planners can enter data for specific departments only.**
> **A:** Four-layer approach:
> (1) **Roles:** GMs = Power User, Directors = Power User, CFO = Power User, Planners = Planner
> (2) **Entity security:** Each GM gets Write to their hotel, None to others. Directors get Read to their region's hotels. CFO gets Write to All_Hotels.
> (3) **Department security (custom dim):** Planners get Write to their department only (e.g., F&B planner → Write to F&B_Dept, None to Rooms_Dept).
> (4) **Form permissions:** Revenue forms → Write for GMs and Planners, Read for Directors. P&L forms → Read for GMs, Write for CFO.
> This creates a matrix where each user sees only their intersection of Entity × Department, ensuring data integrity across the organization.
