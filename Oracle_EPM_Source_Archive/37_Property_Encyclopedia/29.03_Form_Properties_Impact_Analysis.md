# Form Properties: Performance Impact Analysis

This document analyzes the physical impact that specific UI Form Properties have on the underlying Essbase engine. Checking the wrong box on a form can crash the entire server.

## 1. "Suppress Missing Blocks" vs "Suppress Missing Data"

This is the most critical distinction in EPM Form design.

*   **Suppress Missing Data:** Essbase runs the query, retrieves every single data block requested by the Row/Column intersections, loads them into the WebLogic RAM, checks if the specific cell is `#MISSING`, and if so, hides the row/column on the screen.
    *   *Impact:* Extremely high memory consumption. If you query 1 million blocks, Essbase must read 1 million blocks from disk to RAM just to hide 990,000 of them.
*   **Suppress Missing Blocks:** Essbase checks the Block Index (the sparse hierarchy pointers) *before* going to disk. If the pointer says "this block doesn't exist", Essbase skips it entirely. It never touches the disk and never loads it to RAM.
    *   *Impact:* Near-instant query times. 
    *   *The Catch:* This only works if your Rows/Columns are built using Sparse dimensions. If you put Dense dimensions on the rows and suppress blocks, Essbase still has to load the whole block to see if the dense cell is empty.

## 2. "Enable Save on Open"

This property is a checkbox in the Form Options. 

*   **What it does:** When a user clicks to open the form, EPM immediately simulates a "Save" action, which triggers all "Run on Save" calculation scripts before the form even renders.
*   **The Intent:** Used when a form contains dynamically generated data (like current FX rates) that must be recalculated based on today's date before the user looks at it.
*   **The Impact:** Disastrous if misused. If 50 users log in at 9:00 AM and open a form that takes 30 seconds to calculate, the Essbase server will immediately spawn 50 simultaneous calculation threads. The CPU will spike to 100%, and the system will hang. Use sparingly.

## 3. "Valid Intersections" Application on Forms

By default, forms respect global Valid Intersection rules (e.g., Cost Center 100 cannot use Account 5000).

*   **The Property:** You can uncheck "Suppress Invalid Data" in the Grid Properties.
*   **The Impact:** If unchecked, the form will still display the invalid intersection (Row: Cost Center 100, Col: Account 5000), but the cell will be grayed out (Read-Only). 
*   *Best Practice:* Always leave "Suppress Invalid Data" checked. Rendering grayed-out cells consumes UI rendering time and clutters the screen for the end-user.
