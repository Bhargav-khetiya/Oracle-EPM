# Entity and Custom Dimension Properties

While the Account and Time dimensions dictate math, the Entity and Custom dimensions dictate the shape, security, and aggregation paths of the organization.

## 1. Entity Dimension Specifics

The Entity dimension represents the structural hierarchy of a company (e.g., Global -> North America -> USA -> NY Office).

### Aggregation and Consolidation Options
Entities typically aggregate straight up the hierarchy (using the `+` operator). However, in Financial Consolidation and Close (FCCS) or complex Planning models, this changes:
*   **Proportional Consolidation:** If a parent company only owns 80% of a subsidiary Entity, you cannot simply add 100% of the subsidiary's revenue. The Entity property must be set to factor in a Consolidation Percentage, which requires specialized calculation rules or FCCS built-in logic.
*   **Intercompany Eliminations:** A critical property for Entities in financial models is the "Intercompany" flag. If an Entity trades with another Entity within the same parent, that revenue/expense must be eliminated at the parent level to prevent double-counting. 
    *   *Setup:* Both the Entity and the Account must be flagged for Intercompany eliminations, and a corresponding "Intercompany" custom dimension is required.

### Base Currency Property
Every Entity must have a Base Currency defined. This property tells the system: "Any data entered into this Entity is assumed to be in this currency."
*   If a user inputs 100 into the "UK_Office" entity (Base Currency = GBP), the system stores 100 GBP. 
*   When a user queries the "Global" parent in USD, the system uses the exchange rate to translate that 100 GBP to USD on the fly.

## 2. Custom Dimensions

Custom dimensions (e.g., Product, Project, Cost Center, Market) are typically Sparse dimensions used to slice the Account data further.

### Key Properties for Custom Dimensions
*   **Valid Intersections:** While not a property on the dimension itself, custom dimensions are heavily restricted by Valid Intersection rules. For example, if the "IT Department" Entity should never plan for "Manufacturing Expenses" Accounts, this is blocked at the intersection level.
*   **Alias Tables:** Custom dimensions often have cryptic names (e.g., "PROD_10293"). The Alias property allows you to map a readable name ("16oz Glass Bottle") to the member name. 
    *   *Best Practice:* Use multiple alias tables for different languages or reporting standards (e.g., "Default" = English, "French" = French).

## 3. Data Storage in Sparse Dimensions

Unlike the Dense Account dimension where "Dynamic Calc" is common, Custom Dimensions are usually Sparse. 

> [!WARNING]
> **Dynamic Calc on Sparse Dimensions is Dangerous.** 
> If you create a parent member in a custom dimension (e.g., "Total Products") and set it to Dynamic Calc, Essbase must traverse every single child block to sum the data at retrieval time. If there are 50,000 products, the retrieval will likely time out. 
> 
> **Best Practice:** Keep Sparse parent members as "Store" and aggregate them in a batch process using `AGG` or `CALC DIM` (Block Storage), or use Aggregate Storage (ASO) where sparse dynamic aggregation is highly optimized.
