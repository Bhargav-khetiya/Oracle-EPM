# Planning Formula Expressions Deep Dive

While Essbase uses calc scripts, Oracle Planning (EPBCS/PBCS) utilizes a specific subset of member formulas, often defined directly in the Dimension Editor. These formulas power dynamic calculations, member math, and driver-based planning.

## 1. Member Math and Hierarchy Rollups

Planning automatically aggregates data based on the hierarchy using Consolidation Operators (`+`, `-`, `*`, `/`, `~`, `%`). However, you often need to override this with explicit Member Formulas.

### Deep Dive: Operator Behaviors
*   `+` (Addition): Default. Adds child to parent.
*   `-` (Subtraction): Subtracts child from parent (e.g., Returns from Gross Sales).
*   `~` (Ignore): The child is ignored during the rollup. Extremely useful for metric/driver members that sit in the hierarchy but shouldn't aggregate (e.g., "Price", "Headcount").

### Example: Weighted Average in a Hierarchy
If you have `Average_Price` sitting under a total, it shouldn't just sum up.
Formula on `Average_Price` (Dynamic Calc):
```essbase
"Total_Revenue" / "Total_Units";
```

## 2. Planning specific @Functions

Planning relies heavily on specific `@` functions for time series, relative references, and conditional logic.

### 2.1 `@PRIOR` and `@NEXT`
These are essential for balance sheets, cash flows, and driver trending.

**Syntax:** `@PRIOR(Member, [n], [Range])`
*   **Member:** Usually a driver or account.
*   **n (Optional):** Number of periods to go back (default is 1).
*   **Range (Optional):** Limits the scope (e.g., `@RELATIVE("YearTotal", 0)` to prevent it from pulling from prior years).

**Example: Beginning Balance**
```essbase
"Beginning_Balance" = @PRIOR("Ending_Balance");
```
*   **Notable Trap:** If `@PRIOR` crosses the year boundary, Essbase naturally handles it *if* Dynamic Time Series (DTS) or a proper time-dimension setup is active. However, crossing years in custom ranges often fails.

### 2.2 `@CURRMBR` (Current Member)
Used to dynamically reference the member currently being calculated. This is crucial for generic logic applied across many members (e.g., using a UDA).

**Example: Currency Conversion using UDA**
```essbase
IF (@ISUDA(@CURRMBR("Entity"), "EUR_Region"))
    "Local_Currency" = "USD_Input" * "EUR_Rate";
ENDIF
```

### 2.3 `@SUMRANGE` and `@AVGRANGE`
Allows calculating a sum or average over a specific list of members, usually time periods.

**Example: Trailing 3-Month Average**
```essbase
"3_Mo_Avg_Sales" = @AVGRANGE(SKIPNONE, "Sales", @CURRMBR("Period") : @PRIOR(@CURRMBR("Period"), 2));
```

## 3. Two-Pass Calculations

Understanding the Two-Pass flag is critical for Planning formulas.

### Deep Dive: Why Two-Pass—
Essbase calculates bottom-up. When ratios (like Margins or Percentages) are calculated at level 0 (e.g., Jan/East), they aggregate correctly. However, at the Parent level (Q1/Total_Geo), Essbase normally just sums the Level 0 percentages (e.g., 10% + 15% + 12% = 37%), which is mathematically incorrect. 

A Parent margin should be `Total_Parent_Revenue / Total_Parent_Cost`. 

By tagging the Margin member as **Two-Pass**, Essbase calculates it *again* after the main aggregation is complete, using the fully aggregated Parent Revenue and Parent Cost, resulting in the correct ratio.

### Two-Pass Checklist:
*   Member must be marked as `Dynamic Calc` or `Dynamic Calc and Store`.
*   Member must have a member formula (e.g., `A / B`).
*   The "Two Pass Calculation" property must be checked.
*   **Trap:** Do not abuse Two-Pass. Too many two-pass members, especially if they reference other two-pass members, can create circular references or degrade retrieval performance.

## 4. Solve Order (A.K.A Calculation Order)

Solve Order dictates the sequence in which Dynamic Calc members are evaluated when an intersection involves multiple dynamic members across different dimensions.

### Deep Dive: Solve Order Matrix
Imagine intersecting a dynamic Period ("Q1" = Jan+Feb+Mar) with a dynamic Account ("Margin" = Profit/Rev). Does Essbase calculate the Q1 sum first, then the Margin— Or the Margin first, then sum it for Q1—

*   **Lower Solve Order evaluates FIRST.**
*   **Default Solve Orders:**
    *   Accounts: 0 (calculated first)
    *   Time/Period: 1
    *   Other Sparse: 2+

**The Margin Trap:** If Account has Solve Order 0, Margin is calculated at Level 0. Then Period (Solve Order 1) sums those margins. This is wrong. 
**The Fix:** Assign the "Margin" member a Solve Order *higher* than the Period dimension (e.g., 50). This forces the time aggregation to happen first, and the Margin is calculated last on the aggregated data.
